## 3. 三条结构性发现

### 🔴 结构一 · "站点/开发者"维度只应用到了业务表，没应用到平台能力层

这是本代推演最重要的发现，被 4 个视角独立命中。

| 层次 | 是否已站点化 | 证据 |
|---|---|---|
| 业务数据表（策略 / 评估 / 状态 / 动作 / 主体 / 事实） | ✅ 已做 | 第一代 R5 修正 + CI 门禁 |
| **平台能力层**（凭据 / 授权 / 路由 / 令牌 / 审计 / 运维 / 协同） | ❌ **完全没做** | 本次 12 张表 |

**根因**：第一代的 CI 门禁写成"**站点作用域表的**唯一键必须含 `site_id`"——而那些表要么标着 `siteScoped: false`，要么根本没声明，**门禁永远不会报错**。

**修正**（已部分落地）：引入 `ownerScope` + `ownerId` **非空**组合替代可空的 `siteId`：

```ts
ownerScope: col.enum('ag_owner_scope', ['platform','developer','site','user']).notNull(),
ownerId:    col.varchar(64).notNull().default('platform'),
```

> **为什么必须非空**：PostgreSQL 的唯一索引把多个 NULL 视为**互不相同** → 唯一约束静默失效。
> 这是"用可空 siteId 做唯一键"的经典陷阱。

**CI 门禁升级为两条**：① 站点作用域表唯一键含 `site_id`；② **含凭据/权限/路由/令牌/审计/计量的表必须含 `ownerScope` 或 `siteId`**——按表名白名单逐表签署《站点维度矩阵》。

### 🔴 结构二 · 声称正确性的机制，在数据模型里没有承载物

一致性视角的方法论级发现：

| 声称的机制 | 在 02 文档里的承载物 | 实情 |
|---|---|---|
| H1 `indeterminate` 不降级 | `ag_eval_outcome` 枚举 | ❌ **枚举里没有 indeterminate** |
| P2 `baseline` 回退 | `ag_user_policy_state.baseline` | ✅ 已有 |
| 05 §2.2 防抖 | `lastGroupChangeAt` 列 | ❌ **无此列** |
| L4 结果树缓存 | 缓存键定义 | ❌ **无定义** |
| DC-2 状态 CAS | `version` 列 | ❌ **无此列** |

**结论**：凡是声称正确性的机制，都必须能在 `02-数据模型.md` 里**指出承载它的列、约束或锁**——指不出来，它在多实例下就不成立。

> 这条已作为**新的审查准则**纳入本文档。

### 🔴 结构三 · PostgreSQL 的运行时语义没有被当作设计约束

文档把以下都当成"声明层属性"，但它们在 PG 里都是**具体行为**：

| PG 行为 | 后果 |
|---|---|
| **父表 RLS 不自动作用于子分区** | 分区隔离失效，绕过父表可直接读分区 |
| **未来分区需要人建** | 跨月写入报 `no partition of relation found` → 评估记录丢失但动作已执行 |
| **分区表不支持 `CREATE INDEX CONCURRENTLY`** | 迁移生成器会生成阻塞写入的普通索引 |
| **CIC 失败留下 `indisvalid=false` 索引** | 名字在、占空间、查询不走 → 全表扫描但 `db:check` 显示正常 |
| **RLS 只能用 `site_id` 前导索引** | 现有站点级索引**没有一个**以 `site_id` 打头 → 放大站点数倍 |

## 7. 结论

**第二代推演证实：第一代的"收敛"是局部的。**

真正的结论不是"又发现了 48 个问题"，而是**两种方法论各自有系统性盲区**：

| 方法 | 强 | 盲 |
|---|---|---|
| 单线程路径走查（第一代） | 能发现机制缺失、语义矛盾、执行顺序问题 | **看不见"作用域维度"这类横切关注点** |
| 多视角独立审查（第二代） | 能发现横切缺口（维度、备份、PG 语义、配额乘数） | 对"机制内部的逻辑漏洞"不如路径走查 |

**下一步（第三次推演应换的方法）**：

> 不再问"还会怎么坏"，而是**逐条规则做"承载力检查"**——
> 凡文档中声称具备某性质（幂等 / 可复现 / 不降级 / 隔离 / 可审计）的地方，
> 都必须在 `02-数据模型.md` 中指出**承载它的列、约束或锁**；指不出来的，一律判定为"未落地"。

这正是第二代给出的方法论升级，也是比 48 个 bug 更值钱的产出。

## 8. 第五视角（实现者）的独特发现

> 前四个视角都在找"**会怎么坏**"，实现者视角找"**写不出来**"——它发现的是一类前四者完全没覆盖的问题：**契约未冻结**。

### 🔴 结构四 · 契约未冻结（新增）

| 类别 | 不一致 | 后果 |
|---|---|---|
| **kind 全集** | 03 §1.2 六种 / 06 §5.4 五种 / 02 §4.1 四种 / 03 §1.4 注释四种 | `provider` / `feature` **装不进去** → M1-3 卡死 |
| **动作标识** | `newapi-set-group:set_group` / `newapi-set-group:set_group` / `newapi-set-group:set_group` —— **三种拼法** | 两种写法 = 两个幂等键 = **重复执行**（对 set_group 就是多踢一次会话） |
| **寻址 @ 槽位** | `fact:x@instance` 与 `identity:oidc@ref` **复用同一位置** | 分词器无法判定 `@` 后是实例键还是 ref |
| **namespace ≠ pluginId** | enricher `namespace: llm` vs `pluginId: llm-review` | `fact:llm.pr_score` 发布时被判"插件不存在" |
| **`$ref` 内外联** | 04 §1.2.5 说"发布时内联"，§1.2.6 说"不自动内联" | 规范 AST 形态未定 → 同一逻辑算出两个 `specHash` |
| **插件协议** | JSON-RPC 只定义了 `channel.collect` | provider / action / enricher 的调用契约缺失 → **M1-1 无法开工** |
| **核心仍持 newapi 客户端** | 05 §2.2 用 `ctx.newapi.*`，与"核心 grep newapi = 0"门禁冲突 | M6-9 门禁必然失败 |
| **绑定自动性四处矛盾** | M3-4 说"绝不自动绑定"、04 §1.2.7.2 说 `autoLink: true`、05 §1.3 自动落库 | 同一 (user,plugin,instance) 被两套规则处理 |

### ⚠️ 对"承载力检查"规则的升级

**最关键的一条**：

> **求值器根本不产出 `indeterminate`。** 04 §1.5 的 `evaluate()` 返回的是**分支上作者手写的 outcome**，
> 而我上一轮在本文档把 X3 标为"✅ 已落地"（数据库枚举加了 indeterminate）。
> **列有了，但没有任何代码路径能算出它。**

这暴露了规则本身的不完整——我只检查了**数据库有没有承载物**，没检查**代码路径会不会产出它**。

**规则升级为两条**：凡声称具备某性质（幂等 / 可复现 / 不降级 / 隔离 / 可审计）的地方，必须同时指出：

1. **承载它的列 / 约束 / 锁**（→ `02-数据模型.md`）
2. **产出或消费它的代码路径**（→ `04-表达式引擎.md` / `05-核心机制.md`）

指不出任何一条，即判定为"**未落地**"。

### 两代三方法，各有系统性盲区

| 方法 | 强 | 盲 |
|---|---|---|
| **路径走查**（一代，7 轮） | 机制缺失、语义矛盾、执行顺序 | 看不见"横切维度" |

### 三代推演的方法论演进

```
一代：路径走查              → 找"机制缺失"       （72 条）
二代：多视角并行            → 找"横切缺口"       （60 条）
三代：应当做【规格冻结】     → 找"契约不一致"     ← 下一步
```

**第三次推演的正确形态**（由实现者视角给出）：

1. **三张清单**：kind 全集 / 动作标识规范形 / 寻址 root 与 namespace·instance·ref 的槽位定义
2. **三个协议**：进程插件 JSON-RPC 方法表 / PluginHost 双向接口 / `evaluate` 的输入输出错误契约
3. **一条规则**：凡声称的状态或语义，必须在 02 里指出承载它的列，**并在 04/05 里指出产出它的代码路径**

> **这三个「一」完成之前，动手 M1 会造成并行开发的合并冲突，且冲突不会在编译期暴露**——
> 枚举与字符串都在运行期才炸。

**② 门禁的根因是「标记驱动」而非「白名单驱动」**

我设计的 `db:check` 规则是"声明了 `siteScoped: true` 却缺 `site_id` → 启动失败"。
但**全文档没有任何一张表声明过 `siteScoped: true`** → **门禁永远不触发**。

**已修复**：改为**白名单驱动**（显式列出 12 张站点表 + 12 张能力层表），不再依赖标记。

**③ 「✅ 已落地」有 6 处不成立**

| 位置 | 声称 | 实情 |

## 13. 九代推演的最终结论

```
一代  路径走查        → 机制缺失        （72 条）
二代  多视角并行      → 横切缺口        （60 条）
三代  规格冻结+反查    → 契约不一致      （222 条不一致 + 71 条规格）
四代  因果序与时序    → 顺序不可实现
五代  可执行的不变量   → 不可执行的保证  （10 条）
六代  失败传播        → 掩盖/放大/误归类
七代  可逆性          → 不可逆且无警告
八代  可观测与诊断     → 静默黑洞        （H1 只完成一半）
九代  价值/复杂度      → 过度设计        （-56 人日）
```

**四条最贵的教训**：

1. **收敛是检查粒度的函数**（三代）——换粒度就换盲区；
2. **声称必须能执行**（五代）——不可判定的短语比错误更危险；
3. **修正必须复核副作用**（九代）——**每一轮推演都在给下一轮加负担**；
4. **换的是箭头的方向**（四/七代）——正向审查永远发现不了「缺失的逆操作」与「目标状态不可达」；
5. **静默与响亮是两个独立轴**（六代）——信号齐全，错误仍可能被送到**错误的处置分支**（missing 把 owner 不同的四类失败压成一个布尔）；
6. **失败方向决定可靠性等级**（六代）——授予失败 = 少给（可接受），收回失败 = **多给（危险）**，两者风险相反却共用一套机制；
7. **键必须与资源归属同构**（六代）——限流 / 熔断 / 预算的键取资源名而资源按 developer 隔离 = 设计期即可消除的跨租户故障传播。

### 13.1 两条可直接落地的启动期不变量

| # | 不变量 | 来源 |
|---|---|---|
| 1 | `事实 TTL ≥ 主体数 ÷ 外部 API 配额` | 一代 H3 |
| 2 | `maxGrantLifetime ≤ min(策略版本 / 评估 / 审计 / 动作流水 的保留期)` | 第 7 代 N9 |

> 两条都是**启动期校验**：不满足即告警。它们把「配额」与「可回滚窗口」从散落的参数变成了**可断言的不等式**。

### 13.2 「删除」必须拆成三个概念（第 7 代 N5/N6/N7）

| 概念 | 语义 | 承载 |
|---|---|---|
| **撤销 revoke** | 保留行，置 `revokedAt` | `ag_checkin_entitlements` / `ag_plugin_grants` / `ag_plugin_tokens` |
| **停用 disable** | 停止生效，可恢复 | 各表的 `status` |
| **消除 purge** | 物理删除，需墓碑 | 新增 `cleanup.softdeleted` 任务 + 审计墓碑 |

> 文档里三者**全部被写成「删除」**，直接导致：`checkin:revoke` 硬删但列上有 `revokedAt`（死列）；插件有 disabled/removed 却无恢复期；站点有 archived 却无 deleted。

### 13.3 逆操作的零重保障（第 7 代）

> **逆操作不是把系统带回过去，而是在新的时刻再做一次有代价的写入。**
> `restore` 会**再次踢会话**；`deduct` 可能收不回已消费的额度；`revert-revocation` 会再次通知。
> 文档对正向动作有**三重保障**（幂等 / 防抖 / 审计），对逆操作**零重保障**。

**下一步不是第十代推演**，而是：

1. **裁决第 9 代的 10 项减法建议**（尤其 N4：RLS 是否推迟——它与二代/三代结论相反）；
2. **修完第 5 代的 8 条不可执行保证**（N2/N3/N4/N5/N6/N8/N9/N10）；
3. **按 MVP 清单动手 M1**——而不是按完整设计动手。
