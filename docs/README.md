# 通用信任引擎 —— 设计文档

> 代号 `access-gate`｜**基于插件的通用信任引擎**
> 用可插拔插件采集信任证据 → 用嵌套表达式判定信任等级 → 用动作插件把结果投射到任意下游系统（new-api 分组 / Discord 角色 / MC 白名单 / K8s RBAC）。
>
> 核心只认识四个抽象：**Subject 主体 · Fact 证据 · Policy 策略 · Grant 授予**。核心代码中不出现任何具体系统名。
> **new-api 是第一个官方接入，不是架构前提。**

## 30 秒速览

**要解决的问题**：任何系统都要回答"这个人值不值得信任、该给他什么权限"，而现实中它几乎总是靠**人工判断**——不可配置、不可审计、不可复核，而且**每接一个新系统就要重做一遍**。

**首个落地场景**：new-api 的分组（`user.group`）决定用户能用哪些模型、按什么倍率计费，但**分组只能管理员手工改**（`POST /api/user/manage` 没有改分组能力），签到也**没有门槛**。

**做法**：外置一个 Node.js 服务

1. **认人** —— 通过 OIDC 拿到稳定标识，与**任意下游系统的主体**对齐；
2. **验人** —— **运行期插件**采集与加工事实；新增验证方式 = 装一个插件；
3. **判人** —— **嵌套表达式** + **有序分支**（不同分支可不同条件、不同动作）；求值产出**完整结果树**；
4. **动人** —— 经 **action 插件**投射到下游；不满足按策略回退；
5. **协同** —— 插件可注册**子路由**；平台内置**跨项目资格断言协议**；
6. **留痕** —— 全程审计，支持试算、预览、灰度。

**四条硬约束**（来自对首个接入方 new-api 的源码调研，详见 01 §2）：

| 约束 | 推论 |
|---|---|
| 没有 webhook / 事件流 | 只能"主动轮询 + 对账" |
| 不支持按 `oidc_id` 检索用户 | 必须自建身份映射索引 |
| 改分组会 bump `auth_version` 并踢掉全部会话 | 写操作必须幂等 + 防抖 |
| 不校验 ID Token 签名（只调 userinfo） | **EC（ES256）可安全启用**，仍以 RSA 并存兜底 |

## 关键决策速查

> 每条均已定案；**被否决的方案与理由**见 [决策记录](./CHANGELOG.md)。

| # | 决策 | 一句话理由 | 详见 |
|---|---|---|---|
| D1 | 插件**运行期装配** | 编译期模块无法动态扩展 | 03 §1 |
| D2 | **嵌套表达式 + 有序分支** | 模式枚举表达不了"不同分支不同条件" | 04 §1 |
| D3 | 表达式**三形态等价**（YAML / JSON / 图形） | AST 唯一真理；换编辑器不产生新版本 | 04 §1.2.6 |
| D4 | **统一寻址** + 绑定解析 | 多套写法无法表达实例与跨系统身份 | 04 §1.2.7 |
| D5 | **通用信任引擎**（非 new-api 附属） | 核心不认识任何具体系统 | 03 §1.16 |
| D6 | **通用对账器** | 核心不含任何下游的分页细节 | 05 §4 |
| D7 | UI 贡献是**一等能力** | 签到这类功能没有入口等于不存在 | 03 §1.17 |
| D8 | 实例维度**由插件声明** | 凭据类共享、目标类独立、webhook 多例 | 03 §1.19 |
| D9 | **内置随项目，外置落 DB** | 文件系统不保证持久化 | 03 §1.19.4 |
| D10 | **仅 PostgreSQL** | 消除方言层，换来 RLS / advisory lock / 分区 | 01 §5 |
| D11 | 数据库**独占** | 不 JOIN 下游表是 provider 抽象的前提 | 01 §5.0 |
| D12 | **两身份域**（developer 含 admin / enduser） | OIDC 已是可信平台，无需为 admin 另立认证 | 08 §3 |
| D13 | 层级 **开发者 → 站点** | 站点是隔离边界 + 配置单元 | 08 §2 |
| D14 | 平台模式是**平台设置项** | admin 可改；切换可逆、不删数据 | 08 §11 |
| D15 | **id 锚点 + 用户名可变** | 改名不断链、不影响会话 | 08 §3.2 |
| D16 | 站点隔离**双层强制** | 应用层注入 + PostgreSQL RLS | 01 §5.5 |

## 技术栈一句话

```
Node.js 22 + TypeScript
  ├── 基础运行架构（kernel）：配置 / 日志 / DI / 事件总线 / 调度器 / HTTP / 认证
  │     ＋ 插件宿主（plugin-host）：清单 / 权限 / 沙箱 / 进程 / 调用代理
  ├── 平台能力（插件只能经宿主消费）：密钥托管 · 出站白名单代理 · LLM 网关 · KV · 指标
  │     ＋ 入站端点托管（插件子路由挂载 / 五种鉴权 / 限流 / OpenAPI）
  ├── 跨项目协同（core/verify）：HMAC 签名 · 资格断言(ES256) · 设备码流 · 调用方管理
  ├── 插件（plugins/）：builtin/（随构建产物）· runtime/（外置插件缓存，权威在 DB）
  ├── 内核功能（core/）：identity · policy-engine · action-executor · subjects · audit
  └── 数据访问层（★ PostgreSQL 专属，无方言映射）：
        Schema 声明层（defineTable，单一事实来源）
          └── 查询编译层（Query AST → PG SQL + 站点作用域强制注入）
                └── 驱动层（pg 池 + 事务上下文 + RLS 上下文）
```
