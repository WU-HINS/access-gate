> **方法**：拿真实运行时路径逐步走一遍，看每一步发生什么、耗多少、可能怎么坏。
> **目的**：找出纸面设计里没想清楚的地方。每条发现都对应一处设计修正。

> 本文件为**全量推演**：12 类场景 × 60 条路径，发现 **27 个问题**（3 高危 / 9 中危 / 15 健壮性）。

## 1. 高危发现

### H1 · 渠道故障被当成"条件不满足" → 大规模误降级

```
GitHub 挂 → 采集超时 → fact missing
  → $onMissing=fail_closed → 判 false → unsatisfied
  → granted → at_risk（宽限 72h）→ 仍失败 → revoked
  → 【依赖 GitHub 的主体集体被踢下线】
```

**根因**：把"**我们无法验证**"与"**我们知道不满足**"混为一谈。

**修正**：状态机引入 `indeterminate`

| 结果 | 条件 | 允许的迁移 |
|---|---|---|
| `satisfied` | 必需事实齐备且通过 | → satisfied / granted |
| `unsatisfied` | **必需事实齐备**且不通过 | → at_risk → revoked |
| **`indeterminate`** | **有关键事实 missing** | ❗ **保持原状态，不得降级** |

**原则**：**降级的证据要求高于升级**。

> ✅ 已落地：05-核心机制 §2.1.1

### H2 · RLS 静默失败

```sql
USING (site_id = current_setting('app.site_id', true)::uuid)
                                    ↑ 未设置时返回 NULL
```
→ `site_id = NULL` **恒为假** → 查询**静默返回空结果**（看似"没数据"，实则"权限错"）。

**修正**：去掉 `true`（未设置即抛错，fail-closed）+ 强制事务内 + 值由会话派生。

> ✅ 已落地：01-总体设计 §5.5

### H3 · 外部 API 配额与规模不匹配

```
事实 TTL  ≥  主体数 ÷ 外部 API 配额(次/小时)
10 万 ÷ 5000/h  →  TTL ≥ 20 小时
```

**修正**：部署时校验该不等式并告警 + **三级触发**（本地粗筛 → 外部采集 → LLM）。

## 2. 中危发现

### M1 · 首次访问全屏 unknown

`explain` 不触发采集（避免误调用），但新用户没有任何事实 → 页面全是"❓ 未知"，用户以为系统坏了。

**修正**：首次访问**异步触发一次 fast 评估** + 前端轮询；此后走 explain；手动"重新检测"限频。

### M2 · 动作部分成功 → 半应用状态

3 步动作中第 1 步成功、第 2 步失败 → 主体处于"分组已改但签到未解锁"，而状态机只记 `satisfied`。

**修正**：
```
ActionPlan 每步独立记录：planned → running → succeeded / failed / skipped
appliedActions 存【逐步结果】而非最终值
部分失败 → 整体标记 partially_applied，进入重试队列（而非当成功）
管理端展示"半应用"并提供"仅重试失败步骤"
```

### M3 · JWKS 轮换期的验签失败窗口

轮换后立即用新 kid 签发，但下游缓存的 JWKS 还是旧的（TTL 5 分钟）→ 验签失败，登录中断。

**修正：两步轮换（先发布、后使用）**
```
① 新密钥以 standby 发布到 JWKS（不签发）
② 等待 ≥ 下游缓存 TTL × 6（默认 30 分钟）
③ 才转 active，旧密钥转 retiring
④ 旧密钥保留 ≥ token 最长有效期（24h）后才移除
```

> 关键：**绝不允许"先生效再发布"**。此前的 active/standby/retiring 状态机方向正确，但**过渡期时长**未定义——现明确为 `JWKS 缓存 TTL × 6`。

### M4 · 迁移中断导致状态不一致

`db:migrate` 执行第 3 条时被 kill → `ag_migrations` 记录与库结构不一致。

**修正**：
- **每条迁移一个独立事务**（PG 的 DDL 大部分可事务化）：要么全成要么全败；
- **例外**：`CREATE INDEX CONCURRENTLY` 不能在事务内 → 标记为 `nonTransactional`，失败需人工确认后重跑；
- `ag_migrations` 记 `pending/applied/failed` + **校验和**（防迁移文件被改）；
- 发现 `failed` → **拒绝启动**并给出修复指引。

### M5 · 多实例同时启动做迁移

**修正**：迁移前抢 `pg_advisory_lock('migrate')`；未抢到者**等待轮询**迁移完成，而非各自执行。

### M6 · 插件升级导致 factSchema 变更，已发布策略失效

插件 v2 删除了 `total_stars`，而线上 5 条策略引用了它。

**修正：升级时做向后兼容检查**
```
factSchema 对比：
  · 删除字段 → 扫描引用该字段的已发布策略
       ├─ 有引用 → 【阻止升级】并列出策略 code
       └─ 无引用 → 允许，UI 警示
  · 修改类型 → 同样检查（求值语义可能变化）
  · 新增字段 → 允许
```

### M7 · 时钟漂移导致 HMAC 与 JWT 校验失败

NTP 失步 10 分钟 → HMAC 时间戳超出 ±5 分钟容差 → **所有外部调用被拒**；JWT 的 `exp`/`iat` 也可能异常。

**修正**：启动时与每小时检测 NTP 同步状态，**失步即告警**；容差可配置；响应返回服务器时间便于调用方校准。

### M8 · RLS 不防"注入错值"

应用层若把 `app.site_id` 设成 B 站点（因 bug 或参数透传），RLS 会**忠实地**用 B 放行。

**修正**：`app.site_id` **必须由会话派生**（会话创建时已校验归属），**绝不接受请求参数**；路由参数只用于校验，不用于注入。

**定位澄清**：RLS 防的是"**漏注入**"，不是"**注入错值**"——后者是应用层校验的职责。两者互补，**不可互相替代**。

### M9 · 表达式求值错误未被容错

`score` 权重全 0 → 除零；或字符串与数字比较。

**修正**：求值器返回第四种结果 `error`
```ts
type Outcome = 'satisfied' | 'unsatisfied' | 'indeterminate' | 'error';
```
- `error` 与 `indeterminate` **同样不推进状态机**，但**额外告警管理员**（这是配置问题，不是数据问题）；
- 发布前静态校验尽可能拦截（类型检查、除零检测）。

### M10 · 连接池耗尽

全量对账（长事务）+ 巡检（批量）+ 用户请求（实时）同时打满连接池。

**修正**：
- **连接池分区**：`realtime` / `batch` 各自独立池，互不饿死；
- **长任务不持有长事务**：对账按页提交（每 100 行一个事务）；
- 池耗尽时：realtime 优先，batch **主动退避**并降并发。

### M11 · 版本升级期间的新旧并存

滚动升级时新实例跑新 schema、旧实例跑旧 schema；若迁移是破坏性的，旧实例立刻崩溃。

**修正：迁移分两阶段（expand / contract）**
```
阶段 1（expand，向后兼容）：只新增（加列/表/索引），不删不改 → 新旧实例都能工作
阶段 2（contract，清理）：等所有实例升级完（观察期 ≥ 1 个发版周期）→ 再删旧列
```
**禁止**在同一次发布里既加又删。

## 3. 健壮性发现

| # | 场景 | 问题 | 修正 |

## 5. 结构性认识

1. **"无法验证"是一等状态**（H1）——多数系统 bug 出在把 unknown 当成 false。
2. **RLS 与访问控制的职责边界**（H2 / M8）——DB 层防"漏"，应用层防"错"，互补不可替代。
3. **配额是硬约束，不是优化项**（H3）——它决定 TTL、触发策略与产品体验的边界。
4. **迁移是长周期操作**（M4 / M5 / M11）——expand/contract + 抢锁 + 单事务是线上安全底线。
5. **轮换的本质是"先让所有人知道，再开始使用"**（M3）——无论密钥、配置还是插件版本。
6. **池化资源的隔离比调优更重要**（M10）——实时与批量混用一个池，迟早互相饿死。

## 6. 深层推演：语义与不变量

> 前两轮推的是"运行时路径会怎么坏"；这一轮推的是"**语义上是否自洽**"。后者更隐蔽——每条规则单独看都对，组合起来却矛盾。

### 6.1 三轮累计发现 47 个问题

| 轮次 | 视角 | 新增 |
|---|---|---|
| 第一轮 | 7 个典型路径 | 7 |
| 第二轮 | 12 类 × 60 条路径 | +20 |
| **第三轮** | **语义与不变量** | **+20** |

### 🔴 P1 · 级联回退缺失（严重）

**场景**：站点配了两条阶梯策略

```yaml
# 策略 A（tier 1）      onSatisfied: set_group → basic
# 策略 B（tier 2）      onSatisfied: set_group → vip2
# 两者的 onUnsatisfied 都写 set_group → default
```

**推演**：

| 步骤 | A | B | 期望分组 | 按当前设计 |
|---|---|---|---|---|
| 初始 | ✅ | ✅ | vip2 | vip2 ✅ |
| B 不再满足 | ✅ | ❌ | **basic**（A 仍要求） | **default** ❌ |

**B 失效时，用户被从 vip2 直接打到 default，丢掉了仍然满足的 A 所给的 basic。**

**根因**：`onUnsatisfied` 写的是**静态目标值**，而不是"回退到剩余策略所能支撑的档位"。

**修正：`set_group` 拆成两个动作**

```yaml
onSatisfied:
  - action: "newapi-set-group:set_group"
    params: { group: "vip2" }           # 声明"我要求 vip2"
onUnsatisfied:
  - action: "newapi-set-group:restore"  # ★ 不是 set_group(default)
    params: {}                           # 回退目标由执行器计算
```

**执行器的回退算法**：

```
① 收集该主体【所有仍处于 granted / satisfied 的策略】所要求的目标分组
② 若有 → 取 tier 最高者
③ 若无 → 回退到 baseline（该主体首次被策略接管前的原值）
④ 若 baseline 已被人工改动 → 交 driftPolicy 处理，不擅自覆盖
```

### 🔴 P2 · 降级不应覆盖人工设置

**场景**：管理员在 new-api 手工把某用户设为 `vip3`（策略从未管过他），随后他不满足策略 → 执行 `set_group: default` → **手工设置被抹掉**。

**修正：引入 baseline（接管前原值）**

```ts
ag_user_policy_state {
  baseline:       { "newapi-set-group:set_group": "vip3" },   // ★ 首次接管时的原值
  appliedActions: { "newapi-set-group:set_group": { value: "vip2", from: "vip3" } },
}
```

**原则**：**平台只回滚"它自己造成的变更"，绝不覆盖从未被它管理过的值。**

### 🔴 P3 · 空数组的真值陷阱

```yaml
all: []    # 数学上恒真 —— 业务上"没有任何条件"意味着什么？
any: []    # 恒假
```

**推演**：若策略编辑失误把条件清空，`all: []` 会让**全站主体立即满足** → 大规模误升级。

**修正**：
- **发布时静态拒绝空数组**："`all` / `any` 不能为空——无条件通过请显式写 `always: true`"；
- 新增显式节点 `{ always: true }` / `{ never: true }`，让"无条件"成为**有意的表达**而非副作用。

### 🟡 P4 · 共享配置的权限边界未定义

`config.scope: developer` 的配置被该开发者**名下所有站点共享**。

**推演**：开发者有站点 A/B/C，A 的管理员改了 GitHub token → **B、C 的采集立即受影响**。

**修正**：
```
修改 developer 级配置时：
  ① 显示影响面："此变更将影响你名下 3 个站点（A / B / C）"
  ② 需显式确认
  ③ 写审计（含影响站点列表）
  ④ 变更后通知其他站点的管理员
```

### 🟡 P5 · 事实的时间一致性

**推演**：策略同时引用 `fact:github.total_stars`（1 小时前）与 `fact:github.account_age_days`（3 天前）→ 判定基于"半新半旧"的组合。

**修正**：
- **同一次采集产出的事实必须原子写入**（同一 `pluginId + instanceKey + collectedAt`）；
- 结果树标注每个事实的**采集时间**；
- 时间敏感的组合可声明 `$maxSkew: 1h`，超出则判 `indeterminate`。

### 🟡 P6 · 评估用镜像还是实时？

| 方案 | 问题 |
|---|---|
| 用镜像 | 可能基于 6 小时前的数据（用户刚被改成 vip3） |
| 每次实时查 | 10 万主体 × 每次评估 = 打爆 provider |

**修正：分级新鲜度**

```
策略可声明 subjectFreshness：
  · 'cached'（默认）—— 接受镜像（≤ 对账周期）
  · 'fresh'          —— 评估前强制刷新该主体（有配额代价）
对 freshness=fresh 的主体，评估频率自动降级
```

### 🟡 P7 · tier 相同时的动作冲突未定义

两条策略 tier 都是 2、都要求 `set_group` 但目标不同（`vip2` vs `vip2-pro`）。设计说"取 tier 高者"——**tier 相同呢？**

**修正**：加 tie-breaker
```
tier 高者 → priority 小者 → 仍相同 → 【拒绝执行并告警】
                                      （宁可不动，也不随机选一个）
```

### 🟡 P8 · 时区语义未统一

签到按站点时区、巡检按服务器时区、宽限期按 UTC、`account_age_days` 用 UTC 日期差——**四套基准混用**。

**修正**：

| 场景 | 基准 |
|---|---|
| 签到日期边界 | **站点时区**（业务日） |
| 宽限期 / TTL / 巡检 | **UTC 绝对时间**（时长语义） |
| `account_age_days` 等派生 | **UTC**（文档注明） |
| 展示 | 站点时区 |

关键区分：**"某一天"用站点时区，"多长时间"用 UTC**。

### 🟡 P9 · 审计写入失败时是否阻断操作？

**修正：按敏感度分级**

| 操作 | 审计失败时 |
|---|---|
| 敏感（改分组 / 改权限 / 密钥 / 插件安装） | ❌ **阻断**（合规要求，不能丢） |
| 普通（查看 / 列表 / 非敏感读） | ⚠️ 降级为本地日志，不阻断 |

### 🟡 P10 · 灰度哈希用什么键

若用 `username` 做稳定哈希 → 用户改名后**灰度结果跳变**。

**修正**：**哈希必须基于不可变键** —— 平台用户用 `id`（UUID）；主体维度用 `(provider, externalId)`。

### 🟡 P11 · 阶梯跳跃语义

用户直接满足 tier 3，但从未满足 tier 2（`requiresTier: 2`）→ 能进吗？

**修正**：`requiresTier` = **当前状态要求**，非历史
```
requiresTier: 2  表示"评估 tier3 前，要求 tier2 策略【当前】为 satisfied"
若用户直接满足 tier3（阶梯条件通常单调递增）→ 会连带满足 tier2
若 tier2 不满足而 tier3 满足（条件非单调）→ 按 requiresTier 拒绝
```

### 🟡 P12 · 插件卸载后的事实引用

插件卸载，但事实还在，策略仍引用 → 求值时找不到插件。

**修正**：命名空间对应插件不存在 → 该地址为 `missing` → 归入 `indeterminate`（**不降级**）。

### 🟡 P13 · 归档站点

**修正**：
```
归档 = 停止一切自动化（不再巡检 / 不再执行动作）+ 只读 + 【保留数据】
  · 主体仍可查看
  · 策略不可发布
  · 保留期限由 admin 配置（默认永久）
  · 恢复归档 → 重新开始巡检（不追溯）
```

### 🟡 P14 · 评估进行中绑定被修改

评估已加载事实 → 用户此时解绑 GitHub → 评估用旧事实完成 → 执行动作。

**修正**：评估开始时记录**事实快照指纹**；执行动作前**重新校验关键绑定仍存在**；若已消失 → 放弃本次动作并重新排队。

### 🟢 P15–P20

| # | 场景 | 修正 |
|---|---|---|
| P15 | 幂等键跨期重复 | 幂等键含**日期或策略版本**；跨窗口重复是"有意重发"而非 bug |
| P16 | 同一动作被两条策略要求 | 幂等键含 `policyId` → 会执行两次；改为含**目标值**（相同目标只执行一次） |
| P17 | 动作成功但响应超时 | 重试前先**读回校验**目标状态，已达则视为成功 |
| P18 | 会话在评估中过期 | 评估是后台任务，不依赖会话；用户侧刷新时重新鉴权 |
| P19 | 策略发布与在途评估竞态 | 评估**锁定策略版本 id**；发布新版本不影响在途评估 |
| P20 | 大量主体同时到宽限期 | 按 `nextCheckAt` 排序分片，天然错峰；极端情况降并发保护 provider |

## 8. 第四轮：修正的副作用与新边界

> 前三轮修正引入了新的设计元素（`restore` / `baseline` / `always`）。这一轮推的是**这些修正会不会带来新问题**，以及更深的边界。

### 🔴 Q1 · LLM 的非确定性破坏"可复现"承诺

**推演**：设计承诺"每次判定都有输入快照，可复现"。但 LLM 评审**同一输入两次结果可能不同**（采样温度、模型静默更新）——于是：

```
用户申诉"我为什么被拒" → 管理员用当时的 inputs 复现 → 得到【不同】的 pr_score
→ 结果树与实际判定不一致 → 审计失去可信度
```

**修正：LLM 结果必须缓存并锁定**

```
① llm.invoke 的结果按【输入指纹】缓存（含 promptVer + model 版本）
② 评估记录中存 LLM 的【输出】，而不仅是输入
③ 复现时【读缓存】，绝不重新调用
④ promptVer / model 变更 = 新指纹 = 新输入（历史评估仍用旧值复现）
⑤ 模型需固定版本（如 gpt-4o-mini-2024-07-18），避免静默漂移
```

**原则**：**任何非确定性来源都必须被"快照 + 锁定"，否则"可复现"就是空话。**

### 🔴 Q2 · 策略删除后的已授权状态

**推演**：策略 P 授予了 5000 个主体 vip2，随后 P 被**删除**（不是禁用）。

| 问题 | 说明 |
|---|---|
| 谁负责回收？ | 策略没了，巡检不会再评估它 → 状态永久停留在 `granted` |
| 主体还在 vip2 | 但授予它的依据已不存在 |
| `ag_user_policy_state` 变成孤儿 | 外键指向已删除的策略 |

**修正：删除策略必须处理其授权后果**

```
删除策略 P 时：
  ① 统计影响面："将影响 N 个主体，其中 M 个当前为 granted"
  ② 要求显式选择处理方式：
       · orphan_restore（推荐）—— 对受影响主体执行 restore（回退到剩余策略或 baseline）
       · orphan_keep          —— 保持现状，仅标记状态为 orphaned 并告警
       · orphan_block         —— 转 blocked，等人工逐个处理
  ③ 无论哪种，`ag_user_policy_state` 保留（不级联删除），状态改 orphaned
  ④ 写审计（含影响面）
```

**禁用（disable）vs 删除（delete）的语义必须区分**：

| 操作 | 巡检 | 已授权 | 可恢复 |
|---|---|---|---|
| **禁用** | 停止评估 | **保持**（视为仍满足） | 一键恢复 |
| **删除** | 不适用 | 按上述三选一处理 | 不可恢复（需重建） |

### 🟡 Q3 · webhook 写入的事实可被伪造影响判定

**推演**：插件端点接收外部推送 → 写 fact → 直接影响判定。若该 webhook 的 HMAC 密钥泄露 → 攻击者可**伪造事实**（如"我在某社区是版主"）→ 骗取升级。

**修正**：
```
① 事实标记来源：source ∈ { plugin_pull, plugin_push(webhook), manual, import }
② 策略可要求：$requireSource: plugin_pull   （只信任主动采集的事实）
③ webhook 写入的事实有【独立 TTL】（更短）+ 变更告警
④ 高价值策略（授予高权限）默认【不接受 push 事实】
```

### 🟡 Q4 · 评估与动作之间的时间窗

**推演**：评估时 satisfied → 动作排队（因 new-api 不可用）→ 30 分钟后执行 → 此时条件已不满足。

**修正**：动作执行前校验**评估时间与事实新鲜度**
```
若 now - evaluation.evaluatedAt > actionMaxAge（默认 15 分钟）
   → 放弃本次动作，重新排队评估
并在动作流水记录 evaluatedAt 与 executedAt 的差值（供排障）
```

### 🟡 Q5 · 单个字段类型错误导致整批采集失败

**推演**：插件返回 20 个字段，其中 1 个类型不符 → `factSchema` 校验拒绝 → **整个采集作废**（其余 19 个可用字段也丢了）。

**修正：字段级容错**

| 字段类型 | 处理 |
|---|---|
| 非关键字段校验失败 | **丢弃该字段** + 告警，其余保留 |
| 关键字段（策略引用了它）校验失败 | 该字段标记 `missing`（归入 `indeterminate`） |
| 超过 50% 字段失败 | 整体采集标记 `failed`（可能 schema 已变） |

### 🟡 Q6 · 容量增长

| 表 | 增速（10 万主体） | 3 年 |
|---|---|---|
| `ag_evaluations` | 10 万/天（每主体每天 1 次） | **1.1 亿行** |
| `ag_audit_log` | 数十万/天 | **数亿行** |
| `ag_plugin_facts` | 稳定（UPSERT） | 100 万行 |

**修正**：
- `ag_evaluations` **按月分区** + **成功评估降采样**（连续 10 次 satisfied 且无变化 → 只记 1 条 + 计数）；
- `ag_audit_log` 按月分区 + 归档到冷存储（保留 180 天热数据）；
- 分区裁剪由 Schema 层的 `partitionByRange` 声明驱动。

### 🟡 Q7 · 动作失败率熔断

**推演**：new-api 的 PAT 权限被改 → 某策略的所有 `set_group` 全部 403 → **每次巡检都失败**，日志爆炸，且无人知晓（除非看告警）。

**修正**：**动作级熔断**
```
同一 (策略, 动作) 连续失败 N 次（默认 10）或失败率 > 50%（窗口 1h）
   → 暂停该动作，策略状态转 degraded
   → 管理端红色告警 + 通知
   → 人工修复后一键恢复
```

### 🟡 Q8 · 主体 externalId 变化

**推演**：provider 侧的主键变化（如 new-api 重建用户，id 变了）→ 平台侧变成"新主体"，旧主体成孤儿。

**修正**：
- 对账时发现"旧 id 消失 + 新 id 出现且绑定键相同" → 标记为**疑似迁移**，**不自动合并**（可能误合并两个不同的人）；
- 管理端提供"合并主体"工具（人工确认）；
- 孤儿主体进入 `orphaned` 状态并告警。

### 🟡 Q9 · 表达式引用了"已禁用插件"的事实

**推演**：插件被 admin 禁用（平台级），但站点策略仍引用其命名空间。

**修正**（与 P12 一致）：命名空间不可用 → 该地址 `missing` → 归入 `indeterminate`；
同时**站点级告警**："本站点引用的插件 X 已被平台禁用，相关策略无法评估"。

## 10. 第五轮：站点化引入的 URL 维度问题

> 前四轮都在推"逻辑"，这轮推"**寻址空间**"。站点化是后加的维度，而插件端点、UI 路径、协同协议都是**站点化之前**设计的——它们之间可能对不上。

### 🔴 R1 · 插件端点没有站点维度（严重）

**推演**：插件端点挂载规则是

```
/api/plugins/<pluginId>/<path>
```

但 `config.scope: site` 的插件在**每个站点有一份独立配置**（如 `newapi-provider` 在站点 A 指向 api-a，在站点 B 指向 api-b）。

**问题**：同一个 URL `/api/plugins/newapi-provider/verify/start` 在站点 A 和 B 下**指向哪个配置？**

| 尝试 | 结果 |
|---|---|
| 用会话的 activeSiteId | 但端点可能被**无会话的外部系统**调用（bot / webhook） |
| 用第一个站点 | 错——站点 B 的调用会用到站点 A 的凭据 |
| 用 Host 头推断 | 不可靠（站点可能共享域名） |

**这是个真实缺口**：站点化与端点设计没有对齐。

**修正：端点 URL 必须携带站点**

```
/api/plugins/<siteSlug>/<pluginId>/<path>
                          ↑ 新增站点维度

multi 实例的插件再加一层：
/api/plugins/<siteSlug>/<pluginId>/<instanceKey>/<path>
```

**连带调整**：

| 项 | 变化 |
|---|---|
| 端点注册表 `ag_plugin_endpoints` | `mountPath` 不再含站点；站点在**请求时**解析 |
| 路由冲突检测 | 改为 `(siteSlug, method, path)` 维度 |
| 端点发现 `/api/plugins/_endpoints` | 返回按站点分组的列表；匿名只可见 `visibility: public` 的 |
| `pluginToken` | **绑定到站点**（token 内编码 siteId），避免跨站点冒用 |
| OpenAPI 文档 | 按站点分别生成 |

### 🔴 R2 · UI 贡献的路径与站点上下文

**推演**：插件声明 `ui.pages[].path = "/checkin"`，但用户在站点上下文里的实际 URL 是 `/me/<devId>/<siteId>/checkin`。

**修正**：**插件声明的 UI 路径是"站点相对路径"**，由宿主拼接站点前缀：

```
插件声明：           /checkin
用户门户渲染为：      /me/:devId/:siteId/checkin
开发者控制台渲染为：  /console/:siteId/checkin（若 audience 含 admin/developer）
```

插件**不应知道**站点前缀的存在——它只声明"我要一个 /checkin 页面"。

### 🟡 R3 · 插件端点的鉴权与站点归属

**推演**：`pluginToken` 若不绑定站点 → 站点 A 的 token 可用于调用站点 B 的同名端点 → **跨站点越权**。

**修正**：
```
签发 pluginToken 时必须指定站点（或显式标记为平台级）
校验时：token.siteId 必须与 URL 中的 siteSlug 一致，否则 403
平台级 token（如跨站点的 bot）需显式声明 scope: platform，并记录审计
```

### 🟡 R4 · 协同验证协议的站点归属

**推演**：`/api/verify/v1/assert` 是**平台级**端点，但断言内容（某主体的资格）是**站点级**的。

**问题**：调用方请求"用户 X 的 tier"，但没说是**哪个站点**的 tier。

**修正**：`/assert` 请求体必须含 `site`（siteSlug）：

```jsonc
{
  "site": "site-a",                    // ★ 新增：哪个站点
  "subject": { "type": "platform_user_id", "value": "..." },
  "claims": ["eligible", "tier"]
}
```

且调用方的 `verify_clients` 需声明**允许访问的站点列表**（`allowedSites`）——默认只允许其所属站点。

### 🟡 R5 · 事实命名空间与站点的关系

**推演**：`fact:github.total_stars` 在站点 A 和 B 下是**不同的值**（不同用户绑定、不同配置）。

**问题**：`ag_plugin_facts` 的唯一键是 `(userId, namespace, instanceKey)`——**没有 siteId**！

**这是个数据模型缺陷**：站点 A 采集的事实会覆盖站点 B 的。

**修正**：`ag_plugin_facts` 的唯一键必须含站点：

```ts
t.unique(['siteId', 'userId', 'namespace', 'instanceKey'], { name: 'uq_ag_facts_scope' })
```

同理检查**所有**业务表的唯一键是否都带 `site_id` 前缀——这是站点化的**一致性检查项**，应进 CI。

### 🟡 R6 · 主体（ag_external_subjects）是否需要站点维度

**推演**：`ag_external_subjects` 的键是 `(provider, externalId)`。若站点 A 与 B 都接同一个 new-api 实例 → 同一主体在两个站点下是**同一条记录**，但属性可能被两个站点的对账**互相覆盖**。

**修正**：明确 `ag_external_subjects` 的定位

| 方案 | 说明 |
|---|---|
| **站点级镜像**（推荐） | 键改为 `(siteId, provider, externalId)`——每个站点独立镜像，互不干扰；代价是同一 provider 在多站点下重复存储 |
| 平台级共享 | 键保持 `(provider, externalId)`，但**只允许一个站点配置该 provider 实例** |

推荐**站点级**：符合"站点是隔离边界"的一致原则，且避免跨站点的隐式耦合。

### 🟡 R7 · 分区表的主键约束

**推演**：`ag_evaluations` 按 `created_at` 分区。PG 要求**分区表的唯一约束必须包含分区键**。

但当前设计的主键是 `id`（bigserial），不含 `created_at` → **建表会失败**。

**修正**：
```ts
// 分区表的主键必须含分区键
t.primaryKey(['id', 'createdAt'])
// 或：不设主键，改用 (id, created_at) 的唯一索引
```

这是**实现层的硬约束**，Schema 声明层应能表达并校验。

### 🟡 R8 · 时间函数与确定性

**推演**：若表达式允许 `now()`，则同一策略在不同时刻求值结果不同 → 破坏"输入快照可复现"。

**修正**：**表达式禁止时间函数**
```
❌ 表达式里写 days_between(fact:github.created_at, now())
✅ 由插件在采集时算好并产出 fact:github.account_age_days
```

理由：时间相关的计算必须**在采集时刻固化**，否则评估不可复现。
（已在设计中通过 `derive` 阶段体现，此处明确为**禁止项**并加入静态校验。）

## 12. 第六轮：站点化的连带约束

> 站点级唯一键修正（R5）之后，会连锁出几个必须一并明确的约束。

### 🔴 S1 · `provider` 插件的作用域必须限定为 `site`

**推演**：主体（`ag_external_subjects`）现在是**站点级**的。若允许 `provider` 插件声明 `config.scope: developer`（一份配置服务多个站点），就会出现：

```
一份 newapi-provider 配置（指向 api-x）
   ↓ 对账
主体数据要写入【多个站点】的 ag_external_subjects
   ↓
但主体是站点级的 → 要么重复写 N 份，要么跨站点共享
   ↓
两个选择都与"站点是隔离边界"冲突
```

**修正：`kind: provider` 的插件强制 `config.scope: site`**

| kind | 允许的 config.scope | 理由 |
|---|---|---|
| **`provider`** | **仅 `site`** | 主体是站点级的；跨站点共享会造成隔离语义混乱 |
| `channel` / `enricher` | `developer`（推荐）或 `site` | 凭据可共享，产出的事实是站点级的（配置共享、数据隔离） |
| `action` | `site`（推荐）或 `developer` | 动作作用于站点内的主体 |
| `identity` | 平台级 | 身份源是平台级的 |
| `feature` | `site` | 功能面向站点内的用户 |

**静态校验**：`kind: provider` 且 `scope: developer` → **拒绝安装**并说明原因。

### 🟡 S2 · 对账必须按 `(siteId, providerId)` 分片

**推演**：主体是站点级的 → 对账不能再"按 provider 一次跑完"。

若 100 个站点都配了 `newapi-provider` → 需要 **100 次独立对账**（各自的分页、游标、配额）。

**修正**：
```
对账任务的调度单元 = (siteId, pluginId, instanceKey)
  · 各自独立的游标（ag_provider_sync_state 的键加 siteId）
  · 各自独立的配额预算
  · 共享一个工作池，避免 100 个任务同时打满
```

**连带**：`ag_provider_sync_state` 的主键从 `provider` 改为 `(siteId, provider)`。

### 🟡 S3 · 用户标签（tags）的站点维度

**推演**：`me.tags` 当前是 `ag_users.tags`（平台级）。若用户在站点 A 被标记 `verified:contributor`，站点 B 的策略里 `me.tags` 也会看到它。

**问题**：这违反了"站点间互不可见"。而且用户在 A 的验证结果可能**不应该**让 B 受益（B 没做这个验证）。

**修正：tags 改为站点级**

```ts
// 从 ag_users.tags 移出，改为独立表
ag_user_site_tags {
  siteId, userId, tag, source, createdAt
  unique: (siteId, userId, tag)
}
```

`me.tags` 求值时取**当前站点**的标签。跨站点的标签需求 → 用 `subject:<provider>@<site>.*` 显式引用。

### 🟡 S4 · 平台级属性的隐私边界

**推演**：站点策略可以写 `me.email` / `me.email_verified`——这些是**平台级**属性。于是：

| 问题 | 说明 |
|---|---|
| 站点能否看到用户 email 原文？ | 不应该——那是平台级信息 |
| 但判定"教育邮箱"需要它 | 需要的是**判定结果**，不是原文 |
| 站点管理员查看用户详情时 | 只能看到该站点的主体信息 |

**修正：区分"判定可用"与"可查看"**

```
判定时（表达式求值）：
  · me.email_verified   → 可用（布尔）
  · me.email_domain     → 可用（仅域名，不含本地部分）
  · me.email            → ❌ 不可用（静态校验拒绝）

查看时（站点管理员）：
  · 只显示该站点的主体信息（subject:newapi.*）
  · 平台级属性（email 原文）→ 仅 admin 可见 + 审计
```

**原则**：**判定需要的是"结论"，不是"原始数据"**。站点能问"这个用户是不是教育邮箱"，但看不到邮箱本身。

### 🟡 S5 · 新建站点的引导流程

**推演**：新建站点后是空的（无 provider 配置、无策略）。开发者面对空白不知从何下手。

**修正**：站点创建向导
```
① 站点信息（siteId / 昵称）
② 选择并配置 provider（平台已安装的 provider 列表 → 填凭据 → 测试连通）
③ 首次对账（显示主体数量）
④ 从模板创建第一条策略（或从空白开始）
⑤ 完成
```

### 🟡 S6 · 站点数量对调度的影响

**推演**：100 个站点 × 各自的巡检 + 对账 + 清理任务 = 数百个调度单元。

**修正**：
```
调度不是"每站点一个定时任务"，而是：
  · 一个全局的【站点扫描任务】按优先级轮转
  · 每次处理 N 个站点的到期工作
  · 站点间公平调度（避免大站点饿死小站点）
```

## 14. 第七轮：收敛验证（端到端生命周期）

> 前六轮都是"局部找茬"。这轮换方法：**让一个用户走完整生命周期**，看所有机制是否协同工作。
> 若一路顺畅 → 说明理论自洽；若卡住 → 说明还有缺口。

### 14.1 走查

| 时刻 | 事件 | 涉及机制 | 结果 |
|---|---|---|---|
| T0 | alice 首次登录站点 A1 | OIDC → 建号 → 站点上下文 → **首访触发 fast**（M1） | ✅ |
| T0+ | 评估 `edu-basic`（只依赖 email 域名） | declarative 采集 → 判定 satisfied → 动作 set_group | ⚠️ **见 T1** |
| T1 | 绑定 new-api 账号 | 对账 → 绑定键匹配 → 自动绑定 → 触发评估 → **动作重放** | ✅ |
| T2 | 绑定 GitHub | OAuth → 采集 → **enricher 链**（github → llm-review）→ LLM 缓存与预算 | ✅ |
| T2+ | 满足 tier2 | 级联：tier1(basic) + tier2(vip2) → **取 tier 高者** | ✅ |
| T3 | 30 天后 GitHub 故障 | 事实过期 + 采集失败 → **`indeterminate` → 保持 vip2**（H1） | ✅ |
| T4 | 用户删仓库，star 掉到 50 | unsatisfied → at_risk（72h）→ revoked → **`restore` 到 basic**（P1） | ✅ |
| T5 | 切到站点 B1 | 站点上下文切换 → B1 无绑定 → `indeterminate` → 不动作 | ✅ |
| T6 | 站点 B1 转移给另一开发者 | **见 T2** | ⚠️ |
| T7 | 用户注销 | 双向软删（L15） | ✅ |

**七轮走查下来，前六轮的修正全部协同生效**——H1（故障不降级）、P1（级联回退）、M1（首访触发）、Q1（LLM 锁定）都在真实路径上正确工作。

但走查暴露了 2 个新缺口：

### 🔴 T1 · 动作目标未绑定时的处理未定义

**推演**：T0+ 时，`edu-basic` 策略满足（只依赖 `fact:email.domain`），但动作 `set_group` 的目标是 `subject:newapi@A1`——**该主体尚未绑定**（用户还没在 new-api 登录过）。

当前设计对这种情况**没有定义**：动作会失败（主体不存在），但失败原因被归为普通错误 → 重试 → 反复失败 → 可能触发熔断（Q7）。

**修正：动作的"未绑定"是一等状态，不是错误**

```
动作执行前：
  ① 解析目标主体（subject:newapi@A1）
  ② 未绑定 → 动作状态 = blocked_unbound（【不是 failed】）
       · 不计入失败率（不触发熔断）
       · 进入"待绑定"队列
       · 用户侧显示："满足条件！绑定 new-api 账号后即可生效"
  ③ 绑定事件 → 自动重放该队列
```

**意义**：这实际上是一个**转化引导**——用户看到"我已经满足，只差绑定"，绑定动机远强于"未知"。

### 🟡 T2 · 站点归属变更时的会话与状态处理

**推演**：站点 B1 从开发者 D1 转移给 D2。

| 问题 | 说明 |
|---|---|
| D1 的会话仍指向 B1 | 但 B1 已不属他 → 应立即失效 |
| 用户在 B1 的状态（granted） | 归属变了，策略也换了 → 旧状态无意义 |
| B1 的对账游标 | 继续沿用（数据还在） |
| 迁移中的在途动作 | 应放弃 |

**修正**：
```
站点归属变更时：
  ① 使 D1 名下所有【activeSiteId = B1】的会话失效
  ② B1 的所有 ag_user_policy_state 转 orphaned（策略已变）
  ③ 取消 B1 的在途动作（planned / running）
  ④ 保留主体与事实（数据不丢，但需重新评估）
  ⑤ 通知 D1 与 D2
  ⑥ 写审计
```
