# 01 · 总体设计

## 1. 背景与目标

### 1.1 背景与定位

**问题的本质**：任何提供服务的系统（AI 网关、社区、游戏服务器、K8s 集群）都要回答同一个问题——
**"这个人值不值得信任？该给他什么权限？"**

现实中它几乎总是靠**人工判断**：管理员看贡献、看资历、看关系，然后手工改一个分组 / 加一个角色 / 拉进白名单。
这套做法不可配置、不可审计、不可复核，而且**每接一个新系统就要重做一遍**。

**本项目的定位**：一个**通用信任引擎（Trust Engine）**——

> 用**可插拔的插件**采集信任证据 → 用**表达式**判定信任等级 → 用**动作插件**把信任等级投射到任意下游系统。

它不绑定任何具体系统，只认四个抽象：

| 抽象 | 含义 | 由谁实现 |
|---|---|---|
| **Subject 主体** | 被信任的对象（用户） | `provider` 插件（new-api / Discord / K8s …） |
| **Fact 证据** | 支撑判断的信号 | `channel` / `enricher` 插件（GitHub / LLM / 邮箱 …） |
| **Policy 策略** | 判定规则（表达式 + 分支） | 管理员用 YAML / JSON / 图形编辑 |
| **Grant 授予** | 判定结果与投射动作 | `action` 插件 |

**部署形态**：既可作为**单站点自部署**（`standalone` 模式，只有内置开发者 + 终端用户；模式由 admin 在平台设置中切换），也可作为**多站点 SaaS**（控制平面 / 站点平面 / 用户平面，**开发者（含 admin）与终端用户两身份域** + 行级站点隔离）开放给其他开发者对接。详细设计见 06 文档。

**new-api 是第一个官方接入，但不是架构前提**：把 `plugins/builtin/newapi-*` 全部删掉，引擎依然完整可用——只是暂时没有下游系统可投射。

**为什么从 new-api 切入**：new-api 用 `users.group` 决定可用模型与计费倍率，但**分组只能管理员手工改**（`POST /api/user/manage` 无改分组能力），签到也**没有门槛**（`CheckinSetting` 只有 enabled/min/max）。社区运营中"给优质用户升级"完全靠人工。

### 1.2 目标

构建一个**通用的、基于插件的信任引擎**，实现：

| 目标 | 说明 |
|---|---|
| **G1 主体可对齐** | 通过 OIDC / OAuth 拿到稳定标识，与**任意下游系统**的主体一一对应 |
| **G2 证据可采集** | **运行期插件**组合多种信号（GitHub 指标 / LLM 评审 / 邮箱 / 邀请 / 付费…） |
| **G3 判定可表达** | **嵌套表达式**（`and`/`or`/`not`/比较）任意组合；**有序分支**允许不同分支不同条件；提供 **YAML / JSON / 图形** 三种等价表示 |
| **G4 授予可投射** | 判定结果经 `action` 插件投射到任意下游（new-api 分组 / Discord 角色 / MC 白名单 / K8s RBAC） |
| **G5 过程可审计** | 每次判定都有输入快照、结果树、动作与执行结果，可复现、可试算、可回滚 |
| **G6 能力可扩展** | 新增验证方式 / 新增下游系统 = **安装一个插件**，无需改主程序、无需重新构建 |
| **G7 跨项目可协同** | 插件可注册子路由；内置资格断言协议，让外部系统与平台**双向验证** |

### 1.3 非目标（明确不做）

- ❌ 不做 AI 网关 / 不做流量转发（那是 new-api 等系统的职责；本引擎只在**信任决策**层介入）。
- ❌ 不替代任何下游系统的用户管理后台。
- ❌ **不内建任何具体渠道的采集逻辑**——全部是插件。
- ❌ **核心代码中不出现任何具体系统名**（包括 new-api）；核心只认识 Subject。
- ❌ 不改变下游系统的计费与额度内核。
- ⏳ **多站点 SaaS 是独立阶段（M7）**，不阻塞单站点自部署；单站点形态下架构已预留 `site_id`，可平滑升级。

## 2. 首个接入方：new-api 源码调研

> 本章结论来自对仓库 `new-api/`（main @ `3524fe0b1`）源码的实读。
> 它们是 `newapi-provider` 与 `newapi-*` action 插件的**实现依据**，**不是核心架构假设**——核心不认识 new-api。

> 本章全部结论来自对仓库 `new-api/`（main @ `3524fe0b1`）源码的实读，是后续所有设计决策的依据。

### 2.1 能力矩阵

| 能力 | new-api 现状 | 位置 | 本项目如何使用 |
|---|---|---|---|
| 内置 OIDC 登录 | ✅ 有 | `setting/system_setting/oidc.go`、`oauth/oidc.go` | 模式 1 的对齐锚点 |
| OIDC 用户标识 | ✅ `users.oidc_id` = ID Token 的 `sub` | `oauth/oidc.go` `GetUserInfo` | 对齐键 |
| **ID Token 签名校验** | ❌ **不校验**：内置 OIDC 与自定义 Provider 都只拿 `access_token` 调 `userinfo` | `oauth/oidc.go`、`oauth/generic.go` | **EC（ES256）签名可安全使用**，见 05 文档 §8 |
| 自定义 OAuth Provider | ✅ 有，支持 field mapping（gjson JSONPath）+ well-known + 准入策略 | `model/custom_oauth_provider.go`、`oauth/generic.go` | 模式 2 的接入方式 |
| 自定义 Provider 绑定表 | ✅ `user_oauth_bindings(provider_id, provider_user_id)` | `model/user_oauth_binding.go` | 模式 2 的对齐键 |
| 用户列表（分页） | ✅ `GET /api/user/?p=&page_size=&sort_by=&sort_order=` | `controller/user.go` `GetAllUsers` | **全量对账数据源** |
| 用户详情 | ✅ `GET /api/user/:id`，**返回含 `oidc_id`** | `controller/user.go:503` | 单点校验 |
| 用户搜索 | ⚠️ `GET /api/user/search?keyword=` 仅匹配 **id / username / email / display_name** | `model/user.go` `SearchUsers` | **不能按 oidc_id 搜** |
| 改用户分组 | ⚠️ `PUT /api/user/`（read-modify-write，需完整对象） | `controller/user.go` `UpdateUser` → `EditWithTx` | 升级动作的唯一通道 |
| 禁用 / 启用 / 删号 | ✅ `POST /api/user/manage` | `controller/user.go` `ManageUser` | 违规处置 |
| 加额度 | ✅ `POST /api/user/manage` `{action:"add_quota"}` | 同上 | 签到 / 奖励发放 |
| 读 OAuth 绑定 | ✅ `GET /api/user/:id/oauth/bindings` | `controller/custom_oauth.go` | 模式 2 对齐核验 |
| 签到 | ✅ `GET/POST /api/user/checkin` | `controller/checkin.go` | 见 §2.3 的取舍 |
| 签到门槛 | ❌ 无分组限制 | `setting/operation_setting/checkin_setting.go` | 需本项目补偿 |
| 事件 / Webhook | ❌ 无 | — | 只能轮询 |
| 分组清单 | ⚠️ 存于 option，需 root 读 `/api/option/` | `setting/` | 可静态配置或 root 拉取 |

### 2.2 认证方式（本项目调用 new-api 的方式）

new-api 的 Dashboard 接口（`/api/**`）支持 **PAT（Personal Access Token）**：

```http
Authorization: Bearer <access_token>
```

- Token 由用户在 new-api 个人设置页生成（`POST /api/user/token`），存于 `users.access_token`。
- 中间件识别为 `dashboardCredentialPAT`，`AdminAuth()` 要求该用户 `role >= RoleAdminUser`。
- **本项目使用一个专用管理员账号的 PAT**，而非 root，遵循最小权限。

### 2.3 三条硬约束（架构由此决定）

#### 约束 A：没有事件流 → 必须"对账式"同步

new-api 不会告诉你"某用户刚注册 / 刚改了邮箱"。因此：

- **同步器**采用"**游标增量 + 周期全量校验**"：按 `id` 升序分页拉取，记录 `last_synced_id` 与 `last_full_sync_at`；
- 全量对账用于发现"改绑 OIDC""换邮箱"这类不回改 `id` 的变更；
- 所有同步写入都是 **UPSERT + 软删除标记**，保证幂等。

#### 约束 B：不能按 `oidc_id` 检索 → 必须自建身份索引

`SearchUsers` 的 LIKE 条件只覆盖 `username / email / display_name / id`。所以：

- 本项目维护本地表 `identity_links`，键为 `(provider, provider_user_id)`，值为 `newapi_user_id`；
- 该表由**全量同步**（读 `GET /api/user/` 的 `oidc_id` 字段）与**用户自助绑定**两条路径填充；
- 查人时**只查本地索引**，不查 new-api，避免每次登录都全表扫描。

> 可选的上游增强（见 §7）：给 new-api 提 PR 增加 `GET /api/user/by-identity?column=oidc_id&value=...`，本项目保留 feature-detect 分支。

#### 约束 C：改分组会踢人下线 → 写操作必须幂等 + 防抖

`EditWithTx` 中：

```go
authChanged := (updatePassword && current.Password != newUser.Password) || current.Group != newUser.Group
if authChanged {
    newUser.AuthVersion, _ = IncrementUserAuthVersionWithTx(tx, user.Id)  // → RevokeAllUserSessions
}
```

**推论**：

1. **值不变就不写**：动作执行器必须做 diff，目标分组 == 当前分组时直接跳过（这是安全的，因为 Go 侧也是先比较再 bump）。
2. **防抖与合并**：同一用户在高频巡检下若反复横跳（satisfied ⇄ unsatisfied），会造成反复登出。必须引入 **grace period（宽限期）** 与 **最小变更间隔（`min_change_interval`，默认 6h）**。
3. **写入串行化**：同一用户的写操作走**用户级互斥锁**，避免 read-modify-write 竞态（PUT 需要完整对象，并发 PUT 会互相覆盖）。

### 2.4 `PUT /api/user/` 的正确用法（易踩坑）

```go
// controller/user.go UpdateUser
if updatedUser.Role != common.RoleGuestUser && updatedUser.Role != originUser.Role { error }
updatedUser.Role = originUser.Role
...
if err := updatedUser.EditWithTx(tx, updatePassword); err != nil { ... }
```

`EditWithTx` 实际只写这几个字段：

```go
updates := map[string]any{"username", "display_name", "group", "remark"}
if updatePassword { updates["password"] }
```

**因此本项目构造的 payload 必须是**：

```jsonc
{
  "id": 123,
  "username": "<原样回填，不能为空>",
  "display_name": "<原样回填>",
  "group": "<目标分组>",
  "remark": "<原样回填>"
  // 不带 role（留空即 RoleGuestUser=0，可通过校验）
  // 不带 password（否则会重设密码！）
}
```

> ⚠️ **安全红线**：`EditWithTx` 对 `remark` 是**全量覆盖**。若本项目用 remark 存自己的标记，会覆盖管理员备注；反之管理员改备注会丢掉本项目的标记。**结论：本项目绝不写 `remark`，回填原值即可；自身状态全部存在本地库。**

### 2.5 签到解锁的两条路线（重要取舍）

new-api 的签到**没有分组门槛**，所以"升级后解锁签到"有三种实现方式：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 平台侧签到（推荐默认）** | 关闭 new-api 内置签到，由本项目提供 `/checkin` 接口，自己判断资格、自己调 `add_quota` 发额度 | 完全可控、门槛任意、可做连签/阶梯奖励 | 需要在 new-api 侧关闭内置签到；签到记录在本项目 |
| **B. 上游扩展** | 给 new-api 提 PR：`CheckinSetting` 增加 `allowed_groups` / `min_group`，并支持通过 API 设置 | 复用 new-api 原生签到 UI | 依赖上游合并；升级链路上有延迟 |
| **C. 仅标记** | 本项目只记录"已解锁"，签到仍由 new-api 开放给所有人 | 改动最小 | 没有真正的门槛，等于没做 |

**设计决策**：**默认走 A**，并把 B 做成可选适配器（`checkin.strategy: local | upstream | hybrid`），代码里用能力探测决定。这样不阻塞在等待上游 PR 上。

## 3. 需求结构化

> 原始描述较发散，这里把它收敛为**六个正交的设计维度**。任何"新玩法"都应该能落到这六个维度里；落不进去的，说明抽象不够，需要回头改内核。

### 维度 1 · 身份来源（Identity Source）

| 模式 | 拓扑 | 谁是谁的 IdP | 对齐键 |
|---|---|---|---|
| **模式 1** 联邦前置 | `new-api ← 中间统一 OIDC → 本项目` | 中间统一 OIDC 同时是 new-api 和本项目的 IdP | `users.oidc_id` == OIDC `sub` |
| **模式 2** 平台即 IdP | `用户 → 本项目（邮箱注册）→ new-api`，本项目对外发 OIDC，new-api 把本项目注册为 **自定义 OAuth Provider** | 本项目是 IdP | `user_oauth_bindings.provider_user_id` == 本项目 `user.id` |

两种模式**共享同一套内核**，差异只体现在 `identity` 模块的两个适配器上（详见 §6）。

### 维度 2 · 验证插件（Verification Plugin）

**运行期可插拔的"证据采集器 + 加工器"**。插件产出结构化 **Fact**，供规则引擎消费。

> **为什么是"运行期插件"而不是"编译期模块"**：把验证渠道做成随主程序发布的硬编码模块（如 `modules/channel-github`）属**编译期耦合**——新增渠道要改主程序、重新构建、重新部署，且主程序会"认识" GitHub，无法接纳未知渠道。因此它们必须是**运行期插件**，宿主不认识任何一个。详见 03 文档第 2 章。

**内置候选插件**（随主程序发布，但可禁用、可替换、可被第三方同 id 实现覆盖）：

| 插件 id | kind | 采集 / 产出 | 备注 |
|---|---|---|---|
| `github` | channel | 账号创建时间、仓库数、followers、**总 star**、组织、绑定邮箱 | declarative；需要 GitHub token |
| `llm-review` | **enricher** | 消费**任意**数组 fact（PR 列表 / MR 列表 / 发帖列表）→ **0-100 质量指数** | **通用能力**，不绑定 GitHub |
| `email-domain` | channel | 邮箱域名（支持通配 `*.edu.cn`、后缀、正则） | 纯本地，零外部依赖 |
| `invite-code` | channel | 邀请码 / 邀请人层级 | 纯本地 |
| `payment` | channel | 是否付费 / 付费金额 | 对接 new-api 充值记录 |
| `oidc-claim` | channel | 从 OIDC ID Token 任意 claim 取值（`hd`、`groups`…） | 通用兜底 |
| `manual-review` | channel | 人工审批 | 兜底 |

**第三方可自行扩展，无需改主程序**：`gitlab` / `gitee` / `discord` / `linuxdo` / `telegram` / 公司内部贡献系统 / 任何 REST API —— 绝大多数用 **declarative 形态**即可，**不写一行代码**。

**插件类型覆盖整条流水线**（不止采集）：

| kind | 方向 | 作用 |
|---|---|---|
| `channel` | 外部 → facts | 采集事实 |
| `enricher` | facts → facts | 加工 / 评分 / 聚合（如 LLM 评审） |
| `action` | 决策 → 外部 | 执行副作用（改分组、发额度、通知） |
| `identity` | 外部 → 身份 | 身份提供方（OIDC RP / OIDC Provider） |

**四向协同闭环**（不只是"平台拉取外部"）：

| 方向 | 机制 | 典型用途 |
|---|---|---|
| 平台 → 外部（拉） | `channel` 插件调外部 API | 拉取 GitHub star 数 |
| 外部 → 平台（调） | **插件端点** `/api/plugins/<id>/*` + 平台内置**协同验证协议** | AI bot 框架调平台验证用户资格 |
| 外部 → 平台（推） | `hmac` 签名的 webhook 端点（declarative 即可，零代码） | 社区推送"该用户升级了"作为事实 |
| 平台 → 外部（推） | 事件订阅 `subscribes` + `callbackUrl` | 平台通知 bot"用户已升级" |

> 插件可注册**子路由**（`manifest.endpoints`），但**不能自己监听端口**——宿主统一负责路由挂载、五种鉴权、限流、审计与 OpenAPI 生成（见 03 文档 §1.13）。

### 维度 3 · 判定表达式（Expression）

> **为什么不用"模式枚举"**：`mode = any|all|quorum|weighted` + 扁平 `items[]` 这类两级结构只能表达"若干条件里满足几个"，**表达不了"不同分支有不同条件"**——需求里的"QQ > 40 直接解锁；20 < QQ < 40 则要求与其它渠道组合达成"就写不出来。

判定语言改为**最基础的 `and / or / not / 比较` 通过任意嵌套组成复合逻辑**，并用**有序分支**表达"不同分支不同条件、不同动作"：

```yaml
requirements:
  branches:
    - id: qq_high                       # if
      label: "QQ 等级 > 40 级"
      when: { gt: { fact.qq.level: 40 } }
      outcome: satisfied
      actions: [ { action: newapi-set-group:set_group, params: { group: "vip3" } } ]

    - id: qq_mid                        # else if —— 条件完全不同
      label: "QQ 等级 20~40 级，需与其它渠道组合达成"
      when:
        all:
          - { gt:  { fact.qq.level: 20 } }
          - { lte: { fact.qq.level: 40 } }
          - atLeast:
              n: 2                          # 满足渠道数量
              of:
                - { $label: "GitHub star ≥ 100", gte: { fact.github.total_stars: 100 } }
                - { $label: "教育邮箱",           matches: { fact.email.domain: ["*.edu.cn"] } }
                - { $label: "PR 指数 ≥ 60",       gte: { fact.llm.pr_score: 60 } }
                - { $label: "有效邀请码",          gte: { fact.invite.used: 1 } }
      outcome: satisfied
      actions: [ { action: newapi-set-group:set_group, params: { group: "vip2" } } ]

  else:
    outcome: unsatisfied
    actions: [ { action: newapi-set-group:set_group, params: { group: "default" } } ]
```

**能力对照**（原始诉求全部保留，且由嵌套自然产生）：

| 原始诉求 | 表达式写法 |
|---|---|
| 任选一 | `any: [...]` |
| 全部必选 | `all: [...]` |
| 部分必选 + 部分可选 | `all: [必选..., atLeast: { n: 2, of: [可选...] }]` |
| 满足渠道数量 | `atLeast: { n: N, of: [...] }` |
| 加权分 | `score: { threshold: T, of: [{weight, expr}...] }` |
| **不同分支不同条件** | **`branches[]`（首个 `when` 为真即生效）** |
| 组合判断（含 LLM） | 任意嵌套，`fact.llm.*` 只是普通事实 |

**两个关键性质**：

- **策略里不写 `channel`**：写到 `fact.qq.level`，宿主就从命名空间反查插件并解析依赖（含 enricher 的递归依赖）。换插件、加渠道都不用动策略。
- **可解释**：求值产出完整结果树，用户能看到"走了哪个分支、满足了几项中的几项、每项实际值是多少"（详见 04 文档 §1）。

### 维度 4 · 生命周期（Lifecycle）

用户原话："不再满足自动取消 / 单次满足 / 组合满足 / 任务巡检条件"。

| mode | 语义 |
|---|---|
| `one_shot` | 一旦满足，永久保留（不回收） |
| `auto_revoke` | 每次评估都重算；不满足则（经宽限期后）回退 |
| `manual` | 满足后进入待审批队列，人工确认才生效 |
| `periodic` | 按固定周期强制重验（如每 30 天），过期未续则回退 |

统一实现为一个**状态机**（详见 05 文档 §3）：

```
        ┌──────────┐  评估通过   ┌───────────┐  动作成功  ┌───────────┐
        │ unknown  │ ─────────▶ │ satisfied │ ─────────▶ │  granted  │
        └──────────┘            └───────────┘            └───────────┘
              ▲                        │                        │
              │  评估不通过             │ 评估不通过              │ 周期到期/不满足
              │                        ▼                        ▼
        ┌───────────┐            ┌───────────┐            ┌───────────┐
        │ evaluating│ ◀───────── │  at_risk  │ ──宽限期──▶ │  revoked  │
        └───────────┘            └───────────┘            └───────────┘
```

### 维度 5 · 动作（Action）

| 动作 | 说明 |
|---|---|
| `newapi-set-group:set_group` | 改分组（幂等、防抖、带审计） |
| `newapi-add-quota:add_quota` | 发额度（签到 / 奖励） |
| `newapi-set-status:set_status` | 禁用 / 启用 |
| `checkin:grant` / `checkin:revoke` | 解锁 / 收回签到资格 |
| `notify.webhook` | 外发通知（企业微信 / TG / Discord） |
| `tag.add` / `tag.remove` | 打本地标签，供后续分流 |

### 维度 6 · 分流与阶梯（Routing & Ladder）

- **分流**：策略带 `match` 条件（用户属性 / 已有标签 / 来源 / 注册时间），只有匹配上的用户才走该策略。多策略按 `priority` 排序，**首个命中生效**（`exclusive`）或**全部生效取最高档**（`highest_tier`）。
- **阶梯**：策略集声明 `tier` 与 `requires_tier`，形成 DAG；用户逐级解锁，高 tier 的动作覆盖低 tier。

### 4.2 "基础运行架构 + 解耦功能实现" 的落地方式

> **模块化 ≠ 插件化**：把可扩展性做成"编译期模块"（`src/modules/channel-github`）只是**模块化**——新增渠道仍要改主程序并重新构建。只有**运行期插件体系**才能做到"装一个插件即可用"，详见 03 文档第 2 章。

#### 4.2.1 内核只提供"能力"，不提供"业务"

| 内核能力 | 接口 | 说明 |
|---|---|---|
| 配置 | `ctx.config.get<T>(path)` | 分层：默认值 → 配置文件 → 环境变量 → DB 覆盖 |
| 日志 | `ctx.log.child({ plugin })` | 结构化 JSON，自动带 `trace_id` / `pluginId` |
| DI | `ctx.provide(key, factory)` / `ctx.inject(key)` | 供内核与插件宿主自身装配 |
| 事件总线 | `ctx.events.emit(type, payload)` / `on(type, handler)` | 内核组件间通信；插件不直接订阅 |
| 任务调度 | `ctx.scheduler.every('24h', handler, { key })` | 带分布式锁、退避、超时 |
| HTTP | `ctx.http.route(method, path, schema, handler)` | 自动挂路由、鉴权、参数校验、错误封装 |
| 存储 | `ctx.db`（Repository 工厂） | 见 §5 |
| 迁移 | `ctx.migrations.register(table)` | 由 Schema 声明自动推导 |
| **插件宿主** | `ctx.plugins.*` | 清单校验、权限授予、进程管理、调用代理、事实校验 |

#### 4.2.2 三个层次的可扩展性（务必区分）

| 层次 | 扩展方式 | 需重新构建主程序？ | 适用 |
|---|---|---|---|
| **插件层** | 安装/启用插件（运行期） | ❌ **不需要** | 一切渠道、评分、动作、身份源 |
| **内核能力层** | 新增宿主 API | ✅ 需要（但极少变动） | 平台级新能力（如新增"短信网关"） |
| **数据访问层** | 新增 Schema 声明 | 需迁移，但无需改内核 | 新表 |

**判断标准**：若一个需求"只是要接一个新网站 / 新指标 / 新动作"，它就必须落在**插件层**，不允许改内核。

#### 4.2.3 插件宿主（Plugin Host）的职责

宿主属于内核，插件是宿主加载的外部单元。宿主负责：

| 职责 | 说明 |
|---|---|
| 清单校验 | `apiVersion` / `engines` / `digest` / 签名 / schema 合法性 |
| 权限授予 | 安装时逐项审查并授予；运行期每次调用都校验 |
| 生命周期 | install → validated → enabled → disabled → removed |
| 运行管理 | 进程启动/健康检查/崩溃重启/超时杀进程/资源限额 |
| 能力代理 | 密钥、出站 HTTP、LLM、KV、指标——全部经宿主 |
| 事实校验 | 插件产出的事实先过 `factSchema` 校验再落库 |
| 命名空间 | 事实按 `pluginId` 隔离；策略按 `pluginId` 寻址 |
| 依赖检查 | 卸载前检查是否有策略/绑定依赖 |
| 可观测 | 调用次数、耗时、失败率、崩溃、配额余量 |

#### 4.2.4 "宿主无知"的硬性验收标准

```
验收 1：把 plugins/builtin/ 整个目录删除 → 主程序仍能正常启动
        （只是没有任何渠道可用，管理端提示"尚未安装任何插件"）

验收 2：主程序核心逻辑中 grep 'github' → 0 命中
        （只允许出现在文档 / 注释 / 测试夹具中）

验收 3：安装一个全新的第三方插件（如 gitlab）：
        无需改动代码、无需重新构建、无需重启主程序，
        策略编辑器里立刻出现 fact.gitlab.* 的路径补全
```

#### 4.2.5 内置插件与第三方插件同构

内置插件放在 `plugins/builtin/`，**走完全相同的插件契约**（同一份 manifest 规范、同一套宿主 API、同一套权限模型）。唯一区别：内置插件默认受信任、可用 `in-process`；第三方默认 `process`。

这样做的好处是：**内置插件本身就是插件契约的参考实现与回归测试**——契约设计得不好，第一个受不了的就是内置插件。

## 5. 数据访问层设计（PostgreSQL 专属）

> **决策**：**只支持 PostgreSQL**。放弃 MySQL / SQLite 兼容，因此**不需要方言映射**，也不需要驱动抽象层——直接用 `pg`。
>
> 这不是能力缩水，而是**把省下的复杂度换成 PG 独有的加固能力**（见 §5.5 行级安全）。

### 5.0 数据库独占（部署硬约束）

**本项目独占一个 PostgreSQL 数据库，不与任何下游系统（new-api / Discord / 自建社区…）共用。**

| 含义 | 说明 |
|---|---|
| 独立数据库 | 不与 new-api 共用同一个库或 schema |
| 独立角色与连接池 | 专属数据库角色，权限只覆盖本项目的表 |
| 独立备份 / 迁移 | 升级与回滚互不影响 |
| **不跨库 JOIN** | 下游数据只能经 **provider 插件同步**到 `ag_external_subjects`，**绝不 JOIN 下游表** |

**为什么必须独占**：

1. **迁移自由**——本项目要频繁演进 schema（迁移生成 + drift 检测），共用库会把两边的升级节奏绑死；
2. **权限最小化**——专属角色 + RLS 才有意义；若应用账号能读下游表，RLS 只保护了自己那部分，等于半开；
3. **故障隔离**——本项目的重查询（全量对账、影响面预估）不会拖慢下游系统的生产流量；
4. **架构一致性**——本项目连 new-api 都是通过**插件 + API** 访问的，数据库层面更不该越界。**"不 JOIN 下游表"正是 provider 抽象成立的前提**。

> 这一条是"核心不认识任何具体系统"在**数据层**的体现。

### 5.1 分层职责（三层）

```
① Schema 声明层   defineTable / col.* / 索引 / 约束         ← 唯一事实来源
        │  推导
        ▼
② 查询编译层     Query AST → PG SQL（含作用域强制注入）     ← 业务不写 SQL 字符串
        │  编译产物
        ▼
③ 驱动与连接     pg（node-postgres）+ 连接池 + 事务上下文    ← 不再抽象
```

**与早期设计的差异**：

| 早期 | 现在 | 原因 |
|---|---|---|
| 四层（含 Dialect 转义抽象） | **三层** | 只有一种方言，转义表无意义 |
| `Dialect` 接口 + 3 个实现 | **删除** | — |
| `Driver` 接口 + 3 个驱动 | **删除**，直接用 `pg` | 连接态无差异可映射 |
| 查询 AST 编译器 | **保留** | 业务层仍不写 SQL；且承担**作用域注入**职责 |
| Schema 声明 + drift 检测 | **保留并强化** | 唯一事实来源，与方言无关 |

### 5.2 ① Schema 声明层（"定义对齐"）

**"定义对齐"的三层含义**：

1. **定义即结构**：TS 声明是唯一事实来源，DDL 由它推导，**禁止手写 `CREATE TABLE`**；
2. **定义与库对齐（drift detection）**：启动时 / CLI 执行 `db:check`，比对实际库结构与声明：
   - `missing`（声明有、库没有）→ **启动失败**（fail-fast）
   - `drifted`（类型/可空性/默认值不一致）→ 启动告警 + 健康检查降级
   - `extra`（库有、声明没有）→ 仅告警（允许应急字段）
3. **定义与代码对齐**：表/字段类型自动推导到 Repository 的 TS 类型，字段改名引发编译错误。

```ts
export const users = defineTable('ag_users', {
  id:          col.uuid().primaryKey().defaultSql('uuidv7()'),
  email:       col.varchar(255).notNull(),
  status:      col.enum('ag_user_status', ['pending','active','disabled']).notNull().default('pending'),
  primarySubject: col.jsonb().nullable(),
  createdAt:   col.timestamp({ withTz: true }).notNull().defaultNow(),
}, (t) => [
  t.unique(['email'],   { name: 'uq_ag_users_email', where: 'deleted_at IS NULL' }),
  t.index (['status'],  { name: 'ix_ag_users_status' }),
]);
```

**PG 专属类型可以放心使用**（不再需要任何降级）：`uuid` / `jsonb` / `text[]` / `timestamptz` / `interval` / `inet` / `numeric` / 原生 `enum`。

### 5.3 ② 查询编译层

**业务层写 AST，不写 SQL 字符串**：

```ts
const rows = await ctx.db.select(users)
  .where(and(eq(users.status, 'active'), gt(users.createdAt, since)))
  .orderBy(desc(users.createdAt))
  .limit(50)
  .run();
```

**职责重新定义**（不再翻译方言，而是做三件事）：

| 职责 | 说明 |
|---|---|
| **AST → PG SQL 编译** | 标识符引用、参数占位（`$1,$2`）、类型转换 |
| **作用域强制注入** | 自动追加 `site_id = $n`；无作用域时抛错（见 08 文档 §7） |
| **安全边界** | 标识符白名单（只允许 Schema 声明过的表/列）；值一律参数化；`raw()` 需显式声明 |

```ts
interface PgCompiler {
  compile(node: SqlNode, scope: ScopeCtx): CompiledSql;
  compileDdl(plan: MigrationPlan): string[];
}

interface CompiledSql {
  sql: string;
  params: unknown[];
  debug: string;      // 供日志/审计：参数内联后的可读 SQL（脱敏）
}
```

**因此可以删掉的东西**：方言能力矩阵、`lower()` 降级、UPSERT 三态、`RETURNING` 回退、数组/JSON 的跨方言模拟、部分索引的生成列替代方案。

### 5.4 ③ 驱动与连接（直接用 pg）

```ts
import { Pool } from 'pg';

const pool = new Pool({ connectionString, max: 20 });

// 事务：业务只写 ctx.db.transaction(fn)，无需透传 client
await ctx.db.transaction(async (tx) => { /* ... */ });
```

| 关注点 | 做法 |
|---|---|
| 连接池 | `pg.Pool`，按实例配置 |
| 事务 | `AsyncLocalStorage` 携带 client，业务层无感知 |
| 嵌套事务 | `SAVEPOINT` |
| 批量读 | `pg-query-stream` / `COPY` |
| 类型解析 | 自定义 `pg.types.setTypeParser`（`timestamptz` / `numeric` / `int8` 的 JS 映射） |
| **池分区** | **`realtime`**（用户请求）与 **`batch`**（对账 / 巡检）用**独立连接池**，互不饿死；长任务**不持有长事务**（对账按页提交，每 100 行一个事务）；池耗尽时 realtime 优先，batch 主动退避降并发 |

> ⚠️ **`int8`（bigint）**：`pg` 默认返回字符串（防精度丢失）。本项目统一用 `BigInt` 解析或明确标注为字符串，避免隐式转换错误。

### 5.5 站点作用域强制 + 行级安全（★ PG 独有加固）

**两道防线**：

```
第一道（应用层）：查询编译层自动注入 site_id = $n
        │  万一漏了 / 被绕过
        ▼
第二道（数据库层）：PostgreSQL 行级安全（RLS）
```

```sql
ALTER TABLE ag_policies ENABLE ROW LEVEL SECURITY;
ALTER TABLE ag_policies FORCE ROW LEVEL SECURITY;   -- 连表属主也受约束

-- ★ current_setting 不带第二个参数 true
--   不带 true → 未设置时【抛错】（fail-closed）
--   带 true    → 未设置时返回 NULL → site_id = NULL 恒为假 → 【静默返回空结果】（危险）
CREATE POLICY site_isolation ON ag_policies
  USING (site_id = current_setting('app.site_id')::uuid);
```

应用层在每个事务开始时设置上下文：

```sql
BEGIN;
SET LOCAL app.site_id = '0192a1b2-...';
-- 之后所有查询自动受 RLS 约束，即使应用层忘了加条件
COMMIT;
```

**为什么这是实质增益**：应用层注入依赖代码正确性，RLS 由数据库强制——**即使业务代码有 bug 或有人写了裸 SQL，也读不到别的站点数据**。

| 注意点 | 处理 |
|---|---|
| 表属主默认绕过 RLS | 必须 `FORCE ROW LEVEL SECURITY` |
| 连接池复用 | 用 **`SET LOCAL`**（事务级，结束自动失效）；**绝不用 `SET`**（会话级会污染下一个请求） |
| **必须在事务内** | `SET LOCAL` 在事务外**无效** → RLS 拿不到值。故**所有业务查询强制走事务**（Repository 层保证），CI 中禁止事务外查询 |
| **★ 单一事务入口（D17 前置 3，不可推迟）** | **所有业务查询必须走 `ctx.db.transaction(fn)` 单一入口**，CI **禁止事务外查询**。这是把「后补 RLS」成本压到 **O(1)** 的**唯一条件**——一旦读路径走 autocommit，后补就要审计每一条读路径（O(仓库)）。**推迟 RLS 不等于推迟这条约束** |
| **值来自会话而非参数** | `app.site_id` 由**会话的 `activeSiteId`** 派生（会话创建时已校验归属），**不接受查询参数** |
| **★ 批处理上下文** | 后台任务**没有会话**，必须显式定义第三种上下文：调度器按 `(siteId, …)` **逐站点开事务**并 `SET LOCAL app.site_id`；**单站点失败隔离**（不 abort 整批）；`BYPASSRLS` 仅限显式跨站点管理查询且强制审计。**禁止**用「默认站点」兜底——那会让其余站点的数据「UI 上还在、但永不评估」 |
| 迁移 / 管理操作 | 用单独的、带 `BYPASSRLS` 的管理角色 |
| 性能 | RLS 条件走 `site_id` 索引，开销可忽略 |

### 5.6 可以放心使用的 PG 能力

| 能力 | 用途 |
|---|---|
| `jsonb` + GIN 索引 | 属性袋查询（`attributes @> '{"group":"vip"}'`） |
| **部分唯一索引**（`WHERE`） | 如 `(site_id, plugin_id)` 只对 `status='enabled'` 唯一 |
| `ON CONFLICT ... DO UPDATE` | 对账 UPSERT |
| `RETURNING` | 写入即返回，省一次查询 |
| **`pg_advisory_lock`** | 分布式单飞锁 → **`ag_locks` 表可以删除** |
| **`LISTEN/NOTIFY`** | 多实例间的轻量事件广播 |
| **生成列**（`GENERATED ALWAYS AS`） | 从 `jsonb` 提取可索引列 |
| **行级安全 RLS** | 站点隔离第二道防线（§5.5） |
| **声明式分区** | `ag_evaluations` / `ag_audit_log` 按月分区 |
| `COPY` | 全量对账的批量写入 |
| `inet` / `cidr` | 网络规则与审计 IP |
| `interval` | TTL、宽限期、复核周期 |

### 5.7 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 数据库 | **PostgreSQL 16+（唯一支持）** | 不支持 MySQL / SQLite |
| 驱动 | **`pg`（node-postgres）** | 不抽象、不多驱动 |
| 查询层 | **自研**（`packages/db`，仅 PG 编译器） | 保留 AST + 作用域注入 + drift 检测 |
| 迁移 | 自研（Schema 声明推导 PG DDL） | 单一目标，无需多方言生成 |

> **备选路径**：若想进一步减少自研量，可用 **Kysely**（PG 方言）或 **Drizzle**（pg-core）替代自研查询层——**只针对 PG 时它们最简洁**。自研的价值集中在两点：**作用域强制注入**与 **drift 检测**；这两点若能以封装解决，就不必自研。

## 6. 两种身份集成拓扑

> **与 06 文档的分工**：本节讲**平台 ↔ 下游系统**的身份集成拓扑（谁是谁的 IdP、如何对齐）；06 文档讲**平台内部**的身份域划分（developer / enduser）与站点化。两者正交。

### 6.1 模式 1 · 联邦前置（中间统一 OIDC）

```
            ┌──────────────────────┐
            │  中间统一 OIDC       │  ← 唯一 IdP，在 new-api 中注册为 "OIDC"
            └───────┬──────────┬───┘
      ①登录/授权    │          │  ①登录/授权
                    ▼          ▼
          ┌──────────────┐  ┌──────────────────┐
          │   new-api    │  │  本项目 access-gate│
          │ users.oidc_id│  │  identity_links   │
          └──────┬───────┘  └────────┬──────────┘
                 │ ②管理员 PAT 调用   │
                 │◀──────────────────┘
                 │  GET /api/user/  (全量对账，读 oidc_id)
                 │  PUT /api/user/  (改 group)
```

**对齐流程**：

1. 用户在 new-api 通过 OIDC 登录 → `users.oidc_id = sub`；
2. 本项目全量对账拉取用户列表（`GET /api/user/` 返回体含 `oidc_id`），建立 `sub → newapi_user_id` 索引；
3. 用户访问本项目 → 走同一个 OIDC → 拿到 `sub` → 查本地索引 → 命中即对齐；
4. **未命中** → 引导用户去 new-api 完成一次 OIDC 绑定（跳 `{newapi}/login`），或由本项目在本地创建"待对齐"记录，等下一轮对账自动补上。

**降级策略**（索引未命中时的可选兜底）：

- 若 OIDC 提供了 `email` 且 new-api 用户邮箱唯一 → 用 `GET /api/user/search?keyword=<email>` 精确匹配（需 `email_verified` 为真），命中后写入索引；
- 兜底仍需**用户确认**（防止邮箱撞号），采用"发送确认链接"流程。

**前置条件**：中间统一 OIDC **必须**在 new-api 中注册为 OIDC（否则 `oidc_id` 为空，无从对齐）——这是用户已明确的约束，本项目在健康检查中会**显式检测并告警**。

### 6.2 模式 2 · 平台即 IdP

```
   ┌────────────┐  ①GitHub OAuth   ┌──────────────────┐  ②本项目发 OIDC
   │  GitHub    │◀────────────────▶│  本项目 access-gate│──────────────┐
   └────────────┘                  │  （邮箱注册 + 白黑名单）           │
                                   └────────┬─────────┘                ▼
                                            │ ③管理员 PAT         ┌──────────────┐
                                            │◀────────────────────│   new-api    │
                                            │  PUT /api/user/     │ 注册本项目为  │
                                            │  (改 group)         │ 自定义 OAuth  │
                                                                    └──────────────┘
```

**流程**：

1. 用户在本项目**邮箱注册**（校验邮箱白名单 / 黑名单：支持精确、后缀、通配、正则）；
2. 本项目对外提供 **OIDC Provider** 端点（`/.well-known/openid-configuration`、`/authorize`、`/token`、`/userinfo`、`/jwks.json`）；**ID Token 默认用 EC P-256（ES256）签名，JWKS 同时发布 RSA 公钥兜底**（见 05 文档 §8）；
3. 在 new-api 后台把本项目注册为**自定义 OAuth Provider**：
   - `well_known` = `https://gate.example.com/.well-known/openid-configuration`
   - `user_id_field` = `sub`（本项目用户 ID）
   - `username_field` = `preferred_username`，`email_field` = `email`
   - 可选：`access_policy` 用 new-api 原生的准入条件做一层粗过滤；
4. 用户从 new-api 点"用 access-gate 登录" → 回跳后 new-api 写入 `user_oauth_bindings(provider_id, provider_user_id = sub)`；
5. 本项目通过 `GET /api/user/:id/oauth/bindings` 或全量对账核验绑定，建立映射；
6. 用户在平台侧绑定 **GitHub** → 采集指标 → 规则判定 → 升级分组。

**关键设计点**：

- **`sub` 必须稳定**：本项目 `user.id`（UUID）即 `sub`，**永不复用、永不改变**；邮箱变更不影响 `sub`。
- **邮箱白/黑名单是准入闸门，不是升级条件**：白名单决定"能否注册"，升级条件在规则引擎里独立配置。
- **双向信任**：new-api 信任本项目的 OIDC 签名（**默认 ES256，JWKS 双算法并存**，见 05 文档 §8）；本项目信任 new-api 的管理员 PAT。
- **签名算法**：本平台默认用 **EC P-256（ES256）** 签发 ID Token，并以 `standby` 方式**常驻发布** RSA 公钥。已核实 new-api 当前**不校验 ID Token 签名**（内置 OIDC 与自定义 Provider 都只调 `userinfo`），故 EC 可安全启用；保留 RSA 是为上游未来启用验签时兜底，且切换 `activeAlg` 无需改代码、无需用户重新登录。

## 7. 首个接入方的边界与可选上游增强

> 本节内容**只针对 new-api**（第一个官方接入方）。其他下游系统同理——需要什么增强，取决于其 API 能力，不影响核心架构。

本项目**默认不改 new-api 一行代码**。但下列增强能显著提升体验，作为**可选 patch** 提供给上游：

| # | 增强 | 收益 | 优先级 |
|---|---|---|---|
| P1 | `GET /api/user/search` 支持 `oidc_id` / `email` 精确匹配参数 | 免去全量对账，实时对齐 | 高 |
| P2 | `CheckinSetting` 增加 `allowed_groups` / `min_group` | 原生签到支持分组门槛（路线 B） | 中 |
| P3 | 用户分组变更的 **Webhook / SSE 事件** | 免轮询，实时联动 | 中 |
| P4 | `POST /api/user/manage` 增加 `action: "set_group"` | 避免 read-modify-write 竞态 | 中 |
| P5 | 提供 `GET /api/user/by-identity` 通用身份查询 | 模式 1/2 统一对齐 | 低 |
| P6 | 自定义 Provider 的 ID Token 验签支持 EC（`SupportedSigningAlgs: ["RS256","ES256"]`） | 未来启用验签时不被算法卡死 | 低 |

**本项目对 P1–P5 全部做 feature-detect**：启动时探测能力，有则用快路径，无则走兜底路径，**不硬依赖**。

## 9. 非功能需求

| 维度 | 要求 |
|---|---|
| **性能** | 单实例 ≥ 500 QPS 管理读；单次评估 P95 < 800ms（不含外部 API）；全量对账 10 万用户 < 5min |
| **可用性** | 无状态水平扩展；调度任务用分布式锁（PG advisory lock / Redis）保证单飞 |
| **一致性** | 动作执行"至多一次 + 幂等重放"：`action_log` 唯一键 `(user_id, policy_id, action, target_value)` |
| **安全** | PAT 加密存储（AES-GCM，密钥来自环境变量/KMS）；OIDC 私钥不落库；全部写操作审计 |
| **可观测** | 结构化日志 + Prometheus 指标（评估次数、命中率、动作成功率、外部 API 配额余量） |
| **可测试** | 内核、插件宿主、declarative 解释器均可脱离数据库单测；提供 `MemoryDriver`、`FakeNewApiServer`、`FakePluginHost`（用于插件契约一致性测试） |
| **国际化** | 前端 i18n（zh-CN / en-US），与 workbuddy-manager 一致 |

## 10. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **Node.js 22 LTS + TypeScript 5** | 用户指定；原生 `fetch`、`AsyncLocalStorage`、`node:test` |
| 后端框架 | **Fastify**（备选：NestJS） | 插件/装饰器模型天然契合"内核 + 宿主 + 插件"；性能好；Schema 校验内建 |
| 校验 | **Zod** | 配置 schema、API 入参、策略 DSL 统一用它 |
| JOSE / OIDC | **`jose`**（RP 验签 + IdP 签发） | 原生支持 **ES256/384/512**、RS256、EdDSA；JWKS 生成与轮换 API 完整 |
| 查询层 | **自研**（`packages/db`，仅 PG 编译器） | 保留 AST + **作用域强制注入** + drift 检测；**不再需要方言降级** |
| 数据库 | **PostgreSQL 16+（唯一支持）** | 锁定 PG 换来 **RLS / advisory lock / 部分索引 / jsonb / 分区**，并消除方言层 |
| 队列/调度 | 内核内置（DB 表 + advisory lock） | 避免引入 Redis 依赖；量大时可插 `redis` 后端 |
| 插件运行时 | **JSON-RPC over stdio**（process）+ 受限表达式解释器（declarative） | 进程隔离简单可靠；声明式**无代码执行**，风险最低 |
| 插件沙箱 | 子进程资源限额（CPU/内存/FD）+ 出站白名单代理；Docker 部署可加 seccomp/只读 fs | 第三方插件默认不可信 |
| 前端 | **React 19 + Vite + Tailwind v4 + shadcn/ui** | 与 workbuddy-manager 视觉一致（见 04 文档） |
| 测试 | `vitest`（单测） + `testcontainers`（集成，可选） | — |
| 部署 | Docker + docker-compose；单二进制可选 `node --experimental-sea` | — |

> **为什么查询层自研而不直接用 Drizzle/Kysely？**
> **为什么锁定 PG 后仍需一层自研？** 方言翻译的价值消失了，但另外两个职责没有替代品：**作用域强制注入**（站点隔离的第一道防线）与 **drift 检测**。这两点若能通过 Kysely/Drizzle 的插件或封装实现，就完全可以不自研——届时自研层可缩到几百行（只做注入与校验）。
