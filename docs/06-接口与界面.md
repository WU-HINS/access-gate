# 第一部分 · HTTP API 契约

## 1. 总则

| 项 | 约定 |
|---|---|
| Base | `https://gate.example.com/api` |
| 编码 | JSON（`application/json`），UTF-8 |
| 鉴权（用户） | `Cookie: ag_session=<token>`（HttpOnly + SameSite=Lax + Secure） |
| 鉴权（管理员） | 同上，但会话带 `role: admin`；另支持 `Authorization: Bearer <admin_pat>` 供自动化 |
| 幂等 | 所有写操作接受 `Idempotency-Key` 头 |
| 分页 | `?page=1&pageSize=20`；响应 `{ items, total, page, pageSize }` |
| 错误 | `{ success: false, code: "GATE_XXX", message: "...", details?: {...}, traceId }` |
| 时间 | 一律 ISO-8601 带时区 |

**错误码分段**：`GATE_1xxx` 参数/校验，`GATE_2xxx` 鉴权，`GATE_3xxx` 身份对齐，`GATE_4xxx` 插件/端点，`GATE_5xxx` 策略，`GATE_6xxx` 动作/上游，`GATE_7xxx` 跨项目协同，`GATE_9xxx` 系统。

#### 5.2.2 敏感值的可见性与审计

> **设计立场**：`oidc_id` / `provider_user_id` 是**标识符而非凭证**，管理员排查对齐问题必须能看到完整值；但它们可用于跨站身份关联，所以**"能看到"必须配"看得到被记录"**。

| 字段 | 列表页 | 详情页 | 审计 |
|---|---|---|---|
| `oidc_id` / `provider_user_id` | 脱敏 `01J8XK…QZ` | ✅ **完整原值** | 调用详情接口记 `identity.view` |
| 平台 `user.id`（= sub） | 完整 | 完整 | — |
| 邮箱 | 脱敏 `a***@tsinghua.edu.cn` | ✅ 完整 | 记 `identity.view` |
| GitHub `login` / numeric id | 完整 | 完整 | — |
| `claimSnapshot` | — | ✅ 完整（已脱敏邮箱等） | 记 `identity.view` |
| new-api `access_token` | ❌ **永不返回** | ❌ 永不返回 | — |
| 密码哈希 / OIDC 私钥 | ❌ **永不返回** | ❌ 永不返回 | — |

**实现要点**：

1. 详情接口每次调用写一条 `ag_audit_log`（`action='identity.view'`，`targetType='user'`），带 `trace_id` 与操作人；**不**把值本身写进审计（避免审计表成为泄露源）。
2. 列表接口只返回脱敏值，需要完整值必须进详情页 —— 让"查看"成为一次有意识的动作。
3. 前端提供**一键复制** OIDC 值（排障高频操作），复制动作也记一次轻量审计。
4. `export` 接口额外要求二次确认 + 每分钟限流 + 强制审计。
5. 全部脱敏函数**服务端实现**，前端不做脱敏（防止绕过 API 直接拿全量）。

|---|---|---|
| `GET` | `/admin/policies` | 策略列表（含阶梯视图） |
| `GET` | `/admin/policies/:code` | 详情（含当前 active 版本） |

| `POST` | `/admin/policies/:code/preview-impact` | 影响面预估：全量跑一遍，只统计不改动 |
| `GET` | `/admin/policies/:code/expression?format=yaml\|json\|graph` | **取指定形态的表达式**（三种等价表示） |
| `PUT` | `/admin/policies/:code/expression?format=...` | 按指定形态写入（服务端统一转规范 AST） |
| `POST` | `/admin/policies/:code/expression/convert` | 形态互转 `{ from, to, content }` |
| `POST` | `/admin/policies/:code/expression/validate` | 任意形态校验 → 返回规范 AST + 错误节点路径 |
| `GET` | `/admin/policies/:code/expression/schema` | 返回表达式 JSON Schema（供外部工具与 IDE 校验） |

> **三种形态等价**（YAML / JSON / Graph），服务端以**规范 AST** 为唯一真理；`specHash` 只对规范 AST 计算，因此"同一逻辑分别用 YAML 与图形编辑"不会产生无意义的版本差异。详见 04 文档 §1.2.6。

#### 5.4.1 安装流程（权限审查是必经环节）

安装**不会立即生效**：先 `validated`，由管理员逐项审查权限并配置，才允许 `enable`。

```http
POST /admin/plugins/install
{ "source": "upload", "file": "<base64 .gatespkg>" }

→ {
    "plugin": { "id": "gitlab", "kind": "channel", "version": "1.0.0", "runtime": "process" },
    "digestVerified": true,
    "signatureVerified": false,
    "engineCompatible": true,
    "status": "validated",
    "requiresApproval": true,
    "permissions": [
      { "permission": "secrets:read:gitlab.token", "risk": "high",
        "reason": "读取你为该插件配置的 GitLab 访问令牌" },
      { "permission": "http:egress:gitlab.com", "risk": "medium",
        "reason": "向 gitlab.com 发起请求（仅此域名）" },
      { "permission": "storage:write:self", "risk": "low",
        "reason": "写入自有私有 KV（配额 10 MB）" }
    ],
    "configSchema": { /* JSON Schema，前端据此生成表单 */ },
    "factSchema":   { /* 策略编辑器据此做 fact.* 路径补全 */ }
  }
```

#### 5.4.2 插件与策略的联动

| 事件 | 行为 |
|---|---|
| 插件 `enable` | 其 `namespace` 立刻出现在策略编辑器的 `fact.` 补全里 |
| 插件 `disable` | 引用它的策略标记为 `degraded`，总览告警；评估时按 `onMissingFact` 处理 |
| 插件卸载（无依赖） | `namespace` 从补全中移除；历史事实保留只读 |
| 插件卸载（有依赖） | ❌ **拒绝**，返回 `GATE_4xx` 并列出依赖的策略 code |
| 插件升级 | 新旧版本并存，切换后旧版本 `retired` 保留 N 天可回滚 |

## 6. OIDC 双向联邦（平台 ↔ 项目）

> 两个方向都产出**可登录的凭证**，且注册在同一张表里，各有**永不变的唯一标识符** `ref`（见 03 文档 §1.18）：
> - `outbound`（`platform:*`）：平台是 IdP，项目是 RP —— 用户用平台账号登录项目；该凭证同时可作为**登录平台自身**的凭证；
> - `inbound`（`external:*`）：项目是 IdP，平台是 RP —— 用户用**项目账号登录平台**（联邦登录）。

### 6.0 注册与登录（inbound）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/admin/oidc/providers` | OIDC 注册表（含 ref / direction / 状态 / 最近调用） |
| `POST` | `/admin/oidc/providers` | 注册一个 OIDC 端点（自动分配或指定 `ref`） |
| `PUT` | `/admin/oidc/providers/:ref` | 修改（issuer / scopes / **exposedClaims** / allowPlatformLogin） |
| `POST` | `/admin/oidc/providers/:ref/discover` | 拉取并校验 well-known（含 `id_token_signing_alg_values_supported`） |
| `POST` | `/admin/oidc/providers/:ref/test` | 联调测试（走完整授权码流程） |
| `GET` | `/auth/oidc/:ref/start` | **用户登录平台**：发起联邦登录 |
| `GET` | `/auth/oidc/:ref/callback` | 联邦登录回调 |

**最小暴露**：只有 `exposedClaims` 里声明的 claim 能被表达式读取（`identity:oidc@<ref>.<claim>`），其余 claim 既不落库也不可见。

### 6.0.1 outbound：平台作为 IdP

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/.well-known/openid-configuration` | 发现文档 |
| `GET` | `/oauth/authorize` | 授权端点（PKCE 必需） |
| `POST` | `/oauth/token` | 令牌端点（`authorization_code` + `refresh_token`） |
| `GET` | `/oauth/userinfo` | 用户信息 |
| `GET` | `/oauth/jwks.json` | 公钥集（**EC + RSA 并存**） |
| `POST` | `/oauth/revoke` | 令牌吊销 |

### 6.1 Discovery 文档（EC 相关字段）

```jsonc
{
  "issuer": "https://gate.example.com",
  "authorization_endpoint": "https://gate.example.com/oauth/authorize",
  "token_endpoint": "https://gate.example.com/oauth/token",
  "userinfo_endpoint": "https://gate.example.com/oauth/userinfo",
  "jwks_uri": "https://gate.example.com/oauth/jwks.json",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "subject_types_supported": ["public"],
  "scopes_supported": ["openid", "profile", "email"],

  // ← 必须如实列出当前 JWKS 中【实际存在】的算法，不得虚报
  "id_token_signing_alg_values_supported": ["ES256", "RS256", "ES384", "RS384", "EdDSA"],

  "code_challenge_methods_supported": ["S256"],   // PKCE 必需
  "claims_supported": ["sub","email","email_verified","preferred_username","name","picture","gate_tier","gate_tags"]
}
```

> ⚠️ **不得虚报算法**：若声明了 `ES256` 但 JWKS 里没有 P-256 公钥，下游按声明选算法会直接验签失败。Discovery 内容由 JWKS 实际内容**派生**，不手写。

### 6.2 JWKS 响应（EC 与 RSA 双算法并存）

```jsonc
{
  "keys": [
    {
      "kty": "EC", "use": "sig", "alg": "ES256", "kid": "ec-2026-09-p256",
      "crv": "P-256",
      "x": "f83OJ3D2xF1Bg8vub9tLe1gHMzV76e8Tus9uPHvRVEU",
      "y": "x_FEzRu9m36HLN_tue659LNpXW6pCyStikYjKIWI5a0"
      //   ↑ ES256 签名 64 字节（r||s），比 RS256 短很多
    },
    {
      "kty": "EC", "use": "sig", "alg": "ES384", "kid": "ec-2026-09-p384",
      "crv": "P-384", "x": "...", "y": "..."
    },
    {
      "kty": "RSA", "use": "sig", "alg": "RS256", "kid": "rsa-2026-09",
      "n": "0vx7agoebGcQSuuPiLJXZptN9nndrQmbXEps2aiAFbWhM78LhWx4cbbfAAtVT86zwu1RK7aPFF...",
      "e": "AQAB"
      //   ↑ standby：不用于签发，但永久发布，作为只支持 RS256 的下游的兜底
    }
  ]
}
```

**ID Token header** 会带 `kid` 指向具体密钥，下游按 `kid` 选 key 即可，无需猜测：

```jsonc
{ "alg": "ES256", "kid": "ec-2026-09-p256", "typ": "JWT" }
```

### 6.3 new-api 侧接入提示

| 事项 | 说明 |
|---|---|
| 当前是否验签 | **不验签**（已核实源码）：内置 OIDC 与自定义 OAuth Provider 都只用 `access_token` 调 `userinfo`，`id_token` 未被校验 → **用 ES256 完全没问题** |
| 核对算法声明 | new-api 后台的「获取 Discovery 配置」（`POST /api/option/...` → `FetchCustomOAuthDiscovery`）会把 discovery 原样返回，可用它核对 `id_token_signing_alg_values_supported` |
| 若未来启用验签 | `coreos/go-oidc` 的 `oidc.NewVerifier` **默认只接受 RS256**，必须显式加 `SupportedSigningAlgs: []string{"RS256","ES256"}` |
| 兜底手段 | JWKS 里 `RS256` 公钥 `standby` 常驻；必要时把 `oidc.signing.activeAlg` 切成 `RS256`，**无需改代码、无需用户重新登录** |

## 7. 对外协同与 Webhook

四个方向合起来才是完整的跨项目协同：**平台拉取外部**（插件 channel）、**外部调用平台**（协同协议 + 插件端点）、**外部推送平台**（webhook 端点）、**平台推送外部**（出站 webhook）。

### 7.1 出站 Webhook（平台 → 外部）

```http
POST <你的 webhook>
X-Gate-Signature: sha256=<HMAC>
{
  "event": "policy.granted",
  "eventId": "evt_...",
  "subject": { "type": "platform_user_id", "value": "0192a1b2-..." },
  "policy": "contributor-tier2",
  "changes": [{ "action": "newapi-set-group:set_group", "from": "default", "to": "vip2" }],
  "at": "2026-09-21T00:00:00Z"
}
```

事件类型：`policy.granted` / `policy.revoked` / `policy.at_risk` / `action.failed` / `sync.drift_detected` / `checkin:granted` / `challenge.approved`。

投递语义：**至少一次**，接收方须按 `eventId` 幂等。

### 7.2 跨项目协同验证（平台内置标准协议，不依赖任何插件）

> 用途：外部项目（AI bot 框架、其他社区、内部系统）验证"某人在本平台的资格"。设计详见 03 文档 §1.14。

#### 7.2.1 调用方管理（管理端）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/admin/verify/clients` | 调用方列表（含 scopes、最后调用时间、调用量） |
| `POST` | `/admin/verify/clients` | 注册调用方（**secret 仅返回一次**） |
| `PUT` | `/admin/verify/clients/:id` | 修改（scopes / callbackUrl / allowedSubjects） |
| `POST` | `/admin/verify/clients/:id/rotate` | 轮换 secret（支持新旧并存过渡期） |
| `POST` | `/admin/verify/clients/:id/suspend` | 暂停 |
| `DELETE` | `/admin/verify/clients/:id` | 吊销 |
| `GET` | `/admin/verify/assertions` | 断言流水（按 client / subject / 时间过滤） |
| `POST` | `/admin/verify/assertions/:id/revoke` | 撤销某条断言 |

#### 7.2.2 请求签名规范

```http
X-Gate-Client:    vc_7f3a...
X-Gate-Timestamp: 1758412800
X-Gate-Nonce:     8f2c...
X-Gate-Signature: sha256=<HMAC(secret, method + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + bodyHash)>
```

- 时间戳容差 **±5 分钟**；nonce 在该窗口内去重（防重放）；
- `bodyHash` = SHA-256(body) 的 hex；GET 请求体为空串。

#### 7.2.3 协同验证端点（外部调用）

| 方法 | 路径 | scope | 说明 |
|---|---|---|---|
| `POST` | `/api/verify/v1/assert` | `assert:read` | **资格断言**（核心） |
| `POST` | `/api/verify/v1/challenge` | `challenge:create` | 发起设备码流挑战 |
| `GET` | `/api/verify/v1/challenge/:id` | `challenge:create` | 轮询挑战结果 |
| `POST` | `/api/verify/v1/revoke` | `assert:read` | 撤销某 subject 的临时关联 |
| `GET` | `/api/verify/v1/jwks` | — | 断言签名公钥（转发平台 JWKS；**可匿名访问**） |

**`/assert` 请求 / 响应**：

```jsonc
// 请求
{
  "subject": { "type": "platform_user_id", "value": "0192a1b2-..." },
  "claims":  ["eligible", "tier", "tags", "policies"]
}

// 响应
{
  "matched": true,
  "subject": { "type": "platform_user_id", "value": "0192a1b2-...", "displayName": "alice" },
  "assertions": {
    "eligible": true,
    "tier": 2,
    "tags": ["verified:contributor"],
    "policies": [{ "code": "contributor-tier2", "state": "granted" }]
  },
  "issuedAt":  "2026-09-21T00:00:00Z",
  "expiresAt": "2026-09-21T00:05:00Z",
  "issuer":    "https://gate.example.com",
  "signature": "eyJhbGciOiJFUzI1NiIsImtpZCI6ImVjLTIwMjYtMDktcDI1NiJ9..."
}
```

> **调用方验证流程**：用 `/api/verify/v1/jwks`（或平台 `/.well-known/jwks.json`）取公钥 → 按 `kid` 验 `signature` → 校验 `iss` / `expiresAt` / `subject` 与请求一致。
> 这样**断言可以离线复核**，不依赖对平台的实时信任。

**`/challenge` 设备码流**：

```jsonc
// 请求
{ "subject": { "type": "discord_id", "value": "1234567" }, "scopes": ["assert:read"] }

// 响应
{ "challengeId": "ch_...", "userCode": "ABCD-1234",
  "verifyUrl": "https://gate.example.com/verify",
  "expiresIn": 600, "interval": 3 }

// 轮询 GET /api/verify/v1/challenge/ch_...
{ "status": "pending" }                                     // 或 approved / denied / expired
{ "status": "approved", "assertion": { /* 同 /assert 响应 */ } }
```

#### 7.2.4 官方薄 SDK

| 语言 | 包 | 覆盖能力 |
|---|---|---|
| TypeScript | `@gate/verify-client` | 签名、`assert`、`challenge` 轮询、JWKS 验签、事件回调验签 |
| Python | `gate-verify` | 同上（供 NoneBot2 / BotPy / 自建 bot 使用） |

**各大框架的接入方式见 03 文档 §1.14.2**：绝大多数 bot 框架**不需要平台侧插件**，直接用标准协议即可。

### 7.3 插件端点（外部 → 插件）

#### 7.3.1 挂载规则

### 10.2 策略编辑器（核心页面）

四段式：**左表达式（三形态可切）/ 中图形化树 / 右上动作 / 底部试算**。

**表达式编辑区支持三种等价视图，随时切换、互不丢失**：

```
┌─ 表达式 ──────────────────────────── [ YAML │ JSON │ 图形 ] ─┐
│  ● YAML   手写 / Git 管理 / Code Review（策略即代码）          │
│  ● JSON   程序生成 / 复制粘贴 / 与外部工具交换                  │
│  ● 图形   拖拽嵌套、分支编排（非技术管理员友好）                 │
└──────────────────────────────────────────────────────────────┘
切换视图时服务端做 AST 规范化转换；布局信息（节点坐标）随图形视图单独保存。
同一逻辑用任一视图编辑，specHash 相同 —— 不会因为换了编辑器就产生新版本。
```

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ contributor-tier2   v4 (draft)              [校验] [试算] [影响面] [发布]      │
├──────────────────────────────┬───────────────────────────────────────────────┤
│ ① 表达式（YAML）              │ ② 表达式树（可视化，可拖拽嵌套）                │
│                              │                                               │
│ requirements:                │  ▾ 分支（按序，首个命中生效）                   │
│   branches:                  │  ┌─────────────────────────────────────────┐  │
│     - id: qq_high            │  │ ① QQ 等级 > 40 级              [if]     │  │
│       when:                  │  │    └ > fact.qq.level   40               │  │
│         gt: {fact.qq.level:40}│  │    → vip3                              │  │
│       outcome: satisfied     │  ├─────────────────────────────────────────┤  │
│       actions: [...]         │  │ ② QQ 等级 20~40 且组合达成  [else if]   │  │
│                              │  │    └ AND                                │  │
│     - id: qq_mid             │  │       ├ > fact.qq.level   20            │  │
│       when:                  │  │       ├ ≤ fact.qq.level   40            │  │
│         all:                 │  │       └ 至少 2 项（共 4 项）             │  │
│           - gt:  {...}       │  │          ├ GitHub star ≥ 100            │  │
│           - lte: {...}       │  │          ├ 教育邮箱                     │  │
│           - atLeast:         │  │          ├ PR 指数 ≥ 60                 │  │
│               n: 2           │  │          └ 有效邀请码                    │  │
│               of: [...]      │  │    → vip2                               │  │
│   else: {...}                │  ├─────────────────────────────────────────┤  │
│                              │  │ ③ else                        [兜底]    │  │
│                              │  │    → default                            │  │
│                              │  └─────────────────────────────────────────┘  │
│                              │  [+ 添加分支]  [+ 嵌套组]  [引用 $ref]         │
├──────────────────────────────┴───────────────────────────────────────────────┤
│ ③ 试算   用户 [alice ▾]   覆盖事实 [+ 添加]              [运行试算]           │
│                                                                              │
│  分支① qq_high            ❌  fact.qq.level = 32 ≤ 40                        │
│  分支② qq_mid             ✅  已满足 2/4 项                                  │
│    ├ GitHub star ≥ 100    ✅  212 ≥ 100                                      │
│    ├ 教育邮箱             ❌  gmail.com 不匹配 *.edu.cn                       │
│    ├ PR 指数 ≥ 60         ✅  71 ≥ 60                                        │
│    └ 有效邀请码           ❌  0 < 1                                          │
│  分支③ else               —   未求值（② 已命中）                              │
│  ────────────────────────────────────────────────────────────                │
│  结论：satisfied（分支②）   预计动作：newapi-set-group:set_group → vip2                 │
└──────────────────────────────────────────────────────────────────────────────┘
```

**编辑器的四个关键能力**：

| 能力 | 说明 |
|---|---|
| **任意嵌套** | 拖拽把条件放进 `all` / `any` / `atLeast` 组里，层数不限；树与 YAML 双向同步 |
| **分支编排** | 上下拖动调整分支顺序（顺序即优先级）；一键在"单一表达式"与"多分支"之间切换 |
| **实时求值** | 选一个真实用户（或覆盖事实），底部实时出结果树，**每一层的实际值都可见** |
| **路径补全** | 输入 `fact.` 按插件 `factSchema` 补全；`user.` / `binding.` 补全内置字段 |

> **YAML 与可视化双向同步**：可视化改动回写 YAML；YAML 解析失败时右侧标出错误节点路径。比"纯表单"更适合运维，比"纯 YAML"更易上手——而且**嵌套结构用树展示远比缩进清晰**。

### 10.3 我的资格（用户侧）

数据源就是 04 文档 §1.6 的**结果树**——用户看到的不是"不满足"，而是"差在哪一项、差多少"。

```
┌──────────────────────────────────────────────────────────────────────────┐
│  贡献者认证                                              状态：已通过      │
│  当前分组 default  →  vip2（将于下次同步生效）                             │
├──────────────────────────────────────────────────────────────────────────┤
│  判定过程                                                                 │
│                                                                          │
│  ❌ 分支 1 · QQ 等级 > 40 级                                   未通过     │
│       QQ 等级 32，需要 > 40                                               │
│                                                                          │
│  ✅ 分支 2 · QQ 等级 20~40 级，需与其它渠道组合达成             已通过     │
│       ✅ QQ 等级 32（需 20 ~ 40）                                         │
│       ✅ 需满足 4 项中的 2 项 —— 已满足 2 项                              │
│          ✅ GitHub 总 star ≥ 100 · 当前 212                              │
│          ✅ LLM 有效 PR 指数 ≥ 60 · 当前 71                               │
│          ❌ 教育邮箱 · 当前 gmail.com（需 *.edu.cn / *.edu）              │
│          ❌ 有效邀请码 · 未使用                                           │
│                                                                          │
│  ⏭ 分支 3 · 贡献突出但 QQ 等级不足                              未求值     │
│       已由分支 2 通过，无需继续判定                                        │
├──────────────────────────────────────────────────────────────────────────┤
│  🔓 每日签到   已解锁（1000 ~ 5000 额度 / 日）              [ 去签到 ]     │
│  事实更新于 2 小时前                                  [ 手动重新检测 ]    │
└──────────────────────────────────────────────────────────────────────────┘
```

**展示原则**：

1. **按分支展示**，而不是把条件拍平——用户要理解"我走的是哪条路"；
2. **每一项都显示实际值**，不只显示 ✓/✗（"212 ≥ 100" 比"通过"有用得多）；
3. **未求值的分支明确标注**"未求值（已由分支 N 通过）"，避免用户误以为是 bug；
4. 计数型节点（`atLeast`）显示 **"已满足 m/n 项"**，让用户知道距离通过还有多远；
5. 默认走 `explain` 模式（**不触发新采集**），只有点「手动重新检测」才做完整采集。

5. 「对齐诊断」区块用 ✅/⚠/❌ 直接给结论，不让管理员自己比对两串 UUID。

| **界面** | 该插件贡献的前端位置：导航项 / 页面 / 插槽 / 设置面板，含**可见角色**、渲染形态（declarative / remote-module / iframe）、审批与启用状态；提供**实时预览**与逐条禁用 |
| **运行** | 调用流水（状态/耗时/出站域名/被拒权限）、崩溃与重启记录、日志流（SSE） |

#### ④ 与策略编辑器的联动（体验核心）

```
策略编辑器 → 规则项的 channel 下拉：
┌────────────────────────────────┐
│ 选择插件                        │
│ ● github        channel  已启用 │
│ ● gitlab        channel  已启用 │
│ ○ discord       channel  未安装 │  ← 灰显 + "安装后可选用"
│ ○ linuxdo       channel  未安装 │
└────────────────────────────────┘

输入 fact. 时自动补全（数据来自插件 manifest.factSchema）：
┌────────────────────────────────────────────┐
│ fact.gitlab.                                │
│   ├ account_age_days   integer  账号年龄（天）│
│   ├ project_count      integer  项目数       │
│   └ total_stars        integer  总 star 数   │
└────────────────────────────────────────────┘
```

> 这段联动的意义：**装一个插件，策略编辑器里立刻多出一个命名空间**——动态扩展的能力对使用者是可感知的，而不只是后端的一行配置。

### 10.7 插件 UI 扩展点（前端如何被插件扩展）

平台前端是**固定的宿主外壳 + 可变的插件贡献**。插件不修改宿主的代码，只往预置扩展点里"投递"内容。

#### 10.7.1 启动流程

```
平台前端启动
   │
   ├─ ① GET /api/ui/manifest          ← 拉取所有【已启用且已审批】的 UI 贡献，按角色过滤
   │
   ├─ ② 填充扩展点注册表
   │     nav     → 追加到顶部 ManagementBar
   │     page    → 追加到路由表
   │     slot    → 注册到 <PluginSlot name="..." />
   │     settings/adminPage → 追加到管理端
   │
   └─ ③ 渲染时按 renderMode 分派到三个内置渲染器
```

```jsonc
// GET /api/ui/manifest 响应（节选：签到插件）
{
  "nav": [
    { "pluginId": "checkin", "id": "checkin", "label": "每日签到",
      "icon": "gift", "path": "/checkin", "audience": "user", "order": 20,
      "badge": { "when": "$.today == false", "text": "未签到" } }
  ],
  "pages": [
    { "pluginId": "checkin", "path": "/checkin", "title": "每日签到",
      "audience": "user", "renderMode": "declarative", "blocks": [ /* 块树 */ ] }
  ],
  "slots": {
    "user.dashboard.top": [
      { "pluginId": "checkin", "order": 10, "renderMode": "declarative", "block": { /* … */ } }
    ]
  },
  "settings": [ { "pluginId": "checkin", "schema": { /* configSchema */ } } ]
}
```

#### 10.7.2 三个内置渲染器

| 渲染器 | 输入 | 关键保障 |
|---|---|---|
| `DeclarativeRenderer` | 块树（`stats` / `action` / `form` / `table` / `chart` / `calendar` / `markdown` / `tabs` / `section`） | 只用宿主 shadcn 组件；**禁用 `dangerouslySetInnerHTML`**；模板插值 HTML 转义；markdown 走 DOMPurify |
| `RemoteModuleLoader` | ESM bundle URL | 校验签名与 CSP 白名单；挂 **Shadow DOM** 隔离样式；包错误边界 + 骨架屏；加载失败降级为提示 |
| `PluginIframe` | 页面 URL | 独立 origin + `sandbox` 属性；postMessage 桥做鉴权透传；不用时卸载 |

#### 10.7.3 宿主预置插槽

| slot | 位置 | 典型用途 |
|---|---|---|
| `user.dashboard.top` | 用户首页顶部 | 签到状态卡、资格进度 |
| `user.dashboard.sidebar` | 用户首页侧栏 | 快捷入口 |
| `user.profile.tabs` | 个人资料页 Tab | 渠道绑定管理 |
| `admin.overview.cards` | 管理总览卡片区 | 插件健康度 |
| `admin.user.detail.tabs` | 用户详情抽屉 Tab | 该插件的事实 / 绑定面板 |
| `admin.policy.editor.toolbar` | 策略编辑器工具栏 | 插件提供的校验 / 预览工具 |

#### 10.7.4 数据获取：必须经宿主代理

```
declarative 块的 source: { method: GET, url: "/api/plugins/checkin/status" }
        │
        ▼
宿主 UI 数据代理
   ├─ 校验该 url 是否属于【当前页面所属插件】的已批准端点
   │     ├─ 是   → 放行（自动附当前用户会话）
   │     └─ 否   → 拒绝（插件不能借 UI 读别的插件的数据）
   ├─ 限流 + 审计
   └─ 返回数据
```

> **这条约束是 UI 扩展安全的基石**：装了签到插件，它也只能读签到插件自己的端点，**读不到**你的策略判定明细、其他渠道的绑定信息。

## 11. 交互细节清单

| 场景 | 交互 |
|---|---|
| 策略发布 | 二次确认弹窗，展示 **影响面预估**（将升级 N 人 / 回退 M 人），输入策略 code 才能确认 |
| 分组变更 | Toast 明确提示"该用户会被强制重新登录"（因为 `auth_version` 变更） |
| 试算 | 结果面板固定底部，支持"复制为测试用例" |
| 长任务（全量对账） | 顶部进度条 + 可折叠日志抽屉（SSE 推送） |
| 表格 | 列可配置、密度可切（紧凑/舒适）、支持 URL 同步筛选条件 |
| 空状态 | 每种列表都有专属空状态文案 + 主行动按钮 |
| 危险操作 | `AlertDialog` + 输入确认词 |
| 插件安装 | 三步向导；**权限逐项勾选**；未签名插件要求显式确认信任 |
| 插件禁用/卸载 | 先展示「依赖检查」结果（策略引用 N 条），有依赖时禁止卸载 |
| 插件试运行 | 展示「将要写入的事实」供确认，而不是只报成功 |
| 加载 | 骨架屏（`auto-skeleton-react` 或 shadcn `Skeleton`），不用转圈 |
| 错误 | 顶部 `Alert` 显示 `traceId`，一键复制给管理员 |

## 12. 与参考项目的差异（有意为之）

| 维度 | workbuddy-manager | 本项目 | 原因 |
|---|---|---|---|
| 导航 | 顶部 ManagementBar | **同** | 保持一致的观感 |

| 实时性 | 轮询 | 轮询 + SSE（任务进度） | 长任务体验需要 |
