# 03 · 插件体系

> 本文档定义**能力层**：一切采集 / 加工 / 动作 / 身份 / 功能能力都由插件提供，**核心不认识任何具体系统**。

## 1. 插件体系（Plugin System）

> **为什么插件必须"运行期装配"**：把"验证渠道"做成随主程序发布的**模块**（`modules/channel-github`），并把 GitHub 的指标（`fact.github.total_stars` 等）当成平台内置概念，会带来三个后果：
>
> - **模块是编译期的**：新增一个渠道要改主程序、重新构建、重新部署；
> - **强耦合**：主程序的策略校验器"认识" GitHub，无法接纳未知渠道；
> - **无法动态扩展**：用户想加 GitLab、Gitee、公司内部贡献系统、某个垂直社区，都得改主程序。
>
> 本节改为**真正的插件体系**：主程序**不认识任何具体渠道**，只提供插件宿主（Host）与宿主 API；一切采集、加工、动作都由插件在**运行期**提供。

### 1.1 核心原则

| 原则 | 含义 |
|---|---|
| **宿主无知** | 主程序代码中**不出现** `github` / `discord` / `edu` 等任何具体渠道的名字 |
| **运行期装配** | 插件在运行时安装、启用、禁用、卸载，**无需重新构建主程序** |
| **能力受控** | 插件只能通过宿主 API 访问外部世界，权限逐项声明与授予 |
| **契约稳定** | 插件面向 `gate.plugin/v1` 契约编程，契约版本化、向后兼容 |
| **默认隔离** | 第三方插件默认**进程外运行**，密钥永不直接交给插件 |

### 1.2 插件类型（kind）

插件贯穿整条流水线，而不只是"采集"：

| kind | 方向 | 职责 | 典型插件 |
|---|---|---|---|
| **`provider`** | **主体 ↔ 平台** | **下游系统的"主体目录"：列出 / 查询 / 读属性 / 写状态** | **newapi-provider、discord-provider、minecraft-provider、k8s-provider** |
| `channel` | 外部 → facts | 采集事实（信任证据） | github、gitlab、linuxdo、email-domain、invite-code、payment |
| `enricher` | facts → facts | 加工、评分、聚合、去重 | llm-review、risk-score、aggregate、dedupe |
| `action` | 决策 → 外部 | 执行副作用（把信任等级投射到下游） | newapi-set-group、discord-assign-role、minecraft-whitelist |

> **动作标识的规范形（★ 实现者-3）**：`<pluginId>:<actionName>`，如 `newapi-set-group:set_group`。
> 它是**幂等键的输入**——同一动作的两种写法会产生两个幂等键 → **重复执行**（对 `set_group` 就是多踢一次用户会话）。
> **发布时静态校验拒绝其它拼法**；旧的点号写法（`ns.action`）已废弃。
> `appliedActions` / `baseline` 的键也必须用规范形。
| `identity` | 外部 → 身份 | 身份提供方 | oidc-rp（模式 1）、oidc-provider（模式 2）、github-login |
| **`feature`** | **平台 → 用户** | **提供面向用户的功能（UI 贡献 + 端点 + 后台任务）** | **checkin（签到）、onboarding、referral、invite** |

> **`provider` 是"通用信任引擎"的关键**：它让核心只认识 **Subject（主体）**，不认识 new-api / Discord / K8s 等任何具体系统。详见 §2.16。
>
> **`endpoints`（对外 HTTP）与 `ui`（前端贡献）是所有 kind 都可以声明的通用能力**——任何插件都能既提供后端逻辑，又给用户一个界面入口。详见 §2.13 与 §2.17。
>
> **`identity` 属于高权限插件**：它能决定"你是谁"。因此**仅允许**以 `in-process`（官方内置）或 `process`（签名验证通过）形态运行，且安装需二次确认。

### 1.3 运行形态与信任模型

同一个插件契约，可以有四种运行形态。**安全性与便利性成反比**：

| runtime | 代码执行 | 密钥可见性 | 网络出口 | 适用场景 | 默认 |
|---|---|---|---|---|---|
| `declarative` | ❌ **无代码** | 仅模板占位符，由宿主注入 | 仅 manifest 声明的域名 | API 型渠道（占 80%） | ✅ 推荐 |
| `process` | ✅ 子进程 | 只能通过宿主 API 按需获取 | 由宿主代理，白名单 | 第三方插件、任意语言 | ✅ 第三方默认 |
| `container` | ✅ 独立容器 | 同上 | 网络策略限制 | 高安全要求 / 不可信插件 | 可选 |
| `in-process` | ✅ 宿主进程内 ESM | ⚠️ **理论上可读全进程内存**（含 PAT、私钥） | 无限制 | **仅官方内置 / 已签名插件** | 受限 |

**策略**：

1. 能用 `declarative` 解决的，**绝不写代码**；
2. 第三方插件一律 `process` 起步；
3. `in-process` 需要满足全部条件：包签名验证通过 + 管理员显式确认风险 + 插件在官方信任列表内；
4. `identity` 类型插件不允许 `declarative`（它需要真正的协议交互）。

### 1.4 插件清单（manifest）规范

```yaml
apiVersion: gate.plugin/v1          # 契约版本，宿主据此判断兼容性
kind: channel                       # channel | enricher | action | identity
id: github                          # 全局唯一；同时作为 fact 的默认命名空间
name: GitHub 账户
version: 1.4.0
description: 采集 GitHub 账号年龄、仓库数、总 star、组织等公开指标
author: official
license: MIT
homepage: https://github.com/your-org/gate-plugin-github

runtime: declarative                # declarative | process | container | in-process
entry: ./plugin.mjs                 # runtime != declarative 时必需
digest: sha256:9f2c...              # 包内容摘要（完整性）
signature: MEUCIQ...                # 可选：发布者签名（可信度）

engines:
  gate: ">=1.0.0 <2.0.0"            # 宿主版本区间，不满足则拒绝安装

# ── 能力声明 ───────────────────────────────────────────────
capabilities:
  binding: oauth2                   # none | oauth2 | manual | webhook | scheduled
  refresh: true                     # 支持定期重新采集
  revoke: true                      # 支持解绑
  quickCheck: false                 # 支持轻量预判（不做完整采集）

# ── 权限申请（安装时逐项授予，运行期强制校验）─────────────────
permissions:
  - "secrets:read:github.client_secret"
  - "secrets:read:github.token"
  - "http:egress:api.github.com"
  - "cache:write:self"
  - "storage:write:self"
  - "user:view:basic"               # 只能看 id/username/email(脱敏)

# ── 配置 schema（JSON Schema，宿主据此自动生成后台表单）────────
configSchema:
  type: object
  properties:
    totalStarsMode:
      type: string
      enum: [top100, exact]
      default: top100
      title: 总 star 统计口径
      description: top100 只统计最热门的 100 个仓库（1 次 API 调用）；exact 精确遍历（更慢更耗配额）
    cacheTtl: { type: string, default: "24h", title: 事实有效期 }
  required: [totalStarsMode]

# ── 事实 schema（策略编辑器据此做路径补全与静态校验）───────────
factSchema:
  type: object
  properties:
    created_at:        { type: string, format: date-time }
    account_age_days:  { type: integer, title: 账号年龄（天） }
    public_repos:      { type: integer }
    followers:         { type: integer }
    total_stars:       { type: integer, title: 总 star 数 }
    organizations:     { type: array, items: { type: string } }
    has_verified_email:{ type: boolean }

# ── 声明式采集（runtime: declarative 时使用）──────────────────
collect:
  request:
    method: POST
    url: https://api.github.com/graphql
    headers:
      Authorization: "Bearer {{ secrets.github.token }}"
      Accept: application/json
    body:
      query: |
        query($login: String!) {
          user(login: $login) {
            createdAt followers { totalCount } publicRepos
            repositories(ownerAffiliations: OWNER, isFork: false, first: 100,
                         orderBy: {field: STARGAZERS, direction: DESC}) {
              nodes { stargazerCount }
            }
          }
        }
      variables: { login: "{{ binding.externalName }}" }
  extract:
    - { path: "$.data.user.createdAt",                  as: created_at }
    - { path: "$.data.user.followers.totalCount",       as: followers }
    - { path: "$.data.user.publicRepos",                as: public_repos }
    - { path: "$.data.user.repositories.nodes[*].stargazerCount", as: total_stars, transform: sum }
  derive:
    - { as: account_age_days, expr: "days_between(created_at, now())" }
```

**关键点**：`id` 即**事实命名空间**。策略里写 `fact.github.total_stars`，其中 `github` 是插件声明的 id，**宿主只是按名字寻址，不理解其含义**。装一个 `gitlab` 插件，就自动多出 `fact.gitlab.*` 可用。

### 1.5 宿主 API（插件能调用的一切）

插件**不能**直接 `import` 主程序内部模块，只能通过注入的 `ctx.host`：

```ts
interface PluginHost {
  // 日志（自动带 pluginId / trace_id）
  log(level: 'debug'|'info'|'warn'|'error', msg: string, meta?: object): void;

  // 自己的配置（只读，已合并默认值）
  config: { get<T>(): T };

  // 密钥（仅 permissions 中声明过的 key 可读；declarative 形态下仅模板占位符）
  secrets: { get(name: string): Promise<string> };

  // 出站 HTTP（仅 permissions 白名单域名；宿主统一限流、超时、重试、脱敏日志）
  http: { request(req: HttpRequest): Promise<HttpResponse> };

  // 插件私有 KV（命名空间隔离 + 配额）
  storage: { get(k): Promise<unknown>; set(k, v, ttl?): Promise<void>; del(k): Promise<void> };

  // 缓存（跨用户共享，带 TTL）
  cache: { get<T>(k: string): Promise<T|null>; set(k, v, ttl): Promise<void> };

  // 事实输出（宿主做 schema 校验后才落库）
  facts: { emit(facts: Record<string, unknown>): Promise<void> };

  // 受限用户视图（无敏感字段）
  user: { view(): Promise<{ id: string; username: string; emailMasked: string; tags: string[] }> };

  // LLM 能力（仅 enricher；走宿主预算/缓存/限流，插件无法绕过）
  llm: { invoke<T>(p: { prompt: string; schema: ZodType<T>; model?: string }): Promise<{ data: T; tokens: number }> };

  // 指标
  metrics: { counter(n: string, labels?: object): void; gauge(n: string, v: number): void };

  // ── 对外服务能力（★ 跨项目协同的关键）────────────────────
  // 宿主接收外部 HTTP 请求，完成鉴权/限流/审计后，再转发给插件处理。
  // 插件不能自己监听端口；能注册哪些路径由 manifest.endpoints 决定。
  routes: { handle(req: PluginRequest): Promise<PluginResponse> };

  // 事件订阅（manifest.subscribes 声明后生效）
  events: { on(type: string, handler: (payload: unknown) => Promise<void>): void };

  // 平台级协同验证断言（受 'verify:assert' 权限保护）
  verify: { assert(q: AssertQuery): Promise<AssertionResult> };
}
```

**三条硬规则**：

1. **密钥不落插件**：`secrets.get()` 返回的是一次性使用凭据；`declarative` 形态下插件**根本拿不到密钥**，只有宿主在发请求时注入。
2. **网络必须代理**：所有出站请求经宿主，域名白名单之外的请求直接拒绝（防 SSRF / 防外传数据）。
3. **LLM 必须走宿主**：`llm.invoke` 统一计费、缓存、限流、日预算。插件自建 LLM 客户端会被网络白名单拦住。
4. **入口也必须经宿主**：插件**不能自己监听端口**；对外暴露的每个路径都必须在 `manifest.endpoints` 中声明，由宿主挂载、鉴权、限流、审计（详见 §2.13）。

### 1.6 插件生命周期

```
  ┌──────────┐  上传/URL/目录
  │  none    │──────────────────▶┌───────────┐
  └──────────┘                   │ installed │  校验 manifest / digest / signature / engines
                                 └─────┬─────┘
                                       │ 静态校验通过（schema、权限清单可解析）
                                       ▼
                                 ┌───────────┐
                                 │ validated │  等待管理员配置与授权
                                 └─────┬─────┘
                         配置完成 + 权限逐项授予
                                       ▼
                                 ┌───────────┐  注册 fact 命名空间、绑定、调度
                                 │  enabled  │◀──────────┐
                                 └─────┬─────┘           │ enable
                                       │ disable         │
                                       ▼                 │
                                 ┌───────────┐───────────┘
                                 │ disabled  │  保留数据与配置
                                 └─────┬─────┘
                                       │ uninstall（需确认，提示影响面）
                                       ▼
                                 ┌───────────┐
                                 │  removed  │
                                 └───────────┘
```

**卸载前的依赖检查**（关键，避免策略静默失效）：

```http
GET /admin/plugins/:id/dependents
→ { "policies": ["contributor-tier2", "edu-basic"], "bindings": 12847, "facts": 12847 }
```

存在依赖时**拒绝卸载**，必须先把相关策略里的 `channel: <id>` 改掉或禁用策略。

### 1.7 声明式插件（覆盖 80% 场景）

绝大多数渠道本质是"**调一个 HTTP 接口，把响应字段映射成事实**"。这不需要写代码。

声明式插件支持的能力：

| 能力 | 配置项 |
|---|---|
| 请求方法/URL/头/体 | `collect.request.*` |
| 模板变量 | `{{ secrets.* }}` `{{ binding.* }}` `{{ config.* }}` `{{ user.* }}` |
| 响应提取 | `extract[].path`（JSONPath）、`as`、`transform`（sum/avg/count/first/last/min/max/join/len） |
| 派生字段 | `derive[].expr`（受限表达式：日期差、四则、条件） |
| 分页 | `collect.pagination`（cursor/offset/page，带最大页数保护） |
| 多步请求 | `collect.steps[]`（上一步结果可被下一步引用，如"先换 token 再查数据"） |
| 绑定流程 | `binding.oauth2` 声明授权/令牌端点，宿主负责 OAuth 交互 |
| 错误映射 | `collect.errors[]`（把上游错误码映射成"未绑定/无权限/配额耗尽"） |

**安全**：模板与表达式由宿主的**受限解释器**执行，不涉及 `eval`；JSONPath 只读，不产生副作用。

### 1.8 进程插件协议（runtime: process）

子进程通过 **stdio 上的 JSON-RPC 2.0** 与宿主通信（比 HTTP 更简单，无需端口管理）：

```jsonc
// 宿主 → 插件：初始化
{ "jsonrpc": "2.0", "id": 1, "method": "plugin.init",
  "params": { "pluginId": "gitlab", "apiVersion": "gate.plugin/v1", "config": {...} } }

// 宿主 → 插件：采集
{ "jsonrpc": "2.0", "id": 2, "method": "channel.collect",
  "params": { "userId": "0192...", "binding": { "externalName": "alice" }, "deadlineMs": 15000 } }

// 插件 → 宿主：请求能力（宿主校验权限后执行）
{ "jsonrpc": "2.0", "id": 101, "method": "host.http.request",
  "params": { "method": "GET", "url": "https://gitlab.com/api/v4/users/alice" } }

// 插件 → 宿主：返回事实
{ "jsonrpc": "2.0", "id": 2, "result": { "facts": { "account_age_days": 1200 } } }
```

**进程管理**：宿主负责启动、健康检查、崩溃重启（指数退避）、空闲回收、超时杀进程、资源限额（内存/CPU/文件描述符）。
**沙箱加固**（可选，Docker 部署时）：只读文件系统、无网络（除宿主代理）、非 root、seccomp。

### 1.9 内置插件：GitHub 只是一个普通插件

这是本节最重要的修正。**主程序里不存在 `github` 这个词**：

```
plugins/
├── builtin/                      # 随主程序发布，但走【同一套】插件接口
│   ├── github/                   # ← 和第三方插件完全同构
│   │   ├── manifest.yaml
│   │   └── plugin.mjs            # 或纯 declarative，无代码
│   ├── email-domain/
│   ├── invite-code/
│   ├── llm-review/               # enricher
│   ├── newapi-set-group/         # action
│   └── oidc-provider/            # identity
└── installed/                    # 运行期安装的第三方插件
```

**内置插件与第三方插件的唯一区别**：

| 维度 | 内置 | 第三方 |
|---|---|---|
| 分发 | 随主程序包 | 上传 / URL / 目录 |
| 信任 | 默认可信 | 需签名或管理员确认 |
| runtime | 可用 `in-process` | 默认 `process` |
| 可否卸载 | 可禁用，不建议卸载 | 可卸载 |

**测试验收**：把 `plugins/builtin/` 整个目录删掉，主程序**仍能正常启动**（只是没有任何渠道可用）。这是"宿主无知"的硬性验收标准。

### 1.10 LLM 能力是平台能力，不是插件

原始需求里的"接入大模型 LLM 进行判断"被设计为：

- **宿主提供** `llm.invoke()` 平台能力（预算、缓存、限流、成本统计、多模型路由都在宿主）；
- **`llm-review` 是一个 enricher 插件**，它声明"输入哪些 fact 路径、输出什么 fact"：

```yaml
# plugins/builtin/llm-review/manifest.yaml
apiVersion: gate.plugin/v1
kind: enricher
id: llm-review
runtime: declarative
permissions: ["llm:invoke", "cache:write:self"]

consumes:                            # 声明消费的 fact 路径
  - "github.pr_list"                 # ← 注意：它不认识 GitHub，只是消费一个数组字段
  - "gitlab.mr_list"

produces:
  namespace: llm
  factSchema:
    type: object
    properties:
      pr_score:            { type: number, minimum: 0, maximum: 100 }
      pr_count_effective:  { type: integer }
      reason:              { type: string }

config:
  promptVersion: v3
  batchSize: 5
  maxItems: 30
  rubric:                            # 评分细则可配置
    substantiality: 0.40
    influence: 0.25
    complexity: 0.20
    collaboration: 0.15
  model: gpt-4o-mini
  budget: { dailyTokens: 2000000 }
```

**收益**：同一个 `llm-review` 插件既能评 GitHub PR，也能评 GitLab MR、也能评"某社区的发帖质量"——只要上游 channel 插件产出对应的数组字段。**LLM 评审从"GitHub 专属功能"变成"通用能力"**。

### 1.11 安全模型汇总

| 威胁 | 对策 |
|---|---|
| 插件读取 PAT / 私钥 | `in-process` 之外拿不到；`declarative` 完全拿不到；密钥访问逐项授权并审计 |
| 插件外传数据 | 出站必须经宿主，域名白名单；请求/响应日志脱敏 |
| 插件绕过 LLM 预算 | 网络白名单挡住自建客户端；只能用 `llm.invoke` |
| 插件 SSRF | 宿主解析目标 IP，拒绝内网/环回/元数据地址 |
| 插件耗尽资源 | 进程级 CPU/内存/FD 限额；调用超时；并发上限 |
| 恶意插件包 | digest 校验 + 可选签名验证 + 权限清单人工审查 |
| 插件崩溃拖垮宿主 | `process` 形态天然隔离；`in-process` 调用包 try/catch + 熔断 |
| 插件静默失效导致策略误判 | 卸载前依赖检查；事实过期后策略按 `onMissingFact` 处理（默认 `fail_closed`） |
| **插件端点被滥用**（新增） | 每个端点必须声明 + 管理员逐条批准；五种鉴权；按 IP/token/插件三维限流；body 大小与超时限制；可单独禁用某个端点 |
| **插件端点越界 / 覆盖宿主路由**（新增） | 强制 `/api/plugins/<pluginId>/` 前缀；保留路径黑名单；`method+path` 冲突检测；拒绝 `..` 与编码穿越 |
| **重放攻击**（新增） | HMAC 带时间戳（容差 ±5 min）+ nonce 窗口去重 |
| **插件伪造调用者身份**（新增） | 鉴权在**插件之前**由宿主完成；插件只能拿到已认证的调用者上下文，无法自行判断"谁在调我" |
| **协同断言被伪造**（新增） | 平台对每条断言用 ES256 签名并附 `issuer`/`expiresAt`；调用方用平台 JWKS 独立验签 |
| **跨项目凭据泄露**（新增） | client secret 只存哈希、仅注册时返回一次；支持多枚 `pluginToken` 与逐枚吊销；断言短时效（默认 5 min） |

### 1.12 版本、签名与分发

| 项 | 规则 |
|---|---|
| 契约版本 | `apiVersion: gate.plugin/v1`；宿主支持多版本并存，新版本破坏性变更才升 `v2` |
| 兼容性检查 | 安装时校验 `engines.gate` 与宿主版本；不满足直接拒绝并给出明确提示 |
| 插件版本 | 语义化版本；同一 `id` 可并存多版本，但只有一个 `enabled` |
| 升级 | 支持滚动升级：新版本先 `validated`，切换后旧版本转 `retired`，保留 N 天可回滚 |
| 摘要 | `digest` 必填，安装时校验；不一致拒绝 |
| 签名 | 可选；配置了信任公钥时，签名无效则拒绝 |
| 分发 | ① 上传 `.gatespkg`（tar.gz）② 从 URL 安装 ③ 从本地目录安装（开发） |
| 回滚 | 保留上一版本包，一键回滚 |

#### 1.12.1 信任分级：签名要求按来源分级

**本地上传的插件可以跳过签名，但必须显式确认信任并留审计。**

| 来源 | 签名要求 | 附加要求 | 允许的形态 |
|---|---|---|---|
| `builtin`（随主程序发布） | — | 无 | 全部（含 `in-process`） |
| **本地上传 / 本地目录** | **可跳过** | **管理端显式勾选「我信任此插件的代码」** + 写审计（谁、何时、哪个版本） | `process` / `container` / `declarative`；`in-process` 与 `remote-module`（前端代码）**仍需签名或第二次确认** |
| `url`（远程安装） | **必须** | 签名无效直接拒绝 | 按签名等级 |

**两次独立确认**（对应两类可执行代码，互不替代）：

```
安装向导 · 步骤 ② 权限审查 之后新增：
┌──────────────────────────────────────────────────────────────────┐
│  代码信任确认                                                     │
│                                                                  │
│  ⚠ 该插件包未签名。启用后：                                        │
│                                                                  │
│  ☑ 我信任此插件的【后端代码】（将以独立进程运行）                    │
│      确认人：admin@example.com    时间：2026-09-21 10:12           │
│                                                                  │
│  ☐ 我信任此插件的【前端代码】（将加载到平台页面里运行）              │
│      ⓘ 前端代码与平台页面同源，风险高于后端进程隔离                  │
│                                                                  │
│  以上两项确认都会写入审计日志，可随时在插件详情中撤销。              │
└──────────────────────────────────────────────────────────────────┘
```

| 确认项 | 保护的是什么 | 未勾选时 |
|---|---|---|
| 后端代码信任 | 插件进程能读到的**自己那部分密钥** | 插件仍可装但 `enable` 被拒 |
| **前端代码信任** | 插件 bundle 与平台页面**同源执行** | UI 贡献中 `renderMode=remote-module` 的部分不加载（`declarative` 不受影响） |

**撤销**：插件详情页可随时撤销任一确认项 → 立即禁用对应能力（后端进程停止 / 前端 bundle 不再加载），并写审计。

> **为什么分开确认**：`process` 后端有 OS 进程隔离兜底；而 `remote-module` 前端 bundle 跑在平台页面里，**能读 DOM、能发请求、能碰 localStorage**——它的风险等级不同，不该共用一次勾选。

### 1.13 插件端点（Plugin Endpoints）—— 让插件能对外提供服务

> 前面所有能力都是"**宿主调用插件**"（拉取事实）。但跨项目协同要求反过来：**外部系统要能调用平台**。
> 典型场景：AI bot 框架（Discord / Telegram / QQ / Slack / Koishi / NoneBot / Minecraft 服务端插件）需要回调平台，完成"用户在社区的身份 ↔ 平台账号"的协同验证。

#### 1.13.1 挂载规则

```
https://gate.example.com/api/plugins/<pluginId>/<path>
                            └──────┬──────┘
                        宿主强制前缀，插件无法越界到别人的命名空间
```

**保留路径**：`/api/plugins/_*`（宿主专用，如 `_endpoints` / `_health`）；路径中的 `..`、编码穿越、以及注册到宿主已有路由上的尝试一律拒绝。

#### 1.13.2 manifest 声明

```yaml
endpoints:
  - path: /verify/start
    method: POST
    auth: none                     # none | hmac | pluginToken | session | admin
    visibility: public
    description: 生成一次性验证码（供 bot 框架匿名调用）
    rateLimit: { perMinute: 60, perIp: true }
    requestSchema:  { type: object, properties: { discordId: { type: string } }, required: [discordId] }
    responseSchema: { type: object, properties: { userCode: { type: string } } }

  - path: /verify/poll
    method: GET
    auth: pluginToken              # 宿主签发的服务令牌
    rateLimit: { perMinute: 600 }

  - path: /webhook/community
    method: POST
    auth: hmac
    hmac:
      header: X-Signature-256
      algo: sha256
      secretRef: community.webhook_secret    # 密钥托管在宿主，插件拿不到
    maxBodyBytes: 262144
    timeoutMs: 10000
```

#### 1.13.3 五种鉴权

| auth | 机制 | 适用 |
|---|---|---|
| `none` | 完全公开 | 一次性验证码生成（**本身就是设计给匿名 bot 调的**）；需管理员显式批准，UI 上红色警示 |
| `hmac` | HMAC-SHA256 + 时间戳 + nonce 防重放；**密钥托管在宿主** | webhook 接收、服务间调用 |
| `pluginToken` | 宿主为插件签发的服务令牌（`gtp_...`），可多枚、可吊销、可限 scope | bot 框架长期调用 |
| `session` | 需要平台用户会话（浏览器） | 用户交互页面 |
| `admin` | 需要管理员 | 运维接口 |

#### 1.13.4 运行形态支持矩阵（重要约束）

| runtime | 能否注册端点 | 原因 |
|---|---|---|
| `declarative` | ⚠️ **仅 `kind: webhook`** | 无代码，宿主只能按声明执行"接收 → 校验 → 提取 → 写事实 / 触发评估" |
| `process` | ✅ 任意端点 | 宿主经 JSON-RPC 转发 |
| `container` | ✅ 任意端点 | 同上 |
| `in-process` | ✅ 任意端点 | 直接调用 |

**declarative 的 webhook 端点**（零代码覆盖大量场景）：

```yaml
endpoints:
  - path: /webhook/community
    method: POST
    auth: hmac
    hmac: { header: X-Signature-256, algo: sha256, secretRef: community.webhook_secret }
    kind: webhook                  # ← declarative 只支持这一种
    onReceive:
      subject:
        by: body.user.email        # 如何定位平台用户
        fallback: reject
      facts:
        namespace: community
        extract:
          - { path: "$.data.level",     as: level }
          - { path: "$.data.joined_at", as: joined_at }
      then: [emitFacts, triggerEvaluation]
```

#### 1.13.5 宿主的六项职责（插件只写 handler）

| 职责 | 说明 |
|---|---|
| **路由挂载** | 强制前缀 + 保留路径黑名单 + **冲突检测**（两个插件不得注册同一 `method+path`） |
| **鉴权** | 按声明校验；HMAC 密钥在宿主，插件拿不到 |
| **限流** | 按 IP / token / 插件三维度令牌桶 |
| **请求校验** | body 大小、schema 校验、超时、并发上限 |
| **审计** | 每个请求写 `ag_plugin_invocations`（`op='endpoint'`），含来源 IP、token 指纹、状态码、耗时 |
| **文档与发现** | 聚合所有启用端点生成 OpenAPI；`GET /api/plugins/_endpoints` 列出全部可用端点供对接方发现 |

#### 1.13.6 权限与隔离

- 权限字符串：`route:register:/verify/*`；安装时**逐条展示"该插件将对外暴露以下端点"**，管理员逐条批准。
- 插件之间路径隔离；`process` 插件端点崩溃不影响宿主与其他插件。
- 端点可随时在管理端**单独禁用**（不必禁用整个插件）。

### 1.14 跨项目协同验证（Cross-Project Verification）

这是 §2.13 的主要用途，**分两层设计**。

#### 1.14.1 第一层：平台内置的标准协同协议（core，不依赖任何插件）

任何外部项目（bot 框架、其他社区、内部系统）都能对接。

**① 调用方注册**

```http
POST /admin/verify/clients
{
  "name": "Discord Bot (社区A)",
  "scopes": ["assert:read", "challenge:create", "event:subscribe"],
  "callbackUrl": "https://bot.example.com/gate/events",
  "allowedSubjects": ["platform_user_id", "email", "discord_id"]
}
→ {
    "clientId": "vc_7f3a...",
    "secret": "gts_...",          // 仅返回一次；平台只存哈希
    "hmacAlgo": "sha256"
  }
```

**② 请求签名**（所有调用统一）

```http
X-Gate-Client:    vc_7f3a...
X-Gate-Timestamp: 1758412800
X-Gate-Nonce:     8f2c...
X-Gate-Signature: sha256=<HMAC(secret, method + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + bodyHash)>
```

时间戳容差 ±5 分钟；nonce 在窗口内去重（防重放）。

**③ 资格断言（核心端点）**

```http
POST /api/verify/v1/assert
{
  "subject": { "type": "platform_user_id", "value": "0192a1b2-..." },
  "claims":  ["eligible", "tier", "tags", "policies"]
}

→ {
    "matched": true,
    "subject": { "type": "platform_user_id", "value": "0192a1b2-...", "displayName": "alice" },
    "assertions": {
      "eligible": true,
      "tier": 2,
      "tags": ["verified:contributor"],
      "policies": [{ "code": "contributor-tier2", "state": "granted" }]
    },
    "issuedAt":  "2026-09-21T00:00:00Z",
    "expiresAt": "2026-09-21T00:05:00Z",
    "issuer":    "https://gate.example.com",
    "signature": "<平台对断言签名的 JWS（ES256）>"
  }
```

> **`signature` 是协同验证的信任基石**：项目 B 拿到断言后可用平台 JWKS 独立验签，确认"该资格断言确由平台签发且未被篡改"。这与 05 文档 §8 的 EC 密钥体系**复用同一套 JWKS**。

**④ 设备码流**（用户在 bot 侧发起验证的标准解法，对齐 RFC 8628）

```
① Bot:  POST /api/verify/v1/challenge
         { "subject": { "type": "discord_id", "value": "1234567" }, "scopes": ["assert:read"] }
   →     { "challengeId": "ch_...", "userCode": "ABCD-1234",
           "verifyUrl": "https://gate.example.com/verify",
           "expiresIn": 600, "interval": 3 }

② Bot 提示用户："请在 https://gate.example.com/verify 输入 ABCD-1234"

③ 用户打开链接 → 平台要求登录 → 展示
   "Discord Bot (社区A) 请求验证你的身份，将获得：eligible / tier / tags"
   → 用户确认 → 平台建立【临时关联】（discord_id ↔ 平台账号）

④ Bot:  GET /api/verify/v1/challenge/ch_...
   → 等待中 { "status": "pending" }
   → 已完成 { "status": "approved", "assertion": { …同 ③… } }
   → 已拒绝 { "status": "denied" }
   → 已过期 { "status": "expired" }
```

**⑤ 主动推送（可选）**

```http
POST https://bot.example.com/gate/events
X-Gate-Signature: sha256=<HMAC>
{
  "event": "policy.granted",
  "subject": { "type": "platform_user_id", "value": "0192a1b2-..." },
  "assertions": { "eligible": true, "tier": 2 },
  "at": "2026-09-21T00:00:00Z"
}
```

**⑥ 撤销与复核**

- `POST /api/verify/v1/revoke`：平台主动撤销某 subject 的临时关联；
- 断言 `expiresAt` 默认仅 5 分钟 → **调用方应缓存 + 订阅事件**，而不是每次实时查；
- 所有断言签发与撤销写 `ag_verify_assertions`，可审计、可追溯。

#### 1.14.2 第二层：插件提供的生态适配（各 bot 框架）

平台提供标准协议，**具体框架的对接由插件完成**。内置参考实现 `bot-bridge`：

```yaml
# plugins/builtin/bot-bridge/manifest.yaml
apiVersion: gate.plugin/v1
kind: channel
id: bot-bridge
runtime: process
permissions:
  - "route:register:/verify/*"
  - "route:register:/bind/*"
  - "verify:assert"
  - "storage:write:self"
  - "events:subscribe:policy.granted,policy.revoked"

endpoints:
  - { path: /verify/start,  method: POST, auth: none,        visibility: public }
  - { path: /verify/poll,   method: GET,  auth: pluginToken }
  - { path: /bind/complete, method: POST, auth: hmac }

subscribes: [policy.granted, policy.revoked, checkin:granted]
```

**各大框架的接入形态**：

| 框架 / 场景 | 接入方式 | 是否需要平台侧插件 |
|---|---|---|
| **NoneBot2 / Koishi / BotPy** | 官方插件调用 `/api/verify/v1/*` | ❌ 不需要（直接用标准协议） |
| **Discord / Slack / Telegram Bot** | 同上 + 斜杠命令注册 | ❌ 不需要 |
| **Minecraft 服务端插件**（Paper/Velocity） | 调 `/api/verify/v1/assert`，用于"仅认证用户可进服" | ❌ 不需要 |
| **需要平台侧 webhook 接收** | 装一个 `declarative` webhook 插件即可（零代码） | ✅ 装插件 |
| **需要复杂交互（多步、状态机）** | 装 `process` 形态插件 | ✅ 装插件 |

> **设计要点**：**协议属于 core，适配属于插件**。平台不去实现每一个 bot 框架，而是提供稳定协议 + 参考实现 + 官方薄 SDK（TS / Python 各一）。

#### 1.14.3 与"验证渠道"构成四向闭环

协同验证本质是**双向**的，四向齐备才算完整：

| 方向 | 机制 | 例子 |
|---|---|---|
| **平台 → 外部**（拉） | `channel` 插件调外部 API | 拉取 GitHub star 数 |
| **外部 → 平台**（调） | `endpoints` + 标准协同协议 | bot 调平台验证用户资格 |
| **外部 → 平台**（推） | `hmac` webhook 端点 | 社区推送"该用户升级了"作为事实 |
| **平台 → 外部**（推） | `subscribes` + `callbackUrl` | 平台通知 bot"用户已升级" |

### 1.15 事件订阅（Event Subscription）

manifest 声明 `subscribes: [policy.granted, ...]`，宿主在事件发生时按序调用已订阅插件的 handler。

| 项 | 规则 |
|---|---|
| 事件类型 | 见 06 文档 §7 的事件清单 |
| 投递语义 | **至少一次**；插件需幂等（事件携带 `eventId`） |
| 失败处理 | 重试 3 次（指数退避）后进死信队列，并记 `ag_plugin_invocations` |
| 顺序 | 同一 subject 的事件保序；不同 subject 可并行 |
| 隔离 | 插件 handler 超时 / 异常不影响其他插件与主流程 |
| 权限 | `events:subscribe:<type>` 逐项授予 |

### 1.16 provider 插件：主体目录（★ 让引擎与具体系统彻底解耦）

> **为什么下游系统也必须是插件**：若把 new-api 当作核心假设（核心有 `ag_newapi_users` 镜像表、`sync-newapi` 同步器、`sdk-newapi` 包，表达式里隐含 `users.group`），本项目就只是"new-api 的附属工具"，无法服务其他系统。
> 因此把**下游系统**也抽象成插件：核心只认识 **Subject（主体）**，不认识 new-api、Discord 或任何具体系统。

#### 1.16.1 定位转变

```
修正前： new-api 权限升级网关（new-api 是核心假设）
修正后： 通用信任引擎（Trust Engine）
          —— 用插件采集信任证据，用表达式判定信任等级，
             用动作插件把信任等级投射到任意下游系统
          new-api 只是【第一个官方接入】，不是架构前提
```

#### 1.16.2 provider 插件接口

```ts
export interface ProviderPlugin {
  /** 列出主体（供通用对账器分页拉取） */
  listSubjects(cursor: string | null, limit: number)
    : Promise<{ subjects: ExternalSubject[]; nextCursor: string | null }>;

  /** 按下游系统主键取主体 */
  getSubject(externalId: string): Promise<ExternalSubject | null>;

  /** 按身份键查主体（如 oidc_id / email）—— 用于身份对齐的快路径 */
  findSubject?(by: { key: string; value: string }): Promise<ExternalSubject | null>;

  /** 主体属性 schema：供表达式路径补全与静态校验 */
  readonly subjectSchema: ZodType;

  /** 能力探测：决定对账走快路径还是慢路径 */
  readonly capabilities: {
    list: boolean;
    findByIdentity: boolean;
    update: boolean;
    create: boolean;
  };
}

/** 通用主体模型 —— 一切下游系统的统一投影 */
export interface ExternalSubject {
  /** 下游系统的主键（new-api 的 users.id / Discord 的 user id / K8s 的 subject name） */
  externalId: string;
  displayName?: string;
  email?: string;
  /** 属性袋：new-api 的 group/quota/used_quota/... 全部放这里，核心不解释其含义 */
  attributes: Record<string, unknown>;
  /** 原始对象（脱敏后），仅用于排障展示 */
  raw?: unknown;
}
```

#### 1.16.3 核心因此变得系统无关

| 关注点 | 修正前 | 修正后 |
|---|---|---|
| 主体存储 | `ag_newapi_users`（new-api 专用列） | **`ag_external_subjects`**（provider + externalId + attributes 属性袋） |
| 对账 | `sync-newapi` 核心模块 | **`core/sync` 通用对账器** + provider 的 `listSubjects` |
| 主体属性引用 | `users.group` 隐含在文档各处 | 表达式里统一写 **`subject.group`**（由策略绑定的 provider 解析） |
| 改分组 | `newapi-set-group:set_group` 内建动作 | **action 插件** `newapi-set-group:set_group` |
| 读用户 | `sdk-newapi` 核心包 | provider 插件内部实现，核心只调接口 |
| 身份对齐键 | `users.oidc_id` | **provider 声明的 identity keys**（`capabilities.findByIdentity` + `findSubject`） |

**硬性验收标准**：核心代码 grep `newapi` / `new-api` → **0 命中**（只允许出现在插件包、文档、测试夹具中）。

#### 1.16.4 策略如何绑定 provider

```yaml
apiVersion: gate/v1
metadata:
  code: contributor-tier2
spec:
  provider: newapi                    # ← 本策略作用于哪个主体目录
  match:
    all:
      - eq: { subject.status: 1 }     # subject.* 指向该 provider 的属性
  requirements:
    branches:
      - id: qq_high
        when: { gt: { fact.qq.level: 40 } }
        outcome: satisfied
        actions:
          - { action: "newapi-set-group:set_group", params: { group: "vip3" } }
```

| 引用形式 | 含义 |
|---|---|
| `subject.<attr>` | 策略绑定的 provider 的主体属性（`subject.group`、`subject.quota`） |
| `subject.<providerId>.<attr>` | 显式指定某 provider（跨系统策略，如"new-api 分组 与 Discord 角色"联合判定） |
| `fact.<namespace>.<path>` | 插件采集的证据（与 provider 无关） |
| `binding.<pluginId>.<field>` | 用户在外部渠道的绑定信息 |

#### 1.16.5 官方接入：new-api 变成一组普通插件

```
plugins/builtin/
├── newapi-provider/          # provider：users 目录 + 属性读写 + 身份键（oidc_id / email）
├── newapi-set-group/         # action：改分组（幂等 + 用户级锁 + 防抖）
├── newapi-add-quota/         # action：加额度
├── newapi-set-status/        # action：禁用 / 启用
├── newapi-oidc-identity/     # identity：模式 1（中间统一 OIDC 对齐）
└── ...
```

**其他下游系统同样只是一个插件**：

| 系统 | provider 插件 | action 插件 |
|---|---|---|
| new-api | `newapi-provider` | `set_group` / `add_quota` / `set_status` |
| Discord | `discord-provider` | `assign_role` / `send_dm` |
| Minecraft | `minecraft-provider` | `whitelist_add` / `grant_permission` |
| Kubernetes | `k8s-provider` | `bind_role` |
| 自建社区 | `declarative` provider（纯 YAML，走 REST） | `declarative` action |

> **这就是"通用信任引擎"的实质**：同一套证据采集 + 表达式判定 + 审计体系，可以同时服务于多个下游系统，而它们之间互不知晓。

#### 1.16.6 多 provider 共存

- 一个主体可同时存在于多个 provider（用户在 new-api 有账号、在 Discord 有身份）；
- `ag_external_subjects` 的键是 `(provider, externalId)`，天然支持多系统；
- `ag_identity_links` 把多个 provider 的主体串到同一个**平台用户**上；
- 策略通过 `provider` 字段声明作用域；跨系统策略可用 `subject.<providerId>.<attr>` 联合判定。

### 1.17 插件 UI 贡献（前端扩展点）

> **为什么 UI 必须是一等能力**：只让插件提供后端能力（采集/判定/动作/端点）是不够的——很多功能**天然是面向用户的界面**，最典型的是 **签到**：平台侧的签到插件必须能给用户一个"签到"入口与页面，否则功能等于不存在。
>
> 因此：**UI 贡献是插件的一等能力**，与 `endpoints` 同级。

#### 1.17.1 三种 UI 形态（与后端 runtime 呼应）

| 形态 | 插件提供 | 宿主做什么 | 安全 | 适用 |
|---|---|---|---|---|
| **`declarative`**（推荐） | JSON 块树 + 数据源声明 | 用内置 shadcn 组件渲染 | ✅ **无代码执行** | 表单 / 列表 / 统计卡 / 日历 / 图表 —— 覆盖 80% |
| **`remote-module`** | ESM bundle URL | `import()` 动态加载 + 错误边界 + Shadow DOM 隔离 | ⚠️ 需签名 + CSP 白名单 | 复杂交互（拖拽、实时协作） |
| **`iframe`** | 页面 URL | 内嵌 iframe + postMessage 桥 | ✅ 完全隔离 | 不受信任的第三方、异构技术栈 |

> **默认必须是 `declarative`**。签到这种页面用声明式完全够用（统计卡 + 按钮 + 日历 + 表格），**零前端代码、零 XSS 风险**。

#### 1.17.2 扩展点类型

| 类型 | 说明 | 示例 |
|---|---|---|
| `nav` | 顶部 ManagementBar 的一个入口 | 「每日签到」 |
| `page` | 独立路由页面 | `/checkin` |
| `slot` | 挂到宿主预置的**具名插槽** | 用户首页顶部的"签到状态卡" |
| `settings` | 管理端的插件配置面板（由 `configSchema` 自动生成） | 签到额度范围 |
| `adminPage` | 管理端独立页面 | 签到记录管理 |

**宿主预置插槽清单**（插件只能挂到这些位置，不能凭空插入布局）：

| slot | 位置 | 典型用途 |
|---|---|---|
| `user.dashboard.top` | 用户首页顶部 | 状态卡片（签到、资格进度） |
| `user.dashboard.sidebar` | 用户首页侧栏 | 快捷入口 |
| `user.profile.tabs` | 个人资料页 Tab | 绑定管理 |
| `admin.overview.cards` | 管理总览卡片区 | 插件健康度 |
| `admin.user.detail.tabs` | 用户详情抽屉 Tab | 该插件的事实 / 绑定面板 |
| `admin.policy.editor.toolbar` | 策略编辑器工具栏 | 插件提供的校验 / 预览工具 |

#### 1.17.3 声明式 UI 的块类型

宿主内置以下块，插件只能**组合**它们：

| 块 | 用途 |
|---|---|
| `stats` | 指标卡片组（数值 + 单位 + 趋势） |
| `action` | 按钮 / 动作（含确认、Toast、成功刷新、禁用条件） |
| `form` | 表单（字段由 JSON Schema 生成，含校验） |
| `table` | 表格（分页 / 排序 / 筛选） |
| `chart` | 图表（折线 / 柱状 / 饼图） |
| `calendar` | 日历热力图（签到场景天然需要） |
| `markdown` | 富文本（经 DOMPurify 净化） |
| `tabs` / `section` | 布局容器（可嵌套） |
| `custom` | 挂载 `remote-module`（显式声明，需签名） |

**数据绑定**：块里的 `source` 声明 `{ method, url }`，宿主**代理请求**（带当前用户会话）并做鉴权校验；模板用 `$.path` 取值，支持 `{placeholder}` 插值。

#### 1.17.4 完整示例：签到插件

new-api 有签到实现，但**没有分组门槛**（`CheckinSetting` 只有 enabled/min/max）。平台侧 `checkin` 插件的职责是：**先查策略资格，再决定是否放行**。

```yaml
# plugins/builtin/checkin/manifest.yaml

  - "route:register:/status"
  - "route:register:/checkin"

  - "ui:contribute:nav,page,slot"
  - "action:invoke:newapi-add-quota:add_quota"     # ★ 插件间调用，需显式授权
  - "policy:read:self"                   # 读取当前用户的策略状态以判断资格
  - "storage:write:self"

configSchema:
  type: object
  properties:

    quotaMin:       { type: integer, default: 1000 }
    quotaMax:       { type: integer, default: 5000 }

    timezone:       { type: string, default: "Asia/Shanghai" }

# ── 后端端点（已有能力）────────────────────────────────
endpoints:
  - { path: /status,  method: GET,  auth: session }
  - { path: /checkin, method: POST, auth: session }
  - { path: /history, method: GET,  auth: session }

# ── ★ 前端贡献（新增能力）──────────────────────────────
ui:
  nav:
    - id: checkin
      label: "每日签到"
      icon: gift
      path: /checkin

      order: 20
      badge:                                   # 动态徽标
        source: { method: GET, url: "/api/plugins/checkin/status" }

        text: "未签到"

  pages:
    - path: /checkin
      title: 每日签到
      audience: user
      layout: standard
      blocks:
        - type: stats
          columns: 3
          items:
            - { label: "连续签到", value: "$.streak",     unit: "天" }
            - { label: "本月累计", value: "$.monthTotal", unit: "额度" }
            - { label: "今日状态", value: "$.todayText" }
          source: { method: GET, url: "/api/plugins/checkin/status" }

        - type: action
          label: "立即签到"
          variant: primary
          action: { method: POST, url: "/api/plugins/checkin/checkin" }
          disabledWhen: "$.today == true"
          disabledText: "今日已签到"
          onSuccess: { toast: "签到成功，获得 {quotaAwarded} 额度", refresh: true }
          onError:   { toast: "{message}", variant: destructive }

        - type: calendar
          title: 本月签到
```

#### 1.17.5 前端渲染架构

```
平台前端启动
   │
   ├─ GET /api/ui/manifest        ← 宿主聚合所有【已启用】插件的 ui 贡献
   │     按当前用户角色过滤（user / admin）
   │
   ├─ 注册到前端扩展点注册表
   │     nav    → ManagementBar 追加导航项
   │     pages  → 路由表追加 <PluginPage pluginId path />
   │     slots  → <PluginSlot name="user.dashboard.top" /> 渲染
   │
   └─ 渲染时按形态分派
         declarative    → <DeclarativeRenderer blocks={...} />
         remote-module  → <RemoteModuleLoader url={...} />   (签名校验 + Shadow DOM + 错误边界)
         iframe         → <PluginIframe url={...} />
```

**宿主提供的三个渲染器**（平台前端内置，插件无法绕过）：

| 渲染器 | 职责 |
|---|---|
| `DeclarativeRenderer` | 把块树渲染成 shadcn 组件；**不使用 `dangerouslySetInnerHTML`**（markdown 除外，走 DOMPurify） |
| `RemoteModuleLoader` | 动态 `import()`，校验签名与 CSP，挂载到 Shadow DOM，包错误边界与骨架屏 |
| `PluginSlot` | 具名插槽容器；按 `order` 排序；插件异常时**静默跳过并记录**，绝不白屏 |

#### 1.17.6 数据获取与鉴权

插件页面的所有请求都**经宿主代理**，前端只声明 `{ method, url }`：

```
前端 (declarative 块)
   │  source: { method: GET, url: "/api/plugins/checkin/status" }
   ▼
宿主 UI 数据代理
   ├─ 校验：该 url 是否属于【当前页面所属插件】的已批准端点？
   │     ├─ 是 → 放行（自动带上当前用户会话）
   │     └─ 否 → 拒绝（插件不能借 UI 读别的插件的数据）
   ├─ 限流 + 审计
   └─ 返回数据
```

**关键约束**：插件 A 的 UI **只能调插件 A 自己的端点**，以及宿主明确公开的通用接口（如 `/api/me`）。这防止"装一个签到插件，结果它偷偷读你的策略判定明细"。

#### 1.17.7 插件间调用

签到插件需要"发额度"，而发额度是 `newapi-add-quota` action 插件的能力。宿主提供受控的插件间调用：

```ts
// 插件 A 内部（process 形态经 JSON-RPC host.action.invoke）
const r = await ctx.host.actions.invoke('newapi-add-quota:add_quota', {
  subject: { provider: 'newapi', externalId: '1024' },
  value: 3000,
  reason: 'checkin:2026-09-21',
});
```

| 规则 | 说明 |
|---|---|
| 权限 | 必须声明 `action:invoke:<pluginId>:<actionName>`，安装时逐项授予 |
| 幂等 | 被调用方仍走自己的幂等键；调用方提供 `reason` 参与幂等键计算 |
| 审计 | 记一条 `ag_plugin_invocations`（`op='action.invoke'`），含调用方与被调方 |
| 循环 | 宿主检测调用链深度（上限 8），防止插件互相调用成环 |

#### 1.17.8 安全

| 威胁 | 对策 |
|---|---|
| 插件注入恶意 JS | `declarative` **无代码执行**；`remote-module` 需签名 + CSP 白名单 + Shadow DOM；`iframe` 独立 origin |
| 插件借 UI 越权读数据 | 所有请求经宿主代理，**只能访问自己的已批准端点**；宿主公开接口白名单 |
| XSS | 声明式渲染禁用 `dangerouslySetInnerHTML`；markdown 走 DOMPurify；模板插值做 HTML 转义 |
| 样式污染宿主 | `remote-module` 挂 Shadow DOM；`declarative` 只能用宿主组件（无自定义 CSS 注入） |
| 破坏布局 / 白屏 | 插槽有尺寸约束；插件渲染包**错误边界**，异常静默跳过并上报，不影响宿主与其他插件 |
| UI 贡献失控 | 与端点一样**逐条审批**；可单独禁用某个 nav 项 / 页面 / 插槽，不必禁用整个插件 |

#### 1.17.9 与端点审批的对称性

```
安装插件
  ├─ 权限审查（secrets / http / llm / action:invoke …）
  ├─ 端点审查（将对外暴露哪些 HTTP 路径）
  └─ UI 审查（将出现在哪些位置、哪些角色可见）    ← 新增
```

三者都支持**单独禁用**与**变更审计**——插件的能力边界对管理员完全透明。

### 1.18 OIDC 双向联邦与统一身份标识

> 需求原话：**"项目的 OIDC 双向开放是【平台对项目】和【项目对平台】；平台对项目的 OIDC 可以作为登录平台的凭证，反之是作为平台的登录凭证。每个 OIDC 使用唯一标识符，方便表达式获取。"**

#### 1.18.1 双向含义

| 方向 | 谁是谁的 IdP | 凭证用途 | 标识符示例 |
|---|---|---|---|
| **outbound**（平台 → 项目） | 平台是 IdP，项目是 RP | ① 用户用平台账号登录第三方项目；② **该凭证同时可作为登录平台自身的凭证**（同一 issuer → SSO） | `platform:gate` |
| **inbound**（项目 → 平台） | 项目是 IdP，平台是 RP | 用户用**项目账号登录平台**（联邦登录） | `external:proj-a` |

**两个方向都能产出可登录的凭证**，且注册在**同一张注册表**里，各有唯一标识符。

#### 1.18.2 唯一标识符（`ref`）

```
<scope> ":" <slug>

scope := "platform"    # 平台自建（作为 IdP）
       | "external"    # 外部项目（平台信任它）
```

- 表达式里通过 **`identity:oidc@<ref>.<claim>`** 引用（见 04 文档 §1.2.7）；
- `ref` 一经分配**永不变更**，改名不影响已有策略与绑定；
- 绑定键里也用它：`{ kind: oidc, ref: "external:proj-a", claim: sub }`。

#### 1.18.3 平台作为 IdP（outbound）

- 每个下游项目注册为一个 **client**（`clientId` / `secret` / `redirectUris` / `scopes`）；
- 平台签发 ID Token，可携带 `gate_tier` / `gate_tags`（供项目侧做准入，new-api 的 `access_policy` 可直接用）；
- **这些 token 同时被平台自身接受为会话凭证**——用户从任一项目回来无需重新登录（同一 issuer，天然 SSO）。

#### 1.18.4 平台作为 RP（inbound，联邦登录）

- 每个项目 IdP 注册：`issuer` / `well-known` / `clientId` / `secret` / 信任的签名算法；
- 用户可用该项目账号**登录平台**；
- 登录后平台把外部身份写入 `ag_identities`（`provider = "identity:oidc@<ref>"`）；
- 同一用户可绑定**多个** IdP，统一归到一个平台账号下。

#### 1.18.5 claims 的最小暴露

每个 OIDC 注册项必须显式声明 `exposedClaims`，**只有声明过的 claim 才能被表达式读取**：

```yaml
oidcProviders:
  - ref: "external:proj-a"
    direction: inbound
    issuer: "https://sso.proj-a.example.com"
    exposedClaims: ["sub", "email", "email_verified", "proj_a_level", "proj_a_role"]
    # 未声明的 claim（如 phone、address）在表达式里不可见，也不落库
```

#### 1.18.6 三条 SSO 链路

```
① 平台登录 → 项目      标准 OIDC RP 流程（平台为 IdP）
② 项目登录 → 平台      inbound 联邦（项目为 IdP）
③ 项目A → 平台 → 项目B  平台作为身份中枢：A 的账号在平台完成对齐后，
                        由平台向 B 签发凭证（跨项目协同的安全基础）
```

> 链路 ③ 正是 §2.14 跨项目协同验证的身份侧支撑：**先统一身份，再断言资格**。

### 1.19 插件配置作用域、实例模式与存储形态

#### 1.19.1 两个正交维度（由插件自己声明）

> **为什么实例维度由插件声明**：若平台强制"站点内插件配置一律唯一"，就支持不了"一个站点接多个 webhook"这类场景；但若一律要求多实例，凭据型插件（GitHub、LLM）又会被迫为每个站点重复配置。**这是插件的选择，不是平台强制**——故由 manifest 声明。

| 维度 | 取值 | 含义 |
|---|---|---|
| **配置作用域** `config.scope` | `developer`（★ 推荐默认） | 一个开发者一份配置，其名下**所有站点共享** |
| | `site` | 每个站点一份**独立**配置 |
| **实例模式** `instances.mode` | `singleton`（默认） | 该作用域内只有一个实例 |
| | `multi` | 该作用域内可配置多个实例 |

**四象限**：

| | `singleton` | `multi` |
|---|---|---|
| **`developer`** | 一个开发者一份配置 —— **所有站点共享**（GitHub App 凭据、LLM Key、SMTP） | 一个开发者多份（多个 LLM 供应商，站点按需选用） |
| **`site`** | 每个站点一份（newapi-provider 指向的 new-api 地址） | 每个站点多份（多个 webhook 接收器、多个 bot 适配器） |

#### 1.19.2 manifest 声明

```yaml
# ① GitHub 渠道 —— 凭据是开发者级的，一个开发者一份，所有站点共享
id: github
config:
  scope: developer
  instances: { mode: singleton }

# ② newapi-provider —— 每个站点指向不同的 new-api
id: newapi-provider
config:
  scope: site
  instances: { mode: singleton }

# ③ webhook 接收器 —— 一个站点可接多个外部系统
id: webhook
config:
  scope: site
  instances: { mode: multi }
  instanceKeySchema: { type: string, pattern: "^[a-z0-9-]{1,32}$" }

# ④ LLM 供应商 —— 一个开发者可配多个，站点按需选用
id: llm-provider
config:
  scope: developer
  instances: { mode: multi }
```

**默认值**：`scope: developer` + `mode: singleton`（最省事的组合，适合大多数凭据型插件）。

#### 1.19.2.1 作用域约束（按 kind，静态校验）

| kind | 允许的 config.scope | 理由 |
|---|---|---|
| **`provider`** | **仅 `site`** | 主体（`ag_external_subjects`）是**站点级**的；一份跨站点配置会造成隔离语义混乱 |
| `channel` / `enricher` | `developer`（推荐）/ `site` | **配置可共享，产出的事实按站点隔离** |
| `action` | `site`（推荐）/ `developer` | 动作作用于站点内的主体 |
| `identity` | 平台级 | 身份源本就是平台级的 |
| `feature` | `site` | 功能面向站点内的用户 |

**静态校验**：`kind: provider` 且 `scope: developer` → **拒绝安装**并说明原因。

#### 1.19.3 对寻址的影响

```
<root> ":" <pluginId> [ "@" <instanceKey> ] [ "#" <siteSlug> ] "." <path>
```

| 语法 | 含义 |
|---|---|
| `fact:github.total_stars` | **singleton** 插件，无需实例标识 |
| `fact:webhook@orders.event_count` | **multi** 插件，`@` 后是实例键 |
| `fact:webhook#site-b.event_count` | 跨站点引用 site-b 的默认实例 |
| `fact:webhook@orders#site-b.event_count` | site-b 的 orders 实例 |

**静态校验**（策略发布时强制，避免写错）：

| 情形 | 结果 |
|---|---|
| singleton 插件写了 `@` | ❌ 拒绝发布："plugin github is singleton, '@' is not allowed" |
| multi 插件**没写** `@` | ❌ 拒绝发布："plugin webhook is multi, instance key is required" |
| `@` 后的实例键不存在于本站点配置 | ❌ 拒绝发布 |
| `#` 跨站点引用（非 admin 策略） | ❌ 拒绝发布（站点隔离） |

#### 1.19.4 存储形态：内置随项目，外置落数据库

**两类插件的持久化方式不同**，这是由它们的来源决定的：

| 类型 | 来源 | 持久化方式 | 版本生命周期 |
|---|---|---|---|
| **内置（builtin）** | 项目仓库 `plugins/builtin/` | **随主程序构建产物**（镜像 / 发布包）——天然持久 | 与主程序同步升级 |
| **外置（installed）** | 管理员上传 / URL 安装 | **落入数据库**（`ag_plugin_packages.blob`） | 独立版本管理，可回滚 |

```
┌──────────────────────────────────────────────────────────────┐
│  内置插件（builtin）                                          │
│    源码：plugins/builtin/<id>/                                │
│    部署：随主程序镜像 / 发布包一起分发                          │
│    → 不需要 DB 存储，不需要运行时拉取                          │
├──────────────────────────────────────────────────────────────┤
│  外置插件（installed）                                        │
│    权威存储：ag_plugin_packages.blob（数据库）                 │
│    运行时：解包到 plugins/runtime/<id>/<version>/（可丢弃）     │
│    → 容器重建后启动时从 DB 拉回                                │
└──────────────────────────────────────────────────────────────┘
```

**为什么内置插件不需要落 DB**：它本来就是**构建产物的一部分**——镜像重建、发布包更新都会带上它。再存一份到 DB 是重复，还会引入"DB 里的版本与镜像里的版本不一致"这个新问题。

**为什么外置插件必须落 DB**：它是**运行时上传**的，没有任何构建产物承载它；而本地文件系统不持久（容器重建即丢），所以数据库是唯一可靠的权威层。

**本地目录布局**：

```
plugins/
├── builtin/                    # 内置插件（源码 / 构建产物，随项目）
│   ├── newapi-provider/
│   ├── github/
│   └── checkin/
└── runtime/                    # 外置插件的运行时缓存（可丢弃，加入 .gitignore）
    ├── installed/
    │   └── gitlab/1.0.0/
    └── cache/
```

**启动流程**：

```
① 扫描 plugins/builtin/        → 注册内置插件（读 manifest，校验内置 digest）
② 读 ag_plugins 中 source='installed' 的记录
     ├─ plugins/runtime/ 下已存在且 digest 匹配 → 直接用
     └─ 缺失 / 不匹配 → 从 ag_plugin_packages.blob 取包 → 解包 → 校验 digest
③ 合并注册表（内置 + 外置）→ 开始服务
```

**冲突规则**：

| 情形 | 处理 |
|---|---|
| 外置插件与内置插件 **id 相同** | ❌ **拒绝安装**："id 与内置插件冲突" |
| 外置插件之间 id 相同 | 按版本管理（同一 id 可存多版本，只有一个 `enabled`） |

**可选：对象存储后端**

数据库是默认且推荐的权威层。仅当外置插件包**很大**（含 `node_modules` 的 process 插件可达数十 MB）时，可切到对象存储：

```yaml
plugin:
  storage:
    authority: database | objectstore    # ★ 默认 database
    objectStore: { endpoint, bucket, prefix }
    keepVersions: 3
  runtime:
    dir: plugins/runtime                 # 外置插件的运行时缓存（可丢弃）
    verifyOnStart: true
    allowOfflineStart: true              # DB 不可达时用完好缓存降级启动
```

**备份含义**：备份数据库 = 备份全部**外置**插件；内置插件随主程序发布包一起备份。
