# 02 · 数据模型（声明式 Schema）

> 本文档中的 TS 片段是 **Schema 声明层** 的目标写法；DDL 由声明推导，禁止手写。
> 所有表统一前缀 `ag_`（access-gate），避免与 new-api 的表冲突**即使共用同一个数据库**。

---

## 1. 命名与通用约定

| 约定 | 规则 |
|---|---|
| 表名 | `ag_<领域>_<实体>`，蛇形；如 `ag_user_policy_state`。**本项目独占一个数据库**（不与 new-api 共用），前缀用于可读性与未来合并的可能 |
| 主键 | 业务实体用 **UUIDv7**（`uuid`）；纯日志/流水用 `bigserial` |
| 时间 | 一律 `timestamptz`，字段名 `created_at` / `updated_at` / `deleted_at` |
| 软删除 | `deleted_at IS NULL` 为有效；唯一索引带 `where: 'deleted_at IS NULL'`（PG 部分唯一索引原生支持） |
| JSON | 统一 `jsonb`（PG 原生，可建 GIN 索引） |
| 枚举 | PG **原生 enum**（`col.enum()` 直接映射） |
| 外键 | **逻辑外键**（不建物理 FK），跨模块解耦；由应用层保证 |
| **唯一键** | **站点作用域表的唯一键必须含 `site_id`**。漏了它会造成【静默的跨站点数据污染】——不报错，但站点 A 的数据会覆盖站点 B 的 |
| **作用域归属**（`ownerScope` + `ownerId`） | ★ **所有"平台能力层"的表（凭据 / 授权 / 路由 / 令牌 / 审计 / 运维 / 协同）都必须带这两个非空字段**：`ownerScope ∈ { platform, developer, site, user }`，`ownerId` 为对应主体 id（platform 固定为 `'platform'`）。**为什么不直接用可空的 siteId**：PostgreSQL 的唯一索引把多个 NULL 视为互不相同 → 唯一约束静默失效。故唯一键一律用这两个非空列 |
| **★ CI 门禁（派生规则，非人工白名单）** | **三家独立评估（架构师/实现者/红队）一致指出：人工维护的白名单是缺陷之源**——实测 40 张表中 **14 张不在任何白名单**，且刚补进白名单的两张表**声明仍不满足谓词**（`ag_plugin_instances` 的 `siteId` 可空、`ag_provider_sync_state` 无 `siteId` 列）。**修机制而非修缺陷**——门禁改为**从表声明派生**：<br>**R1** 若表有 `siteId` 列 → 必须 `notNull`；**若有唯一键，其首列必须是 `siteId`**<br>**R2** 若表无 `siteId` 但有 `ownerScope` → 必须 `ownerScope` + `ownerId` 双非空<br>**R3** 若两者皆无 → **必须在「平台级表豁免清单」中，且逐表给出理由**<br>**R4** 违反 R1/R2，或未在 R3 豁免 → `db:check` **启动失败**（不允许「先上线后补」）<br>**豁免清单（须逐表签署理由）**：`ag_users`（平台身份锚点，登录与身份对齐的主体，不属于任何单站点）· `ag_sessions`（会话横跨站点，站点归属由 `activeSiteId` 在运行期约束——登录时尚未选定站点，故不能带 `siteId`）· `ag_plugins`（插件目录，平台级注册表；安装动作是平台级的）· `ag_oidc_providers` / `ag_oidc_signing_keys`（平台级 IdP 配置与签名密钥）· `ag_platform_settings`（平台设置，admin 可改）· `ag_developers`（开发者域，按 `ownerScope` 隔离） · `ag_plugin_configs`（**配置版本历史**：`instanceId` 指向 `ag_plugin_instances`，而实例可能是 developer 级或 site 级 → 本表的归属由父实例决定，不能自带 `siteId`） · `ag_plugin_packages`（**外置插件包体**的权威存储：包体是平台级分发物，与站点无关） · `ag_oidc_login_transactions`（**登录事务**：用户登录时尚未选定站点，与 `ag_sessions` 同理；本表是 R56 架构缺口的修复） · `ag_verify_nonces`（**nonce 防重放**：调用方是平台级的，若加 site_id 则同一调用方在不同站点被视为不同主体，防重放窗口被绕过） · `ag_oauth_clients` / `ag_oauth_codes` / `ag_oauth_refresh_tokens`（**本平台作为 IdP** 的三张表：客户端注册与协议临时凭证都属于「平台级」，与站点无关）<br>**当前违规（第 4 轮门禁对 40 张真实表实跑后的结论，见 `reports/schema-doc-defects.md`）**：`ag_dev_invitations`（`siteId` 可空 + 唯一键首列是 `codeHash`）· `ag_plugin_instances`（双作用域表：`siteId` 可空触发 R1-b，且缺 scope CHECK 触发 R5）<br>**已修正**：`ag_policy_assignments`（补 `siteId` notNull）· `ag_provider_sync_state`（补 `siteId` + 复合主键 `(siteId, provider)`）· `ag_policy_versions`（唯一键补 `siteId` 首列）· `ag_email_rules`（补 `siteId` notNull，改为站点级准入闸门）· `ag_plugin_configs` / `ag_plugin_packages`（补入 R3 豁免并逐表给出理由） |
| 幂等键 | 所有"有副作用"的记录必须有唯一幂等键 |

## 3. ① 身份域

### 3.1 `ag_users` —— 平台用户

```ts
export const users = defineTable('ag_users', {
  id:            col.uuid().primaryKey().defaultSql('uuidv7()'),   // ← OIDC 的 sub，永不变
  email:         col.varchar(255).notNull(),
  emailVerified: col.boolean().notNull().default(false),
  username:      col.varchar(64).notNull(),                       // 展示名，唯一
  passwordHash:  col.varchar(255).nullable(),                     // 模式2 邮箱注册；Argon2id
  status:        col.enum('ag_user_status',
                   ['pending','active','suspended','deleted']).notNull().default('pending'),
  source:        col.enum('ag_user_source', ['local','oidc']).notNull().default('local'),
  locale:        col.varchar(16).notNull().default('zh-CN'),
  tags:          col.jsonb().notNull().defaultSql("'[]'"),         // 分流用标签
  /** ★ 主对齐主体：{ provider, externalId }；取代原先硬编码的 newapiUserId */
  primarySubject: col.jsonb().nullable(),
  profile:       col.jsonb().notNull().defaultSql("'{}'"),         // 昵称/头像等
  lastLoginAt:   col.timestamp({ withTz: true }).nullable(),
  createdAt:     col.timestamp({ withTz: true }).notNull().defaultNow(),
  updatedAt:     col.timestamp({ withTz: true }).notNull().defaultNow().onUpdateNow(),
  deletedAt:     col.timestamp({ withTz: true }).nullable(),
}, (t) => [
  t.unique(['email'],       { name: 'uq_ag_users_email', where: 'deleted_at IS NULL' }),
  t.unique(['username'],    { name: 'uq_ag_users_username', where: 'deleted_at IS NULL' }),
  t.index (['status'],      { name: 'ix_ag_users_status' }),
]);
]);
```

> **`id` 就是 OIDC `sub`**：模式 2 下 new-api 会把 `sub` 写进 `user_oauth_bindings.provider_user_id`；模式 1 下它是本平台的用户主键。用 UUIDv7 兼顾"全局唯一"与"按时间有序（利于索引）"。

### 3.2 `ag_identities` —— 外部身份（对齐表，核心表）

```ts
export const identities = defineTable('ag_identities', {
  ownerScope: col.enum('ag_owner_scope', ['platform','developer','site','user']).notNull(),
  ownerId:    col.varchar(64).notNull().default('platform'), // platform 时固定 'platform'
  id:             col.uuid().primaryKey().defaultSql('uuidv7()'),
  userId:         col.uuid().notNull(),                      // → ag_users.id
  /** 提供方命名空间：
   *   'newapi:oidc'     模式1，中间统一 OIDC 的 sub（= new-api users.oidc_id）
   *   'newapi:oauth'    模式2，new-api 自定义 Provider 的 provider_user_id
   *   'github'          GitHub 账号（数字 id，非 login）
   *   'discord' | 'linuxdo' | 'telegram' | 'oidc:<issuer>' ...
   */
  /** 提供方命名空间：
   *   'subject:newapi'  下游主体目录（= provider 插件 id）
   *   'oidc:<issuer>'   身份提供方（模式 1）
   *   'oauth:newapi'    自定义 OAuth 绑定（模式 2）
   *   'github' | 'discord' | 'linuxdo' | 'telegram' ...

  provider:       col.varchar(64).notNull(),
  providerUserId: col.varchar(255).notNull(),
  /** ★ 反向指向下游主体（对齐结果缓存，避免每次查下游）：{ provider, externalId } */
  subjectRef:     col.jsonb().nullable(),
  /** 原始 claim / profile 快照，用于审计与排障（脱敏后） */
  claimSnapshot:  col.jsonb().notNull().defaultSql("'{}'"),
  verifiedAt:     col.timestamp({ withTz: true }).nullable(),
  createdAt:      col.timestamp({ withTz: true }).notNull().defaultNow(),
  updatedAt:      col.timestamp({ withTz: true }).notNull().defaultNow().onUpdateNow(),
}, (t) => [
  t.unique(['ownerScope','ownerId','provider','providerUserId'], { name: 'uq_ag_identities_provider_uid' }),
  t.index (['userId'],                    { name: 'ix_ag_identities_user' }),
  t.index (['provider'],                  { name: 'ix_ag_identities_provider' }),
]);
]);
```

**对齐查询是热路径**，唯一索引 `(provider, providerUserId)` 保证 O(1)。

### 3.6 `ag_developers` —— 开发者（含 admin）

> **admin 只是 `role = admin` 的开发者**（见 08 文档 §3）。开发者账号**只能由邀请码创建**，无自助注册。

```ts
export const developers = defineTable('ag_developers', {
  id:            col.uuid().primaryKey().defaultSql('uuidv7()'),
  /** ★ 唯一用户名（可变）：登录与展示用；身份锚定在 id，改名不影响任何引用 */
  username:      col.varchar(64).notNull(),
  displayName:   col.varchar(128).notNull(),
  email:         col.varchar(255).notNull(),            // 绑定并可验证
  /** 账密登录（可选）：与 OIDC 可并存；SSO-only 部署时可留空 */
  passwordHash:  col.varchar(255).nullable(),
  emailVerified: col.boolean().notNull().default(false),
  /** ★ admin 只是 developer 的特权角色 */
  role:          col.enum('ag_dev_role', ['admin','developer']).notNull().default('developer'),
  status:        col.enum('ag_dev_status', ['active','suspended','deleted']).notNull().default('active'),
  locale:        col.varchar(16).notNull().default('zh-CN'),
  /** 账号安全（可选）：登录告警 / 会话固定 / IP 白名单
   *  认证强度由受信任的 OIDC 平台保证，平台【不】叠加二次验证 */
  security:      col.jsonb().notNull().defaultSql("'{}'"),
  lastLoginAt:   col.timestamp({ withTz: true }).nullable(),
  /**
   * ★★★ 对应的**平台用户**（`ag_users.id`）——**方案 A**（R101）。
   *
   * ★ 为什么需要它：`ag_plugin_facts.user_id` 的语义是「平台用户」，
   *   而**开发者级插件**（`configScope: 'developer'`，如 `github`）采集到的事实
   *   属于**该开发者**——但 `ag_developers.id` 与 `ag_users.id` **不是同一个值**，
   *   于是「开发者的 GitHub 仓库数」**没有合法的 `userId` 可传**。
   *
   * ★ 方案 A：让**开发者也是平台用户**（他确实要登录、有身份、有会话），用这一列建立映射。
   *   ★ **可空**：兼容既有行（迁移会回填），且允许「尚未建立映射」的过渡态。
   *   ★ 为什么不用「让两个 id 相等」：那会**改变既有语义**
   *     （`ag_sites.developer_id` 等代码假定两者独立）——★ **加列是加法，可回滚**。
   */
  userId:        col.uuid().nullable(),
  createdAt:     col.timestamp({ withTz: true }).notNull().defaultNow(),
  updatedAt:     col.timestamp({ withTz: true }).notNull().defaultNow().onUpdateNow(),
}, (t) => [
  t.unique(['username'],      { name: 'uq_ag_developers_username' }),
  t.unique(['email'],         { name: 'uq_ag_developers_email' }),
  t.index (['role','status'], { name: 'ix_ag_developers_role' }),
], { siteScoped: false });
```

### 3.8 `ag_plugin_instances` —— 插件实例与配置（统一模型）

> **singleton 只是 `instanceKey = 'default'` 的特例**——配置与实例共用一张表，避免两套逻辑。
> 作用域（`developer` / `site`）由插件 manifest 的 `config.scope` 决定（见 03 文档 §1.19）。

```ts
export const pluginInstances = defineTable('ag_plugin_instances', {
  id:          col.uuid().primaryKey().defaultSql('uuidv7()'),
  pluginId:    col.varchar(64).notNull(),
  /** ★ singleton 插件固定为 'default'；multi 插件由管理员命名 */
  instanceKey: col.varchar(32).notNull().default('default'),
  /** 配置作用域（继承插件的 config.scope） */
  scope:       col.enum('ag_plugin_config_scope', ['developer','site']).notNull(),
  /** scope=developer 时填（该开发者名下所有站点共享） */
  developerId: col.uuid().nullable(),
  /** scope=site 时填（仅本站点可用） *
   *  ★ 双作用域表（门禁 R5 豁免）：本表同时承载 developer 级与 site 级配置，故 siteId 可空；
   *  但须有 CHECK 保证「scope 与哪个 id 非空」一致：(scope=site AND siteId NOT NULL AND developerId IS NULL) OR (scope=developer AND developerId NOT NULL AND siteId IS NULL) */
  siteId:      col.uuid().nullable(),
  label:       col.varchar(128).nullable(),
  /** 已按 manifest.configSchema 校验 */
  config:      col.jsonb().notNull(),
  configHash:  col.varchar(64).notNull(),
  /** 平台已安装是前提；此处控制"本例是否启用" */
  enabled:     col.boolean().notNull().default(false),
  updatedBy:   col.uuid().nullable(),
  updatedAt:   col.timestamp({ withTz: true }).notNull().defaultNow().onUpdateNow(),
}, (t) => [
  // ★ R6（唯一键含可空列）—— **已按登记修法 ① 修复**：
  //   PG 把 NULL 视为互不相同，因此建在可空列上的唯一键会**静默失效**
  //   （可插入任意多组重复逻辑键）。加上 `where … IS NOT NULL` 的部分唯一索引后，约束才真正生效。
  //   ★ 前提是查询编译器的 `onConflict` 支持**同一谓词**（`ON CONFLICT (cols) WHERE … DO …`）——
  //     该能力已在 `src/query/ast.ts` / `src/query/compile.ts` 实现，
  //     并由 `test/query-onconflict-where.test.ts` 用**对照组**证明（不带谓词时 PG 报 42P10）。
  t.unique(['developerId','pluginId','instanceKey'], { name: 'uq_ag_plugin_inst_dev', where: 'developer_id IS NOT NULL' }),
  t.unique(['siteId','pluginId','instanceKey'],      { name: 'uq_ag_plugin_inst_site', where: 'site_id IS NOT NULL' }),
], {
  siteScoped: false,   // ★ 跨作用域表：同时存在 developer 级与 site 级记录
  /** ★ R5：双作用域表必须有 CHECK 保证「scope 与哪个 id 非空」一致——
   *  否则可以写出 scope=site 却只有 developerId 的记录，两个唯一键都拦不住它。 */
  dualScopeCheck:
    "(scope = 'site' AND siteId IS NOT NULL AND developerId IS NULL)" +
    " OR (scope = 'developer' AND developerId IS NOT NULL AND siteId IS NULL)",
});
```

**解析顺序**（求值时如何找到配置）：

```
① 插件声明 config.scope = site      → 取 (siteId, pluginId, instanceKey)
② 插件声明 config.scope = developer → 取 (developerId, pluginId, instanceKey)
                                       （该开发者的所有站点共享这一份）
③ 未找到 / 未启用 → 该地址为 missing，交由 $onMissing 处理
```

### 7.4 `ag_oidc_signing_keys` —— OIDC 签名密钥（EC / RSA / OKP 多算法并存）

> 模式 2 下本平台对外签发 ID Token，密钥必须支持 **EC**，并与 RSA **并存发布**（见 05 文档 §8）。
> 私钥**不**放 `ag_secrets`——因为它需要独立的状态机（active / standby / retiring）与轮换元数据。

```ts
export const oidcSigningKeys = defineTable('ag_oidc_signing_keys', {
  id:   col.uuid().primaryKey().defaultSql('uuidv7()'),
  /** JWKS 中暴露的 kid，全局唯一，ID Token header 引用它 */
  kid:  col.varchar(64).notNull(),
  /** 密钥类型 */
  kty:  col.enum('ag_jwk_kty', ['EC', 'RSA', 'OKP']).notNull(),
  /** 签名算法：ES256 | ES384 | ES512 | RS256 | RS384 | RS512 | EdDSA */
  alg:  col.varchar(16).notNull(),
  /** EC: P-256 | P-384 | P-521；OKP: Ed25519；RSA 为 null */
  crv:  col.varchar(16).nullable(),
  /** 公钥 JWKS 片段，可直接下发：EC → {crv,x,y}；RSA → {n,e}；OKP → {crv,x} */
  publicJwk: col.jsonb().notNull(),
  /** 私钥（PKCS#8 PEM），AES-256-GCM 加密；任何 API / 日志 / 审计都不返回 */
  privateCiphertext: col.text().notNull(),
  privateIv:         col.varchar(32).notNull(),
  privateAuthTag:    col.varchar(32).notNull(),
  /** AG_MASTER_KEY 的版本，支持主密钥轮换 */
  masterKeyVersion:  col.integer().notNull().default(1),
  /** active=当前签发并发布；standby=不签发但长期发布（RSA 兼容兜底）；retiring=轮换中，仍发布；retired=已移出 JWKS */
  status: col.enum('ag_signing_key_status',
            ['active', 'standby', 'retiring', 'retired']).notNull().default('standby'),
  activatedAt:          col.timestamp({ withTz: true }).nullable(),
  retiredFromSigningAt: col.timestamp({ withTz: true }).nullable(),
  /** 移出 JWKS 的最早时间 = retiredFromSigningAt + retireAfter（standby 恒为 null，永不过期） */
  removeAfter:          col.timestamp({ withTz: true }).nullable(),
  createdAt: col.timestamp({ withTz: true }).notNull().defaultNow(),
}, (t) => [
  t.unique(['kid'], { name: 'uq_ag_oidc_keys_kid' }),
  // 每种算法最多一个 active、一个 standby（PG 部分唯一索引原生支持）
  t.unique(['alg'], { name: 'uq_ag_oidc_keys_active_alg',  where: "status = 'active'" }),
  t.unique(['alg'], { name: 'uq_ag_oidc_keys_standby_alg', where: "status = 'standby'" }),
  t.index (['status'],      { name: 'ix_ag_oidc_keys_status' }),
  t.index (['removeAfter'], { name: 'ix_ag_oidc_keys_remove_after' }),
]);
```

**状态语义**：

| status | 是否签发 | 是否在 JWKS | 何时使用 |
|---|---|---|---|
| `active` | ✅ | ✅ | 当前 `oidc.signing.activeAlg` 对应的密钥 |
| `standby` | ❌ | ✅ | `jwksAlgs` 中除 activeAlg 外的算法，**永久发布**（RSA 兜底，永不回收） |
| `retiring` | ❌ | ✅ | 轮换下来的旧 active，供已签发未过期的 token 验签 |
| `retired` | ❌ | ❌ | 超过 `retireAfter` 后移出 |

### 4.x `ag_oidc_login_transactions` —— 登录事务（**state + PKCE verifier**）

> ★★ 为什么需要这张表（R56 的架构缺口发现）：
> `LoginTransactionStore` 此前**只有内存实现**，于是：
> · **服务重启** → 进行中的登录全部失效（用户看到「state 无效」）；
> · **多实例部署** → 登录随机失败（A 实例发的 state，负载均衡到 B 实例找不到）；
> · **PKCE 的 `code_verifier` 随进程丢失** → 回调无法完成校验。
>
> ★ 接口要求「**原子取出即删除**」——PG 下必须用 `DELETE ... RETURNING`，
> 用 `SELECT` + `DELETE` 两步会在并发下**取到两次**（state 被重放）。

```ts
export const oidcLoginTransactions = defineTable('ag_oidc_login_transactions', {
  /** ★ state 即主键——「一个 state 只能被取出一次」由主键唯一性保证 */
  state:       col.varchar(128).primaryKey(),
  /** PKCE 的 code_verifier（回调时用它换 token） */
  codeVerifier: col.varchar(256).notNull(),
  /** OIDC nonce（校验 id_token，防重放） */
  nonce:       col.varchar(128).notNull(),
  /** 登录成功后的落点（含 `#realm` 后缀标识身份域） */
  returnTo:    col.varchar(512).notNull(),
  /**
   * ★ 发起登录时携带的**目标站点**（内部 id）——回调成功后自动选中它。
   *
   * ★ 为什么它必须随事务往返：站点在**登录发起时**指定（`?site=`），
   *   而"选定"发生在**回调之后**——中间隔着 IdP 往返，进程状态会丢（多实例尤甚）。
   * ★ 可空：**不带**站点参数的登录是正常路径（用户登录后再自选）。
   * ★★ **列名刻意不叫 `site_id`**：本表是**平台级**表（一次授权的事务，不属于任何站点），
   *   这一列是「用户**想去**哪个站点」这个**普通业务字段**，**不是作用域键**。
   *   而 R1 门禁按**列名**触发（"有 `site_id` 列 → 必须 `notNull`"）——
   *   叫 `site_id` 会被它**合理地**判为违规。改门禁会削弱它、加豁免不适用（本表确有该列），
   *   所以**改名是最诚实的修法**：语义准确，且不再假装自己是作用域键。
   */
  targetSiteId: col.uuid().nullable(),
  /** ★ 过期时间——`purgeExpired` 据此清理；回调时也据此拒绝过期事务 */
  expiresAt:   col.timestamp({ withTz: true }).notNull(),
  createdAt:   col.timestamp({ withTz: true }).notNull().defaultNow(),
}, (t) => [
  t.index(['expiresAt'], { name: 'ix_ag_oidc_login_tx_expires' }),
]);
```

  eventId:       col.varchar(64).notNull(),

  nextAttemptAt: col.timestamp({ withTz: true }).notNull().defaultNow(),
  deliveredAt:   col.timestamp({ withTz: true }).nullable(),
  /** 重试耗尽后落 ag_dead_letters；此处保留最后一次错误便于排障 */
  lastError:     col.text().nullable(),
  traceId:       col.varchar(48).nullable(),
  createdAt:     col.timestamp({ withTz: true }).notNull().defaultNow(),
}, (t) => [
  // ★ R1-b：唯一键首列必须是 siteId（否则跨站点静默冲突）
  t.unique(['siteId', 'eventId'], { name: 'uq_ag_outbox_event' }),
  // 取待投递事件的主查询路径
  t.index (['siteId', 'status', 'nextAttemptAt'], { name: 'ix_ag_outbox_due' }),
]);
```

> **为什么必须与业务同事务写入**（`05 §7.1.2`）：若「先改状态、再异步发事件」，进程在两步之间崩溃会留下
> **「平台侧 granted、下游从未收到通知」**——而下游 bot 的缓存 5 分钟后过期，
> 结果是**用户在下游失去资格，而平台侧一切正常、审计完整、无告警**。反向（`revoked` 丢失）更危险：
> **下游仍持权限而平台认为已收回**。发件箱把「事件」纳入同一个事务，从根上消除这个窗口。

  attempts:   col.integer().notNull(),
  lastError:  col.text().notNull(),
  failedAt:   col.timestamp({ withTz: true }).notNull().defaultNow(),
  /** 人工/自动重放记录（06 §5.5 的列表与重放入口） */

  replayedBy: col.uuid().nullable(),

}, (t) => [

  // 运维视图：按站点列出未重放的死信
  t.index (['siteId', 'replayedAt'], { name: 'ix_ag_dead_letters_pending' }),
]);
```

> **为什么必须存在**（`05 §7.1.2` 的原文教训）：没有这张表时，`granted` 事件推送失败会进

> 有了它，「重试耗尽后落死信」成为**可观测、可重放**的终态（`06 §5.5` 提供列表与重放入口）。
>

> （`05 §7.1.2`）。这条约束正是 `ag_dead_letters` 允许「延迟重放」而不破坏正确性的前提。

## 9. "定义对齐"机制详设

### 9.1 三条对齐链

```
TS 声明 ──(编译期)──▶ 类型 & Repository 签名        【定义 ↔ 代码 对齐】
   │
   │(生成期)
   ▼
迁移文件 ──(执行期)──▶ 实际数据库结构               【定义 ↔ 库 对齐】
   ▲                        │
   └────── drift 检测 ───────┘                       【持续校验】
```

### 9.2 迁移生成（`db:generate`）

1. 读取全部 `defineTable` 声明；
2. 与 `ag_migrations` 表中记录的**已应用快照**（上一版 Schema 的序列化）做 diff；
3. 产出三向差异：`addTable` / `dropTable`(需显式确认) / `addColumn` / `alterColumn` / `dropColumn`(需显式确认) / `addIndex` / `dropIndex`；
4. 生成**可读的** SQL 迁移文件（PostgreSQL）+ 回滚脚本；
5. 危险操作（删表/删列/改类型）默认**不生成**，除非声明 `{ destructive: 'allow' }`。

#### 9.2.1 迁移的执行安全（★ 线上底线）

| 规则 | 说明 |
|---|---|
| **每条迁移一个独立事务** | PG 的 DDL 大部分可事务化——要么全成、要么全败，不留半应用状态 |
| **例外：非事务性迁移** | `CREATE INDEX CONCURRENTLY` 不能在事务块内 → 单独标记 `nonTransactional`，失败需人工确认后重跑 |
| **抢 advisory lock** | 迁移前抢 `pg_advisory_lock('migrate')`；未抢到者**等待轮询**迁移完成，而非各自执行 |
| **校验和** | `ag_migrations` 记录每条迁移的 checksum，防止迁移文件被事后修改 |
| **三态记录** | `pending / applied / failed`；发现 `failed` → **拒绝启动**并给出修复指引 |
| **expand / contract 两阶段** | 阶段 1 只**新增**（加列 / 表 / 索引，向后兼容，新旧实例都能工作）；阶段 2 等所有实例升级完（观察期 ≥ 1 个发版周期）再删旧列。**禁止在同一次发布里既加又删** |

### 9.3 启动期 drift 检测（`db:check`）

对每个声明表查询 PostgreSQL 的 **information_schema** / **pg_catalog**，比对：

| 差异类型 | 行为 |
|---|---|
| `missing_table` / `missing_column` / `missing_index` | ❌ **启动失败**（fail-fast），提示执行迁移 |
| `type_drift` / `nullability_drift` / `default_drift` | ⚠️ 启动告警 + 健康检查降级 |
| `extra_column` / `extra_index` / `extra_table` | ⚠️ 仅告警（`允许手工应急字段`） |
| 迁移表校验和不匹配 | ❌ 启动失败（有人手改过迁移文件） |

### 9.4 与策略声明对齐（`policies:check`）

`config/policies/*.yaml` 是策略的**代码态**；DB 里的 `ag_policy_versions` 是**运行态**。对齐规则：

- 启动时扫描 YAML 目录，计算 `specHash`；
- hash 与 DB 中同 `code` 的 latest 版本不一致 → 生成 **draft 版本**（不自动生效，需人工在 UI 点发布）；
- DB 中存在但 YAML 中已删除的策略 → 标记 `orphan` 告警；
- 支持 `POLICY_AUTOPUBLISH=true` 在开发环境自动生效。

> 这样既能"策略即代码"（可 Git 管理、可 Code Review），又不会因为改错文件直接把线上规则改了。
