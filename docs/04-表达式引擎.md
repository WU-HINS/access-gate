## 1. 表达式与规则引擎（Expression Engine）

> **为什么不用"模式枚举"**：`requirements.mode = any|all|quorum|weighted` + 扁平 `items[]` 这类两级结构只能表达"若干条件里满足几个"，**无法表达"不同分支有不同条件"**。
>
> 例如需求中的："QQ > 40 级可直接解锁；20 < QQ < 40 则要求与其它渠道组合达成"——
> 旧结构写不出来，因为"某个范围需要组合、另一个范围直接通过"是**分支级差异**，不是同一组条件的计数。
>
> 现在改为：**表达式（expression）是唯一的判定语言**，由最基础的 `and / or / not / 比较` 通过**任意嵌套**组成复合判断。

### 1.1 设计立场

| 立场 | 说明 |
|---|---|
| **基础操作符 + 嵌套组** | 只有"与/或/非 + 比较"这类最根本的构造，**没有专用的复合模式**；一切复杂逻辑由嵌套产生 |
| **任意深度** | 嵌套层数不设限（工程上限制 32 层并给出明确报错） |
| **分支可不同条件** | 用有序 `branches`（if / else-if / else）表达"不同分支不同条件、不同动作" |
| **渠道自动推断** | 表达式里写 `fact.qq.level` 就够了，**不需要声明 channel**——宿主从命名空间反查插件 |
| **可解释** | 求值产出**完整结果树**，用户能看到"为什么通过 / 差在哪一项、差多少" |

### 1.2 表达式语法（`gate/expr/v1`）

#### 1.2.1 逻辑节点

```yaml
{ all:  [ E1, E2, ... ] }          # AND，短路：遇 false 即停
{ any:  [ E1, E2, ... ] }          # OR，短路：遇 true 即停
{ not:  E }                        # NOT
{ none: [ E1, E2, ... ] }          # NOR，等价于 not(any(...))

# 计数式（由 any/all 派生出的语法糖，语义明确）：
{ atLeast: { n: 2, of: [ E1, E2, E3 ] } }        # 至少 n 个为真
{ atMost:  { n: 1, of: [ E1, E2 ] } }            # 至多 n 个为真
{ exactly: { n: 1, of: [ E1, E2 ] } }            # 恰好 n 个为真

# 加权分（score 节点，叶子为带权重的子表达式）
{ score: { threshold: 150, of: [ { weight: 2, expr: E1 }, { weight: 1, expr: E2 } ] } }
```

> `atLeast` / `score` 只是 `any`/`all` 的便捷形式，**不是独立机制**；它们能被展开成纯布尔表达式，因此引擎只有一套求值逻辑。

**空白与空数组的语义（★ 必须先定义，否则会成为陷阱）**：

| 写法 | 语义 | 处理 |
|---|---|---|
| `all: []` | 数学上恒真 | ❌ **发布时拒绝** |
| `any: []` | 恒假 | ❌ **发布时拒绝** |
| `{ always: true }` | 恒真 | ✅ 显式表达"无条件通过" |
| `{ never: true }` | 恒假 | ✅ 显式表达"永不通过"（占位 / 禁用） |

**为什么拒绝空数组**：若某次编辑失误清空了条件，`all: []` 会让**全站主体立即满足** → 大规模误升级。
让"无条件"必须**显式写出**（`always`），而不是通过空数组意外达成。

**其他边界**：

| 写法 | 语义 |
|---|---|
| `atLeast: { n: 0, of: [...] }` | 恒真（`n=0` 时无意义）→ 拒绝，要求 `n ≥ 1` |
| `atLeast: { n: > len(of) }` | 恒假 → 拒绝（几乎必然是配置错误） |
| `score.threshold: 0` 且权重全 0 | 除零 → 求值返回 `error`（见 §1.5） |

#### 1.2.2 比较节点（叶子）

统一形式：`{ <操作符>: { <操作数>: <值> } }`

```yaml
{ gt:  { fact.qq.level: 40 } }
{ lte: { fact.qq.level: 40 } }
{ gte: { fact.github.total_stars: 100 } }
{ eq:  { user.status: "active" } }
{ between: { fact.qq.level: [20, 40] } }
{ in:  { user.tags: ["vip", "beta"] } }
{ contains: { fact.github.organizations: "linux-foundation" } }
{ matches: { fact.email.domain: ["*.edu.cn", "*.edu"] } }   # glob
{ regex: { fact.email.domain: "^.*\\.edu$" } }
{ exists: { fact.llm.pr_score: true } }
{ is_empty: { fact.github.organizations: true } }
```

**操作符全集**（与 new-api 的 `access_policy` 保持心智一致，便于管理员迁移）：

| 类别 | 操作符 |
|---|---|
| 比较 | `eq` `ne` `gt` `gte` `lt` `lte` `between` |
| 集合 | `in` `not_in` `contains` `not_contains` `subset_of` `superset_of` `intersects` |
| 字符串 | `matches`(glob) `regex` `prefix` `suffix` |
| 存在 | `exists` `not_exists` `is_null` `is_empty` |
| 时间 | `before` `after` `within_days` |
| 数值 | `divisible_by` |

**约束**：一个比较节点**只允许一个操作数键**（保留键除外）。要"同时满足两个比较"就放进 `all`——不允许在比较节点里堆多个 key，避免 YAML 语义歧义。

#### 1.2.3 操作数（operand）

| 形式 | 含义 |
|---|---|
| `fact.<namespace>.<path>` | 插件产出的事实，如 `fact.qq.level`、`fact.github.total_stars` |
| `user.<field>` | 平台用户属性：`email` `email_verified` `username` `status` `tags` `createdAt` `locale` |
| `binding.<pluginId>.<field>` | 绑定信息：`status` `externalName` `boundAt` `age_days` |
| 字面量 | 数字 / 字符串 / 布尔 / 数组 |

路径支持数组下标与通配：`fact.github.orgs[0]`、`fact.github.repos[*].stars`。

#### 1.2.4 保留属性（`$` 前缀）

任意节点都可带元数据，不影响求值语义：

```yaml
all:
  - $label: "QQ 等级 20~40 级"      # UI 展示文案
    $ttl: 24h                        # 该分支依赖事实的最大复用年龄
    $onMissing: fail_closed          # 事实缺失时的行为：fail_closed | fail_open | skip
    $weight: 2                       # 在 score 节点中的权重
    gt: { fact.qq.level: 20 }
```

#### 1.2.5 可复用子表达式（`defs` + `$ref`）

```yaml
defs:
  github_strong:
    any:
      - $label: "GitHub 总 star ≥ 100"
        gte: { fact.github.total_stars: 100 }
      - $label: "LLM 有效 PR 指数 ≥ 60"
        gte: { fact.llm.pr_score: 60 }
  verified_email:
    all:
      - eq:  { user.email_verified: true }
      - matches: { fact.email.domain: ["*.edu.cn"] }

requirements:
  expression:
    all:
      - $ref: github_strong
      - $ref: verified_email
```

`$ref` 在**发布时**被内联展开（保持 spec 自包含），同时保留原始引用便于 UI 折叠展示。

### 1.2.6 三种等价表示：YAML / JSON / 图形

**AST 是唯一真理，三种表示只是它的序列化形式。**

| 表示 | 面向 | 用途 |
|---|---|---|
| **YAML** | 人 | 手写、Git 管理、Code Review、策略即代码 |
| **JSON** | 程序 | API 传输、SDK 构造、跨语言互操作、**存库的规范形式** |
| **Graph** | 图形编辑器 | 可视化拖拽、大策略的全局把握、非技术管理员 |

**同一个表达式的三种写法**（语义完全等价）：

```yaml
# ① YAML
any:
  - gt: { fact.qq.level: 40 }
  - all:
      - gt:  { fact.qq.level: 20 }
      - lte: { fact.qq.level: 40 }
```

```json
// ② JSON
{ "any": [
    { "gt": { "fact.qq.level": 40 } },
    { "all": [
        { "gt":  { "fact.qq.level": 20 } },
        { "lte": { "fact.qq.level": 40 } }
    ] }
] }
```

```jsonc
// ③ Graph（含布局；布局不参与语义）
{
  "version": "gate/expr-graph/v1",
  "root": "n1",
  "nodes": [
    { "id": "n1", "kind": "any", "position": { "x": 0, "y": 0 } },
    { "id": "n2", "kind": "compare",
      "compare": { "op": "gt", "operand": "fact.qq.level", "value": 40 },
      "position": { "x": 240, "y": -80 } },
    { "id": "n3", "kind": "all", "position": { "x": 240, "y": 60 } },
    { "id": "n4", "kind": "compare",
      "compare": { "op": "gt", "operand": "fact.qq.level", "value": 20 },
      "position": { "x": 480, "y": 20 } },
    { "id": "n5", "kind": "compare",
      "compare": { "op": "lte", "operand": "fact.qq.level", "value": 40 },
      "position": { "x": 480, "y": 100 } }
  ],
  "edges": [
    { "from": "n1", "to": "n2", "order": 0 },
    { "from": "n1", "to": "n3", "order": 1 },
    { "from": "n3", "to": "n4", "order": 0 },
    { "from": "n3", "to": "n5", "order": 1 }
  ],
  "viewport": { "x": 0, "y": 0, "zoom": 1 }
}
```

**Graph 数据模型**：

```ts
interface ExprGraph {
  version: 'gate/expr-graph/v1';
  root: string;                                  // 根节点 id
  nodes: ExprGraphNode[];
  edges: ExprGraphEdge[];
  viewport?: { x: number; y: number; zoom: number };
}

interface ExprGraphNode {
  id: string;                                    // 图内唯一，不参与语义
  kind: 'all' | 'any' | 'not' | 'none'
      | 'atLeast' | 'atMost' | 'exactly' | 'score'
      | 'compare' | 'ref' | 'branch' | 'else';
  label?: string;                                // $label
  meta?: { ttl?: string; onMissing?: 'fail_closed' | 'fail_open' | 'skip' | 'unknown'; weight?: number };
  params?: { n?: number; threshold?: number };   // atLeast.n / score.threshold
  compare?: { op: string; operand: string; value: unknown };  // compare 节点
  ref?: string;                                  // ref 节点引用的 defs 名称
  position: { x: number; y: number };
  collapsed?: boolean;                           // 纯 UI 状态
}

interface ExprGraphEdge {
  id?: string;
  from: string;                                  // 父节点 id
  to: string;                                    // 子节点 id
  order: number;                                 // 兄弟顺序（承载数组语义）
  label?: 'when' | 'then' | 'else' | null;       // 分支语义
}
```

**分支在图形中的表示**：`branch` 节点作为 `branches` 的容器，其子节点为各分支（`when` 边指向条件、`then` 边指向动作），`else` 是特殊子节点。

**保真规则**（转换器的正确性契约）：

| 规则 | 说明 |
|---|---|
| **语义只在 AST** | `position` / `viewport` / `collapsed` / 节点 `id` **不参与语义**，转换时丢弃或重建 |
| **顺序必须保序** | JSON 数组有序；Graph 用 `edge.order` 承载。`all`/`any` 虽逻辑无序，但**顺序影响短路行为与展示**，故往返必须保序 |
| **`$ref` 不自动内联** | YAML/JSON 中为引用，Graph 中为 `ref` 节点（避免大策略图爆炸）；UI 提供"展开预览" |
| **往返保真** | `yaml → ast → graph → ast → yaml` 必须**语义等价**，由 property-based 测试保证（随机生成 AST 做三向往返） |
| **规范形式** | 存库统一为**规范 JSON AST**；YAML/Graph 作为"编辑态"保留，用于恢复编辑器状态 |

**存储**（扩展 `ag_policy_versions`）：

```ts
{
  spec:      col.jsonb().notNull(),     // ★ 规范 AST —— 唯一真理，求值只用它
  specYaml:  col.text().nullable(),     // 原始 YAML（若来自 YAML 编辑）
  specGraph: col.jsonb().nullable(),    // 图形态（含布局；若来自图形编辑）
  specHash:  col.varchar(64).notNull(), // 只对【规范 AST】计算 → 语义去重
  origin:    col.enum('ag_spec_origin', ['yaml','json','graph','migrated']).notNull(),
}
```

> `specHash` 只对规范 AST 计算，因此"同一逻辑分别用 YAML 和图形编辑"会得到**相同 hash**，"内容未变"能被正确识别（不会因为换了编辑器就产生无意义的 draft 版本）。

**API**：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/admin/policies/:code/expression?format=yaml\|json\|graph` | 取指定形态 |
| `PUT` | `/admin/policies/:code/expression?format=...` | 按指定形态写入（服务端统一转 AST） |
| `POST` | `/admin/policies/:code/expression/convert` | 形态互转 `{ from, to, content }` |
| `POST` | `/admin/policies/:code/expression/validate` | 任意形态校验，返回 AST + 错误定位 |

**共享 SDK**：`@gate/expr` 提供 `parseYaml / parseJson / parseGraph / toYaml / toJson / toGraph / validate`，**前后端共用同一份实现**（TypeScript），保证"编辑器所见"与"服务端所算"绝不漂移。

### 1.2.7 统一寻址与绑定解析（★ 跨系统取值的根基）

> **为什么要统一寻址**：`fact.<ns>.<path>` / `subject.<attr>` / `binding.<pluginId>.<field>` 这类多套写法既没有"**实例**"维度（一个插件可接多个 bot / 多个站点），也无法表达"**用户在某个下游系统里是谁**"（这需要绑定解析）。
>
> 因此统一为一套寻址语法，并引入**绑定解析（Binding Resolution）**作为跨系统取值的前置步骤。

#### 1.2.7.1 寻址语法

```
<root> ":" <pluginId> [ "@" <instanceKey> ] [ "#" <siteSlug> ] "." <path>

root := "subject" | "fact" | "identity" | "me"
```

| root | 语义 | 数据来源 |
|---|---|---|
| `subject` | **本站点下游系统里的主体（用户）属性** | `ag_external_subjects.attributes`，需先做绑定解析 |
| `fact` | 插件采集的**证据** | `ag_plugin_facts` |
| `identity` | **身份标识**（OIDC / 渠道绑定） | `ag_identities` + `ag_oidc_providers` |
| `me` | 平台用户自身属性 | `ag_users`（email / tags / status / locale …） |

**默认在"当前站点"作用域内求值**：

```yaml
subject:newapi.group              # 本站点的 newapi（site 作用域 + singleton）
fact:github.total_stars           # 开发者级 singleton（所有站点共享同一份配置）
fact:webhook@orders.event_count   # 本站点的 orders 实例（multi）
me.tags
identity:oidc@external:proj-a.sub
```

**`@instanceKey` 是否必需，由插件自己声明**（见 03 文档 §1.19）：

| 插件声明 | 正确写法 | 写错时 |
|---|---|---|
| `instances.mode: singleton` | 不带 `@` | 带了 `@` → ❌ **拒绝发布** |
| `instances.mode: multi` | **必须**带 `@` | 不带 → ❌ **拒绝发布** |

**`#siteSlug` 跨站点引用**（默认禁止，仅 admin 配置的平台级策略可用）：

```yaml
fact:github#site-b.total_stars        # 显式引用 site-b
fact:webhook@orders#site-b.count
```

> **配置作用域与寻址写法无关**：无论配置是 `developer` 级（共享）还是 `site` 级（独立），寻址写法完全一致——差异只在"这份配置在哪里维护"（见 03 文档 §1.19）。

#### 1.2.7.2 绑定解析：`subject:X@Y` 到底是谁

`subject:newapi.group` 里**没有写用户 ID**——因为它是推导出来的：

```
① 当前评估上下文有一个【平台用户】（如 0192a1b2-…）
② 查 ag_plugin_bindings(平台用户, plugin=newapi, instance=site-a)
      ├─ 命中   → 得到 externalId
      └─ 未命中 → 按该实例声明的 binding.keys 尝试【自动解析】
③ 用 externalId 读 ag_external_subjects(provider=newapi, externalId).attributes.group
④ 任一步失败 → 该操作数为 missing，交由 $onMissing 决定行为
```

**绑定键（binding keys）由插件 manifest 声明**，按优先级尝试：

```yaml
# plugins/builtin/newapi-provider/manifest.yaml
instances:
  - id: site-a
    label: "主站"
    config: { baseUrl: "https://api-a.example.com", tokenRef: "newapi.site_a.pat" }
    binding:
      keys:
        - { kind: oidc,      ref: "platform:gate",    claim: sub, unique: true }  # 本站用户的 oidc_id
        - { kind: oidc,      ref: "external:proj-a",  claim: sub, unique: true }  # 项目 OIDC 联邦
        - { kind: attribute, path: email, unique: true, requireVerified: true }
        - { kind: manual }                                                        # 只能人工绑定
      autoLink: true                # 对账时自动建立绑定
      conflictPolicy: manual_review # 多个候选命中时进入人工裁决，绝不猜
```

**唯一性是硬要求**：`unique: true` 的键在目标系统里必须唯一，否则**拒绝自动绑定**并告警。

#### 1.2.7.3 需求原句 → 表达式写法

> 原句：**当 {QQ AIbot适配器 插件}:{bot绑定对接项目内适配器虚拟ID} 中 ${用户的QQ ID} 的 {等级} >= [40] 时；否则退回；满足则设置 {newapi插件}:{站点编号} 中 {用户ID} 的 {用户所属分组} 为 ("xxx")**

```yaml
spec:
  requirements:
    branches:
      # ── if ───────────────────────────────────────────────────────
      - id: qq_high
        label: "QQ 等级 ≥ 40"
        when:
          gte:
            # {QQ适配器插件}:{适配器虚拟ID} 中该用户的 {等级}
            # ${用户的QQ ID} 由绑定解析自动得出，无需手写
            "fact:qqbot-adapter@bot-main.level": 40
        outcome: satisfied
        actions:
          # {newapi插件}:{站点编号} 中 {用户ID} 的 {分组} 设为 "xxx"
          - action: "newapi-set-group:set_group"
            params:
              instance: site-a                              # {站点编号}
              group:    "xxx"
              # ★ 目标**不需要**写：它来自计划主体（被评估的那个用户），
              #   由动作的 `externalIdOf(context) ?? context.userId` 得出（见下方说明）。
      # ── else ─────────────────────────────────────────────────────
      else:
        outcome: unsatisfied
        actions: []
```

> **动作的目标与判定共用同一套寻址**（避免"判定一套、动作另一套"的割裂）——但要点有三处：
>
> 1. **默认目标 = 计划主体**：动作执行时目标取自被评估的那个用户
>    （`ActionExecutor` → 动作的 `externalIdOf(context) ?? context.userId`），
>    因此 `params` 里通常**不需要**写 `subject`。
> 2. **若确实要在参数里写寻址目标**，参数名须在约定集合内（`target` / `subject` / `scope` / `to`），
>    且值必须是**合法地址**（`subject:<pluginId>.<path>`，可带 `@实例键` / `#站点`）。
>    执行器用与求值**同一个解析器**（`parseAddress`）把它换成具体 `externalId`。
> 3. ★ **解析不出来时动作失败并给出原因**，绝不把寻址串原样交给下游
>    （下游要么看不懂、要么当普通值写进去 = **改错目标**）。
>
> ⚠️ **勘误**：本节示例此前写作 `subject: "subject:newapi"` —— 该写法**缺少 `.` 分隔的路径**，
> 与寻址语法不符（`validateAddress` 把空路径判为 `empty_path` 错误）。已改为不写 `subject`
> （默认目标就是计划主体）；如需显式书写，正确形式是 `subject:newapi.group`。

#### 1.2.7.4 OIDC 绑定：`{站点用户ID} == 用户 OIDC == 项目 OIDC`

> 原句：**`{newapi插件}:{站点ID}:${站点用户ID} == (用户 {Oauth}:{OIDC} == {项目OIDC} 时取值，{newapi插件}:{站点ID} 下唯一绑定)`**

翻译为一条**绑定键**：

```yaml
# newapi-provider 的 site-a 实例
binding:
  keys:
    - kind: oidc
      ref: "external:proj-a"        # {项目OIDC} —— 项目的 OIDC 唯一标识符
      claim: sub                    # 取用户在该 OIDC 下的 sub
      unique: true                  # {站点ID} 下唯一绑定，否则不绑定
```

语义：**用"用户在某项目 OIDC 下的 sub"去该 newapi 站点里找 `oidc_id` 相同的用户；找到且唯一 → 建立绑定；否则不绑定。**

于是策略里只要写：

```yaml
when:
  all:
    - eq:  { "identity:oidc@platform:gate.email_verified": true }
    - gte: { "subject:newapi.quota": 1000000 }
```

`identity:oidc@<ref>` 提供该用户在**某个 OIDC 唯一标识符**下的身份信息，不依赖任何具体下游系统。

#### 1.2.7.5 静态校验

策略发布时，宿主对每个地址做**逐段校验**：

| 检查项 | 失败时 |
|---|---|
| `pluginId` 是否存在且已启用 | ❌ 拒绝发布 |
| `@instance` 是否存在于该插件的 `instances` 声明 | ❌ 拒绝发布 |
| `root=fact` 的 `path` 是否在该插件 `factSchema` 内 | ❌ 拒绝发布 |
| `root=subject` 的 `path` 是否在该 provider 的 `subjectSchema` 内 | ❌ 拒绝发布 |
| `root=identity` 的 `ref` 是否在 `ag_oidc_providers` 中且已启用 | ❌ 拒绝发布 |
| `root=me` 的 `path` 是否在内置用户 schema 内 | ❌ 拒绝发布 |
| 该实例是否至少有一个可达的 `unique` 绑定键 | ⚠️ 警告（策略可能永远 missing） |

错误信息**精确定位到地址片段**，例如：
`spec.requirements.branches[1].when.all[2]: unknown instance "site-c" for plugin "newapi"`

#### 1.2.7.6 与 `$onMissing` 的配合

绑定解析失败、实例不可达、属性不存在——统一都算 `missing`：

| `$onMissing` | 行为 | 适用 |
|---|---|---|
| `fail_closed`（默认） | 判为 false | "用户没绑定 QQ"不应被当作满足 |
| `fail_open` | 判为 true | 少见；仅用于"查不到也不该惩罚" |
| `skip` | 从父节点移除 | 与计数节点组合时**会告警**（分母变化） |
| `unknown` | 标记未知（仅 explain） | 用户进度展示 |

### 1.3 策略结构：两种形态

#### 形态 A · 单一表达式（简单场景）

```yaml
spec:
  match:                       # 分流：本策略适用于谁（同一套表达式语言）
    all:
      - eq: { user.status: "active" }

  requirements:
    expression:
      any:
        - $label: "QQ 等级 > 40，直接通过"
          gt: { fact.qq.level: 40 }
        - all:
            - gt:  { fact.qq.level: 20 }
            - lte: { fact.qq.level: 40 }
            - atLeast:
                n: 2
                of:
                  - { $label: "GitHub star ≥ 100", gte: { fact.github.total_stars: 100 } }
                  - { $label: "教育邮箱",          matches: { fact.email.domain: ["*.edu.cn"] } }
                  - { $label: "PR 指数 ≥ 60",      gte: { fact.llm.pr_score: 60 } }
                  - { $label: "有效邀请码",         gte: { fact.invite.used: 1 } }

  actions:
    onSatisfied:   [ { action: newapi-set-group:set_group, params: { group: "vip2" } } ]
    onUnsatisfied: [ { action: newapi-set-group:set_group, params: { group: "default" } } ]
```

#### 形态 B · 有序分支（if / else-if / else，★ 对应需求原话）

**每个分支可以有完全不同的条件，也可以有完全不同的动作。**

```yaml
spec:
  requirements:
    branches:
      # ── if ────────────────────────────────────────────────
      - id: qq_high
        label: "QQ 等级 > 40 级"
        when:
          gt: { fact.qq.level: 40 }
        outcome: satisfied
        actions:
          - { action: newapi-set-group:set_group, params: { group: "vip3" } }

      # ── else if ───────────────────────────────────────────
      - id: qq_mid
        label: "QQ 等级 20~40 级，需与其它渠道组合达成"
        when:
          all:
            - gt:  { fact.qq.level: 20 }
            - lte: { fact.qq.level: 40 }
            - atLeast:
                n: 2
                of:
                  - { $label: "GitHub 总 star ≥ 100", gte: { fact.github.total_stars: 100 } }
                  - { $label: "教育邮箱",              matches: { fact.email.domain: ["*.edu.cn", "*.edu"] } }
                  - { $label: "LLM 有效 PR 指数 ≥ 60", gte: { fact.llm.pr_score: 60 } }
                  - { $label: "有效邀请码",             gte: { fact.invite.used: 1 } }
        outcome: satisfied
        actions:
          - { action: newapi-set-group:set_group, params: { group: "vip2" } }

      # ── else if（再来一层不同条件）─────────────────────────
      - id: qq_low_but_contributor
        label: "QQ 等级不足，但贡献突出"
        when:
          all:
            - lte: { fact.qq.level: 20 }
            - gte: { fact.llm.pr_score: 85 }
            - gte: { fact.github.total_stars: 500 }
        outcome: satisfied
        actions:
          - { action: newapi-set-group:set_group, params: { group: "vip2" } }

    # ── else ─────────────────────────────────────────────────
    else:
      outcome: unsatisfied
      actions:
        - { action: newapi-set-group:set_group, params: { group: "default" } }
        - { action: checkin:revoke,    params: { scope: "daily" } }
```

**语义**：

| 项 | 规则 |
|---|---|
| 求值顺序 | 按数组顺序，**首个 `when` 为真**的分支生效（短路，后续 `when` 不再求值） |
| `else` | 所有分支都不匹配时生效；可省略（省略即 `outcome: unsatisfied` 且无动作） |
| 分支级动作 | 覆盖策略级 `actions`；未指定时回落到策略级 |
| 分支级参数 | 可覆盖 `gracePeriod` / `minChangeInterval` 等生命周期参数 |
| 与 `expression` 互斥 | 同一 `requirements` 内二者只能出现一个 |

> **形态 B 是形态 A 的超集**：单一表达式等价于"一个 `when` + else"。实现上只保留**分支求值器**，形态 A 在解析期被规整为单分支。

### 1.4 渠道自动推断（策略里不写 `channel`）

表达式里出现 `fact.<namespace>.*`，宿主自动完成依赖解析：

```
① 遍历表达式树，收集所有 fact 命名空间引用
     { gt: { fact.qq.level: 40 }, gte: { fact.github.total_stars: 100 } }
     → 引用集合 { "qq", "github" }

② 命名空间 → 插件
     查 ag_plugins.namespace（唯一索引）→ qq 插件、github 插件

③ enricher 的依赖递归展开（按 manifest 的 consumes 声明）
     fact.llm.pr_score  →  llm-review 插件 consumes ["github.pr_list"]
                        →  需要先有 github 插件的 pr_list 事实

④ 拓扑排序成 DAG，按需调用（命中未过期缓存则跳过）

⑤ 静态校验（发布时）：引用了未安装/未启用的命名空间 → 拒绝发布
```

**收益**：

- 策略里**完全没有渠道概念**，只有事实路径 → 换插件、加插件、改 namespace 都不用动策略；
- 天然支持"不同分支用不同渠道"——各分支引用各自的事实，宿主求并集；
- **未走到的分支不会触发采集**（配合短路求值），省外部调用。

> ⚠️ **短路与采集的交互**：`fast` 模式下，第一个分支命中后，后续分支引用的事实**不会被采集**。这正是想要的行为（省成本），但也意味着"用户进度展示"需要另一种模式（见 §3.5）。

### 1.5 求值引擎

两种模式，服务于不同目的：

| 模式 | 用途 | 短路 | 事实缺失 | 外部调用 |
|---|---|---|---|---|
| `fast` | **判定**（巡检、动作前置） | ✅ 是 | 按 `$onMissing` | 只采必需的 |
| `explain` | **展示**（用户进度、管理端诊断） | ❌ 否（全量） | 标记 `unknown` 而非失败 | **不触发新采集**，只用已有事实 |

```ts
async function evaluate(user, policy, mode: 'fast' | 'explain', ctx) {
  // 1. 分流匹配
  if (!matchesScope(user, policy.spec.match, mode, ctx)) return { skipped: true };

  // 2. 收集事实依赖 → 拓扑排序 → 按需采集（explain 模式只读缓存）
  const needed = collectFactRefs(policy.spec.requirements);
  const facts  = await ctx.plugins.ensureFacts(user, needed, { allowFetch: mode === 'fast' });

  // 3. 按分支求值（首个 when 为真即生效；explain 模式求完全部分支）
  const branchResults = [];
  for (const b of policy.spec.requirements.branches) {
    const r = evalExpr(b.when, { facts, user, mode });
    branchResults.push({ branch: b, ...r });
    if (r.passed && mode === 'fast') break;      // ← 短路
  }

  const matched = branchResults.find(r => r.passed) ?? policy.spec.requirements.else;
  return {
    outcome:  matched?.outcome ?? 'unsatisfied',
    matchedBranchId: matched?.id ?? null,
    tree:     buildExplainTree(branchResults),   // ← 完整结果树
    factsSnapshot: facts,
  };
}
```

**事实缺失的处理**（`$onMissing`，默认继承策略级 `onMissingFact`）：

| 值 | 语义 |
|---|---|
| `fail_closed`（默认） | 该节点判为 false —— 宁可暂不升级，也不误判 |
| `fail_open` | 该节点判为 true |
| `skip` | 该节点从父节点中移除（`all`/`any` 少一项参与计数） |
| `unknown` | 只用于 `explain` 模式：标记为未知，不影响判定 |

> `skip` 用在 `atLeast.n` 上要小心：分母变化可能造成"缺数据反而更容易通过"。引擎会在 `skip` 与计数节点组合时**发出告警**，建议改用 `fail_closed`。

**求值结果有四种**（不只是布尔）：

```ts
type Outcome = 'satisfied' | 'unsatisfied' | 'indeterminate' | 'error';
```

| 结果 | 触发 | 状态机行为 |
|---|---|---|
| `satisfied` | 判定通过 | 正常推进 |
| `unsatisfied` | 事实齐备且判定不通过 | 正常推进（可进入降级流程） |
| `indeterminate` | **关键事实 missing**（渠道故障 / 配额耗尽） | ❗ **保持原状态，不得降级** |
| `error` | 求值异常（除零 / 类型错 / 超时） | ❗ **保持原状态** + **告警管理员**（这是策略配置问题，不是数据问题） |

> `indeterminate` 与 `error` 都不推进状态机，但**运维语义不同**：前者是"外部不可用"，后者是"你的策略写错了"。发布前的静态校验应尽量把 `error` 拦截在配置阶段（类型检查、除零检测）。

#### 1.5.1 三种结果如何被【产出】（★ 引擎契约，此前只有数据库列）

> **警告**：本节的四态表曾只写进数据库枚举（02 §6.2），而**求值器根本不产出 `indeterminate`**——
> `evaluate()` 返回的是**分支上作者手写的 outcome 字段**，整条路径算不出第三态。列有了，没人写。

**产出规则（唯一权威）**：

```
① 节点级判定：
     事实齐备 → 按比较操作符求值 → passed / failed
     事实缺失或过期 → 按 `$onMissing`：
          fail_closed（默认） → failed
          fail_open           → passed
          skip                → 该节点从父节点移除
          unknown             → ★ indeterminate（向上传播）

② 三值真值表（★ 必须定义，否则 indeterminate 无法传播）：
     all  ：任一 indeterminate → indeterminate（除非已有 false 短路）
     any  ：任一 indeterminate → indeterminate（除非已有 true 短路）
     not  ：indeterminate → indeterminate
     atLeast/score ：「已达成的通过数」不足以判定、且至少一个 indeterminate → indeterminate

③ 分支级：
     按序求值 when：
        · 首个为 true  → 命中
        · 全部为 false → 走 else
        · ★ 无 true、且存在 indeterminate → 【整体 indeterminate，不走 else】
          （这是 H1 的关键：不能把"无法验证"降级成"不满足"）

④ 策略级：
     命中分支取该分支的 outcome；无命中且无 indeterminate → unsatisfied
```

**判定优先级**：`$required: true` 的事实缺失 → 直接 `indeterminate`（无论 `$onMissing` 写什么）；非关键事实缺失走 `$onMissing`。

| 保留属性 | 语义 |
|---|---|
| `$required` | ★ **该事实为关键事实**：缺失即整体 `indeterminate`，不得降级 |
| `$onMissing` | 非关键事实缺失时的行为（fail_closed 默认 / fail_open / skip / unknown） |
| `$label` `$ttl` `$weight` | 展示 / 新鲜度 / 权重 |

**结果树节点必须携带状态**：`state: passed | failed | missing | indeterminate`（此前只有 `passed: boolean`，无处表达 missing）。

### 1.8 策略合并与阶梯

```
按 priority 升序遍历命中的策略：
  - collision=exclusive    → 首个 satisfied 即停止，采用它的动作
  - collision=additive     → 所有 satisfied 的动作全部执行（动作层做冲突检测）
  - collision=highest_tier → 全部求值，取 tier 最大者
阶梯：requiresTier 未满足的策略直接跳过（不评估，省成本）
```

**动作冲突检测**：若两条策略对同一用户给出不同的 `newapi-set-group:set_group`，取 `tier` 高者并写审计告警。

### 1.9 从旧格式迁移

旧 `mode + items` 到表达式的机械映射（提供 `policies:migrate` 工具自动完成）：

| 旧写法 | 新表达式 |
|---|---|
| `mode: any` | `{ any: [item1.assert, item2.assert, ...] }` |
| `mode: all` | `{ all: [...] }` |
| `mode: quorum, quorum: 2` | `{ atLeast: { n: 2, of: [...] } }` |
| `mode: weighted, threshold: T` | `{ score: { threshold: T, of: [{weight, expr}, ...] } }` |
| `item.required: true` | 提到外层：`{ all: [ ...required, { atLeast: {...} } ] }` |
| `item.channel: qq` | **删除**（由 `fact.qq.*` 自动推断） |
| `item.title` | `$label` |
| `item.ttl` | `$ttl` |

> 迁移后**不再保留两套求值逻辑**——引擎只有分支求值器一种实现。

### 1.10 求值器的安全约束

| 约束 | 说明 |
|---|---|
| **无代码执行** | 表达式由受限解释器求值，**不使用 `eval` / `new Function`**；无循环、无赋值、无函数定义 |
| **可判定终止** | 结构是有限树，天然终止；嵌套深度上限 32、节点总数上限 2000 |
| **路径只读** | `fact.*` / `user.*` / `binding.*` 仅可读，不可写 |
| **无副作用** | 求值过程不产生任何外部调用（采集由依赖解析阶段单独完成） |
| **正则安全** | `regex` 使用 RE2 语义引擎（无回溯爆炸）；模式长度与执行时间受限 |
| **资源上限** | 单次求值 CPU 时间上限（默认 50ms），超时判为 error 并告警 |
