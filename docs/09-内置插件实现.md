# 09 · 内置插件实现

> 本文档是**可照着写代码**的实现说明。设计规范见 [03-插件体系 §2](./03-插件体系.md)，这里只讲**每个内置插件具体怎么实现**。
>
> 覆盖：`newapi-provider`（provider）、`newapi-*`（action 组）、`github`（channel，declarative）。

---

## 1. 通用规范

### 1.1 插件目录结构

```
plugins/builtin/<plugin-id>/
├── manifest.yaml          # 必需：契约声明
├── plugin.mjs             # runtime != declarative 时必需：入口
├── README.md              # 建议：配置说明与权限理由
└── tests/                 # 建议：契约一致性测试
    ├── manifest.test.ts
    └── collect.test.ts
```

**declarative 插件没有 `plugin.mjs`**——全部逻辑在 `manifest.yaml` 里声明。`github` 就是这类。

### 1.2 manifest 速查

| 字段 | 必需 | 说明 |
|---|---|---|
| `apiVersion` | ✅ | 固定 `gate.plugin/v1` |
| `kind` | ✅ | `provider` / `channel` / `enricher` / `action` / `identity` / `feature` |
| `id` | ✅ | 全局唯一；**与内置插件冲突的外置插件会被拒绝安装** |
| `version` | ✅ | 语义化版本 |
| `runtime` | ✅ | `declarative` / `process` / `container` / `in-process` |
| `engines.gate` | ✅ | 宿主版本区间，不满足则拒绝安装 |
| `config.scope` | ✅ | `developer`（推荐）/ `site` |
| `instances.mode` | ✅ | `singleton`（默认）/ `multi` |
| `permissions` | ✅ | 逐项授予；运行期强制校验 |
| `configSchema` | ✅ | JSON Schema → 自动生成配置表单 |
| `factSchema` / `subjectSchema` | 按 kind | 产出契约 → 策略编辑器路径补全与静态校验 |
| `binding` | channel/provider | 绑定键、OAuth 配置 |
| `collect` | declarative | 采集声明 |
| `endpoints` | 可选 | 对外 HTTP 端点 |
| `ui` | 可选 | 前端贡献 |

### 1.3 开发与调试

```bash
# 本地加载（不安装，直接指向源码目录）
gate plugin dev ./plugins/builtin/github

# 校验 manifest（含 schema、权限、engines）
gate plugin validate ./plugins/builtin/github

# 用样例主体跑一次采集，打印将写入的事实
gate plugin test ./plugins/builtin/github --subject ./fixtures/user.json

# 端到端：跑一次求值
gate policy simulate contributor-tier2 --user <id> --facts ./fixtures/facts.json
```

### 1.4 契约一致性测试（内置插件必做）

因为内置插件与第三方**走完全相同的契约**，所以它们就是契约的参考实现与回归测试：

| 测试 | 断言 |
|---|---|
| manifest 校验 | `gate plugin validate` 通过；`factSchema` 与 `collect.extract` 的 `as` 字段**一一对应** |
| 事实 schema 一致 | 采集产出的样例事实能通过 `factSchema` 校验 |
| 权限最小化 | 声明的权限**逐条**有 README 说明理由；无多余权限 |
| 静态校验联动 | 策略里写错 `fact.` 路径时，能被精确定位并拒绝发布 |
| 崩溃隔离 | 采集抛错 / 超时不影响宿主与其他插件 |

## 2. `newapi-provider`（provider 插件）

### 2.1 职责

把 new-api 抽象成平台能理解的**主体目录**：列出用户、按 ID 取用户、按身份键查用户，并把 new-api 的用户字段**原样装进属性袋**。

**它不做判断**——"什么算优质用户"由策略决定，与插件无关。

### 2.2 manifest

```yaml
apiVersion: gate.plugin/v1
kind: provider
id: newapi-provider
name: new-api 主体目录
version: 1.0.0
runtime: process
entry: ./plugin.mjs

engines: { gate: ">=1.0.0 <2.0.0" }

config:
  scope: site              # ★ 每个站点指向不同的 new-api
  instances: { mode: singleton }

permissions:
  - "secrets:read:newapi.pat"          # 管理员 PAT（只读用户目录 + 写用户属性）
  - "http:egress:api.example.com"      # 仅目标域名
  - "storage:write:self"

configSchema:
  type: object
  properties:
    baseUrl:  { type: string, format: uri, title: "new-api 地址" }
    patRef:   { type: string, default: "newapi.pat", title: "管理员 PAT 的密钥名" }
    pageSize: { type: integer, default: 100, maximum: 100, title: "对账分页大小" }
  required: [baseUrl]

# ★ 主体属性契约 —— 策略里 subject:newapi.<字段> 的可选范围
subjectSchema:
  type: object
  properties:
    username:      { type: string }
    display_name:  { type: string }
    email:         { type: string }
    group:         { type: string,  title: "用户分组" }
    status:        { type: integer, title: "1=启用 2=禁用" }
    role:          { type: integer }
    quota:         { type: integer }
    used_quota:    { type: integer }
    request_count: { type: integer }
    aff_code:      { type: string }
    oidc_id:       { type: string,  title: "OIDC 主体标识（模式 1 对齐键）" }

# ★ 绑定键：平台用户 → 该站点下的 new-api 用户
binding:
  keys:
    - { kind: oidc,      ref: "platform:developer", claim: sub, unique: true }
    - { kind: oidc,      ref: "platform:enduser",   claim: sub, unique: true }
    - { kind: attribute, path: email, unique: true, requireVerified: true }
    - { kind: manual }
  autoLink: true
  conflictPolicy: manual_review

provider:
  capabilities:
    list: true
    findByIdentity: false      # ★ new-api 不支持按 oidc_id 检索
    update: true
    create: true
  # 参与指纹计算的字段：只有这些变了才触发下游
  watch: [username, display_name, email, group, status, role, oidc_id]
```

### 2.3 `listSubjects` 实现

```ts
async listSubjects(cursor: string | null, limit: number) {
  const cfg = ctx.host.config.get();
  const pat = await ctx.host.secrets.get(cfg.patRef);

  // new-api 是 LIMIT/OFFSET 分页，没有 sinceId 过滤
  const page = cursor ? Number(cursor) : 1;
  const res = await ctx.host.http.request({
    method: 'GET',
    url: `${cfg.baseUrl}/api/user/?p=${page}&page_size=${limit}&sort_by=id&sort_order=asc`,
    headers: { Authorization: `Bearer ${pat}`, Accept: 'application/json' },
  });

  const body = res.json();
  if (!body?.success) throw new Error(`newapi list failed: ${body?.message}`);

  const items = body.data?.items ?? [];
  const total = body.data?.total ?? 0;
  const seen  = page * limit;

  return {
    subjects: items.map(toSubject),
    nextCursor: seen < total ? String(page + 1) : null,   // null = 对账结束
  };
}

/** new-api 用户对象 → 通用 ExternalSubject */
function toSubject(u: any) {
  return {
    externalId: String(u.id),
    displayName: u.display_name || u.username,
    email: u.email || undefined,
    attributes: {                       // ★ 原样装袋，核心不解释
      username:      u.username,
      display_name:  u.display_name,
      email:         u.email,
      group:         u.group,
      status:        u.status,
      role:          u.role,
      quota:         u.quota,
      used_quota:    u.used_quota,
      request_count: u.request_count,
      aff_code:      u.aff_code,
      oidc_id:       u.oidc_id,
    },
    raw: redact(u),                     // 脱敏：剔除 access_token / password
  };
}

function redact(u: any) {
  const { access_token, password, ...rest } = u;
  return rest;
}
```

### 2.4 `getSubject` / `findSubject`

```ts
async getSubject(externalId: string) {
  const res = await http.get(`${cfg.baseUrl}/api/user/${externalId}`);
  if (!res.ok) return null;
  const body = res.json();
  return body?.success ? toSubject(body.data) : null;
}

/** findSubject：new-api 不支持按 oidc_id 检索，故只能声明 false
 *  宿主会因此走"本地镜像表 + 绑定索引"的快路径 */
async findSubject(by: { key: string; value: string }) {
  if (by.key === 'email') {
    const res = await http.get(`${cfg.baseUrl}/api/user/search?keyword=${encodeURIComponent(by.value)}`);
    const items = res.json()?.data?.items ?? [];
    const hit = items.filter((u: any) => u.email?.toLowerCase() === by.value.toLowerCase());
    return hit.length === 1 ? toSubject(hit[0]) : null;   // ★ 非唯一返回 null，绝不猜
  }
  return null;   // 其他键不支持
}
```

### 2.5 能力探测：声明 vs 实测

```ts
async probe() {
  return {
    list:           await tryGet('/api/user/?p=1&page_size=1'),
    findByIdentity: false,     // 源码确认：SearchUsers 只匹配 username/email/display_name/id
    update:         await tryGet('/api/user/1'),   // 能读即认为有写权限（真正写时再校验）
    create:         false,
  };
}
```

宿主每个全量周期比对 `declared` 与 `actual`，**不一致必须告警**（通常是 new-api 升级导致）。

### 2.6 实现坑点（源码调研结论）

| 坑 | 说明 | 应对 |
|---|---|---|
| **无 `sinceId` 过滤** | `GetAllUsers` 只有 `LIMIT/OFFSET` | 走"首页探测 + 周期全量"；**不要假装有真增量** |
| **不能按 `oidc_id` 检索** | `SearchUsers` 的 LIKE 只覆盖 id/username/email/display_name | `findByIdentity: false`；靠本地镜像表建索引 |
| **`PUT /api/user/` 需完整对象** | 缺字段会被覆盖 | 必须先 `GET` 再 `PUT`，回填 username/display_name/remark |
| **绝不能带 `password`** | 带了会**重设密码** | 请求体显式剔除 |
| **`remark` 全量覆盖** | 用 remark 存自己的标记会覆盖管理员备注 | **绝不写 remark**，回填原值 |
| **改 `group` 会踢人** | `EditWithTx` 中 group 变化 → bump `auth_version` → `RevokeAllUserSessions` | 幂等（值不变不写）+ 最小变更间隔 + 宽限期 |
| **role 字段校验** | `PUT` 时 role 必须为 0 或与原值相同 | 请求体**不带 role** |

### 2.7 对账性能

10 万用户按 `page_size=100` 需 1000 次请求。宿主的分页间退避（默认 50ms）+ 并发 1（同一 provider 串行），实测约 1 分钟。若 new-api 压力敏感，调大 `pageSize` 或拉长对账周期。

## 3. `newapi-*` action 插件组

### 3.1 `newapi-set-group`

```yaml
apiVersion: gate.plugin/v1
kind: action
id: newapi-set-group
version: 1.0.0
runtime: process
config: { scope: site, instances: { mode: singleton } }
permissions:
  - "secrets:read:newapi.pat"
  - "http:egress:api.example.com"
  - "subject:read:self"        # 读当前分组以做幂等比对
```

**实现要点**：

```ts
async execute({ subject, params }) {
  const target = params.group;
  const fresh  = await provider.getSubject(subject.externalId);

  // ① 幂等：值不变直接跳过（避免无谓地踢用户下线）
  if (fresh.attributes.group === target) {
    return { skipped: true, reason: 'no_change' };
  }

  // ② read-modify-write：必须回填完整对象，且绝不能带 password / role
  const payload = {
    id:           Number(fresh.externalId),
    username:     fresh.attributes.username,
    display_name: fresh.attributes.display_name,
    group:        target,
    remark:       fresh.raw?.remark ?? '',   // ★ 回填原值，绝不写自己的标记
  };

  const res = await http.request({
    method: 'PUT',
    url: `${cfg.baseUrl}/api/user/`,
    headers: { Authorization: `Bearer ${pat}`, 'Content-Type': 'application/json' },
    body: payload,
  });

  if (!res.ok) {
    // 4xx 不重试（配置/权限问题）；5xx 由宿主退避重试
    throw new ActionError(res.status >= 500 ? 'retryable' : 'fatal', res.text());
  }
  return { skipped: false, from: fresh.attributes.group, to: target };
}
```

> **用户级锁**：宿主对同一 `subject` 的写操作串行化（`ctx.host.locks.withSubjectLock`），避免并发 read-modify-write 互相覆盖。

### 3.2 `newapi-add-quota`

```ts
async execute({ subject, params, idempotencyKey }) {
  // 幂等键由宿主生成（05 §3.0.1 冻结公式，actionSeq），重试复用同一键

  });
  if (!res.ok) throw new ActionError(res.status >= 500 ? 'retryable' : 'fatal', res.text());
  return { granted: params.value };
}
```

## 4. `github`（channel 插件，declarative）

### 4.1 职责与产出

采集 GitHub 账号的公开指标，产出 `fact:github.*`。

**不采集 PR 列表**——那是 `github-pr-fetch` 的事；PR 质量评分由 `llm-review` 这个 enricher 完成（职责分离，见 §5.3）。

### 4.2 manifest（完整，零代码）

```yaml
apiVersion: gate.plugin/v1
kind: channel
id: github
name: GitHub 账户指标
version: 1.0.0
runtime: declarative          # ★ 纯声明，无 plugin.mjs
engines: { gate: ">=1.0.0 <2.0.0" }

config:
  scope: developer            # ★ 凭据是开发者级的，所有站点共享一份
  instances: { mode: singleton }

permissions:
  - "secrets:read:github.token"
  - "http:egress:api.github.com"
  - "cache:write:self"

configSchema:
  type: object
  properties:
    totalStarsMode:
      type: string
      enum: [top100, exact]
      default: top100
      title: 总 star 统计口径
      description: top100 = 只统计最热门的 100 个仓库（1 次 API 调用）；exact = 精确遍历（更慢、更耗配额）
    cacheTtl: { type: string, default: "24h", title: 事实有效期 }
    minRepoStars: { type: integer, default: 0, title: "只统计 star 数 ≥ 此值的仓库" }
  required: [totalStarsMode]

factSchema:
  type: object
  properties:
    created_at:          { type: string, format: date-time }
    account_age_days:    { type: integer, title: 账号年龄（天） }
    public_repos:        { type: integer }
    followers:           { type: integer }
    total_stars:         { type: integer, title: 总 star 数 }
    organizations:       { type: array, items: { type: string } }
    has_verified_email:  { type: boolean }

# ── OAuth 绑定（用户授权一次，之后长期复用）─────────────────
binding:
  oauth2:
    authorizationEndpoint: https://github.com/login/oauth/authorize
    tokenEndpoint:         https://github.com/login/oauth/access_token
    scopes: [read:user, user:email]           # ★ 最小权限：不申请 repo
    clientIdRef:     github.client_id
    clientSecretRef: github.client_secret
    userInfoRequest: { method: GET, url: https://api.github.com/user }
    externalIdPath:   "$.id"                  # ★ 用数字 id，不用 login（可改名）
    externalNamePath: "$.login"
  onRebind: refresh                            # 重新绑定时刷新事实

# ── 采集声明 ────────────────────────────────────────────
collect:
  request:
    method: POST
    url: https://api.github.com/graphql
    headers:
      Authorization: "Bearer {{ secrets.github.token }}"
      Accept: application/json
      User-Agent: "access-gate/1.0"
    body:
      query: |
        query($login: String!, $first: Int!) {
          user(login: $login) {
            databaseId
            createdAt
            isEmailVerified
            followers { totalCount }
            repositories(ownerAffiliations: OWNER, isFork: false,
                         first: $first, orderBy: {field: STARGAZERS, direction: DESC}) {
              totalCount
              nodes { stargazerCount }
            }
            organizations(first: 10) { nodes { login } }
          }
        }
      variables:
        login: "{{ binding.externalName }}"
        first: "{{ config.totalStarsMode == 'exact' ? 100 : 100 }}"   # 见 §4.4 说明

  extract:
    - { path: "$.data.user.createdAt",                            as: created_at }
    - { path: "$.data.user.followers.totalCount",                 as: followers }
    - { path: "$.data.user.repositories.totalCount",              as: public_repos }
    - { path: "$.data.user.isEmailVerified",                      as: has_verified_email }
    - { path: "$.data.user.organizations.nodes[*].login",         as: organizations }
    - { path: "$.data.user.repositories.nodes[*].stargazerCount", as: total_stars, transform: sum }

  derive:
    - { as: account_age_days, expr: "days_between(created_at, now())" }

  # 上游错误 → 语义化结果（而不是笼统失败）
  errors:
    - { match: { status: 401 }, as: 'unbound',  message: "GitHub token 失效，请重新绑定" }
    - { match: { status: 403, bodyContains: "rate limit" }, as: 'rate_limited' }
    - { match: { status: 404 }, as: 'not_found', message: "GitHub 账号不存在或已改名" }
```

### 4.3 提取与派生

| 阶段 | 作用 |
|---|---|
| `extract` | 从响应按 JSONPath 取值，`transform` 支持 `sum`/`avg`/`count`/`first`/`last`/`min`/`max`/`join`/`len` |
| `derive` | 派生字段（受限表达式：日期差、四则、条件），**避免在策略里写时间函数** |

`account_age_days` 在插件层算好，策略里就能直接写 `gte: { "fact:github.account_age_days": 730 }`。

### 4.4 两种 star 口径（必须在 UI 上说清）

| 口径 | 实现 | 代价 | 准确度 |
|---|---|---|---|
| `top100`（默认） | 一次 GraphQL，取最热门 100 个仓库的 star 求和 | 1 次调用 | 近似（对仓库数 > 100 的用户会低估） |
| `exact` | 分页遍历全部仓库 | 数十次调用 | 精确 |

**默认 `top100`**：绝大多数用户仓库数远小于 100，误差可忽略；而 `exact` 会迅速耗尽 API 配额。

### 4.5 配额与缓存

| 手段 | 参数 |
|---|---|
| 事实 TTL | `cacheTtl: 24h`——24 小时内不重复采集 |
| 令牌桶 | 宿主 `QuotaGuard`（GitHub 5000/h） |
| 退避 | 命中 `rate_limited` → 按 `X-RateLimit-Reset` 退避，返回 `missing` |
| 分级触发 | 策略里没引用 `fact:github.*` 时**完全不调用** |

### 4.6 与策略的配合

```yaml
# 策略里不写 channel，只写事实路径
requirements:
  branches:
    - id: gh_strong
      when:
        all:
          - { gte: { "fact:github.total_stars": 100 } }
          - { gte: { "fact:github.account_age_days": 365 } }
      outcome: satisfied
      actions: [ { action: "newapi-set-group:set_group", params: { group: "vip2" } } ]
```

宿主据 `fact:github.*` 反查插件 → 该插件 `config.scope: developer` → 取该开发者的配置 → 调用采集。

## 5. 其他内置插件（要点速览）

### 5.1 `email-domain`（channel，declarative）

零外部调用。产 `fact:email.domain` / `is_edu` / `matched_rule`。
配置：`allowDomains` / `denyDomains`（支持 `*.edu.cn` 通配、后缀、正则），`requireVerified: true`。

### 5.2 `invite-code`（channel，declarative）

产 `fact:invite.used` / `code` / `depth`。纯本地查询，无外部依赖。

### 5.3 `llm-review`（enricher，declarative）

**消费任意数组事实，产出评分**——不绑定 GitHub：

```yaml
kind: enricher
id: llm-review
config: { scope: developer, instances: { mode: multi } }   # 可配多个供应商
permissions: ["llm:invoke", "cache:write:self"]
consumes: ["github.pr_list", "gitlab.mr_list"]             # ★ 声明消费的字段
produces:
  namespace: llm
  factSchema:
    properties:
      pr_score:           { type: number, minimum: 0, maximum: 100 }
      pr_count_effective: { type: integer }
      reason:             { type: string }
configSchema:
  properties:
    promptVersion: { type: string, default: v3 }
    batchSize:     { type: integer, default: 5 }
    maxItems:      { type: integer, default: 30 }
    rubric:        { type: object }        # 评分细则权重
    model:         { type: string, default: gpt-4o-mini }
```

**成本控制**：走宿主 `llm.invoke` → 统一预算 / 缓存 / 限流；插件**无法绕过**（网络白名单挡住自建客户端）。

### 5.4 `checkin`（feature）

**先查策略资格，再放行**：

```
用户点签到
  → 宿主注入 policy:read:self 权限的上下文
  → 检查该站点配置的 requirePolicy 是否处于 granted
     ├─ 否 → 拒绝并返回原因（"需先通过贡献者认证"）
     └─ 是 → 写 ag_checkin_records → 调 newapi-add-quota:add_quota
```

含完整声明式 UI（nav + page + slot），见 06 文档 §10.7。

### 5.5 `bot-bridge`（channel + endpoints）

跨项目协同的参考实现：注册 `/verify/start`、`/verify/poll`、`/bind/complete` 三个端点 + 订阅 `policy.granted` 事件。见 03 文档 §1.14.2。

## 6. 实现顺序建议

| 阶段 | 先做哪个 | 理由 |
|---|---|---|
| M2 | `email-domain`、`invite-code` | **零外部依赖**，用来验证插件契约与宿主 API 是否够用 |
| M2 | `newapi-provider` | 第一个 provider，验证主体抽象与对账器 |
| M4 | `newapi-set-group` / `add-quota` | 动作链路打通（幂等、防抖、用户级锁） |
| M2/M5 | `github` | 验证 declarative 解释器与 OAuth 绑定 |
| M5 | `llm-review` | 验证 enricher 与 LLM 网关 |
| M2 | `checkin` | 验证 feature 插件与 UI 贡献 |

**先用零依赖插件验证契约，再接外部系统**——这样契约问题会在最容易调试的时候暴露。
