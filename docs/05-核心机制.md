## 1. 身份对齐（Identity Alignment）

### 1.1 目标

把「一个 OIDC 会话」映射到「一个 new-api 用户」，且这个映射**稳定、可审计、可人工纠正**。

### 1.2 对齐的三种来源（按可信度排序）

| 优先级 | 来源 | 键 | 可信度 | 说明 |
|---|---|---|---|---|
| 1 | **同步对账** | `users.oidc_id` ↔ new-api `users.oidc_id` | 高 | 模式 1；由 new-api 官方登录流程写入 |
| 2 | **OAuth 绑定** | 本平台 `sub` ↔ `user_oauth_bindings.provider_user_id` | 高 | 模式 2；由 new-api 的 OAuth 回调写入 |
| 3 | **邮箱匹配** | 平台 `email` ↔ new-api `email` | 中 | 仅当 `email_verified=true` 且 new-api 侧邮箱唯一，**且需用户确认** |
| 4 | **管理员手工绑定** | 人工指定 | 高（人） | 兜底；写审计 |

> **设计原则：宁可不自动，不可错对齐。** 因为对齐错了 = 把别人的分组改了 = 资损。

### 1.3 对齐算法（伪代码）

```ts
async function resolveIdentity(ctx: SessionCtx): Promise<AlignmentResult> {
  const sub = ctx.oidcClaims.sub;               // 模式1：中间 OIDC 的 sub
                                                // 模式2：本平台 user.id

  // 路径 1：本地索引（热路径，O(1)）
  const cached = await identities.find({ provider: ctx.provider, providerUserId: sub });
  if (cached?.subjectRef && await isStillValid(cached)) {
    return { status: 'aligned', subjectRef: cached.subjectRef, via: 'cache' };
  }

  // 路径 2：直查下游（若该 provider 支持按身份键查）
  const provider = await ctx.providers.forSite();     // ★ 当前站点的主体目录，非具体系统
  if (provider.capabilities.findByIdentity) {
    const hit = await provider.findSubject({ key: 'oidc_id', value: sub });
    if (hit) return persistAndReturn(hit, 'direct');
  }

  // 路径 3：本地镜像表（全量对账产物）
  const mirrored = await newapiUsers.findByOidcId(sub);
  if (mirrored) return persistAndReturn(mirrored, 'mirror');

  // 路径 4：邮箱兜底（需 email_verified + 唯一性 + 用户确认）
  const emailHit = await tryEmailFallback(ctx);
  if (emailHit.kind === 'unique') return { status: 'needs_confirm', candidate: emailHit.user };
  if (emailHit.kind === 'ambiguous') return { status: 'manual_review', reason: 'email_conflict' };

  // 路径 5：未对齐 → 引导绑定
  return { status: 'unlinked', guidance: buildBindingGuidance(ctx) };
}
```

### 1.4 未对齐时的引导（两种模式不同）

**模式 1（new-api 已有 OIDC）**：
```
用户在平台登录成功，但平台在 new-api 找不到对应 oidc_id
        │
        ├─ new-api 侧存在同邮箱用户 → 提示"检测到你已有 new-api 账号，
        │     请前往 new-api 使用 OIDC 登录一次以完成绑定" → 跳转 {newapi}/login
        │
        └─ new-api 侧无此用户 → 提示"请先在 new-api 注册/登录" → 跳转 {newapi}/register
                                  完成后回到平台，下一轮对账自动对齐
```

**模式 2（平台是 IdP）**：
```
用户在平台注册（邮箱通过白/黑名单校验）
        │
        ├─ 已有 new-api 账号 → 在 new-api 点"用 access-gate 登录"
        │     → new-api 写入 user_oauth_bindings → 对账后对齐
        │
        └─ 无 new-api 账号 → new-api 的 OAuth 首登会自动建号（new-api 原生行为）
              → 同样写入绑定 → 对齐
```

### 1.5 冲突与异常处理

| 场景 | 处理 |
|---|---|
| 一个 new-api 用户被两个平台用户争抢 | 先到先得 + 告警；后者进入 `manual_review`，管理员裁决 |
| 平台用户换绑 GitHub | 旧 GitHub 身份标记 `revoked`，事实重算，触发重新评估 |
| new-api 侧 `oidc_id` 变更（换了 IdP 账号） | 对账发现 `fingerprint` 变化 → 旧 identity 置 `revoked` + 告警 |
| new-api 用户被删除 | 镜像表逻辑删除 → 平台用户转 `blocked`（不再发动作） |
| new-api 不可达 | 对齐走缓存；动作进入排队（`planned`），恢复后重放 |

## 2. 生命周期状态机

### 2.1 状态与迁移

```ts
type State = 'unknown' | 'evaluating' | 'satisfied' | 'granted' | 'at_risk' | 'revoked' | 'blocked';
```

| 当前 | 事件 | 下一个 | 动作 |
|---|---|---|---|
| `unknown` | 首次评估 **satisfied** | `satisfied` | 执行 onSatisfied |
| `unknown` | 首次评估 unsatisfied | `unknown` | 无（记录） |
| `satisfied` | 动作全部成功 | `granted` | 记录 `appliedActions` |
| `granted` | 周期评估 satisfied | `granted` | 无（幂等跳过） |
| `granted` | 周期评估 **unsatisfied**（事实完整且新鲜） | `at_risk` | 记 `graceUntil = now + gracePeriod`，**不发动作** |
| **任意** | **评估为 `indeterminate`**（关键事实 missing / 渠道故障） | **保持原状态** | ❗ **不推进状态机**；记告警；提高该主体的巡检频率 |
| `at_risk` | 宽限期内恢复 | `granted` | 取消 `graceUntil` |
| `at_risk` | 宽限期到期且**仍为 unsatisfied** | `revoked` | 执行 onUnsatisfied |
| `at_risk` | 宽限期到期但为 **indeterminate** | `at_risk`（延长） | ❗ **延长宽限期**并告警，**不降级** |
| `revoked` | 重新满足 | `satisfied` | 执行 onSatisfied（受 `minChangeInterval` 限制） |
| 任意 | 连续失败 ≥ `maxFailStreak` | `blocked` | 停止自动判定 + 告警，等人工处理 |
| 任意 | 主体被删 / 禁用 | `blocked` | 不执行任何动作 |

#### 2.1.1 三种评估结果（★ 降级的证据要求高于升级）

```ts
type Outcome = 'satisfied' | 'unsatisfied' | 'indeterminate';
```

| 结果 | 定义 | 允许的迁移 |
|---|---|---|
| `satisfied` | 必需事实齐备且判定通过 | → `satisfied` / `granted` |
| `unsatisfied` | **必需事实齐备**且判定不通过 | → `at_risk` → `revoked` |
| **`indeterminate`** | **有关键事实 missing**（渠道故障 / 配额耗尽 / 事实过期且无法刷新） | ❗ **只能保持原状态**，**不得降级** |

**核心原则：降级的证据要求高于升级。**

- **升级**（给权限）：缺数据时保守（`fail_closed`，不升级）——用户损失小，可等；
- **降级**（收权限）：**必须有明确的、新鲜的不满足证据**——否则一次第三方故障就会造成大规模误伤。

**为什么**：GitHub 挂 3 天 → 若把"无法验证"当成"不满足"，所有依赖 GitHub 条件的主体会在宽限期后**集体被降级并踢下线**。
这不是"用户不再满足"，而是"我们无法验证"——**两者必须走不同分支**。

**判定为 `indeterminate` 的条件**（满足任一）：

1. 策略中标记为关键的事实（`$required: true`）缺失或过期无法刷新；
2. 提供该事实的插件处于 `error` / 崩溃 / 配额耗尽状态；
3. 采集返回 `rate_limited` 且无法在宽限期内恢复。

**运维表现**：连续 `indeterminate` → 管理端告警"渠道 X 已不可信 N 小时，影响 M 个主体"，而非静默降级。

#### 2.1.1.1 ★ 辩论裁决：indeterminate 必须拆回本义

> **辩题**：H1「indeterminate 不降级」是否产生了更坏的问题？
> **裁决**：**反方胜**——H1 的**原则**成立（降级的证据要求高于升级），但 **实现**错了。
> 错误在于把 `indeterminate` 定义为「**有关键事实 missing**」，于是它成了一个**垃圾桶**。

| | 原实现 | 裁决后 |
|---|---|---|
| **`indeterminate` 的域** | **全部 missing** | **仅「外部不可用且不可归因于主体」** |
| **分诊责任** | 策略作者（`$required` 开关） | **插件边界**（那里已有 owner 信息） |
| **同一 401 的结局** | 标 `$required` → **永久冻结**；未标 → 72h 后 **revoked** | **两版本相同** = `unbound` → 用户可见「请重新绑定」 |

**关键证据**：`09 §4.2` 的插件边界**已经**区分了三类根因（401→unbound、403→rate_limited、404→not_found），
但 `collect.errors` 的映射**没有任何下游消费定义**——**信息在边界被丢弃**，分诊开关却落在了策略作者手里。

**修正：按 owner 分流（不再依赖 `$required`）**

| 根因 | owner | 处置 |
|---|---|---|
| `unbound`（401，用户可自愈） | **user** | → 待绑定队列 + **用户侧**提示「请重新绑定」（复用 `blocked_unbound` 四件套） |
| `not_found`（404） | subject | → `unsatisfied` |
| `rate_limited` / `quota` | **platform** | → 独立归因 `throttled`（**不复用** indeterminate 的告警文案） |
| 外部服务不可用 | platform | → `indeterminate`（**本义**） |
| schema / 类型漂移 | plugin | → `error` |

**★ 对称化**：H1 只约束了降级方向，但 `fail_open` 允许 missing → passed，
即**渠道故障时用户被升级**——同样违反 H1 原则。必须补上升级方向的对称约束。

**CI 黄金对照实验**（可执行验收）

```
同一主体、同一策略两版本：
  P1: $required: true
  P2: 默认 fail_closed
注入 401 / 403 / 404，断言：
  401 → 两版本结局相同且 = unbound（用户可见「请重新绑定」）
  403 → 同为 indeterminate
  404 → 同为 unsatisfied
通过条件 = 结局与 $required 解耦
```

**反向回归**：07 §5 场景 D（断开 new-api）与 10 文档 T3（30 天后 GitHub 故障）**必须仍走 indeterminate**——
若被降级，说明**拆过头**。

**方法论**：这是第 5 代「声称必须能执行」的一次真实应用——裁决的验收条件是可跑的断言，而非措辞。

#### 2.1.2 ★ H1 的「后半个修正」：静默保持必须配主动外部信号

> **第 8 代推演的结论**：H1 把「错降级」改成了「静默保持」——**语义上更安全，但运维上更危险**：
> **系统可以健康地、正确地、稳定地永远不工作。**
>
> 判据：若一个 `indeterminate` 状态能持续 30 天而不产生任何人类可见的信号，则 H1 的修正**只完成了一半**。

任何把「不动作」作为正确行为的机制，都必须配一个**主动、周期重复、带持续时长**的外部信号：

| 要求 | 内容 |
|---|---|
| **指标** | `gate_indeterminate_subjects{siteId,provider,instanceKey}` 与 `gate_indeterminate_duration_seconds`（直接读 `indeterminateSince`；**仅有列不够，必须同时有查询与指标两条路径**） |
| **告警** | **状态型告警，周期重复**（默认每 1h 重申一次，携带「已持续 N 小时」）——而非事件型「只发一次」 |
| **审计** | `alert.raised` / `alert.acknowledged` / `alert.silenced`（静默**必须带期限且到期自动恢复**） |
| **界面** | 管理端「待处理事项」卡片与告警码**一一对应**，且按**站点**过滤 |

**通用条款**：凡设计中存在「不动作 / 跳过 / 保持原状」的分支，必须同时给出 ① 它的指标 ② 它的告警重复周期 ③ 它的诊断入口。缺任一项，该分支即为「静默黑洞」。

`one_shot` 模式：`granted` 后**只走自环**，永不迁移到 `at_risk`/`revoked`。
`manual` 模式：`satisfied` 后停在 `satisfied` 并产生一条待审批；管理员批准后才 `granted`。
`periodic` 模式：`granted` 时设 `nextCheckAt = now + periodicRevalidate`，到期**强制重新采集事实**（忽略缓存 TTL）。

#### 2.1.4 ★ 第二条启动期不变量：授权有效期 ≤ 最短保留期（第 7 代发现）

> **问题**：保留期参数彼此独立，没有任何不变量把「回滚可达性」与「授权时长」绑定。
> `one_shot` 策略是**永久授权**，但其版本（keepVersions: 3）、评估（90 天）、审计（180 天）、动作流水（30 天）**都有保质期**。
> 后果：一个 3 年前的永久授权，**既无法复现、也无法解释、更无法回滚**。

**修正**：建立与 H3 配额不等式并列的**第二条启动期不变量**——

```
maxGrantLifetime  ≤  min(策略版本保留期, 评估保留期, 审计保留期, 动作流水保留期)
```

| 要求 | 内容 |
|---|---|
| **启动校验** | 配置不满足该不等式 → **启动告警**（与 H3 同手法） |
| **one_shot 必须声明** | `maxLifetime`（默认不小于审计保留期），否则**发布校验拒绝** |
| **清理任务必须跳过** | `keepVersions` 清理时**跳过**仍被 `state IN ('granted','satisfied')` 引用到的版本（否则状态指向被删版本 = 悬空引用） |

### 2.2 幂等与防抖（关键） ★ 撤销是显式因果事件，不是「下一次评估的输入变化」（第 4 代发现）

> **目标状态不可达**：解绑本应收回授权，但这条链上每一步都符合文档，**终点却与意图相反**——
> 解绑 → 重评估 → 事实 missing → `indeterminate` → **不降级**（H1）→ **权限永久保留**。
> 静态清单式审查永远看不到它，因为**没有一条规则是错的**。

**修正**：把「撤销」建模为一类**显式因果事件**（主动传播），而非被动推导。

| 要求 | 内容 |
|---|---|
| **显式事件** | 新增 `binding.revoked`，**直接驱动迁移「任意 → revoked」**（跳过 at_risk 与宽限期）并执行 onUnsatisfied |
| **事实失效** | `ag_plugin_facts` 增加 `invalidatedAt` / `invalidReason`；解绑时**同事务**标记该 `(provider, instanceKey)` 事实失效 |
| **第 5 种地址态** | `04 §1.5.1` 增加 `revoked`（**区别于 missing**：命中 revoked 走 `unsatisfied` 而非 indeterminate） |
| **协同域对齐** | `/revoke` 按 `(subjectType, subjectValue)` 批量置 `revokedAt`；事件清单补 `assertion.revoked` |

**判据**：若存在一条路径能让「已撤销的绑定」仍然支撑「已授予的权限」，则该路径即为**因果断裂**。

### 2.2 幂等与防抖（关键）

因为**改分组会踢用户下线**（约束 C），所以：

```ts
async function applyGroupChange(user, targetGroup, ctx) {
  // ① 值不变直接跳过（new-api 侧也是先比较再 bump，但我们要避免无谓的 PUT）
  if (user.group === targetGroup) return { skipped: true, reason: 'no_change' };

  // ② 最小变更间隔
  const last = await ctx.state.lastGroupChangeAt(user.id);
  if (last && Date.now() - last < policy.lifecycle.minChangeInterval) {
    return { skipped: true, reason: 'rate_limited' };
  }

  // ③ 用户级互斥（避免同用户并发 read-modify-write）
  return ctx.locks.withUserLock(user.id, async () => {
    // ④ read-modify-write：必须拿完整用户对象
    // ★ 经 provider 插件读写，核心不出现任何具体系统名
    const provider = await ctx.providers.forSite();
    const fresh = await provider.getSubject(user.primarySubject.externalId);
    const payload = {
      ...fresh.attributes,             // 原样回填全部属性
      group: targetGroup,              // 只改目标字段
      remark: fresh.attributes.remark, // 原样回填（绝不写自己的标记）
    };
    await provider.updateSubject(user.primarySubject.externalId, payload);

    // ⑤ 本地镜像同步
    await ctx.subjects.updateAttributes(user.primarySubject, { group: targetGroup });
    await ctx.metrics.inc('gate_group_change_total');
    return { skipped: false, from: fresh.group, to: targetGroup };
  });
}
```

## 3. 动作执行器（Action Executor）

### 3.0.1 ★ 幂等键的规范形（第 5 代 N2：必须可执行）

> **问题**：原公式 `hash(userId + policyId + action + targetValue + dedupeWindow)` 中，
> `dedupeWindow` **在全部 13 份文档中只出现在两行注释里**——从未定义、无取值、无列。
> 而幂等必须由**跨调用可比较的纯函数键**承载。

**唯一权威公式（冻结）**：

```
idempotencyKey = hash(siteId, userId, policyId, actionSeq, action)
```

| 规则 | 内容 |
|---|---|
| **删除** | `targetValue`（回到原值会被永久去重，见一代 P16）与 `dedupeWindow`（从未定义） |
| **actionSeq** | 来自 `ag_user_policy_state.actionSeq`，在生成 ActionPlan 的同一事务内自增 |
| **跨期重发** | 表达为 `actionSeq` 递增，**不再依赖时间桶** |
| **唯一约束** | `(siteId, idempotencyKey)` |

**为什么 actionSeq 能同时满足两个相反要求**：同一计划的任意次重试复用同一 seq → **不重复执行**；状态再次迁移 → seq 变化 → **回到原值也能重新执行**。

---

### 3.1 执行模型：Plan → Execute → Verify

```
① Plan     根据评估结果生成 ActionPlan（有序动作列表），做冲突检测与去重
② Execute  逐条执行，每条写 ag_actions_log（含幂等键）
③ Verify   回读 new-api 确认目标状态达成（getUser 比对 group）
④ Compensate 若某条失败且策略声明了 compensation，反向执行
```

```ts
interface ActionPlan {
  userId: string;
  policyId: string;
  evalId: number;
  steps: ActionStep[];      // 有序
}
interface ActionStep {
  action: string;
  params: Record<string, unknown>;
  idempotencyKey: string;   // = hash(siteId, userId, policyId, actionSeq, action)
  compensation?: ActionStep;
  optional?: boolean;       // 失败是否阻断后续
}
```

### 3.2 内置动作

| 动作 | 实现 | 幂等策略 |
|---|---|---|
| `newapi-set-group:set_group` | `PUT /api/user/`（见 §2.2） | 目标值 + 当前值比对 |
| `newapi-add-quota:add_quota` | `POST /api/user/manage {action:'add_quota', value}` | ★ **按 §3.0.1 冻结公式**（`actionSeq`，**不含日期桶**）——沿用含日期的写法会与冻结公式冲突，且 `restore` 无 targetValue 可入键 |
| `newapi-set-status:set_status` | `POST /api/user/manage {action:'disable'/'enable'}` | 状态比对 |
| `checkin:grant` | 写本地 `ag_checkin_records` 的资格标记 + 清缓存 | 唯一键 `(user, scope)` |
| `checkin:revoke` | 删除资格标记 | 存在性检查 |
| `tag.add/remove` | 本地 `ag_users.tags` | 集合操作天然幂等 |
| `notify.webhook` | 出站 HTTP | 幂等键 + 重试退避 |

### 3.3 失败处理

| 失败类型 | 处理 |
|---|---|
| new-api 5xx / 超时 | 指数退避重试（1s/5s/30s/2m/10m），最多 `maxAttempts` 次 |
| new-api 4xx（参数错/权限错） | **不重试**，立即告警（这是配置错误，重试无意义） |
| 部分动作成功 | 记录中间态；`optional: false` 的失败会阻断后续并触发补偿 |
| 全部失败 | 用户策略状态保持原值（不误伤），写 `blocked` 计数 |

### 3.4 回滚

```http
POST /api/admin/actions/:id/rollback      # 单条回滚
POST /api/admin/users/:id/rollback        # 该用户所有已应用动作回滚
```

回滚依据 `ag_actions_log` 的 `request`/`response` 与 `ag_user_policy_state.appliedActions`（记录了"改之前是什么"）。

### 3.5 级联回退与 baseline（★ 不覆盖人工设置）

**问题**：动作的 `onUnsatisfied` 若写死 `set_group: default`，会在两个场景出错——

| 场景 | 错误后果 |
|---|---|
| **级联回退**：策略 B 失效但策略 A 仍满足 | 用户从 vip2 掉到 default，**丢掉 A 给的 basic** |
| **覆盖人工**：管理员手工设的 vip3，策略从未管过 | **手工设置被抹掉** |

#### 修正一：`set_group` 拆成两个动作

```yaml
onSatisfied:
  - action: "newapi-set-group:set_group"
    params: { group: "vip2" }            # 声明"我要求 vip2"
onUnsatisfied:
  - action: "newapi-set-group:restore"   # ★ 不是 set_group(default)
    params: {}                            # 回退目标由执行器计算
```

#### 修正二：执行器的回退算法

```
回退时：
① 收集该主体所有【仍为 granted / satisfied】的策略所要求的目标值
② 若有 → 取 tier 最高者
      （tier 相同 → priority 小者；仍相同 → 【拒绝执行并告警】，宁可不动也不随机选）
③ 若无 → 回退到 baseline（首次被策略接管前的原值）
④ 若 baseline 已被人工改动 → 交 driftPolicy 处理，不擅自覆盖
```

#### 修正三：记录 baseline

```ts
ag_user_policy_state {
  /** 首次接管前各受管属性的原值 —— 只回滚自己造成的变更 */
  baseline:       { "newapi-set-group:set_group": "vip3" },
  appliedActions: { "newapi-set-group:set_group": { value: "vip2", from: "vip3" } },
}
```

**原则**：**平台只回滚"它自己造成的变更"，绝不覆盖从未被它管理过的值。**

#### 修正四：动作前重新校验关键绑定（P14）

评估开始时记录事实快照指纹；**执行动作前重新校验关键绑定仍存在**（廉价检查）。
若绑定已消失（用户中途解绑）→ 放弃本次动作并重新排队评估。

---

#### 修正五：目标主体未绑定 → `blocked_unbound`（不是失败）

**场景**：策略满足了（如仅依赖 `fact:email.domain`），但动作目标 `subject:newapi@A1` **尚未绑定**。

**错误做法**：当成普通失败 → 重试 → 反复失败 → 触发熔断。

**正确做法**：

```
动作执行前：
  ① 解析目标主体
  ② 未绑定 → 状态 = blocked_unbound（【不是 failed】）
       · 不计入失败率（不触发熔断）
       · 进入"待绑定"队列
       · 用户侧提示："满足条件！绑定 new-api 账号后即可生效"
  ③ 绑定事件 → 自动重放该队列
```

> 这实际上是一次**转化引导**：用户看到"已满足，只差绑定"，绑定动机远强于看到"未知"。

---

#### 修正六：逐步状态与"半应用"（M2）

**场景**：一个策略的动作是 `[set_group, grant_checkin, notify]`，第 1 步成功、第 2 步失败 → 主体处于"分组已改但签到未解锁"。
若只记 `satisfied`，重试时会从头执行（语义混乱）。

**修正**：**每步独立记录状态**

```ts
type StepStatus = 'planned' | 'running' | 'succeeded' | 'failed' | 'skipped' | 'blocked_unbound';

ag_actions_log {
  action: 'newapi-set-group:set_group',
  status: StepStatus,
  // ★ 逐步结果而非最终值
  result: { value: 'vip2', from: 'default' },
}
```

| 情形 | 处理 |
|---|---|
| 全部成功 | 整体 `succeeded` |
| 部分失败（可重试） | 整体 `partially_applied`，**只重试失败步骤** |
| 部分失败（不可重试） | `failed` + 告警；**不推进状态机**（归入 `error`） |
| 目标未绑定 | 该步 `blocked_unbound`，不阻断其他步骤 |

**管理端展示**："半应用"状态 + [仅重试失败步骤] 按钮。

---

#### 修正七：动作终态到状态机的完整映射（★ 收敛性，第 5 代发现）

**问题**：`satisfied --动作全部成功--> granted` 只覆盖了「有成功步骤」的情形。**「全部 skipped」与「零步骤」没有归类**：

- 用户在平台接管前**已经是目标值**（`driftPolicy=platform_wins` 已改对，或手工设过）→ 唯一动作必然 `skip`（`reason=no_change`）→ 没有成功步骤 → **状态永远停在 `satisfied`**；
- 而签到资格判定（05 §5.2 条件 3）要求策略处于 **`granted`** → **该用户永远不能签到**。
- 同理 `else: actions: []` 这类零动作策略也拿不到 granted。

**修正：全量映射表（枚举 × 处置，缺一即门禁失败）**

| 动作计划终态 | 条件 | 状态机处置 |
|---|---|---|
| 全部 succeeded | — | → `granted` |
| **全部 skipped** | 无失败步骤 | ★ **→ `granted`**（记 `skipReason=no_change`，语义=「目标值已满足」） |
| **零步骤** | 命中分支未声明动作 | ★ **→ `granted`**（记 `skipReason=no_actions_declared`） |
| 部分 succeeded + 部分 skipped | 无失败 | → `granted` |
| `partially_applied` | 有可重试失败 | 保持 `satisfied`，★ **纳入 `actions.retry` 扫描集**（此前只扫 failed） |
| `blocked_unbound` | 目标未绑定 | 保持 `satisfied`，进待绑定队列 |
| `failed`(fatal) | 不可重试 | 保持 `satisfied` + 告警 |

**重试语义（冻结）**：对同一 `idempotencyKey` 的行做 `UPDATE`（而非插入新行，避免唯一键冲突），**只重发 failed / blocked_unbound 步骤**。

**门禁**：`StepStatus` 枚举的每个值 × 状态机处置必须全覆盖——新增枚举值必须同时给出处置。

## 4. 通用对账器（Subject Sync）

> **为什么对账器必须是通用的**：对账逻辑若内嵌 new-api 的分页细节，核心就再次耦合到具体系统。因此改为**通用对账器**——核心只调用 provider 插件的 `listSubjects` / `getSubject`，**不认识任何具体系统**。

### 4.1 对账流程（系统无关）

```
遍历所有已启用的 provider 插件
   │
   ├─ 调用 provider.listSubjects(cursor, limit)   ← 插件负责翻译成自己的 API
   │
   ├─ 对每个 ExternalSubject 计算 fingerprint
   │     fingerprint = hash(provider + externalId + 关注属性集合)
   │     关注属性集合由 provider 的 subjectSchema 中标记 watch: true 的字段决定
   │
   ├─ fingerprint 未变 → 只更新 synced_at（轻量，不触发下游）
   │
   └─ fingerprint 变化 → UPSERT ag_external_subjects + 发领域事件
          ├─ SubjectCreated            → 尝试自动对齐身份
          ├─ SubjectAttributesChanged  → 若与平台期望不一致，标记 drift
          └─ SubjectDeleted            → 平台用户转 blocked
```

### 4.2 两条同步路径

| 路径 | 频率 | 条件 | 实现 |
|---|---|---|---|
| **增量** | 1 min | provider `capabilities.cursor === true` | 用 provider 返回的 `nextCursor` 真增量拉取 |
| **增量（降级）** | 1 min | provider 无游标 | 拉首页（按 provider 声明的主键倒序），遇到已知 id 即停 |
| **全量对账** | 6 h（可配） | 始终 | 分页遍历全部主体，标记本轮未出现者为 `deleted` |；★ **到期 job 必须重新求值后才执行收回**（第 6 代 N3）——禁止用 lastOutcome 等陈旧结论直接 revoke，否则恢复时会误收回已恢复者并引发千级同时踢下线 |

> **降级路径是常态**：并非所有下游系统都提供 `since` 过滤。核心统一走"首页探测 + 周期全量"，**真增量是优化而非前提**——这样任何 REST 系统都能接入。

### 4.3 通用领域事件

| 事件 | 载荷 | 订阅方 |
|---|---|---|
| `subject.created` | provider, externalId | identity 模块（尝试自动对齐） |
| `subject.attributes_changed` | provider, externalId, changedKeys | drift 检测、策略重评估触发 |
| `subject.deleted` | provider, externalId | 平台用户 blocked、动作停止 |

### 4.4 能力探测

宿主在启动时与每个全量周期执行：

```ts
for (const p of ctx.plugins.byKind('provider')) {
  const declared = p.manifest.provider.capabilities;   // 插件【声明】的能力
  const actual = await probeProvider(p);               // 宿主【实测】的能力
  await ctx.providerSyncState.saveCapabilities(p.id, { declared, actual });
  if (diff(declared, actual)) ctx.log.warn('provider capability mismatch', { p: p.id });
}
```

**声明与实测不一致**是最常见的接入问题（如 new-api 升级后接口变化），必须显式告警而非静默降级。

### 4.5 drift（外部被手工改动）的处理

管理员绕过平台，直接在下游系统改了主体的属性（如 new-api 里手工改了 `group`）：

| 配置 `driftPolicy` | 行为 |
|---|---|
| `platform_wins`（默认） | 下一轮巡检改回平台期望值，并**告警**（可能有人在手工干预） |
| `manual_wins` | 检测到 drift 后把该主体策略状态转 `blocked`，等管理员在平台确认 |
| `ignore` | 只记录，不改 |

`driftPolicy` 可按 provider 单独配置（不同下游系统的容忍度不同）。

### 4.6 以 new-api 为例：provider 实现要点

> 以下属于 **`newapi-provider` 插件的内部实现细节**，不是核心假设。列出是因为它是第一个官方接入，踩坑点值得记录。

| 事项 | 结论（源码核实） |
|---|---|
| 列主体 | `GET /api/user/?p=&page_size=&sort_by=id&sort_order=asc`（**LIMIT/OFFSET 分页，无 `sinceId` 过滤** → 走降级路径） |
| 主体属性 | `id / username / display_name / email / group / status / role / oidc_id / quota / used_quota / request_count` 全部进 `attributes` 属性袋 |
| 身份键 | `oidc_id`（模式 1）、`email`（兜底，需唯一）、自定义 OAuth 绑定 `provider_user_id`（模式 2） |
| 改属性 | `PUT /api/user/`（read-modify-write，需回填 username/display_name/remark，**绝不能带 password**） |
| 加额度 | `POST /api/user/manage { action: 'add_quota', value }` |
| 改状态 | `POST /api/user/manage { action: 'disable' / 'enable' }` |
### 7.1.1 指标标签白名单（★ 防自伤式可观测性 DoS）

> **风险**：03 §1.5 给插件开放 `ctx.metrics.counter(name, labels)` 且 labels 无约束——一个有 bug（或恶意）的插件把 `userId` 放进 label，即可让时序数据库基数爆炸，**拖垮全平台监控**，并连带摧毁诊断能力本身。

| 规则 | 内容 |
|---|---|
| **标签白名单** | 仅允许 `siteId` / `pluginId` / `instanceKey` / `kind` / `outcome` / `status` / `action` / `errorKind`；**禁止** `userId` / `subjectId` / `externalId` 等无界值 |
| **基数上限** | 单插件 ≤ 1000 个时间序列；超限丢弃 + 告警（不拒绝，避免影响业务） |
| **站点维度** | 所有指标**必须**带 `siteId`（平台级用 `'platform'`）——否则站点运营者无法按站点下钻 |
| **indeterminate 必须可见** | ★ 必须新增 `gate_eval_outcome_total{outcome,siteId,policy}` 与 `gate_indeterminate_subjects{siteId,provider}`——否则 H1（最高危修正）的保护机制失败时**在监控上与"系统健康"完全同形** |
| **独立存活信号** | 除 `/healthz` 外，必须有**外部黑盒探测**（心跳/合成请求）；因为"系统显示健康但审计早已停写"这类分叉，只有外部视角能发现 |

| 写操作副作用 | 改 `group` 会 bump `auth_version` 并**踢掉该用户所有会话** → 必须幂等 + 防抖（见 §3.2） |
| 认证 | 管理员 PAT：`Authorization: Bearer <access_token>`，要求 `role >= RoleAdminUser` |

**能力探测的实际结果**（驱动快慢路径）：`list: true` / `findByIdentity: false`（new-api 的 `SearchUsers` 不支持按 `oidc_id` 检索）/ `update: true` / `create: true`。

## 5. 签到资格与发放

### 5.1 三种策略（对应 01 文档 §2.5 的取舍）

```yaml
checkin:
  strategy: local            # local | upstream | hybrid
  timezone: Asia/Shanghai
  requirePolicy: contributor-tier2     # 需要哪条策略处于 granted 才可签
  reward:
    base: { min: 1000, max: 5000 }
    streakBonus:                        # 连签阶梯
      - { days: 7,  multiplier: 1.5 }
      - { days: 30, multiplier: 3.0 }
    cap: 20000
  turnstile: { enabled: true }          # 人机校验（复用 new-api 的 Turnstile 配置）
```

### 5.2 用户侧流程（local 策略）

```
GET  /api/checkin/status   → { eligible: bool, reason, today: bool, streak, nextReward }
POST /api/checkin          → 校验资格 → 校验人机 → 写记录 → 调 newapi-add-quota:add_quota → 返回奖励
```

资格判定顺序（短路）：

1. 平台用户 `status == active`？
2. 已对齐 new-api 用户？（未对齐不可签，防止发错人）
3. 是否存在某条 `requirePolicy` 处于 `granted`？
4. 今日未签？
5. 人机校验通过？

### 5.2.1 写入顺序（★ 防重复发额度）

**必须先写记录（幂等锚点），再发额度**：

```
① INSERT INTO ag_checkin_records (user_id, checkin_date, ...)
     ON CONFLICT (site_id, user_id, checkin_date) DO NOTHING   -- ★ 必须与 02 §6.4 的唯一键一致
     ├─ 插入成功 → 继续
     └─ 冲突     → 直接返回"今日已签到"（幂等成功，不报错）
② 调 newapi-add-quota（幂等键含 userId + checkinDate）
     ├─ 成功 → 回填记录的 grantVia / newapiLogId
     └─ 失败(5xx) → 记录保留，进入补偿队列重试
③ 对账任务定期比对 ag_checkin_records 与 provider 侧的额度变动：
     ├─ "记了但没发" → 补发
     └─ "发了但没记" → 告警（人工核）
```

**为什么不能反过来**：若先发额度再写记录，两个并发请求会**都发出额度**，唯一键只挡住记录——账实不符且用户多得。

用 `ON CONFLICT ... DO NOTHING` 把"是否已签"变成**数据库层面的原子判定**，而不是"查询‒判断‒写入"的三步竞态。

### 5.3 幂等与对账

- 唯一键 `(userId, checkinDate)` 防重复；
- `add_quota` 的幂等键按 §3.0.1 冻结公式（`actionSeq`）——同一计划的任意次重试复用同一 seq，**不会发两次**；跨计划重发由 seq 递增自然表达；
- 提供 `POST /api/admin/checkin/reconcile`：比对本地记录与 new-api 的额度变动，发现"发了但没记"或"记了但没发"。

### 6.2 分片与限流

```ts
// 评估任务按 userId 哈希分片，多实例并行
ctx.scheduler.every('15m', chunkedJob({
  key: 'policy.recheck',
  shardBy: 'user_id',
  shards: ctx.config.jobs.shards,        // 默认 = 实例数
  batchSize: 200,                        // 每批 200 用户
  concurrency: 8,                        // 批内并发
  rateLimit: { perSecond: 50 },          // 保护 new-api 与外部 API
  onError: 'continue',                   // 单用户失败不影响整批
}));
```

### 6.3 单飞与 fencing

```ts
// PostgreSQL：pg_try_advisory_lock（会话级，连接断开自动释放）
const lock = await ctx.locks.acquire('job:sync.provider.full', { ttl: '10m', renew: true });
if (!lock) return { skipped: true };
try { await run(lock.fencingToken); } finally { await lock.release(); }
```

### 6.3.1 ★ 配额与熔断的键必须与资源归属同构（第 6 代发现）

> **问题**：桶键取「资源名」（`github:graphql`、`llm:tokens`），而资源的归属是 developer / site。
> 后果：**开发者 A 的站点把桶打满 → B / C 的采集全部 missing**，而告警把原因归给「渠道 X 不可信」——**实际渠道完全正常**，管理员查 token / 网络永远查不到「邻居掏空了桶」。
> 同时全局桶**低估**真实配额（每个开发者本应各 5000/h）。

**修正：键的维度必须与资源的归属维度同构**

```
quota:{ownerScope}:{ownerId}:{pluginId}:{instanceKey}:{resource}
```

| 要求 | 内容 |
|---|---|
| **新增归因** | `throttled(owner=platform)`——**不得复用 indeterminate 的告警文案**（渠道正常，是配额被邻居占用） |
| **熔断分区** | 熔断区分插件级 / 站点级，并给出**按站点分组的受影响清单** |
| **告警文案** | 必须带 owner 与受影响站点数，而非只说「渠道 X」 |

> **通用规则**：**每个限流 / 熔断 / 预算的键，必须与其保护资源的归属同构。**
> 键取资源名而资源按 developer 隔离 = **设计期即可消除的跨租户故障传播 + 错误归因**。

### 6.4 配额保护

外部 API（GitHub / LLM）统一走 `QuotaGuard`：

```ts
await ctx.quota.withTokenBucket('github:graphql', { capacity: 5000, refillPerHour: 5000 }, async () => {...});
await ctx.quota.withBudget('llm:tokens', { daily: 2_000_000 }, async () => {...});
```

超限时**不抛错**，而是让事实采集返回 `missing`，由策略的 `onMissingFact` 决定（默认 `fail_closed`：宁可暂不升级，也不误判）。

## 8. OIDC 密钥与签名算法（EC 支持）

### 8.1 为什么要显式设计算法

OIDC 的 **ID Token 签名算法**是互操作中最容易踩坑的地方：

- 不同语言的库默认算法偏好不同（`coreos/go-oidc` 的 `NewVerifier` 在未显式配置时 **只接受 RS256**）；
- EC 密钥更短、签名更快、JWKS 更小，但部分老旧客户端不支持；
- 一旦上游把算法写死，换算法就是**全站登录中断**。

因此本平台把"算法"当作**一等配置**，而不是实现细节。

### 8.2 支持矩阵

| 密钥类型 | 算法 | 曲线/参数 | 默认 | 说明 |
|---|---|---|---|---|
| **EC** | `ES256` | P-256 | ✅ **默认签发** | 签名最短（64 字节），性能最好 |
| EC | `ES384` | P-384 | 可选 | 更高强度 |
| EC | `ES512` | P-521 | 可选 | — |
| **RSA** | `RS256` | ≥ 2048 bit | ✅ **默认并存** | 最大兼容性，覆盖所有下游 |
| RSA | `RS384` / `RS512` | ≥ 2048 bit | 可选 | — |
| OKP | `EdDSA` | Ed25519 | 可选 | 现代化，但生态支持面窄 |
| ❌ | `none` | — | **永久禁止** | — |
| ⚠️ | `HS256` / 对称 | — | 默认禁止 | 仅当显式配置 `allowSymmetricForClient` 时对单个受信 client 开启 |

### 8.3 核心策略："EC 为默认，RSA 并存"

```yaml
oidc:
  issuer: https://gate.example.com
  signing:
    activeAlg: ES256            # 新签发的 ID Token 用哪种算法
    jwksAlgs: [ES256, RS256]    # JWKS 里同时发布的算法族 —— 让下游各处都能验通
    rotateEvery: 90d            # 密钥轮换周期
    retireAfter: 24h            # 旧公钥在 JWKS 中保留时长（必须 > token 最长有效期）
    fallbackAlg: RS256          # 紧急兼容开关：下游只认 RS256 时秒切，不改代码
```

**为什么默认"两套并存"**：

1. 下游 new-api 当前**不验签**（见 §8.5），EC 完全没问题；
2. 但只要上游哪天启用了验签（无论用 go-oidc 还是别的库），若其默认只支持 RS256，**EC-only 会直接导致登录失败**；
3. JWKS 里同时挂 `ES256` 与 `RS256` 两个公钥（各带独立 `kid`），任何一方都能验证通过；
4. 若发现某下游确实只认 RSA，把 `activeAlg` 切成 `RS256` 即可，**无需重新发号、无需用户重新登录**（因为 RSA 公钥一直都在 JWKS 里）。

### 8.4 密钥生命周期

```
① 生成      ES256 → P-256 密钥对；RS256 → 2048+ bit
              ↓
② 加密存储   私钥 AES-256-GCM 加密后存 ag_oidc_signing_keys（主密钥来自 AG_MASTER_KEY）
              ↓
③ 发布      派生公钥写入 JWKS 端点，带 kid / use=sig / alg / kty / crv
              ↓
④ 使用      签发时用 active 密钥，ID Token header 带 kid
              ↓
⑤ 轮换      生成新密钥 → 置 active → 旧密钥转 retiring（仍在 JWKS 中）
              ↓
⑥ 退役      retireAfter 到期且无有效 token 引用 → status=retired，移出 JWKS
```

**强约束**：私钥**永不**离开服务进程内存与加密存储；日志、审计、API 响应中一律不出现私钥（统一用 `kid` 引用）。

#### 8.4.1 密钥轮换：两步走（先发布、后使用）

| 步骤 | 动作 | 等待 |
|---|---|---|
| ① | 生成新密钥，以 `standby` 状态**发布到 JWKS**（此时**不签发**） | — |
| ② | 等待下游 JWKS 缓存过期 | ≥ 缓存 TTL × 6（默认 **30 分钟**） |
| ③ | **必须同事务**：先置旧密钥 `retiring`，**再**置新密钥 `active`（第 5 代 N9：02 §7.4 的 `uq_ag_oidc_keys_active_alg` 部分唯一索引使「先升后降」**必撞唯一索引**；拆两语句则有**零 active 窗口** → 全站登录中断） | — |
| ④ | 旧密钥从 JWKS 移除 | ≥ token 最长有效期（**24h**） |

**绝不允许"先生效再发布"**——否则下游在其 JWKS 缓存过期前会因**未知 `kid`** 而验签失败，导致**登录中断**。

> 同理适用于：加密密钥（`ag_secrets.keyVersion`）、插件版本、配置变更——**轮换的本质是"先让所有人知道，再开始使用"**。

### 8.5 与 new-api 的实际兼容性（已核实源码）

| new-api 路径 | 是否校验 ID Token 签名 | 结论 |
|---|---|---|
| 内置 OIDC（`oauth/oidc.go`） | ❌ **不校验**，只用 `access_token` 调 `userinfo` 取 `sub`/`email` | 中间统一 OIDC 用 EC 还是 RSA **都无影响** |
| 自定义 OAuth Provider（`oauth/generic.go`） | ❌ **不校验**，`id_token` 仅被解析进结构体，用户信息全部来自 `UserInfoEndpoint` | 本平台（模式 2）**用 EC 签发 ID Token 不影响 new-api** |
| Telegram（`oauth/telegram.go`） | ✅ 用 `oidc.NewRemoteKeySet` + `verifier.Verify` | 与本项目无关（固定 issuer） |

> **实现提示**：这恰恰是本平台 RP 侧（模式 1 登录时验证中间统一 OIDC）的价值点——**本平台自己必须做到真正的验签**，用 `jose` 库完整校验 `iss / aud / exp / nonce / alg`，并支持 EC 公钥（`kty: EC`, `crv: P-256`）。不能像 new-api 那样只信 userinfo。

### 8.6 上游兼容性建议（可选 PR）

若未来希望 new-api 对自定义 Provider 也做真正的 ID Token 验签，需要注意：

```go
// coreos/go-oidc v3 的 oidc.NewVerifier 默认仅支持 RS256
// 必须显式扩展，否则 EC 签发会验不过
verifier := provider.Verifier(&oidc.Config{
    ClientID:             p.config.ClientId,
    SupportedSigningAlgs: []string{"RS256", "ES256"},   // ← 关键
})
```

**这正是"JWKS 双算法并存"策略兜底的原因**：即使上游漏配 `SupportedSigningAlgs`，只要 JWKS 里有 RS256 公钥且 `activeAlg` 可切换，就能快速恢复。

### 8.7 RP 侧（模式 1）的算法处理

本平台作为 RP 验证中间统一 OIDC 时：

| 校验项 | 要求 |
|---|---|
| 签名算法 | 接受 IdP 在 `id_token_signing_alg_values_supported` 中声明的算法，**含 ES256/384/512** |
| 显式拒绝 | `none`；除非 client 配置显式允许，否则拒绝 `HS*` |
| 公钥来源 | 优先 JWKS（按 `kid` 选 key），支持 `kty: EC` 与 `kty: RSA`；禁止仅凭 `x5c` 跳过验证 |
| 必校验 | `iss` / `aud` / `exp` / `iat`（容差 60s）/ `nonce` |
| 密钥轮换 | JWKS 缓存 ≤ 5 分钟；验签失败且 `kid` 未知时**强制刷新一次 JWKS** 再判定 |
| 算法绑定 | 校验每个 key 的 `alg` 与 JWS header 一致，防止算法混淆攻击（alg confusion） |

## 9. 安全设计

| 面 | 措施 |
|---|---|
| 密钥存储 | PAT / client secret / LLM key 用 AES-256-GCM 加密存 `ag_secrets`，主密钥来自环境变量 `AG_MASTER_KEY`，支持轮换（`keyVersion`） |
| 最小权限 | new-api 侧用**专用管理员账号**（非 root），仅用于用户管理；不读 option（除非启用 P2） |
| 越权防护 | 平台自身的 admin 角色与普通用户严格分离；所有 `/api/admin/**` 走独立鉴权中间件 |
| OIDC 安全 | **默认 ES256 + JWKS 同时发布 RS256 双算法**（见 §8）；`state` + `nonce` + PKCE；私钥 AES-256-GCM 加密、永久不出内存；`aud`/`iss`/`exp` 全校验；拒绝 `none` 与算法混淆；授权码一次性 |
| SSRF | 通过 OIDC 渠道拉取 `well-known` 时限制目标为配置白名单域名，禁止内网地址 |
| 注入 | 转义层是唯一 SQL 拼接点；策略 DSL 的值一律参数化；`raw()` 需显式声明并做 CI 基线 |
| 速率 | 登录/绑定/签到接口按 IP + userId 双维度限流 |
| 数据最小化 | GitHub 只申请 `read:user user:email`；不存用户 token（只用一次换取事实），或加密存储并设 TTL |
| 审计留痕 | 所有写操作强制审计，含操作人、前后值、IP、trace_id |
| **插件入站端点** | 强制前缀 + 保留路径黑名单；鉴权在插件之前完成；HMAC 密钥托管于宿主，插件拿不到；端点级限流与启用开关 |
| **跨项目协同凭据** | client secret 只存哈希、仅注册时返回一次；HMAC 签名含时间戳与 nonce；断言用 ES256 签名可被第三方独立验签；断言默认 5 分钟过期 |
| **协同数据最小化** | 调用方必须显式声明 `scopes` 与 `allowedSubjects`；断言只返回被请求的 claims，不返回原始事实与用户隐私字段 |
