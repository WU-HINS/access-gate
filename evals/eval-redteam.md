# access-gate 架构评估 · 对抗式红队视角（eval-redteam）

> 评估者视角：**对抗式红队**。判据是「**谁能利用它**」。
> 威胁模型按 11 §5 的修正执行：攻击者是**平台内的合法租户**（站点开发者 / 普通用户 / 被钓鱼的用户 / 有 bug 或恶意的插件作者），**不把外部攻击者当唯一威胁**。
> 本文档独立阅读 docs/01–11 + CHANGELOG + README + 14（共 10084 行），所有论断均给出章节定位。

## 第一部分 · 架构成熟度评分（红队口径）

| 维度 | 评分 | 一句话 |
|---|---|---|
| 架构自洽性 | **3 / 5** | 四抽象与九代推演的骨架成立，但存在 3 处**活矛盾**且都落在安全路径上 |
| 数据模型完备性 | **2 / 5** | 40 张表声明细致，但**作用域来源自身没有承载列**，且 14 张表不在门禁白名单内 |
| 安全与隔离 | **1 / 5** | 唯一强制层（RLS）被推迟，作用域来源未定义，跨租户通路至少 6 条且都可复现 |
| 可运维性 | **2 / 5** | 指标/告警/审计设计完整，但锚点表、死信表、迁移表**三张关键表不存在**，审计在 SaaS 下不可归属 |
| 可实现性 | **4 / 5** | 规格已到列名级、验收可执行、第 9 代砍掉最重项；扣分只在 MVP 表清单口径与 /console 契约缺失 |
| 工期与范围可信度 | **2 / 5** | 两套工期未合流，且 11 §14.6 自认两项"冻结"未完成即可开工 |

### 1. 架构自洽性 3/5
**理由**：D1–D15 的抽象层次干净，"宿主无知"与"核心只认四抽象"可验收（01 §4.2.4 的三条验收）；但文档在**同一件事上给出两个结论**，且都发生在隔离与判定路径上，读者按哪一份实现会得到相反的安全属性。
**支撑证据**：① CHANGELOG D16「站点隔离双层强制（应用层注入 + RLS）✅采纳」 vs D17「RLS **推迟**」 vs 07 §3 M0-5「★ 不启用 RLS」；② 04 §1.5.1「`$required: true` 的事实缺失 → 直接 indeterminate（无论 `$onMissing` 写什么）」 vs 05 §2.1.1.1/D20「分诊责任移到插件边界，**结局与 `$required` 解耦**」；③ 02 §3.10 声称 `ag_sessions` 已加 `realm/activeSiteId`，而 02 §3.3 的声明块里**没有这三列**。
**扣分项**：三处矛盾分别对应"隔离是否强制""无法验证如何归类""作用域从哪里来"，即全部落在安全关键路径，而不是文档措辞。

### 2. 数据模型完备性 2/5
**理由**：02 文档是全部文档里质量最高的一份（40 张表、列名级、部分唯一索引、PG 语义都考虑到了）；但按 11 §3 自己立的"承载力检查"准则，**作用域这条主链在数据模型里没有承载物**。
**支撑证据**：① 01 §5.5「app.site_id 由**会话的 activeSiteId** 派生（会话创建时已校验归属）」——而 02 §3.3 `ag_sessions` 只有 id/userId/tokenHash/userAgent/ip/expiresAt/revokedAt/createdAt，**无 realm、无 activeSiteId、无 activeDeveloperId**；② 02 §1 的门禁白名单只覆盖 26 张表，02 实际声明 **40 张**，其中 `ag_policy_assignments`（02 §5.2）**无任何作用域列**、`ag_plugin_configs`（02 §4.2）**无任何作用域列**；③ 白名单点名的 `ag_provider_sync_state`（02 §7.2）主键仍是 provider，**无 siteId 列**，`ag_plugin_instances`（02 §3.8）唯一键首列是 developerId。
**扣分项**：作用域来源缺列、白名单自相矛盾、策略绑定与插件配置两张跨租户语义的表在门禁之外。

### 3. 安全与隔离 1/5
**理由**：威胁模型在 11 §5 已正确修正为"内部租户互攻"，但**控制手段被同一批裁决拆掉**（D17 推迟 RLS、D19 砍哈希链且锚点表不存在），剩下的唯一屏障是"应用层记得注入"，而注入值的来源没有列、没有端点、没有归属校验规则。
**支撑证据**：D17 裁决理由①原文「**站点隔离当前是数据卫生而非安全边界**」；01 §5.5 第二道防线 `FORCE ROW LEVEL SECURITY` 在 07 §3 M0-5 被明确"不启用"；跨租户可复现通路见 Top10 #1/#3/#4/#5/#6/#9。
**扣分项**：我给出的 6 条攻击路径全部只依赖**合法租户权限**，无需外部突破；且其中 3 条的后果是**静默**的（跨站点数据污染、越权读取、资格被冒用），不产生告警。

### 4. 可运维性 2/5
**理由**：05 §7 + §2.1.2 的"指标 + 状态型周期告警 + 告警审计 + 界面一一对应"四件套是全文档最好的运维设计，`gate_indeterminate_subjects` 这类"不动作分支必须可见"的通用条款也正确；但审计与事件这两条运维底线**没有承载表**。
**支撑证据**：① D19 的 `ag_audit_anchors` + JWS 密钥在 02/05/07 **全不存在**（11 §14.2 自认）；② 05 §7.1.2 承诺死信队列，`ag_event_outbox` / `ag_dead_letters` **只出现在 05 的那张表里**，02 无声明、06 §5.5 无重放入口；③ `ag_migrations`（02 §9.2.1 的 checksum 与三态记录）**未声明**（10 §4 M4/M5 已标注）；④ 02 §8 `ag_audit_log.actorType` 枚举为 user/admin/system/job，**没有 developer**，而 siteId 为 NOT NULL。
**扣分项**：出事时"查不到（无 DLQ/无锚点）"与"查不准（无法区分 admin 与 developer、平台级事件无归属站点）"同时存在。

### 5. 可实现性 4/5
**理由**：从"照文档写代码"角度，这是四份文档里最可落地的一段——02 到列名、05 到幂等键公式与状态迁移表、07 到单任务验收，且第 9 代已砍掉自研查询层与图形编辑器这两个最大工期黑洞（11 §12.4）。
**支撑证据**：05 §3.0.1 冻结公式、05 §3.5 修正七的全量终态映射表、07 §5 场景 A 的 8 步可执行验收。
**扣分项**：① 11 §14.6 自认「列名级的 MVP 表清单」未做，而 11 §14.1 判定「"约 12 张表"与实需 ≥19 张矛盾 → **M1 无法按清单开工**」；② 06 文档（HTTP API 契约）里**没有任何 /console 端点**（/console 只出现在 08 §9 与 10 §12 的 URL 说明中）——开发者控制台的策略/插件配置/主体/审计接口在契约层缺失，实现者只能自行发明或直接复用 /admin/**，而后者是**提权入口**。

### 6. 工期与范围可信度 2/5
**理由**：07 §7 是自下而上的 WBS 且带累计列，可信度高于一般估算；但两套口径同时存在且未合流，范围侧还有一批"待补"没有进入任何里程碑。
**支撑证据**：① 07 §7「M0–M2 = **48** 人日 / M0–M6 = **118** 人日」 vs 11 §12.6「M0–M2 从 48 → 约 **30–34** / 完整 M0–M6 从 118 → 约 **60–70**」；② 11 §12.5 自认「不可执行的保证 10 条，已修 2 条，**8 条待修**」「过度设计 10 项、约 **56 人日** 可砍/可简化」；③ 11 §4 的 X8–X19（含 X11 多站点签到套利、X12 设备码流无限流、X13 邮箱兜底可接管账号）**全部标 待补**，且**没有出现在 07 的任何里程碑里**。
**扣分项**：范围未冻结（减法建议未裁决）而工期已给出两个数；"待补"项无归属里程碑，等于没有预算。

## 第二部分 · 关键问题 Top 10（红队口径，按严重度排序）

### #1 【高】出站"域名白名单"与"租户填写的 URL"是两个不同主体的授权，冲突未裁定 → 宿主成为任意出站代理
**位置**：03 §1.5（http.request 仅白名单域名）、03 §1.7（模板变量含 config 占位符）、03 §1.11（SSRF：解析目标 IP 拒绝内网/环回/元数据）、03 §1.19.2、09 §2.2、09 §4.2。
**现象**：`newapi-provider` 的权限是固定字符串 `http:egress:api.example.com`（09 §2.2），但同一份 manifest 的 `configSchema.baseUrl` 是"任意 format: uri"，且实现里所有请求都拼在该 baseUrl 之后（09 §2.3/§2.4）；03 §1.19.2 的实例配置示例也由租户填 baseUrl。文档从未说明**域名白名单是"安装时管理员授予的域名"还是"运行期配置里的域名"**。同理，declarative 插件的 URL 可以来自配置占位符（03 §1.7），而 multi 实例的 webhook 类插件（03 §1.19.2 例③）URL 完全由站点开发者填写。
**攻击路径（站点开发者 = 合法租户）**：
1. 在 SaaS 下开通站点，配置 `newapi-provider` 实例，baseUrl 指向 https://collect.attacker.example；
2. 若"配置优先"，宿主会把该站点的 `secrets:read:newapi.pat` 以 Authorization: Bearer 头发到攻击者域名（09 §2.3 的 header 是硬编码注入的）→ **凭据外送**，并可在控制台读回响应（`ag_external_subjects.attributes` / raw，06 §5.2.1 D 组）；
3. 若"白名单优先"，则任何真实部署（域名不等于 api.example.com）**插件直接不可用**——M1-3「真实 new-api 完成全量对账」无法验收；
4. 无论取哪一支，03 §1.11 的"解析目标 IP 拒绝内网"是**唯一**剩下的控制点，而它没有定义**校验时机**：若先按域名放行再解析连接，攻击者用 DNS rebinding（首次解析返回公网、连接时返回 127.0.0.1 / 169.254.169.254）即可穿过域名白名单。
**后果**：SSRF 边界形同虚设（内网服务探测、云元数据、把宿主 IP 当匿名中继），或插件体系在真实域名下不可用；PAT 外送通道在设计上是"允许"的。
**修正建议**：① 在 03 §1.5 写死优先级：**管理员授予的域名白名单是硬约束，配置里的 host 必须落在白名单内**，配置 schema 用枚举/校验器把 host 限制为白名单域名；② baseUrl 之类改为"从已授予白名单中选择"而非自由输入；③ 明确 SSRF 校验为**连接期**（先解析 → 校验全部 A/AAAA → 用校验后的 IP 直连并带 SNI/Host），并禁止跟随重定向；④ 把 egress 白名单纳入**逐站点**的权限授予视图，使站点开发者能看见"我这一站允许出站到哪些域名"。
**严重度**：高（凭据外送 + SSRF 绕过；且是 M1 就会遇到的功能性死结）。

### #2 【高】"项目侧凭证可作为登录平台的凭证" + 断言与 ID Token 共用同一签名密钥 → 跨信任域冒充
**位置**：03 §1.18.3（outbound：「**这些 token 同时被平台自身接受为会话凭证**」）、03 §1.14.1③（断言 signature 是 JWS，"与 05 §8 的 EC 密钥体系**复用同一套 JWKS**"）、05 §8.2/§8.3、06 §6.0.1（/oauth/token 支持 refresh_token）、06 §6.4（ID Token 含 aud = newapi client_id）、06 §2（认证端点清单）。
**现象**：平台把签发给**第三方项目**的 ID Token 也接受为平台会话凭证（为了 SSO 体验），但 ① 06 §2 的认证端点清单里**没有"用 ID Token 换平台会话"的端点**，其校验规则（是否校验 aud 等于平台自己、是否校验 typ、是否接受 refresh_token）**完全没有定义**；② 协同断言用**同一把 active 密钥、同一个 kid**签发，且断言体只有 iss/issuedAt/expiresAt/signature，**没有 aud / typ / jti**（03 §1.14.1③ 与 06 §7.2.3 的响应体）。
**攻击路径 A（项目方冒充用户）**：
1. 用户 X 用平台账号登录第三方项目 P（P 是平台注册的 client，03 §1.18.1 outbound）；
2. P 在 /oauth/token 拿到 X 的 ID Token（aud = P）与 refresh_token（06 §6.0.1）；
3. P 用该 ID Token 调平台的会话引导端点（03 §1.18.3 承诺"可作为登录平台自身的凭证"）；
4. 若校验只看 iss + 签名 + 未过期，**P 即成为 X 的平台会话**——可读 X 的绑定、代 X 签到、改 X 的资料。
**攻击路径 B（断言当 ID Token 用）**：
1. 攻击者持有一个 verify client（或钓到某个 bot 运营者的 secret，或该 bot 本身被入侵）；
2. 用 /api/verify/v1/assert 取得用户 X 的断言 JWS（assertions.tier=2）；
3. 因为签名密钥与 kid 与 ID Token **完全相同**、断言无 aud/typ，把它当 ID Token 投给任何信任平台 JWKS 的下游（new-api 一旦按 P6 开启验签，或平台自己的会话引导端点）→ **用别人的资格通过准入**。
**后果**：信任边界（项目 ↔ 平台、协同协议 ↔ 登录协议）被同一把钥匙打通；"资格断言可离线复核"这个卖点同时变成了"断言可被重放"。
**修正建议**：① 断言与 ID Token **分离密钥族**（至少分离 kid 并在 JWKS 用 use/key_ops 区分），断言必须含 aud=clientId、typ=gate-assertion+jwt、jti、iat；② 会话引导端点必须在 06 §2 列出并规定：aud 必须等于平台自身、typ=JWT、拒绝 refresh_token 换会话、一次性 jti 去重；③ 重新评估"项目侧 token 可直接登录平台"是否必要——若要保留，必须限定为**同一 issuer 的 RP-initiated 会话续期**（浏览器已有平台会话），而不是"拿 token 直接换会话"。
**严重度**：高（可提权到他人平台账号；且是"设计承诺"而非实现 bug）。

### #3 【高】站点作用域的唯一来源（会话的 activeSiteId）没有承载列、没有切换端点、没有归属校验规则
**位置**：01 §5.5（app.site_id 由会话 activeSiteId 派生、批处理上下文、BYPASSRLS 仅限显式跨站点管理查询）、02 §3.3（ag_sessions 声明）、02 §3.10（声称已加列）、08 §5.4（ag_sessions.realm）、08 §6（用户先选开发者再选站点）、08 §7（crossSite 按角色收敛）。
**现象**：整条站点隔离（注入 + RLS + 审计 + 配额 + 调度分片）都以 session.activeSiteId 为输入，但：
- 02 §3.3 的 `ag_sessions` **没有 realm / activeDeveloperId / activeSiteId 列**（只有 02 §3.10 的一句"加 …"，与声明块矛盾）；
- 06 文档里**没有"切换站点"的端点**（08 §6 的 /me/:devId/:siteId 是前端路由，不是 API）；
- "会话创建时已校验归属"这句是**唯一**的授权描述：对 enduser 而言根本没有"归属"关系（08 §6 明说"用户是平台级的，不做站点成员关系"），对 developer 而言必须校验 ag_sites.developerId == session.developerId，而这条**从未写成规则**；
- crossSite(reason) 的判定被描述为"developer 角色：仅限自己名下的站点"（08 §7），但**没有给出承载它的函数/查询约束**，也没有说控制台端点是否允许传入 siteId。
**攻击路径（开发者 B = 合法租户）**：
1. B 登录开发者控制台，调用站点切换（实现者必然要发明一个，比如 PUT /console/active-site，因为契约里没有）；
2. 若实现只校验"站点存在"（最省事的写法，且文档只写了"已校验归属"这句无主语的话），则 B 可以切到开发者 A 的站点 A1；
3. 之后所有查询按"当前站点"注入 site_id = A1，**注入是合法的、RLS（若启用）也是放行的**——B 在控制台读到 A1 的策略、评估明细（含事实快照与用户属性）、动作流水、审计。
**反向路径（拒绝服务/静默错误）**：若实现严格 fail-closed（01 §5.5 要求无作用域抛错）而 activeSiteId 列不存在/未设置，则**所有业务查询抛 MissingSiteScopeError**；文档同时明令"**禁止用默认站点兜底**"（01 §5.5），于是单站点部署会立刻不可用——这正是 11 §12.5 说的"8 条不可执行保证"里的典型。
**后果**：跨租户读取（提权），或全站不可用；两种结局都源于同一处"作用域来源未定义"，且**都没有告警**。
**修正建议**：① 02 §3.3 补 realm / activeDeveloperId / activeSiteId（并进 02 §1 的能力层白名单）；② 06 补 POST /auth/session/active-site 契约，规定服务端校验：realm=developer 时 ag_sites.developerId == session.developerId，realm=enduser 时只允许"该站点对该用户可见"（至少要求站点 status=active 且用户在该站点有绑定/主体）；③ 把 crossSite() 写成**单一可执行函数 + CI 断言**（"控制台端点不得自行拼接 siteId"），并规定 BYPASSRLS 只在该函数内出现。
**严重度**：高（跨租户读取；同时是 M0 验收与单站点可用性的阻塞点）。

### #4 【高】RLS 被推迟，但"双层强制"仍是文档对外的承诺；且跨站点查询的越权判定无规格
**位置**：CHANGELOG D16（✅采纳"应用层注入 + PostgreSQL RLS"）、D17（裁决**推迟**，并称"站点隔离当前是数据卫生而非安全边界"）、07 §3 M0-5 / §7 出口 / §9（不启用 RLS）、01 §5.5（第二道防线 + FORCE ROW LEVEL SECURITY + SET LOCAL）、08 §13 S5（"已决：单库 + 行级隔离 + RLS"）、README 关键决策表 D16。
**现象**：D17 的推迟结论与 D16/01/08/README 的表述**同时存在于同一套文档**。D17 的理由①是一条**产品假设**——"无站点级协作者角色 → 站点隔离当前是数据卫生而非安全边界"；它的切换触发条件是"出现 ≥2 个互不信任 developer 共享实例"，而 08 §11.2 自己给的规模例子就是"4 个开发者、7 个站点"，08 §13 S1 还开放"普通用户可自建站点"的备选。也就是说，**触发条件是产品决策，而不是安全决策**，而"切换成本 O(1)"这个前提本身被 D17 前置 3 预先决定（11 §14.2 已指出 spike 自证）。
**攻击路径（开发者 A = 合法租户，M7 之后）**：
1. 开发者 A 在自己的站点里放一条策略，用 #siteSlug 跨站点引用（04 §1.2.7.1 允许 fact:github#site-b.total_stars，仅"平台级策略"可用，而"平台级策略"实体**不存在**，11 §12.2 N5 已判"永远 missing"）；

3. RLS 未启用 → 数据库层不再兜底；应用层注入只保护"按站点查询"的路径，crossSite 与任何手写 SQL/迁移脚本/运维查询都是裸的。
**后果**：M0–M6（甚至 M7）期间**只有一道防线**，而这道防线的输入未定义（#3）；"即使有人写了裸 SQL 也读不到别的站点数据"（D16 理由）**不成立**，但文档仍这样承诺——这会让后续的 M6-8"作用域绕过尝试"安全自查得出错误结论。
**修正建议**：① 二选一并全局同步：要么在 M0 启用 RLS（D16 原案），要么把 D16/01 §5.5/08 §13 S5/README 全部改写为"**M0–M6 仅应用层注入，RLS 为 M7 前置**"，并把"跨站点读必须经 crossSite 且写审计"升级为**唯一**允许的跨站点路径；② D17 的 spike 判据补上"4–10 改动文件数"的处置规则（11 §14.2 已指出该区间无规则）；③ 把 D17 的触发条件从"产品决定共享实例"改成**硬性前置**：任何 enable saas 的动作（08 §11.2 的切换流程）必须先满足 RLS 或等价的强制隔离。
**严重度**：高（隔离强度与文档承诺不符；静默的跨站点越权）。

**严重度**：高（跨站点信息泄露 + 低权破坏性操作，两者都只需一个合法 client）。

**修正建议**：① 端点注册表加 siteId（site 作用域）或把 mountPath 恢复为含站点（R1 两种方案二选一），唯一键改为 (siteId, method, path) 且**与运行期解析键完全一致**；② UI 贡献表唯一键改为 (siteId, type, key)，并规定渲染时的解析键 = 唯一键；③ 加一条 CI 断言：**任何注册表的唯一键必须等于运行期查找键**（11 §3"承载力检查"的直接应用）。
**严重度**：中高（鉴权降级；影响面在 M4 之后）。

### #10 【中】设备码流缺少"主体所有权证明"，用户仅凭一个 8 位码即可把自己的资格关联到攻击者控制的外部 ID
**位置**：03 §1.14.1④（设备码流：bot 声明 subject={type:discord_id,value:1234567} → 返回 userCode → 用户输入即"平台建立【临时关联】(discord_id ↔ 平台账号)"）、06 §7.2.3、06 §7.4（确认页）、02 §7.6（ag_verify_challenges.userCode 仅 status='pending' 唯一）、11 §4 X12（"设备码流无限流"待补）、10 §11 R4。
**现象**：RFC 8628 的前提是"**发起方就是用户正在操作的那个客户端**"；本设计把 subjectValue 完全交给调用方声明，用户侧唯一要做的动作是**输入一个 8 位码**（ag_verify_challenges 对 userCode 的唯一约束只在 pending 上，02 §7.6）。确认页（06 §7.4）展示的是"请求方名称"（调用方自填，02 §7.5 name），而不是"将被关联的外部账号标识"。因此**没有任何一步证明该用户拥有 subjectValue 对应的外部身份**，也没有任何一步让用户看到自己正在把账号绑给谁。
**攻击路径（钓鱼 + 合法 client）**：
1. 攻击者用一个已注册的 verify client（或自己申请一个，06 §7.2.1）调 POST /api/verify/v1/challenge，subject = {type: "discord_id", value: 攻击者的 discord id}；
2. 拿到 userCode 后，用社工话术把 https://gate.example.com/verify 与该码发给受害者（"输入这个码领取贡献者奖励"）；
3. 受害者在**自己的平台会话**下输入该码并点同意 → 平台建立"受害者的平台账号 ↔ 攻击者的 discord_id"关联；
4. 攻击者轮询 GET /api/verify/v1/challenge/:id 得到 approved + 断言（eligible/tier/tags），于是**用受害者的资格通过下游 bot 的准入**；
5. 因为 06 §7.4 的确认页只写"请求方：Discord Bot（社区A）"、不写"将关联的 Discord ID 是攻击者的 ID"，受害者无从察觉。
**后果**：资格冒用（欺骗判定）+ 受害者账号被绑到攻击者控制的外部身份（后续 /revoke 由调用方发起，受害者难以自证）；且 11 §4 的 X12 只覆盖了"无限流"，**没有覆盖"无所有权证明"**。
**修正建议**：① 确认页必须显示将被关联的**外部标识符原值**（如 discord_id: 1234567），并要求用户勾选"这是我本人的账号"；② 建立关联前要求 subjectValue 已被该用户在平台内**主动绑定并验证过**（challenge 只能用于"确认已有绑定"，不能用于"创建新绑定"）；③ userCode 长度提到 ≥12 字符（或 8 位数字 + 5 分钟 TTL + 每 client/IP 限流），并让 pending 的唯一性覆盖**所有 client**（防撞码）；④ 关联建立与撤销都写审计并通知用户（邮件/webhook）。
**严重度**：中（需要社工配合，但成功率高且后果是资格冒用；M5 才引入，可在 M5 前修）。

## 第四部分 · 最强与最弱

### 1. 最出色的一个决策：**D5 + D11（通用信任引擎 + 数据库独占/不 JOIN 下游表）**
**为什么**：它把一个"new-api 分组助手"变成可复用的信任内核，而且**它是唯一被写成可执行验收的架构决策**——"把 plugins/builtin/ 整个删掉主程序仍能启动"（01 §4.2.4 验收 1）、"核心逻辑 grep github 为 0"（验收 2）、"装一个 gitlab 插件无需改代码/重建/重启"（验收 3）。更关键的是：**它让"换接入方"变成一件不需要动内核的事**，因此前九代推演中所有关于"具体系统"的风险都被局部化到插件包内（01 §5.0 的"不跨库 JOIN"是它在数据层的镜像）。对比之下，其余大部分"一等能力"（UI 贡献、feature kind、多模型路由、设备码流）都停在"第 0 个实例"上（11 §12.4 的判据），只有 D5/D11 是"第 3 个实例才该提取的抽象"，却被正确地提前做了。
**红队视角的加成**：它同时是**最小化攻击面**的决策——内核不认识具体系统，就意味着不存在"new-api 专用的信任旁路"（01 §2 那一整章的风险被关进了插件边界）。

### 2. 最危险的一个决策：**D17（推迟站点级 RLS）所依据的前提——"站点隔离当前是数据卫生而非安全边界"**
**为什么**：这不是一个实现取舍，而是**用一个产品假设替换了一条安全控制**：
- 前提本身是**可被产品动作推翻的**：触发条件是"出现 ≥2 个互不信任 developer 共享实例"，而 enable saas 就是一次产品动作（08 §11.2），08 §13 S1 还把"普通用户自建站点"列为备选；
- 它把"隔离"的**唯一强制层**拿掉，只留下应用层注入，而注入值的来源（会话 activeSiteId）在数据模型里**没有承载列**（#3）——控制被拿掉的同时，控制的对象也没有定义；
- 它的**失效不可观测**：跨站点数据污染（10 §11 R5 自述"静默的跨站点数据污染，不报错"）、跨站点读取、资格冒用都不产生告警；
- 它的成本论证建立在一个**自证**的 spike 上（11 §14.2：判据被自己的前置决定，恒 ≤3），而且 CHANGELOG D16 与 01 §5.5 仍在对外承诺"双层强制"，导致**文档承诺 > 实际强度**——这比"强度不足"更危险，因为它会误导 M6-8 的安全自查。
**次危险（同量级，但影响面稍窄）**：03 §1.18.3「项目侧 token 同时可作为登录平台自身的凭证」（#2），因为它把"项目 ↔ 平台"的信任边界打通，且是**设计承诺**而非实现疏漏。

### 3. 如果只能改一处：**把"站点作用域"从"会话派生 + 代码注入"改造成"可承载、可断言的显式授权对象"**
具体落点是 **A1**：ag_sessions 补 realm/activeDeveloperId/activeSiteId + 06 补会话切换契约与归属校验规则 + crossSite() 收敛为唯一函数并被 CI 断言。
**为什么是这一处**：它是**唯一同时**满足以下三条的改动——
1. **阻塞面最广**：site_id 注入、RLS 上下文、审计归属、配额分片、调度分片、控制台端点全部以它为输入（01 §5.5、08 §7、08 §10、05 §6.2、10 §12 S2）；
2. **后补成本最高**：D17 前置 3 把"单一事务入口"称为"把后补 RLS 成本压到 O(1) 的唯一条件"——同理，会话作用域一旦晚改，就要审计每一条读路径与每一个控制台端点（这正是 #3 攻击路径的成因）；
3. **改完之后，#4 的文档矛盾可以一次性消解**：无论最终决定"启用 RLS"还是"M7 再启用"，都需要一个**权威的作用域来源**来写验收断言；有了它，D16 与 D17 才可能被写成一个结论而不是两个。
> 附注：若把问题限定为"M1 期间最容易被利用的一处"，答案会变成 **A2（出站白名单）**——但它的影响面是单插件、单站点；A1 的影响面是整个 SaaS 承诺。
