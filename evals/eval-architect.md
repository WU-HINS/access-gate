## 第二部分 · 关键问题 Top 10

### ① 06（接口与界面）整体没有站点维度与开发者身份域——与 08 的三平面正面对撞 【高】

- **位置**：06 §9（信息架构）、06 §5（管理侧）、06 §7.3.1；对比 08 §1（三平面）、08 §6（两级选择）、08 §9（URL 契约）
- **现象**：06 全文 **"开发者" 0 命中、"站点" 1 命中（且是"GitLab 站点地址"）、"site" 0 命中**。06 §9 的信息架构只有「我的空间 + 管理控制台」，没有站点平面；08 §9 却定义了 `/me/:devId/:siteId/*`、`/console/:siteId/*`。更硬的一条：06 §5.5 的 `POST /admin/settings/newapi/test` 是**全局单一连接**，而 08 §4.1 规定 `newapi-provider` 是 `config.scope: site` 的 **每站点一份配置（各站点指向不同 new-api）**。
- **后果**：G4「投射到任意下游」在 API 契约层不成立——一个平台只能表达一个下游连接；站点级 provider 配置（08 §4.1）没有 API 承载；用户无法进入站点上下文，08 §6 的"两级切换器"无接口。M4/M7 必须重写整个管理 API 与 IA（返工量 ≈ 一个前端工作流）。
- **修正**：把 08 §9 的 URL 与两级选择器回写 06 §9；所有管理/同步/插件配置 API 增加 `siteId` 维度（或明确 `crossSite` 语义）；`/admin/settings/<plugin>/test` 改为站点级。
- **违反**：G4、D13「站点是隔离边界 + 配置单元」、01 §4.2.2「新需求必须落插件层」（站点维度不是插件能提供的，属内核能力，必须在契约里出现）。

### ② 刚补进白名单的两张表**仍然违反白名单**（deepseek 基线 #3 的修复不彻底） 【高】

- **位置**：02 §1 line 21（白名单）vs 02 §3.8 line 235（`ag_plugin_instances`）、02 §7.2 line 933（`ag_provider_sync_state`）
- **现象**：白名单要求"每表必须含 `siteId: col.uuid().notNull()`；若有唯一键，其首列必须是 `siteId`"。实际声明：`ag_plugin_instances` 的 `siteId` 是 **nullable**，唯一键 `uq_ag_plugin_inst_dev` 首列是 `developerId`；`ag_provider_sync_state` **根本没有 siteId**，主键仍是 `provider: col.varchar(64).primaryKey()`——而 10 §S2 明确要求"主键从 `provider` 改为 `(siteId, provider)`"。
- **后果**：按 02 §1 的规则，`db:check` 应在 M0 启动时 **fail-fast** → 要么门禁是空文（与 11 §11.2② 声称的"改白名单驱动"矛盾），要么 M0 起不来。若按现状建表，**对账游标是全局的**：站点 A 的游标会让站点 B 漏对账，且不报错（静默跨站点数据污染）。
- **修正**：`ag_plugin_instances` 的 siteId 改 notNull 并调整唯一键语义（或用 `ownerScope/ownerId` 统一）；`ag_provider_sync_state` 主键改 `(siteId, provider)` 并加 siteId。
- **违反**：G1/G4（对账是所有下游对齐的前提）、02 §1 自己的门禁约定。

### ③ G1 的核心表有三个名字，且 provider 契约里没有"身份键"的位置 【高】

- **位置**：01 §2.3 line 111（`identity_links`）、01 §6.1 line 654、03 §1.16.6 line 838（`ag_identity_links`）、02 §3.2 line 77（`ag_identities`）；03 §1.16.2 line 734–755（`ProviderPlugin` 接口）vs 05 §2.2 line 293/299
- **现象**：同一张"对齐表"在三处叫三个名字。更实质的是契约层：`ProviderPlugin` 接口只有 `findSubject?(by: {key, value})`（`key` 是**自由字符串**，05 §1.3 直接硬写 `'oidc_id'`），**没有 `identityKeys` 声明**；接口里也没有任何**写方法**，而 05 §2.2 的伪代码调用了 `provider.updateSubject(...)`。
- **后果**：G1「与任意下游系统的主体一一对应」所依赖的"对齐键"在插件契约里**没有槽位**——第二个 provider（Discord/K8s）接入时，要么改核心（违反 G6），要么临时扩契约（冻结失败）。G4 的写投射同理无契约，`capabilities.update` 声明了却无对应方法。
- **修正**：provider manifest 增加 `identityKeys: [{key, kind, unique, requireVerified}]` 与 `updateSubject/setStatus` 方法；核心只按声明解析，禁止在核心出现 `'oidc_id'` 字面量。
- **违反**：G1、G6（"新增下游系统 = 安装一个插件"）、03 §1.16.3 自己的"硬性验收标准"。

### ④ 「白名单驱动」门禁仍不是派生规则：至少 4 张表逃出，且清单标题计数错误 【高】

- **位置**：02 §1 line 21（两张白名单）vs 02 §2 line 29–39（领域划分）
- **现象**：白名单标题写"**站点作用域（12 表）**"，实际枚举 **14** 张表名。同时下列表**不在任何一张白名单**里：`ag_policy_assignments`（02 §5.2 line 721，**无 siteId**，是决定"谁走哪条策略"的站点级业务表）、`ag_oidc_signing_keys`（私钥表，02 §7.4）、`ag_oidc_providers`（持 `clientSecretRef`，02 §7.9）、`ag_plugin_configs`（持配置内容，02 §4.2）。
- **后果**：11 §11.2② 的根因（"标记驱动 → 门禁永不报错"）只是换成了"**人工清单驱动**"——同一失效模式复现：新增一张站点级表只要不写进清单，门禁永远不报错。`ag_policy_assignments` 无 siteId 意味着分流绑定可跨站点生效。
- **修正**：把白名单改为**从表声明派生的规则**（含 `siteId` 或 `ownerScope/ownerId` 的表强制校验，未声明的表必须显式列入"平台级豁免清单"并给理由）；修正标题计数。
- **违反**：D13、02 §1 自己的门禁约定、11 §11.2② 的方法论结论。

### ⑤ R1（插件端点站点维度）在它点名的两份承载文档里 **0 落地** 【高】

- **位置**：10 §R1 line 720–734 与修正清单 line 843（"落地位置 03 §1.13 / 06 §7"）vs 03 §1.13.1 line 452、06 §7.3.1 line 614
- **现象**：10 §R1 判定 🔴 并要求挂载规则改为 `/api/plugins/<siteSlug>/<pluginId>/<path>`、`pluginToken` 绑定站点、冲突检测改 `(siteSlug, method, path)`。实际：03 §1.13.1 与 06 §7.3.1 都仍写 `/api/plugins/<pluginId>/<path>`；`siteSlug` 在两文档中 **0 命中**（只在 10 与 04 §1.2.7 的寻址语法里出现）。
- **后果**：10 §R1 描述的原始缺口原封不动——多站点下同一 URL 指向哪个站点的插件配置**无解**（用会话则外部调用无会话；用第一个站点则站点 B 的调用会用站点 A 的凭据）。R3（`pluginToken` 跨站点冒用）同样未修。G7 的"插件可注册子路由"在多站点下不可用。
- **修正**：把 10 §R1 的规格逐条写入 03 §1.13.1/§1.13.2 与 06 §7.3（含端点发现与 OpenAPI 按站点分组）。
- **违反**：G7、D13、11 §11.2③「声称 ✅ 已落地有 6 处不成立」的同一类错误。

### ⑥ G5「可回滚」在 Grant 抽象层没有承载：四个抽象中 Grant 无实体、无逆操作契约 【高】

- **位置**：01 §1.1 line 24 / 01 §4.1 line 350（Grant 为一等抽象）vs 02 全部 39 张表
- **现象**：grep `Grant` 在 02 中 **0 命中**——没有任何 grant 实体；最接近的只有 `ag_user_policy_state.appliedActions`（02 §6.1）与 `ag_actions_log`（02 §6.3）。action 插件 manifest（03 §1.4 / 09 §2.2）**没有"是否可逆 / 逆操作是什么"的能力位**。第 7 代已证"全系统唯一逆操作只覆盖 1 个属性"，`add_quota` 不可逆（11 §12.1）。
- **后果**：G5 的"可回滚"是**承诺而非机制**。新接入的下游动作默认不可回滚，而系统**不知情**——回滚 API（05 §3.4）会对任何动作宣称可回滚，实际无逆操作可执行（对应第 5 代 N8：既无动作实现，也无"剩余档位"的权威来源）。
- **修正**：action 契约增加 `reversible: { inverse, requiresReadback }`；核心持久化"授予 ↔ 逆操作"对（即真正的 Grant 实体），无逆操作的动作在 UI/API 上显式标注"不可回滚"。
- **违反**：G5（可回滚）、01 §1.1 的四抽象承诺。

### ⑦ "声称已修"的第 6 代修复（outbox + 死信）在 02/06 里 0 承载 【高】

### ⑧ 目标集合与设计集合不闭合：站点化/SaaS 不在 G1–G7 内，却反向改写了核心契约 【中高】

- **位置**：01 §1.2（G1–G7）、01 §1.3（"多站点 SaaS 是独立阶段 M7，不阻塞单站点"）vs 08 全文 446 行 + D12/D13/D14 + 10 §R1–R8 / §S1–S6
- **现象**：G1–G7 **没有任何一条**要求多租户/站点/身份域。但站点化带来的修正清单包括：`ag_plugin_facts` 唯一键（10 §R5）、`ag_external_subjects` 改站点级镜像（10 §R6）、tags 站点化（10 §S3）、provider 强制 `scope: site`（10 §S1）、端点 URL 加维度（10 §R1）、12+12 表白名单。而 07 §2 line 51 称 M0 的 siteId 是"**零成本预留**"，D17 裁决理由① 却承认"站点隔离当前是**数据卫生**而非安全边界"。
- **后果**：无法用目标给里程碑排优先级——07 §2 只能按"可演示价值"排（自认 P4）；"零成本预留"的假设与 14 张表补列 + 唯一键改造 + 端点维度改写的实际成本不符；M7 的范围与风险没有目标背书，D17 又把它推到了未知时点。
- **修正**：二选一——(a) 把"多站点 SaaS"升格为 **G8** 并单列预算与风险；(b) 按 D17 的触发条件把站点维度降级为可选特性，把 M0 的 siteId 预留从"必须"改回"建议"。
- **违反**：目标反推原则本身（先定目标、再定手段）。

### ⑨ 目标之间冲突：G4「投射到任意下游（复数）」 vs 08「每站点每插件配置唯一」 【中高】

- **位置**：01 §1.2 G4 line 41（"任意下游：new-api 分组 / Discord 角色 / MC 白名单 / K8s RBAC"）vs 08 §2 line 57（"Site → 插件配置 **一对一（每插件）**"）、08 §6 line 6（需求原话"每个站点的插件配置唯一…只能写一个目标平台"）、08 §13 S6 line 446（"保持唯一（默认），需要两个目标就建两个站点"）vs 03 §1.19.1 / 08 §4.1 line 155（`site + multi` 是合法象限）
- **现象**：同一件事在三处有不同答案：03 §1.19.1 已支持 `instances.mode: multi`，08 §4.1 把它列为合法象限，08 §2/S6 却按"每插件一份"设计并保持"待确认"。叠加 10 §R6/§S1 把主体定为**站点级镜像**后，同一自然人在多个下游的身份被切成多份。
- **后果**：G1「与任意下游系统的主体一一对应」与 G4「投射到任意下游」只能在"一个站点一个 provider"的退化形态下成立；多目标场景要么建多站点（主体/标签/状态各存一份，跨站点不可见），要么违反 S6。这是**目标之间的真实冲突**，不是实现细节。
- **修正**：裁决 S6，明确"一个站点可挂多个 provider 实例"，并给出跨站点主体的合并口径（或明确声明"一个站点 = 一个下游"并同步修正 G4 的措辞）。
- **违反**：G1、G4 与 D13 三者不可同时成立。

### ⑩ 「AST 唯一真理 + 三形态等价」是为一个手段建立的不变量；手段被砍后不变量与验收项同时悬空 【中】

- **位置**：CHANGELOG D3 line 49–51、04 §1.2.6 line 147、07 §3 M3-6/M3-7 line 119–120 vs 11 §12.4 line 422（"三形态表达式 → YAML + JSON 双视图（砍图形编辑器）**-12 人日**"）、11 §14.3 line 572
- **现象**：D3 把"YAML/JSON/Graph 三形态等价"写成一等架构不变量（`specHash` 只对规范 AST 计算、M3-6 property-based 往返、M3-7"换编辑器 `specHash` 相同"），而它的**唯一受益者是图形编辑器**。第 9 代建议砍掉图形编辑器（理由：用户画像"非技术管理员"在 13 份文档里从未出现），11 §14.3 随即承认 `specGraph` 成死列、M3-7 验收失效。
- **后果**：典型的"**手段升格为目的**"——不变量、表列（`specGraph`/`origin`）、两条验收项都建立在一个无用户依据的手段上；无论砍与不砍都要返工（砍 → 死列与失效验收；不砍 → 12 人日 + 一个从未被需求确认的用户画像）。
- **修正**：把"三形态等价"从架构不变量降级为**编辑器内部实现约束**（不进 `specHash` 语义、不进验收门槛）；`specGraph` 列的去留与图形编辑器一并裁决。
- **违反**：抽象恰当性（"为第 1 个实例写抽象 = 成本"）、G3（G3 要求的是"三种等价表示"，未要求等价性成为**版本语义的一部分**）。

> **次要证据（不单列，供交叉核对）**：05 §7.1 的 9 个指标 0 个带 siteId（vs §7.1.1 自定规则）；05 §7.1.1 的 `gate_eval_outcome_total` 在 §7.1 不存在；D20 的分流表有 5 条处置，承载它的 `Outcome` 只有 4 态（04 §1.5 line 628），且 04 §1.5.1 line 673 仍写"$required 直判"与 D20 的"与 $required 解耦"互斥（11 §14.6 已自认待修）；02 §1 line 4「即使共用同一个数据库」vs 01 §5.0/D11 数据库独占；07 §7 M0 行算术不一致；07 §4 vs §7 的 F3 排期矛盾。

## 第三部分 · 开工可行性判定

### 1. 现在可以开工 M1 吗？

**不可以。** 但 **M0 的两个地基项（M0-2 Schema 声明层、M0-5 作用域注入 + fail-closed 抛错）可以在补完下表 P1 后立即开工**。

理由（三条，均可执行）：
- 缺陷 ② 使 M0 的验收门槛（"PG 上跑通全部迁移 + `db:check`"）**当场不成立**：两张表违反 02 §1 的门禁规则，要么门禁是空文、要么启动 fail-fast。**这是 M0 自身的阻塞项，不是 M1 的**。
- 缺陷 ③⑤ 决定 M1-1/M1-3（provider 契约）与 M4（插件端点）的契约形态；11 §11.1 已自认"M1-1/M1-3 无法开工"，11 §14.6 已给出"两件冻结"。在这些契约冻结前并行开发会造成**运行期才炸**的合并冲突（11 §10 原话）。
- 缺陷 ① 决定 M1-11（管理端最小）与 M7 的全部 API/IA 形态；它属于"改契约"而非"加功能"，**现在改是 2 人日，M4 之后改是迁移级**（缺陷 ① 自己的后果分析）。

### 3. 若可直接开工，哪些风险可接受

不适用（判定为"不可以"）。但可并行说明**无耦合、可立即启动**的部分：

## 第四部分 · 最强与最弱

### 1. 最出色的一个决策：**D11「数据库独占，绝不 JOIN 下游表」**（01 §5.0 / CHANGELOG D11）

理由：全部 20 条 ADR 里，只有这一条把"核心不认识任何具体系统"（G6/D5）从一个**意图**变成了一个**可在数据层机械检查的约束**——只要 SQL 里不出现 `users.group`，provider 抽象就没有后门可绕。D5 说"核心只认识四抽象"是口号，D11 是让口号失效需要先违反一条硬边界。它是 G1/G4 在**第二个**下游系统上仍可能成立的前提（03 §1.16.6 的多 provider 共存、08 §4.1 的多站点镜像都建立在它之上）。

次优：D1「运行期插件」——它把"新增渠道 = 装插件"从承诺变成验收标准（01 §4.2.4 三条硬性验收），是 G2/G6 唯一可证伪的支撑。

### 2. 最危险的一个决策：**把"站点"设为隔离边界，同时承认真正的边界是 developerId 却不据以设计**（08 §2 + D17 裁决理由① + 11 §12.4 N4 + 08 §6）

理由：D17 裁决白纸黑字写着"站点隔离当前是**数据卫生**而非安全边界"（CHANGELOG D17 理由①），11 §12.4 N4 更直接："**真正的隔离边界是 developerId，不是 siteId**"；而 08 §6 又说"用户是平台级的"。**三个互斥的边界定义同时生效**，于是：每一张业务表的唯一键、每一个 URL、每一份插件配置、每一条审计可见性规则，都按一个**不是安全边界**的维度切分。危险之处不在"切错"，而在**切换触发条件已被自己写明**（D17："出现 ≥2 个互不信任 developer 共享实例 → 按 O(1) 成本立即切换"）——一旦触发，就必须在已经按错误维度落库的事实上再叠一层，而那时 `ag_provider_sync_state`、`ag_policy_assignments`、`ag_external_subjects` 都已经带着错误的作用域键上线了。叠加缺陷 ①（06 全文 0 处站点/开发者）意味着这个维度**连 API 契约都还没进**。

### 3. 如果只能改一处：**把"作用域"从"人工白名单 + 逐表签署"改成"从表声明派生的单一门禁"，并立刻用派生规则扫一遍全部 39 张表**（02 §1）

理由：缺陷 ②（两张表违反刚补的白名单）与缺陷 ④（四张表逃出白名单 + 计数错误）是**同一根因**的产物——11 §11.2② 把"标记驱动"换成"白名单驱动"时，换掉的是**触发方式**而不是**失效模式**（人工清单永远会漏）。这是全部发现中**唯一一处"改一次就能防止后续所有同类缺陷"**的地方：派生规则一旦建立，`ag_policy_assignments`（决定谁走哪条策略）这类今天逃逸的表会自动被纳入，且新增表不再依赖人的记忆。成本 1 人日，收益是消除一个已经复现两次的缺陷类别。
**为什么不是缺陷 ①**：06 补站点维度是 2 人日且**必须做**，但它只修一个文档；派生门禁修的是**产生缺陷的机制**。
