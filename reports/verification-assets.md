# 验证资产清单

> 本文件回答一个问题：**「我怎么知道这东西真的能用？」**
>
> access-gate 的验证不靠「读代码觉得对」，而靠**可复跑的工具**。
> 每个工具都对应本会话真实踩过的坑——**它们不是理论上的检查，是被缺陷逼出来的**。

---

## 一、一句话总览

```bash
npm test                      # 986 个单元/集成测试（含真实 PG 的 pg-real）
npm run ci                    # 11 项门禁（静态为主，秒级到分钟级）
AG_CI_REAL=1 npm run ci       # 11 项全跑，其中第 10 项额外做真实 PG 集成

npm run verify:real           # 真实 PG 动态验证（path-probe + patrol-liveness）
npm run verify:all            # 再加 14 步主线端到端与带负载长跑
```

★ **`AG_CI_REAL=1` 那一项默认标记为 `WARN 未执行` 而不是 PASS**——
因为「跳过 ≠ 通过」，而它覆盖的正是**最难靠静态检查发现**的两类问题：
**未接线**与**事务边界**。

---

## 二、逐个工具：它验什么、能发现哪类问题

### 1. `tools/serve-real-e2e.ts` —— 真实 PG 下的完整主线

| 项 | 内容 |
|---|---|
| **验什么** | 真实 PostgreSQL 启动 → 迁移 → `--mode=real` 起服务 → `/healthz/ready` → OIDC 端点 → 引导登录 → 两级选择 → 提交 → 控制台导航 → 权限边界 → **资格查询** → 站点持久化 |
| **怎么跑** | `node --experimental-strip-types tools/serve-real-e2e.ts` |
| **能发现** | 「内存模式能跑但真实模式不能」——本会话由此发现**迁移运行器不支持外部 PG**、**`ag_migrations` 从未被创建**、**冷启动无登录方式** |
| **当前** | **14/14** |

★ 它**不允许回落内存模式**（`AG_REQUIRE_REAL_PG=1` 会把探测失败变成失败）。

### 2. `tools/path-probe.ts` —— 动态路径覆盖（**六层递进**）

| 项 | 内容 |
|---|---|
| **验什么** | 55 条路径（27 条手工 + 28 条**从路由表自动推导**）的**六层检查**：<br>① 状态码 · ② **契约**（2xx 的字段存在且类型正确）· ③ **错误结构**（4xx 必须有非空 `error`）· ④ **敏感字段**（响应不得含密钥/哈希）· ⑤ **写后读一致**（写进去的数据读得回来）· ⑥ **字段值正确**（写进去的**值**没被改写）· 外加事务错误特征串 |
| **★ 为什么是六层** | 每一层能抓到**上一层抓不到**的问题：<br>· 状态码 → 抓 5xx，但**看不到**「200 但内容错」<br>· 契约 → 抓字段缺失，但**看不到**「字段在、值是错的」<br>· 写后读 → 抓「返回 200 但没写库」，但**看不到**「写进去了、值是错的」<br>· 字段值 → 抓「写入了错的值」<br>★ 每层都有**自测**（植入反例证明能检出），且**每层都明确标注边界**。 |
| **怎么跑** | `node --experimental-strip-types tools/path-probe.ts`<br>`node --experimental-strip-types tools/path-probe.ts --self-test` |
| **能发现** | 「返回 200 但内容是错的」·「4xx 但调用方拿不到可操作信息」·「事务外查询」·「路由未挂载（404）」 |
| **当前** | **55/55**（无事务错误、契约全符合、无敏感字段泄露、写后读一致、字段值正确）；自测 **15/15** |

★ **写操作需要 CSRF token**：探针先从 `/api/me` 取 `csrfToken` 并带上 `X-CSRF-Token`。
★ 我最初把写操作的 403 误判为「会话不是 admin」——**实际是缺 CSRF token**
（错误信息里写得很清楚）。**看到 403 就归因于权限是想当然。**

★ 它抓过的真实缺陷：
- **6 个 500**（嵌套事务：handler 入口事务 × store 工厂事务）；
- **2 个 500**（非法 uuid 直接进 SQL → 应为 400）；
- **1 处静默降级**（`/api/ui/manifest` 无宿主时返回 200 + 空清单）；
- **3 条路由未挂载**（`simulate` / `versions` / **`rollback`**）；
- **1 处静默降级**（`/api/ui/manifest` 无宿主时返回 200 + 空清单）；
- **我自己写错的两处检查规则**：契约猜错字段名（`contributions` 实为 `nav/pages/slots`）、
  「无泄露」扫描与「正向验证」互相矛盾（加 `allowsSecret` 豁免解决）。

★★ 两条设计要点：
1. **路径从路由表自动推导**——手工清单会漂移（我曾写了 6 个端点却忘了加进清单，而它们当时全部 500）；
2. **`--self-test`**——用 8 个用例证明检查函数**不是恒真**。
   （我第一次自测失败两次：一次改了没被探到的路径，一次抛错被转成 500。
   **「没有告警」不等于「没有问题」，也可能是告警没接上**。）

### 3. `tools/patrol-liveness.ts` —— 定时任务**真的执行了吗**

| 项 | 内容 |
|---|---|
| **验什么** | 设 `AG_PATROL_INTERVAL_MS=15000`，观察 `ag_jobs` 的 `run_count` / `last_run_at` / `fail_count` / `status` / `last_error` |
| **怎么跑** | `node --experimental-strip-types tools/patrol-liveness.ts` |
| **能发现** | 「启动了但从不执行」·「执行一次就失败」 |
| **当前** | **5/5** |

★ 它抓过的真实缺陷：巡检**执行即失败**（`TransactionRequiredError`），
而 `run_count` 从 0 变 1 **看起来完全正常**——
★ **「注册了」≠「执行了」≠「成功了」**。

### 4. `tools/soak.ts` —— 带负载长跑（泄漏与累积错误）

| 项 | 内容 |
|---|---|
| **验什么** | 子进程 RSS（`/proc/<pid>/status`）· PG 进程数（**趋势判断**，非绝对值）· `/metrics` 错误计数 · `/healthz/ready` |
| **怎么跑** | `node --experimental-strip-types tools/soak.ts --minutes=2 --load=50` |
| **能发现** | 内存泄漏 · 进程泄漏 · 错误累积 |
| **当前** | 分钟级 **5/5**（5000 请求 0 失败，均延迟 14ms）；**小时级未验证**（需预发环境） |

★ 它抓过的真实缺陷：**PG 实例泄漏 65 分钟**——
根因是 `process.on('exit')` **在信号杀死时不触发**，而 `timeout` 发的正是 SIGTERM。

### 5. `tools/bench.ts` —— 性能（必须用 `http.request`，不能用 `fetch`）

| 项 | 内容 |
|---|---|
| **验什么** | 管理读 QPS / p50 / p95 / p99；全量评估（可指定主体数） |
| **怎么跑** | `node --experimental-strip-types tools/bench.ts --qps-requests=2000 --qps-concurrency=128`<br>`node --experimental-strip-types tools/bench.ts --subjects=100000 --skip-qps` |
| **能发现** | 性能退化 · 算法复杂度问题 |
| **当前** | 管理读 **723/s**（≥500）· 10 万主体 **10.8s** |

★★ **一个测量教训**：早期用 `fetch`/undici 测，把客户端开销算到服务端头上
（空服务器上 `fetch` 539/s vs `http.request` 1386/s，**2.5 倍差**）——
差点让我去优化一个不存在的问题。

★ 它抓过的真实缺陷：`InMemoryFactStore.list()` 是 O(n) 而每主体调用一次 →
**O(n²)**；修后全量评估**提升 89 倍**。

### 6. `tools/route-coverage.ts` —— 静态：实现的路由是否都被挂载

| 项 | 内容 |
|---|---|
| **验什么** | 从 `admin/api.ts` 提取实现的路由，与 `routes.ts` 的 `mount(...)` 清单比对 |
| **怎么跑** | `node --experimental-strip-types tools/route-coverage.ts` |
| **能发现** | 「实现存在但用户调不到」（404） |
| **当前** | **42 条实现 = 42 条挂载，0 未挂载** |

★ 它抓过的真实缺陷：`simulate` / `policies/:code/versions` / **`policies/:code/rollback`**
（后者是目标点名的 M6-2 核心能力，**实现完整但从未挂载**）。

★ **自测过**：临时移除一条挂载，它立刻报出——证明不是恒真。

### 7. `tools/api-coverage.ts` —— 文档声明的端点 vs 实际实现

| 项 | 内容 |
|---|---|
| **验什么** | `docs/06` 声明的 126 个端点 vs 源码实际注册的路由 |
| **怎么跑** | `node --experimental-strip-types tools/api-coverage.ts`<br>`... --write-report`（生成 `reports/api-gap.md`）<br>`... --json` |
| **能发现** | 「路线图 done 但接口没实现」 |
| **当前** | **43.7%**（本会话起始 14.3%） |

★ 它揭示的核心事实：**「路线图 90/90」与「接口面可用」是两个维度**——
路线图是 90 个**任务**（粒度粗），接口面是 126 个**端点**（粒度细）。
M5-6 标 done 时 `/oauth/*` 一条都没实现，正是这个粒度差的结果。

★ **刻意不作为 CI 门禁**：以非零退出会逼人去「消数字」，而不是判断哪些接口真该补。

### 8. `tools/table-coverage.ts` —— 文档声明的表 vs 代码实际读写

| 项 | 内容 |
|---|---|
| **验什么** | `docs/02` 声明的表 vs `src/**` 实际读写的表 |
| **怎么跑** | `node --experimental-strip-types tools/table-coverage.ts` |
| **能发现** | 「有表但代码没用」——**尤其是「被另一种存储方式替代了」** |
| **当前** | 42 张声明 / 42 张建表 / 23 张被引用 / **19 张未使用** |

★ 它抓过的真实缺陷（R30，本会话最有价值的一轮）：
1. **`ag_secrets` 从未被任何代码读写**——而设计文档明确要求用它加密存调用方密钥；
2. **真实 PG 模式下协同验证用的是内存 store**（`InMemoryVerifyClientStore`）
   → 调用方重启即丢，且**管理端写 DB、校验端读内存**，创建的调用方永远校验不过；
3. **`serve.ts` 从未给 admin handler 注入依赖** → 6 个管理端点在真实服务里全部 404；
4. **架构冲突**：handler 入口事务 × store 工厂事务 → 嵌套 → 6 个端点 500。

★★ 与 `api-coverage` 一样**刻意不作为 CI 门禁**——「有表没用」需要人工判断
是「未实现」还是「被替代」。

### 9. `tools/docker-preflight.ts` —— 容器化静态检查

| 项 | 内容 |
|---|---|
| **验什么** | Dockerfile / compose / healthcheck / 卷声明 等静态项 |
| **怎么跑** | `node --experimental-strip-types tools/docker-preflight.ts` |
| **能发现** | 容器配置的静态错误 |
| **当前** | 静态 **10/10**；**5 项真实执行无法验证**（本环境无 Docker） |

★ 它**明确区分**「通过」与「无法验证」，并逐项写出后者：
**静态检查不能替代真实 `docker build` + `compose up`。**

### 10. `tools/authz-coverage.ts` —— 静态：管理端每个路由分支是否都鉴权

| 项 | 内容 |
|---|---|
| **验什么** | `admin/api.ts` 里每个路由分支的体内是否出现 `requireAdmin` / `requireSite` |
| **怎么跑** | `node --experimental-strip-types tools/authz-coverage.ts`<br>`... --self-test` |
| **能发现** | **某个分支忘了鉴权**（越权） |
| **当前** | **35/35 分支已鉴权**；自测 **4/4** |

★★ **第一版只提取到 9 个分支（实际 37 个），而输出是「未鉴权 0」——**
**看起来像「全部安全」，实际漏报了 28 个**。根因是我硬编码了「恰好 6 个空格」的缩进，
而文件里是 6/8/10 三种。★ **而第一版的自测没能发现它**（两个用例恰好都是 6 空格）——
**自测用例必须覆盖真实的多样性**，否则自测给出虚假的安全感。

★ 本工具还**主动自报覆盖范围**（「文件内 method 判断 37 个，本检查提取 35 个，差额说明」），
并明确写出**它不能判断什么**（鉴权是否在所有代码路径上都执行）。

### 11. `tools/ci-gate.ts` —— **11 项**门禁（含 4 个自证）

| 项 | 内容 |
|---|---|
| 1 | `tsc --noEmit` |
| 2 | 单测（全部） |
| 3 | DDL 编译快照对比 |
| 4 | `db:check`（门禁 + 漂移检测） |
| 5 | `site_id` 缺失检测 |
| 6 | **禁止裸 SQL 拼接**（`src/**`） |
| 7 | **核心代码具体系统名 = 0** |
| 8 | **单一事务入口**（禁事务外驱动查询） |
| 9 | 安全自查（越权 / SSRF / 注入 / 密钥 / 会话） |
| 10 | 真实 PG 集成（**默认 WARN 未执行**，`AG_CI_REAL=1` 时执行） |
| 11 | 路由一致性 + **探针检查函数自测** |

★ `--self-test` 证明第 5/6/7 项**不是恒真**（否则它们可能只是「永远通过」）；
第 11 项现在会**先跑两个自测**（探针检查函数 15/15、鉴权检查 4/4），
自测不通过则该项直接 FAIL（「检查不可信，后续结论无意义」）。

★★ 门禁多次**正确拦住我**：第 6/9 项拦住手写 count SQL；
第 8 项拦住新仓储层（`registry-store` / `config-store` / `endpoint-store` /
`user-store` / `grant-store` / `secrets/store` / `client-store-db`）。

## 三、这些工具背后的**共同教训**

本会话 40 轮里，反复出现的模式：

| 模式 | 例 |
|---|---|
| **「启动了」≠「工作了」** | 巡检 `run_count` +1 但执行即失败；调度器从不执行任务 |
| **「实现存在」≠「接好线了」** | `/oauth/*` 没实现；3 条路由未挂载；6 个管理端点未注入依赖 |
| **「内存模式通过」≠「真实模式通过」** | 枚举取值（4 次）、uuid 冲突（4 次）、jsonb、id 形态、分页语义 |
| **「200」≠「内容对」** | 插件列表硬编码；`total` 语义变化；静默降级返回空清单 |
| **「检查通过」≠「检查有效」** | 探针漏检中文错误；契约猜错字段；恒真断言；**自测本身没被触发**；**硬编码 6 空格缩进致 28 个分支漏报而显示「全部安全」**；**检查正则过窄致恒真** |
| **「403」≠「权限问题」** | 写操作全部 403 的真因是**缺 CSRF token**——错误信息里写得很清楚，而我没先读它 |
| **「测量数字低」可能是测量错** | `fetch` 的 2.5 倍开销；soak 把正常连接数波动判为泄漏 |

★★ 因此本项目的验证原则是：

1. **能真实运行的，绝不靠静态推断**（真实 PG、真实 HTTP、真实信号）；
2. **每个检查都要能自证不是恒真**（`--self-test`）；
3. **跳过要显式标注为「未执行」**，不能显示成 PASS；
4. **量化差距比掩盖差距有价值，但量化之后要做的是判断，不是消数字**；
5. **每次扩大检查范围，都会先抓到检查者自己**——这是正常的，也是必要的。
