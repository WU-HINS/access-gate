## 二、这 5 列各自"少的是什么机制"

| 列 | 缺的机制 | 后果 |
|---|---|---|
| `lastEvalId` | 状态**回溯到依据**（哪次评估导致了这个状态） | 排障时只能看"现在是什么状态"，**答不出"为什么会变成这样"** |
| `satisfiedAt` | 区分「**满足**」与「**授予**」两个时刻 | 无法回答"满足后多久才真正授予"（动作延迟/失败的时间度量） |
| `indeterminateSince` | 「**长期不可判定**」的判据 | 「渠道长期故障」与「刚抖动一下」**无法区分**——前者该人工介入，后者该等 |
| `failStreak` | **失败退避**（连续失败 N 次后放缓/暂停） | 上游持续失败时仍按原频率重试（放大故障） |
| `nextCheckAt` | **按时间调度巡检** | 只能全量扫描；`ix_ag_state_next_check` 这个索引**没有查询在用它** |

## 三、处置（逐项，不留沉默）

| 列 | 处置 | 理由 |
|---|---|---|
| `lastEvalId` | **实现** | 成本低（评估写状态时带上 `evaluationId`），价值高（可追溯） |
| `satisfiedAt` | **实现** | 成本低（状态转为 `satisfied` 时写），且它是"授予延迟"度量的分母 |
| `indeterminateSince` | **文档标注** | 它需要"长期不可判定 → 人工介入"的**策略**（阈值、通知渠道）——那是运维决策，不是缺一行代码 |
| `failStreak` | **文档标注** | 同上：退避**策略**（次数、退避曲线）需要定，不能凭空实现一个数字 |
| `nextCheckAt` | **文档标注** | 按时间调度巡检要改调度器语义（从"全量轮询"到"到期唤醒"）——属**架构级改动**，且当前全量扫描在 10 万主体下已通过性能门禁（6.3s），**不是瓶颈** |
| `appliedActions` | **文档标注（被替代）** | 它与 `baseline` 语义重叠，而 `baseline` **在用**（47 处）。应由 `docs/02` 写明二者关系，避免后人以为"两个都该用" |

★ 结论：**2 列实现、3 列显式标注**。关键是**不留沉默**——
`nextCheckAt` 建了索引却无人查询，是这轮审计里最值得记的一条：
**索引也是一种"承诺"**（"我们会按这个列查"），而它当时没有兑现。
