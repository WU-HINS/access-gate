# 方案推荐：开发者级插件的事实记在谁名下？

> **决策问题**：`github` 这类 `configScope: 'developer'` 的插件采集到的事
> （`fact.github.public_repos` 等），在 `ag_plugin_facts` 里应该记在**谁**名下？
>
> **为什么必须决定**：`FactPipeline` 要求 `userId`（其语义是**平台用户** `ag_users.id`），
> 而插件的配置属于**开发者**（`ag_developers.id`）——★ 两者是**不同的 uuid**。
> 在决定之前，**插件的自动调度无法接线**（手动触发端点已可用，但需要调用方显式给 `userId`）。
>
> ★ 本文件给出三种方案 + **明确推荐**，让决策**可以在一轮之内做出**。

---

## 一、事实基础（都已在代码/schema 中确认）

| 事实 | 位置 / 证据 |
|---|---|
| 事实表的主键语义是「**某站点 · 某主体 · 某命名空间**」 | 唯一索引 `uq_ag_facts_user_namespace (site_id, user_id, namespace, instance_key)` |
| `user_id` 是 **NOT NULL uuid**，指向 **`ag_users.id`** | `docs/02` · `migrations/0001_init.sql` |
| 插件的 `configScope` 可以是 `developer` | `github` 插件：`configScope: 'developer'`，配置含 `username` / `token` |
| `ag_developers.id` 与 `ag_users.id` **不是同一个值** | R76 核实：`createDeveloper` 用 `randomUUID()`，且**不写** `ag_users` |
| 插件配置是**开发者级**的（该开发者名下所有站点共享） | `github` 的 `configSchema` 注释：「token 只配一次，被该开发者名下所有站点共享（M4-3）」 |
| 「事实是全局的」这一假设**已被明确否定** | `FactStore` 的说明：「`fact.qq.level` 显然是**某个用户**的 QQ 等级，不是全局值」 |

★ 最后一行很重要：它说明**不能**引入「平台级事实」来绕过这个问题。

---

## 二、三种方案

### 方案 A：让「开发者」也是平台用户（**建立映射**）

**做法**：入驻时为开发者**同时**建一条 `ag_users` 记录（或让 `ag_developers.id` **等于** `ag_users.id`），
于是「开发者」在事实表里就是一个合法的 `user_id`。

| 维度 | 影响 |
|---|---|
| **schema** | ★ 二选一：<br>① 新增 `ag_developers.user_id`（→ `ag_users.id`）**加列**；<br>② 或让 `ag_developers.id` **直接复用** `ag_users.id`（**不加列**，但改变既有语义） |
| **唯一索引** | ★ **不变**（`user_id` 仍是 uuid）——**这是它最大的优点** |
| **既有数据** | 需要**回填**：为既有 `ag_developers` 补 `ag_users` 记录（迁移里一条 `INSERT … SELECT`） |
| **查询** | 不变 |
| **语义** | ★ **最干净**：开发者**确实是**平台的一个主体（他也要登录、也有身份） |
| **风险** | 若选 ②（复用 id），会影响所有把两者当作独立 id 的既有代码（如 `ag_sites.developer_id`） |

★ 与已有设计的呼应：R76 引入的 `DEVELOPER_IDENTITY_PROVIDER`（`identity:oidc@platform:developer`）
说明**开发者身份本就登记在 `ag_identities` 里**——而那张表的 `user_id` 指向 `ag_users.id`。
★★ **所以方案 A 与既有设计方向一致**（开发者本来就是平台用户的一种）。

### 方案 B：让事实表支持「开发者主体」（**加主体类型**）

**做法**：`ag_plugin_facts` 增加 `subject_type`（`user` / `developer`），`user_id` 改名或加 `subject_id`。

| 维度 | 影响 |
|---|---|
| **schema** | ★ **改列**（加 `subject_type` + 可能改 `user_id` 语义） |
| **唯一索引** | ★ **必须一并改**：`(site_id, subject_type, subject_id, namespace, instance_key)`——否则「同一主体一行」的语义会被破坏 |
| **既有数据** | 需要回填 `subject_type = 'user'`（既有行全是用户事实） |
| **查询** | ★ 所有读事实的地方都要带 `subject_type`（`FactStore.get/list` 的签名要变） |
| **语义** | 中性：承认「事实的主体可以是用户或开发者」 |
| **风险** | ★ **改动面最大**（`FactStore` 接口 + 所有调用点 + 索引 + 迁移） |

### 方案 C：记在「配置所属开发者名下的站点主体」

**做法**：遍历该开发者名下的站点与主体，把插件事实**复制**给每个主体。

| 维度 | 影响 |
|---|---|
| **schema** | 不变 |
| **唯一索引** | 不变 |
| **既有数据** | 不需迁移 |
| **查询** | 不变 |
| **语义** | ★ **牵强**：配置是**开发者级**的（一次配置），事实却按**站点主体**存（N 份）——**同一份数据被复制 N 次**，且「谁是主体」本身是站点概念 |
| **风险** | ★ 数据放大（N 个主体 × M 个字段）；且**主体变化时要同步维护**（新主体加入 → 要补历史事实？） |

---

## 三、★ 推荐：**方案 A**（且选「加列」而不是「复用 id」）

### 推荐理由

1. ★★ **唯一索引不用动**——这是最大的工程优势：
   `uq_ag_facts_user_namespace` 的语义（「同一站点同一主体一行」）**完全保持**；
   而方案 B 必须改索引，方案 C 则把「一个事实」变成「N 个事实」。
2. ★ **与既有设计一致**：R76 的 `DEVELOPER_IDENTITY_PROVIDER` 说明开发者身份
   **本就登记在 `ag_identities`**（其 `user_id` → `ag_users.id`）——
   ★ 方案 A 是把这条**已经存在的**关系补全，而不是发明新概念。
3. ★ **语义正确**：开发者**确实**是平台的一个主体（他要登录、有身份、有会话）。
   「开发者的 GitHub 仓库数」是他的事实，不是「某个站点的某个用户」的事实。
4. ★ **改动面可控**：加一列 + 一次回填 + `recordDeveloperIdentity` 时顺带建 `ag_users` 记录。

### 为什么不选另两个

| 方案 | 不选的理由 |
|---|---|
| **B** | ★ 必须改唯一索引 + `FactStore` 接口 + 所有调用点——**为一个边界情况改核心数据模型** |
| **C** | ★ 语义牵强 + 数据放大 N 倍 + 主体变化时维护困难 |

### 为什么不选「复用 id」（方案 A 的变体 ②）

★ 虽然它「不加列」，但会把 `ag_developers.id` 与 `ag_users.id` **绑成同一个值**——
而既有代码（`ag_sites.developer_id` · `ag_developer_*` 表 · 入驻流程）**都假定它们是独立的**。
★★ **加列是加法，复用 id 是改语义**——前者可回滚，后者不可。

## 四、采纳后的落地步骤（可在一轮内完成）

| # | 步骤 | 说明 |
|---|---|---|
| 1 | `docs/02` 给 `ag_developers` 加列 `user_id uuid`（→ `ag_users.id`，可空以兼容既有行） | 走「文档 → 抽取 → DDL」流程 |
| 2 | 迁移里**回填**：为既有 `ag_developers` 建 `ag_users` 记录并回填 `user_id` | 一条 `INSERT … SELECT` + 一条 `UPDATE` |
| 3 | ★ **入驻时**（`redeem()` 的 `onboardIdentity`）**同时**建 `ag_users` 记录并回填 `user_id` | 复用 R91 的结构（**调用方无法忘记**） |
| 4 | 插件调度：`FactPipeline.userId = developer.userId`（取不到则**跳过并记日志**） | 接上 R94 已装配的编排器 |
| 5 | 真实 PG 测试：入驻开发者 → 触发插件采集 → **事实记在该开发者的 `user_id` 下** | 端到端 |

★ 第 3 步是关键：它让「开发者 ↔ 平台用户」的映射**在入驻时自动建立**，
而不是让每个调用方自己查——★ 与 R91 的教训一致（**必须做的步骤放进被调函数里**）。

## 五、★ 如果你倾向其它选择

| 你的关注点 | 建议 |
|---|---|
| 「不想动数据模型」 | 方案 C（**但接受语义牵强与数据放大**） |
| 「想让事实表更通用（未来还有别的 subject）」 | 方案 B（**但请一次改全**：索引 + 接口 + 调用点 + 迁移） |
| ★ **「现在就要能用」** | **方案 A**：它让插件调度**在下一轮就能接线** |

★ 我的推荐是 **A**——但**这个决定属于你**，因为它影响数据模型。
★★ 在你决定之前，`POST /api/admin/plugins/:id/collect`（R94）**已经可用**：
调用方显式传 `userId` 就能采集——**能力已经在了，只是「自动调度」还没有默认的主体语义**。
