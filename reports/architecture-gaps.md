## ★★★★ 设计声明未实现：**`process` 形态的 provider 调用契约**（R129 核对 `docs/11` 结构四）

★ 来自 `docs/11` 的**结构四**（契约未冻结）的第 ⑥ 条。

### 声明（`docs/11` 结构四）

| 类别 | 不一致 | 后果 |
|---|---|---|
| **插件协议** | JSON-RPC 只定义了 `channel.collect` | ★ provider / action / enricher 的调用契约缺失 → **M1-1 无法开工** |

### 代码核实（★ 本轮发现它**仍然成立**）

| 项 | 实际 |
|---|---|
| `process-runtime.ts` 支持的方法 | ★ **只有 `'plugin.init'`**（`grep` 实测）；注释里另提到 `channel.collect` |
| `newapi-provider` 的 `runtime` | ★★ **`'process'`**（`newapi-provider.ts:146`） |
| 宿主如何用它 | ★★ `serve.ts:365` 用 **`createNewApiProvider({ transport, pat, config })` 直接构造** —— **不走 process** |

★★★ 即：**一个声明 `runtime: 'process'` 的 provider 插件，宿主没有协议方法可以调用它**
（没有 `provider.listSubjects` / `provider.getSubject` 之类的 JSON-RPC 方法）。

### ★ 影响范围（**准确界定，不夸大**）

| 场景 | 影响 |
|---|---|
| **内置** provider（`newapi-provider`） | 🟡 **能工作**——`serve.ts` 在**宿主进程内直接构造**它（绕过协议） |
| ★ **第三方** provider 插件（`process` 形态） | ❌ **无法工作**——协议不支持，宿主无从调用 |

★★ 所以这个缺口的**真实后果**是：**「provider 作为可分发插件」这条路是断的**——
★ 内置的能跑（因为被特判进宿主进程），而**架构上承诺的「provider 也是插件」尚未成立**。

★★★ 这与 `docs/03`（插件体系）的承诺形成对照：
★ 文档把 `provider` 列为**六种插件之一**，而协议层只实现了 `channel`。

### 为什么登记而不在本轮修

| 需要的部分 | 说明 |
|---|---|
| JSON-RPC 方法集 | ★ 需要为 provider 定义方法（`provider.listSubjects` / `provider.getSubject` / `provider.capabilities`） |
| 宿主侧适配 | ★ 需要一个**把协议调用包装成 `ProviderPlugin` 接口**的适配器（与 `createNewApiProvider` 对称） |
| ★ 与 `host-factory` 的关系 | ★ R94 的 `host-factory` 已经给了插件**调用宿主**的能力（`host.http.request`）；本项是**反向**（宿主调用插件） |

★ 因此登记。★★ 修复方向清晰（**协议方法 + 宿主侧适配器**），
★ 但它是**插件体系的骨架**，应作为一个**独立任务**做，而不是在复查轮里顺手加。

### ★ 为什么这条比它看起来重要

★★ 这 9 列**不是边角料**，而是**状态机的核心状态**：

| 列 | 它本该支撑什么 |
|---|---|
| `satisfied_at` / `granted_at` | 「什么时候满足/授予的」——★ **审计与解释的基础** |

## ★★★★ 已修复：**Discovery 虚报算法**（R110 复查发现并修）

★ 这是本轮复查中**唯一「能修且已修」**的一条（其余 5 条登记）。

### 声明（`docs/06:410`）

> ⚠️ **不得虚报算法**：若声明了 `ES256` 但 JWKS 里没有 P-256 公钥，
> 下游按声明选算法会直接**验签失败**。Discovery 内容由 JWKS 实际内容**派生**，不手写。

### 缺陷（修复前）

```ts
// src/http/oauth-routes.ts
const document = buildDiscoveryDocument(issuer, ['ES256']);        // ★ 硬编码
const jwks: JwksDocument = await toJwks(deps.signingKeys);          // ★ 却是动态的
```

★★ 即：**JWKS 动态、Discovery 算法硬编码**——正好违反该声明。
★ 若部署用 RS256 密钥，Discovery 仍声明 ES256 → **下游按 ES256 选算法 → 验签失败**（声明自己指出的后果）。

### 修复

```ts
const document = buildDiscoveryDocument(issuer, await algorithmsOfSigningKeys(deps.signingKeys));
```

★ `algorithmsOfSigningKeys` 用 **jose 的 `exportJWK`** 从公钥派生算法：
`EC/P-256 → ES256` · `EC/P-384 → ES384` · `EC/P-521 → ES512` · `RSA → RS256` · `OKP/Ed25519 → EdDSA`。

★★ 未知类型**不声明**（宁可不声明，也不虚报）；空集**不回落**成硬编码（回落等于虚报）。

★ 一处实现细节：本项目的 `KeyObject` 类型来自 **jose**（不是 `node:crypto`），
没有 `asymmetricKeyType`——因此改用 `exportJWK`（JWK 里 `kty`/`crv` 信息更全）。

### 验证（★ 双向验证，不只是「测试通过」）

```
★ ES256 密钥 → Discovery 声明 ["ES256"] ✅ 一致
★ RS256 密钥 → Discovery 声明 ["RS256"] ✅ 一致   ← ★ 若硬编码，这里会失败
```

★ 已固化为回归测试（`test/oauth-routes.test.ts`），★ 它断言「RS256 密钥必须声明 RS256」——
**这正是「不硬编码」的证明**。

★ 即：**「永久授权」与「有限保留期」之间的矛盾没有被任何检查拦住**——
★ 这是**运维层面**的风险（不是数据损坏，而是「出了事查不出来 / 回滚不了」）。

### 为什么登记而不在本轮修

| 原因 | 说明 |
|---|---|
| **它是一个新功能** | 需要：保留期配置项 + `maxGrantLifetime` 配置 + 启动校验 + 发布校验 |
| ★ **且它依赖「保留期清理」的实现** | 而清理任务本身是否存在需先核实（否则校验的是**不存在的参数**） |
| ★ 设计明确但**参数取值未定** | 文档给了不等式，但没给各项保留期的**默认值**（需决策） |

★★★ **进一步核实（本轮）**：「保留期清理」这一层**整体未实现**。

```
grep -rniE "purge|cleanup|retention" src/   → 只命中零散的 purgeExpired（登录事务/nonce/挑战/事实）
grep -rnE "keepVersions|retentionDays"      → 0 结果
```

★ 即：**没有**「策略版本保留 3 个 / 评估 90 天 / 审计 180 天 / 动作流水 30 天」这类**保留期参数**，
也**没有**对应的清理任务（`ag_policies` / `ag_evaluations` / `ag_audit_log` / `ag_actions_log` 都不会被清理）。

★★ 所以那个不等式的**两个问题都存在**：
1. 保留期参数不存在 → **不等式无对象可校验**；
2. `one_shot` 的 `maxLifetime` 不存在 → **发布校验也无对象**。

★★★ 因此正确的修复顺序是**先实现保留期机制**（参数 + 清理任务），**再**加不变量校验——
而不是「先把校验写上」（那会校验不存在的参数，成为**恒真或恒假的假检查**）。

★ 本项**登记为缺口**，不仓促实现：
- 它是一个**新机制**（不是接线，也不是语义未定）；
- ★ 且它需要**参数默认值的设计决策**（文档给了不等式，没给各项保留期）。

★★ 这与本会话其它缺口的区别：**它不是接线问题，也不是语义未定**，
而是「**设计写了、实现漏了**」——属于目标 (3) 的核心发现类型。

## ★★★★ 语义缺口：**开发者级插件的事实记在谁名下？**（R94 发现）

★ 顺着「让插件运行时真正可用」查下去，撞到这个问题。

### 证据

`src/plugin/builtin/features.ts` 的 `github` 插件（**唯一有 `collect` 的内置插件**）：

```ts

configSchema: { properties: { token: {...}, username: {...} } },
collect: {
  request: { method: 'GET', url: 'https://api.github.com/users/{{config.username}}' },
  extract: [{ path: '$.public_repos', as: 'public_repos' }, ...],
},
```

★ 而写入事实时，`FactPipeline` 要求 `userId`，其语义是
**平台用户**（`ag_plugin_facts.user_id` → `ag_users.id`）。

### 缺口

| 问题 | 现状 |
|---|---|
| 插件配置属于谁？ | **开发者**（`ag_developers.id`） |
| 事实要记在谁名下？ | `FactPipeline` 要求**平台用户**（`ag_users.id`） |
| ★ 两者的关系 | ★ **没有映射**（R76 已确认 `ag_developers.id` 与 `ag_users.id` 是**不同的 uuid**） |

★★ 所以「按主体采集」在**开发者级插件**上没有合法的 `userId` 可传。

### ★ 已给出**方案推荐**：见 `reports/adr-plugin-fact-subject.md`

> ★ 该文件给出三种方案 + 各自对 **schema / 唯一索引 / 既有数据 / 查询** 的影响，
> 并**明确推荐方案 A**（让开发者也是平台用户，**加列**而非复用 id）——
> 因为它的**唯一索引不用动**，且与 R76 的 `DEVELOPER_IDENTITY_PROVIDER` 设计方向一致。
> ★ 决策可以在一轮之内做出并落地（落地步骤见该文件 §四）。

### 三种可能的解法（**需要设计决策**）

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 引入「开发者也是平台用户」的映射** | 入驻时为开发者建一条 `ag_users` 记录 | 需要新表/新列 + 迁移；但**语义最干净**（开发者确实是平台的一个主体） |
| **B. 事实表支持「开发者主体」** | `ag_plugin_facts` 增加主体类型（user / developer） | 改 schema + 唯一索引（★ 注意：唯一索引含 `user_id`，改语义要一并改） |
| **C. 开发者级插件的事实记在「配置所属开发者名下的站点主体」** | 需要「开发者 → 站点 → 主体」的遍历 | ★ 语义牵强（配置是开发者级，事实却按站点主体存） |

★ 我**不在这一轮单方面决定**——因为它影响数据模型（迁移 + 唯一索引 + 既有数据）。

### 对 P1-1 的影响

★★ **「何时采集插件事实」这一半被它阻塞**；而**另一半（`host-factory` 的装配）不受影响**——
装配只需要「插件清单 + 依赖」，不需要「主体语义」。
★ 因此本轮先做**装配**，把「采集调度」留给设计决策之后。

## ★★★★★★ 最根本的缺口：**真实模式下没有可用的 OIDC 登录**（R78 发现）

★ 这个缺口是顺着「14 步主线为什么用引导令牌登录」查出来的。

### 证据

```
grep -n "OidcClient" tools/serve.ts
→ 只有一处：156 行的 createDemoIdp()（issuer = 'http://localhost/demo-idp'）

grep -rn "AG_OIDC_ISSUER" src/ tools/
→ src/app/storage.ts:173/177/216 —— **只有 assertProductionReady 的校验与环境读取**

★★ 所以真实模式下：
- `AG_OIDC_ISSUER` / `AG_OIDC_CLIENT_ID` / `AG_OIDC_REDIRECT_URI` 被**校验**（必须存在、必须 https）；

```

★ 「冷启动引导令牌」**确实是**生产冷启动的标准做法，
但它**不是**目标第 (1) 项所说的「登录」（那是**用户**的登录），
更不是第 (3) 项所说的「**真实授权码流程**」。

★ 而 `serve.ts:175` 的注释自己写着：「**生产接入请用真实 IdP**」——
即：**生产 OIDC 接入是一个 TODO，从未完成**。

### 与「测试全绿」的关系

| 验证 | 覆盖的 | 没覆盖的 |
|---|---|---|
| `tools/serve-real-e2e.ts`（14 步，真实 PG + 真实进程） | 引导令牌登录 + 主线 | ★ **OIDC 授权码流程** |
| `test/oidc-federation-e2e.test.ts`（15/15） | ★ 完整 OIDC 流程（state/PKCE/nonce/隔离） | ★ **真实服务进程与真实装配**（它用内存 handler） |

★★ **两个测试各自都通过，而它们的交集——「真实服务进程 + 完整 OIDC 流程」——从来没被验证过**。

★★★ 这是本会话「**路径 A 通过 ≠ 路径 B 没问题**」的最纯粹形态：
**两个绿色的圆没有重叠，而目标要求的是那个重叠区域。**

### 修复需要什么

1. **`serve.ts` 真实模式构造 OidcClient**：从 `AG_OIDC_ISSUER` 等环境变量读配置
   （并做**发现文档**（`.well-known/openid-configuration`）拉取，或直接配置端点）；
2. **一个本地 stub IdP**：提供 `/.well-known` · `/authorize` · `/token` · `/jwks`

3. **在 `serve-real-e2e.ts` 里走完整授权码流程**，并验证两条链路（★ 需要先在 DB 里入驻一个开发者）；
4. ★ 并在 CI 里加一项：**「真实进程 + OIDC 流程」**——否则这个交集会再次空缺。

★ 这是**目标第 (3) 项真正要求的东西**，也是本会话**最后一个未完成的根本缺口**。

★★ 一句话：**「单进程端到端通过」不等于「生产可用」**。

## 六、建议的修复顺序

1. **`ChallengeStore`**（设备码）—— 跨请求 + 跨实例，且表已存在，修复成本最低；
2. **`OAuthStore`** —— 影响「本平台作为 IdP」的完整链路（需要新表）；
3. **`KvStore`** —— 插件数据持久性（表已存在）；
4. **`InvitationStore`** / **`SyncStateStore`** —— 表已存在；
5. **确认 `EndUserStore`** —— 若它真的只写内存，那是**用户数据丢失**，优先级应最高。

★ 每一步都应遵循 R57 的做法：**改 `docs/02` → 抽取 → 生成 DDL → 豁免理由 → 适配器 → 真实 PG 测试**。
★ 且每步都要验证**「重启后仍在」**——这是这些缺口的**唯一有效测试**。

---

## 七、如何在 CI 里防住这类缺口

★ 当前 `impl-pairing` 只**报告**，不作为门禁（因为「只有内存实现」需要人工判断）。

**可加的门禁**（尚未实现）：
- 若某接口**有对应的表**（按命名约定匹配）却只有内存实现 → **FAIL**；
  （对应本文件第三节的 4 个，它们**明确是缺陷**，无需人工判断）
- 若某接口只有内存实现且**被 `serve.ts` 在真实模式下使用** → **WARN**。

★ 前者是**可自动判定**的（表存在 = 意图是持久化），因此适合做门禁。
