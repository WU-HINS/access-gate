# 07 · 实施路线图

> 本文件在**设计定稿后重新规划**。前一版是随设计迭代逐条追加的，存在顺序错乱、依赖倒置与工期低估三类问题（见 §1）。

## 1. 为什么重排

| # | 前一版的问题 | 后果 | 本版对策 |
|---|---|---|---|
| P1 | **里程碑顺序错乱** | M7 排在 M6 之前；M2 里 M2-19 排在 M2-23 之后 | 全面重排，编号连续 |
| P2 | **站点作用域后置到 M7** | M0–M6 的表都不带 `site_id`，M7 要重构所有表 + 所有查询 | **`site_id` 从 M0 就进 schema**，M7 只做 UI 与流程 |
| P3 | **provider 宿主在 M2，但对账在 M1** | 依赖倒置——M1 的对账依赖 M2 才有的 provider 接口 | provider 接口 + 通用对账器**提前到 M1** |
| P4 | **前两个里程碑无可演示价值** | M0 是空壳、M1"能对齐不能升级"，两个月看不到东西 | 改为**垂直切片**：每个里程碑都能演示完整能力 |
| P5 | **前端工作量未独立估算** | 三形态编辑器、插件 UI 渲染器、管理端数十页被塞进"管理端：xxx"一行 | **前端独立成工作流**，与后端并行 |
| P6 | **工期严重偏低** | 设计复杂度翻倍，工期未更新 | 按当前设计重新估算（见 §7） |

## 2. 里程碑总览（按垂直切片）

```
M0 · 地基            PG + Schema 声明 + 查询编译 + 站点作用域(注入/抛错) + 内核 + 认证
      │              ★ 站点字段从第一天就在（standalone 下恒为默认站点）
      ▼
M1 · 第一个切片      主体目录(provider) + 身份对齐 + 最小插件宿主 + 最小表达式引擎
      │              → 用户门户能看到「我的资格」进度          ★ 首次可见价值
      ▼
M2 · 闭环            动作执行器 + 状态机 + 策略版本化 + 试算 + 影响面
      │              → 自动升级分组 + 解锁签到                ★ 首个可用版本
      ▼
M3 · 表达力完整      有序分支 + 全操作符 + 统一寻址 + 三形态编辑器
      │              → "QQ > 40 直接解锁；20~40 需组合"能配出来
      ▼
M4 · 插件平台化      process 运行时 + 端点/UI 宿主 + 权限信任 + 存储分级
      │              → github / llm-review / checkin            ★ 装插件即可用
      ▼
M5 · 跨项目协同      协同协议 + 设备码流 + 断言签名 + 薄 SDK
      │              → AI bot 框架能接入
      ▼
M6 · 加固与运营      可观测 + 回滚 + 灰度 + 压测 + 部署
      ▼
M7 · SaaS 化         开发者/站点 UI + 邀请入驻 + 两身份域 + admin 控制台
                     （作用域机制 M0 已就绪，这里只做 UI 与流程）
```

**关键判断**：

- **M1 结束就有可演示价值**（用户看到"差哪一项"）——比"能对齐不能升级"强得多；
- **M2 结束即首个可用版本**（原方案把闭环放在 M4）；
- **M0 的 `site_id` 是零成本预留**：standalone 下恒为默认站点，SaaS 化时不必重构。

## 3. 任务分解（WBS）

### M0 · 地基（12–15 人日）

| # | 任务 | 验收 |
|---|---|---|
| M0-1 | **后端工程初始化**：Fastify + TS + 分层目录 + 配置加载（默认值 → 文件 → ENV → DB） | `GET /healthz` 返回配置摘要 |
| M0-2 | **Schema 声明层**：`defineTable` / `col.*` / 索引 / 约束 / 类型推导 | 能用 TS 声明出 02 文档全部表 |
| M0-3 | **查询 AST 构建器** | `select/insert/update/delete` + 条件 + 排序 + 分页 + join；单测覆盖全部节点 |
| M0-4 | **PG SQL 编译器** | AST → SQL（标识符 / 占位符 / 类型映射 / DDL）；snapshot 测试 |
| M0-5 | **★ 站点作用域：注入 + 抛错**（**D17 裁决：RLS 推迟**） | 自动注入 `site_id`；无作用域 **fail-closed 抛错**；★ **不启用 RLS**——D17 裁决推迟 `FORCE RLS` / `SET LOCAL` / 逐站点事务，但保留 siteId 列 + 注入 + 抛错 + **单一事务入口** |
| M0-6 | **驱动与连接** | `pg` 池 + `AsyncLocalStorage` 事务 + 类型解析器（`int8`/`numeric`/`timestamptz`） |
| M0-7 | **迁移与 drift 检测** | `db:generate` / `db:migrate` / `db:check`；人为改库结构能被检出并 fail-fast |
| M0-8 | **内核服务** | 日志 / DI / 事件总线 / 调度器 / `pg_advisory_lock`；两实例抢锁只有一者成功 |
| M0-9 | **认证与会话骨架** | 账号模型（`id` 锚点 + `username` 可变）+ 会话 + RBAC（realm/role） |
| M0-10 | **前端工程初始化** | Vite + Tailwind v4 + shadcn/ui（new-york/zinc）+ 主题 + 顶部 ManagementBar + i18n |
| M0-11a | **★ 单一事务入口约束**（D17 前置 3） | 所有业务查询走 `ctx.db.transaction(fn)`；CI 禁止事务外查询 | **后补 RLS 的改动文件数 ≤ 3**（这是 D17 判据的实测项） |
| M0-11 | **CI 门禁** | 单测 + 编译产物 snapshot + `db:check` + **`site_id` 缺失检测** + 禁止裸 SQL 扫描 |

> **M0 验收门槛**：PG 上跑通全部迁移；`db:check` 检出人为 drift；**注入 + fail-closed 抛错 + CI 禁止事务外查询**（★ D17 裁决：验收对象从「RLS 拦住裸 SQL」改为这三项——**RLS 已推迟**）；CI 门禁全部通过。

## 4. 前端工作流（与后端并行）

前一版把前端拆散进各里程碑的"管理端：xxx"一行里，导致**严重低估**。本版把它列为独立工作流，可与后端并行推进。

| 阶段 | 前端交付 | 配合里程碑 |
|---|---|---|

## 5. 端到端验收场景

> **场景 A · edu 邮箱自动升级（M2 出口）**
> 1. 准备 new-api 实例 + 管理员 PAT；配置 `newapi-provider`（`config.scope: site`）；
> 2. 配置策略（**新表达式写法**）：
>    ```yaml
>    requirements:
>      branches:
>        - id: edu
>          when:
>            all:
>              - { eq:      { "me.email_verified": true } }
>              - { matches: { "fact:email.domain": ["*.edu.cn"] } }
>          outcome: satisfied
>          actions:
>            - { action: "newapi-set-group:set_group", params: { group: "basic" } }
>            - { action: "checkin:grant",              params: { scope: "daily" } }
>    ```
> 3. 用户以 `alice@tsinghua.edu.cn` 登录并验证邮箱；
> 4. ≤ 2 分钟内完成评估，new-api 中 `group` 变为 `basic`；
> 5. 用户侧「我的资格」显示"✅ 教育邮箱 · 已解锁签到"；
> 6. 签到成功，额度通过 `add_quota` 到账；
> 7. **重复巡检 10 次，new-api 侧无额外会话吊销**；
> 8. 邮箱改为 `gmail.com` → 宽限期 72h 后自动回退 `default` 并收回签到资格。

> **场景 B · 分支策略（M3 出口）**
> 配出"QQ > 40 直接解锁；20 < QQ < 40 需与其它渠道组合达成"，并在用户侧看到：
> "❌ 分支 1（QQ 等级 32 ≤ 40）· ✅ 分支 2（4 项中已满足 2 项）"。

> **场景 C · 手工干预不打架**
> 管理员在 new-api 手工改分组 → 下一轮对账发现 drift → 按 `driftPolicy` 改回 **并告警**。

> **场景 D · new-api 不可用**
> 断开 new-api → 对账失败但**不影响用户登录与评估** → 动作进入 `planned` 队列 → 恢复后自动重放，不重复发额度。

> **场景 E · 装一个插件（M4 出口）**
> 上传 `gitlab` 插件 → 逐项授予权限 → 勾选代码信任 → 启用 →
> **策略编辑器立刻出现 `fact:gitlab.*` 补全**，全程不改前端代码、不重启主程序。

## 6. 关键路径与并行度

```
关键路径（不可压缩）：
  M0-2/3/4/5 (Schema+编译+作用域)  →  M1-1/2 (provider+对账)  →  M1-7 (身份对齐)
    →  M1-8 (表达式)  →  M2-1/2 (动作+闭环)  ★ 首个可用

可并行：
  · 前端工作流（F0–F2）与 M0–M2 并行
  · M1-6（email-domain，零依赖）可与 M1-1/2 并行——用来先验证插件契约
  · M3（表达力）与 M4（插件平台）在后端可由两人并行，但前端 F3/F4 是瓶颈
  · M7（SaaS）完全独立，可在任意时点插入
```

**瓶颈提示**：**前端（尤其 F3 图形编辑器 与 F4 插件管理）是本项目的进度瓶颈**，不是后端。若只有 1 名全栈，前端工作会串行拉长整体工期。
